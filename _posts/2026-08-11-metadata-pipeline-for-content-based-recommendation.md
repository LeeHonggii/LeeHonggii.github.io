## 모델부터 고르려다 멈춘 이유

처음엔 나도 알고리즘부터 봤다. 협업 필터링(Collaborative Filtering — 비슷한 행동을 한 사용자들의 이력을 근거로 추천하는 방식)을 걸까, 임베딩 기반으로 갈까. 결정을 내리려고 데이터를 열었는데, 거기서 손이 멈췄다.

콘텐츠 34,937건. 각 행에 있는 건 제목 한 줄과 짧은 설명 한 문단. 그게 전부였다. "리더십 커뮤니케이션"과 "팀 협업 스킬 향상"이 얼마나 가까운지, 이 두 문자열만 놓고는 계산할 방법이 없다. 계산에 넣을 수 있는 값이 없는데 모델 얘기를 하는 게 무슨 의미가 있나.

그래서 순서를 바꿨다. 알고리즘을 고르기 전에, 알고리즘이 먹을 수 있는 형태로 데이터를 다시 만들기로.

## 무엇을 붙일지보다 "어떻게 얼려둘지"

붙일 속성 목록 자체는 그렇게 어렵지 않았다. 키워드 태그, 분야 분류, 대상 직무, 대상 수준, 학습 시간. 익숙한 것들이다.

문제는 **키워드였다.** 원문에서 명사만 뽑아 태깅하면 "커뮤니케이션", "의사소통", "소통 스킬"이 세 개의 다른 태그로 흩어진다. 사람 눈에는 같은 개념인데 코사인 유사도 관점에서는 공통 원소가 0이 된다. 이 상태로 콘텐츠 기반 추천을 돌리면 결과가 "관련 있음"이 아니라 "그럴싸한 무작위"에 가까워진다.

그래서 태깅을 시작하기 전에 두 가지를 먼저 확정했다.

첫 번째는 표준 키워드 풀. 전체 카탈로그를 훑어 후보 키워드를 뽑고, 동의어를 통합해 하나의 표준형만 남긴다. 이후 신규 콘텐츠는 이 풀 안에서만 태깅한다. "이 키워드가 풀에 있느냐"라는 단순 검증만으로 담당자가 바뀌어도 일관성이 유지된다.

두 번째는 29개 분야(strand) 분류. 키워드 자체는 세밀하지만, 그 위에 굵은 상위 축이 하나 있어야 한다. 추천 계산에서 이 축은 후보군을 좁히는 상위 필터로 쓰인다.

두 축을 먼저 얼려두고 그 위에서 태깅을 진행하니, 콘텐츠 1건당 평균 10개, 총 34만 개 규모의 개별 메타 값이 붙었다. 모델이 실제로 계산에 넣는 건 콘텐츠 3만 5천 건이 아니라 이 34만 개의 값이라는 걸, 태깅이 끝나갈 때쯤 다시 실감했다.

## 메타데이터가 살아나는 순간

메타데이터가 왜 이렇게까지 중요한지는, 이걸 실제로 소비하는 쪽 코드를 보면 조금 더 손에 잡힌다. 지금 만들고 있는 추천 엔진은 학습자 프로파일과 콘텐츠 사이의 유사도를 여러 축으로 나눠서 계산하는데, 그 축이 이렇게 생겼다.

```python
SIM_PRIOR_W = {'kw': 0.4, 'ncs': 0.3, 'strand': 0.2, 'title': 0.1}
```

`kw`는 키워드 태그 겹침, `ncs`는 직무 코드 축, `strand`는 아까 얼려둔 29개 분야, `title`은 제목 토큰 매칭이다. 가중치의 60%가 `kw`와 `strand`, 즉 우리가 앞단에서 붙여둔 메타데이터에 걸려 있다. 여기가 비어 있거나 표기가 흩어져 있으면, 이 뒤에 붙는 어떤 정교한 로직도 실질적으로는 `title` 하나로만 계산하는 상태가 된다.

추천 결과의 성격을 결정하는 축도 마찬가지다. 학습자 유형별로 "직무 적합도 / 자기이해 / 트렌드" 세 축의 비중을 다르게 준다.

```python
MATRIX = {
    'job': {'level': 0.6, 'self': 0.2, 'trend': 0.2},
    'career': {'level': 0.4, 'self': 0.2, 'trend': 0.4},
    'company': {'level': 0.4, 'self': 0.4, 'trend': 0.2},
}

CHARACTER_AXIS_DELTA = {
    '트렌드 적응가': {
        'job': {'trend': 0.04, 'level': -0.04},
        'career': {'trend': 0.06, 'level': -0.04, 'self': -0.02},
        'company': {'trend': 0.05, 'level': -0.02, 'self': -0.03},
    },
    '새 분야 탐험가': {
        'career': {'level': -0.06, 'self': 0.03, 'trend': 0.03},
        'company': {'level': -0.03, 'self': 0.03},
    },
    # ...
}
```

이 매트릭스 값들이 의미를 가지려면, `level`을 판단할 대상 수준·직무 코드가 있어야 하고 `trend`를 판단할 최근 소비 이력이 붙어 있어야 한다. 알고리즘 쪽 튜닝 파라미터가 아무리 많아 보여도, 이 값들이 걸릴 곳(메타데이터 필드)이 없으면 전부 곱하기 0이 된다.

한 가지 더. 학습자의 경력 단계와 콘텐츠의 대상 단계를 맞추는 매핑도 결국 메타데이터로 돌아간다.

```python
AUDIENCE_STAGE_FIT = {0: 1.0, 1: 0.92, 2: 0.78, 3: 0.65}
CAREER_STAGE = {'온보딩 ~1년': 0, '2~3년': 1, '4~7년': 2, '8~10년': 3, '11년 이상': 4}
CONTENT_STAGE_HINTS = (
    (0, ('신입', '입문', '입문자', '온보딩', '기초', '초급')),
    (2, ('실무', '중급', '레벨업')),
    (3, ('심화', '고급', '전문', '전문가')),
    (4, ('리더', '관리자', '팀장', '임원', '전략')),
)
```

콘텐츠 제목·설명에서 뽑아낸 단서를 단계 값으로 정규화해 두는 것 — 이것도 결국 메타데이터 파이프라인의 일부다. 하드코딩된 힌트 사전으로 시작했지만, 이걸 표준 태그로 흡수해야 한다는 숙제는 아직 남아 있다.

## 아직 얼려두지 못한 것들

파이프라인을 만들어놓고 나니 오히려 안 얼려둔 자리가 눈에 들어온다. 대상 단계는 아직 문자열 힌트 매칭이고, 학습 시간 분포는 붙여만 놨지 실제 추천에서 어떻게 쓸지 정하지 않았다. NCS 직무 코드도 상세 코드까지 쓸지, 대분류에서 자를지 아직 실험 중이다.

추천 품질을 재보는 것도 남았다. 지금 시점에는 태깅이 끝났다는 것과 유사도 계산에 쓸 축이 자리를 잡았다는 것까지가 정직한 진척이다. 정성적으로 결과를 훑어보면 예전보다 "말이 되는 것"들이 위로 올라오긴 하는데, 이걸 수치로 뒷받침하려면 별도의 오프라인 평가 셋을 만들어야 한다. 그건 다음 문제다.
