추천 시스템을 처음 설계할 때 가장 먼저 확인한 건 콘텐츠 원본 데이터였다. 제목, 설명, 등록일. 약 3.5만 건. 여기서 막혔다.

제목만으로는 "이 콘텐츠가 어느 직무에 유용한가"를 계산할 수 없다. "리더십 역량 강화 과정"이라는 제목은 신입 대상인지 임원 대상인지, 영업 직군인지 전 직군인지 아무것도 말해주지 않는다. 설명 텍스트도 마찬가지다. 글자는 있지만 추천 엔진이 신호로 쓸 수 있는 구조가 아니다.

원본 텍스트를 그대로 쓰는 방법도 있다. TF-IDF나 임베딩 기반으로 유사도를 뽑으면 된다. 근데 이 방식은 "등록된 텍스트가 얼마나 좋냐"에 너무 의존한다. 설명이 부실한 콘텐츠, 제목이 유사한 다른 콘텐츠, 오래전에 등록돼서 스타일이 제각각인 콘텐츠가 섞이면 품질이 들쭉날쭉해진다. 관리할 수 없다는 게 진짜 문제다.

그래서 방향을 바꿨다. 원본 텍스트를 해석하는 대신, **통제된 어휘(controlled vocabulary)** 로 구성된 메타데이터를 직접 붙이기로 했다.

---

## 먼저 풀(pool)을 만들었다

태깅부터 시작하면 어떻게 되는지는 예측 가능하다. 비슷한 개념이 다른 표현으로 들어가고, 나중에 합치거나 정리하다 데이터 일관성이 무너진다.

그래서 순서를 바꿨다. 태그 풀과 분류 체계를 먼저 확정하고, 검수를 거친 뒤 동결했다.

키워드 풀: 128개. "리더십", "재무 이해", "커뮤니케이션" 같은 역량·스킬 단위 개념들이다. 이 풀은 콘텐츠에 부착하는 키워드의 전체 선택지다. 여기 없으면 태깅 불가. 신규 추가는 별도 검토 프로세스를 거친다.

분야 분류: 29종. 콘텐츠가 속하는 주제 영역이다. 키워드보다 넓은 개념으로, 한 콘텐츠는 하나의 분야에만 속한다.

이 두 가지가 확정된 뒤에 콘텐츠 태깅을 시작했다.

---

## 메타데이터 스키마

콘텐츠 하나에 붙는 메타데이터는 대략 이런 구조다.

```
{
  keyword_tags,     // 128개 풀에서 선택, 복수 가능
  strand,           // 분야 분류 29종 중 하나
  related_codes,    // 연관 직무 코드 (표준 직무 분류 기반)
  audience_tags,    // 대상 직급·직군
  standard_code,    // 외부 기준 분류 코드
  duration_bucket   // 학습 시간 구간 (예: 1시간 미만, 1~3시간, 3시간 초과)
}
```

여기서 `related_codes`는 "이 콘텐츠가 어느 직무에 유용한가"를 표현한다. 주 직무 외에 보완 직무도 포함한다. 추천 계산 시 직무 매칭에 직접 쓰인다.

`audience_tags`는 대상 직급이다. 팀장 과정인지, 신입 대상인지, 전 직급 공통인지를 구분한다. 추천할 때 사용자 직급과 교차 확인한다.

`duration_bucket`은 단순히 길이 정보가 아니다. 학습 진행성 부스팅에 쓰인다. 짧은 콘텐츠를 먼저 소화한 사용자에게 긴 콘텐츠를 올리는 방식으로 자연스러운 진행 곡선을 만들 때 필요하다.

## 규모 이야기

34,937건 콘텐츠에 메타데이터를 부착했다. 이 숫자를 말할 때 주의할 게 있다.

"메타데이터 34만 개"라고 하면 콘텐츠 수와 혼동된다. 정확히는 **개별 메타 값이 약 34만 개**다. 콘텐츠 1건에 keyword_tags가 3개, related_codes가 2개, 나머지 단일 값들이 붙으면 한 콘텐츠당 7~10개 값이 생긴다. 34,937 × 평균 약 9~10 = 34만 언저리.

키워드 태그만 떼어내면: 34,937건 × 평균 부착 키워드 수. 이 평균값은 아직 집계하지 않았다. 콘텐츠마다 편차가 있어서 분포로 보는 게 맞다.

---

## 이 구조가 추천에서 어떻게 쓰이는가

키워드 풀이 통제된 어휘로 고정돼 있으면 IDF(Inverse Document Frequency — 전체 문서 중 해당 키워드를 가진 문서 비율의 역수) 계산이 안정적으로 된다. 34,937건 전체에서 각 키워드가 몇 건에 붙어 있는지 미리 계산해두고, 사용자 관심 키워드와 매칭할 때 희귀한 키워드에 높은 가중치를 준다.

128개 풀이 고정돼 있으니 IDF 값도 일주일에 한 번 배치로 갱신하면 된다. 원본 텍스트 기반이었다면 어휘 공간이 무한하고 IDF 계산도 불안정했을 것이다.

신호별 가중결합도 메타데이터 덕분에 분리해서 설계할 수 있다. 직무 매칭 신호, 키워드 매칭 신호, 선호 분야 신호를 각각 독립적으로 계산하고 나중에 합친다. 각 신호를 뜯어볼 수 있고, 가중치를 바꿔도 다른 신호에 영향을 주지 않는다.

## 아직 남은 것

키워드 풀 128개가 적절한 숫자인지는 솔직히 모른다. 너무 많으면 희박해지고, 너무 적으면 구분력이 없어진다. 지금 수치는 도메인 검토와 실제 콘텐츠 샘플링을 거쳐 잡은 것이지만, 추천 결과를 실제로 써보기 전까지는 맞다고 확신할 수 없다.

`related_codes`의 보완 직무 범위도 아직 느슨하다. "이 직무에도 쓸 수 있다"의 기준이 태거마다 조금씩 달라서 일관성 검증이 필요하다. 이건 다음 라운드 과제로 남아 있다.
