테이블 이름을 바꾼 뒤에도 조회 쿼리 몇 개가 옛 이름을 계속 보고 있었다. 고친 건 한 줄이다. 그런데 이 한 줄을 "됐다"고 말하기까지는 생각보다 단계가 많았다.

## 증상

스키마를 정리하면서 테이블 이름이 바뀌었다. 쓰기 쪽은 새 이름으로 옮겨졌는데, 목록을 읽어오는 일부 조회 쿼리의 JOIN 대상이 예전 이름 그대로였다. 옛 테이블이 없으니 호출하면 오류가 난다. 원인은 단순했고 수정도 단순했다. JOIN 절의 테이블 이름을 새 이름으로 바꾸면 된다.

## 존재 확인으로는 모자랐다

처음엔 "새 테이블이 DB에 있는지"만 확인하고 넘어가려 했다. 있다. 그런데 이건 이름이 맞다는 증거일 뿐이다.

쿼리에는 테이블 이름 말고도 걸린 게 많다. SELECT 절의 컬럼, ON 조건의 컬럼, 별칭. 이름이 바뀔 때 컬럼까지 같이 바뀌었다면 테이블 존재 확인은 통과하고 실행은 실패한다. 반대로 컬럼이 그대로라 해도 눈으로는 알 수 없다. 그래서 쿼리를 그대로 DB에 실행해보기로 했다.

결과는 이렇게 나왔다.

```
쿼리 실행 성공 ✓  행 5개
```

오류 없이 5행이 돌아왔다. 컬럼 참조가 전부 유효하다는 뜻이다. 이 시점에야 "한 줄 수정이 맞았다"고 말할 수 있었다.

## 행이 나오는 것과 의도대로 나오는 것

5행이 나온 것만으로도 부족하다고 봤다. JOIN은 조용히 틀리는 일이 많다. 이 쿼리는 연결된 항목이 없는 행도 보여줘야 하는 목록이라 LEFT JOIN이다. 이름을 바꾸다가 INNER JOIN으로 바뀌었거나 조건이 어긋나면, 연결 대상이 없는 행이 결과에서 말없이 사라진다. 에러도 없고 행도 나오니 놓치기 쉽다.

그래서 결과 행을 하나씩 봤다. 연결된 대상이 없는 행이 `tools: None`으로 찍혀 나오는 걸 확인했다. 행이 사라지지 않고 비어 있는 채로 남았으니 LEFT JOIN의 의도대로 동작한 것이다.

다만 이 확인은 5행짜리 표본에 대한 것이다. 연결 대상이 많은 행, 여러 개 붙는 행에서 행 수가 부풀어 중복이 생기는지는 이번에 따로 보지 않았다.

## 반영됐는지도 확인해야 했다

수정을 개발 브랜치에 올리는 데서도 시간을 썼다. 네트워크가 분리된 환경이라 원격에 바로 push할 수 없었고, 커밋을 Git 패치로 뽑아 옮겨 적용했다. 이 과정에서 로컬 브랜치와 원격 브랜치가 어긋나 있다는 걸 알게 됐다. 한 번은 엉뚱한 브랜치에 커밋을 적용해버리기도 했다. 패치를 뽑아 다른 브랜치로 옮기면 커밋 해시가 달라지기 때문에, "같은 변경"이라도 git은 같은 커밋으로 보지 않는다.

그래서 마지막에 두 가지를 확인했다. 개발 브랜치 대비 최종 diff에 내가 고친 그 한 줄만 남아 있는지, 그리고 커밋 관계가 의도한 대로인지. diff가 한 줄이면 패치가 정상적으로 얹힌 것이다.

## 남은 것

같은 시기에 목록 API에 페이지네이션을 넣고 응답 필드와 HTTP 오류 처리를 바꿨다. 이쪽은 로컬 커밋까지만 끝났다. 실제 앱을 띄워 DB 바인딩까지 통과하는지는 아직 보지 않았고, 원격에도 올리지 않았다. 랜덤 조회는 페이지 간 중복 문제가 있었지만 기존 무작위 정렬을 유지하기로 했다. 이 선택이 맞는지는 앱을 통해 돌려본 뒤에 다시 판단해야 한다.

방금 한 JOIN 검증은 쿼리를 DB에 직접 던진 것이었다. 앱을 거치면 파라미터 바인딩에서 다른 문제가 나올 수 있다. 이번 수정이 거기서도 괜찮은지는 아직 모른다.
