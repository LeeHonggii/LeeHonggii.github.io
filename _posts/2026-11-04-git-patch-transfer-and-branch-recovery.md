작업은 끝났는데 push를 못 하는 날이 있다. 오늘이 그랬다. 테이블 이름을 바꾼 뒤 남아 있던 JOIN 오류를 찾아 실제 쿼리를 돌려 확인했고, 목록 API에 페이지네이션도 붙였다. 코드는 문제가 아니었다. 이 커밋들을 원격 저장소까지 어떻게 보내느냐가 문제였다.

## 망이 갈라져 있다

내가 코드를 고치는 환경과 개발 브랜치에 push할 수 있는 환경은 네트워크가 분리되어 있다. 한쪽에서 만든 커밋을 다른 쪽으로 파일로 넘겨야 한다.

이때 쓴 것이 Git 패치다. 처음에는 "패치를 만들려면 일단 어딘가에 push해야 하나?"라고 생각했다. 아니다. `format-patch`는 로컬 커밋만 있으면 된다. 원격 저장소에 올릴 필요가 없다.

```bash
# 로컬에서: base 다음 커밋부터 end까지를 패치 파일로
git format-patch <base>..<end>
```

범위 지정이 곧 "어느 커밋부터 보낼지"를 정한다. 파일 하나로 합치고 싶으면 `--stdout > test.patch`로 돌리면 된다. 수신 쪽에서는 이렇게 적용한다.

```bash
git am test.patch
```

`git am`은 패치를 **지금 체크아웃된 브랜치** 위에 커밋으로 쌓는다. 이 문장을 알고는 있었다. 그런데 적용하기 전에 현재 브랜치를 확인하지 않았다.

## 잘못된 브랜치에 붙였다

수신 환경에서 `am`을 실행한 시점에 체크아웃된 브랜치는 개발 브랜치가 아니라 `main`이었다. 패치는 에러 없이 깔끔하게 적용됐다. `am`은 현재 브랜치가 맞는지 판단해 주지 않는다. 적용할 수 있으면 적용한다.

이후 상태를 확인했다.

```bash
git status -sb
git branch -a
```

`git branch -a`를 보고 두 가지를 알았다. 하나는 커밋이 `main`에 붙었다는 것이다. 다른 하나는 로컬에 `develop` 브랜치 자체가 없고 `origin/develop`만 원격 추적 브랜치로 보인다는 것이다.

## 로컬 브랜치를 만드는 일과 서버에 브랜치를 만드는 일은 다르다

원격에 이미 있는 브랜치를 로컬에 만드는 건 서버에 아무 영향이 없다. 그냥 원격 브랜치를 추적하는 로컬 포인터를 하나 더 두는 것이다. 처음에 이 둘을 섞어서 생각했다. 그래서 "개발 브랜치를 새로 만들어도 되나?" 하고 괜히 망설였다.

```bash
git checkout -b develop origin/develop
```

## 커밋 옮기기

개발 브랜치를 만든 다음, `main`에 잘못 붙은 커밋을 옮겼다.

```bash
git cherry-pick main
```

여기서 `main`은 브랜치 이름이지만 cherry-pick에는 **그 브랜치가 가리키는 커밋 하나**로 전달된다. 이 경우에는 `main`의 끝에 방금 적용한 커밋이 있어서 의도대로 동작했다. 커밋이 여러 개였다면 이 방식은 맞지 않는다. 범위를 `A..B`로 주거나 해시를 명시해야 한다. 실행 전에 `main`의 끝이 정확히 옮기려는 커밋인지 로그로 확인하는 편이 안전하다.

`am`과 `cherry-pick`을 거치면 커밋 해시가 바뀐다. 부모 커밋이 달라지기 때문이다. 해시가 같은지로 "잘 옮겨졌나"를 판단할 수 없다. 내용(diff), 부모 커밋, 원격에 반영됐는지를 같이 봐야 한다.

`main`에 남은 커밋을 되돌리는 정리는 따로 해야 한다. 이쪽은 로컬 정리 작업이라 공유 브랜치 이력과 맞춰서 처리하려고 남겨 두었다.

## push는 두 번 다른 이유로 실패한다

```bash
git push origin develop
```

이 명령이 거절당했는데 이유가 서로 다른 두 종류였다.

- `src refspec ... does not match any`: 로컬에 push할 브랜치가 없을 때 나온다. 앞에서 로컬 `develop`이 없는 상태로 push를 시도하면 이 오류가 난다. 이건 내 쪽 상태 문제다. 위의 `checkout -b`로 풀린다.
- `pre-receive` 단계의 내부 API 500: 서버가 push를 받고 훅을 실행하는 도중에 터진 오류다. 로컬 브랜치가 있든 없든 상관없다. 내가 고칠 수 있는 영역이 아니다.

두 메시지는 모두 "push 실패"로 보여서 처음에는 같은 문제로 읽었다. 그런데 오류가 발생하는 단계가 다르다. 앞쪽은 push가 시작되기 전이고, 뒤쪽은 서버가 받은 뒤다. 어디서 실패했는지 보면 누가 고쳐야 하는지가 갈린다.

## 아직 남은 것

- 서버 훅의 500 오류는 원인을 확인하지 못했다. 서버 관리 쪽에 확인이 필요하다. 같은 push를 다시 시도해서 재현되는지도 아직 안 봤다.
- 페이지네이션 변경은 로컬 커밋까지만 끝났다. 실제 앱을 띄워 DB에 바인딩해서 돌려 보는 검증을 아직 못 했다. 랜덤 조회는 기존 무작위 정렬을 유지하기로 했으므로, 페이지 간 중복이 생길 수 있다는 점도 그대로 남아 있다.
- `main`에 잘못 붙은 커밋의 정리.

원격에 반영된 것은 아직 없다.
