목록 API에 페이지네이션을 붙이는 일은 20분짜리 작업으로 보였다. `LIMIT`과 `OFFSET`을 넣으면 끝이라고 생각했다. 실제로는 호출하는 쪽이 받는 응답이 달라졌다.

## offset은 페이지 번호로 정했다

파라미터 이름이 `offset`인데 의미는 페이지 번호다. 이름만 보면 건너뛸 행 수 같지만, 1부터 시작하는 페이지 번호로 해석했다. SQL에 넘기기 직전에 행 수로 바꾼다.

```text
skip = (offset-1) * limit
```

```sql
... LIMIT :limit OFFSET :skip
```

`limit`은 기본 30, 허용 범위는 1~300으로 검증한다. 범위를 두지 않으면 `limit=100000`이 들어왔을 때 사실상 전체 조회가 된다. 페이지네이션을 붙이는 이유가 사라진다.

이름과 의미가 어긋난 것은 마음에 걸린다. 이미 쓰이고 있는 파라미터 이름을 바꾸면 호출자가 깨져서 그대로 두었다. 대신 문서에 "페이지 번호이며 1부터 시작"이라고 적었다.

## 기본값 30이 계약을 바꿨다

전에는 전체를 돌려주던 API가 있었다. 여기에 기본 `limit=30`을 넣으면 파라미터를 안 보내는 기존 호출자도 30개만 받는다. 에러가 나지 않는다. 데이터가 조용히 잘린다.

그래서 이건 구현 변경이 아니라 계약 변경으로 문서에 적었다. "기존 전체 반환 API는 이제 기본 30개만 반환한다"는 문장을 넣었다. 이 문장이 없으면 나중에 누군가 "목록이 왜 30개에서 끊기죠"를 디버깅하게 된다.

## 응답에는 전체 건수가 필요했다

응답 모양은 이렇게 통일했다.

```json
{"totalCount": 100, "list": []}
```

여기서 헷갈린 게 `totalCount`의 의미였다. 현재 응답에 담긴 항목 수가 아니다. 필터 조건에 맞는 전체 항목 수다. 한 페이지에 30개를 돌려줘도 `totalCount`는 100일 수 있다. 응답의 `list` 길이를 세면 되는 값이 아니어서, 같은 필터로 `COUNT`를 따로 돌려야 한다. 프런트가 마지막 페이지를 계산하려면 이 값이 필요하다.

## 실패는 status 필드 대신 HTTP 상태코드로

기존 응답에는 `status` 필드가 있었다. 본문은 200인데 안에서 실패를 알리는 식이다. 이걸 없애고 실패는 HTTP 상태코드로 표현하게 고쳤다. 오류 본문은 이런 모양이다.

```json
{"error_code": "TEMPLATE_QUERY_ERROR", "error_detail": "..."}
```

함정이 하나 있었다. FastAPI는 요청 검증에 실패하면 기본으로 422를 돌려준다. 이 기본 본문은 내가 정의한 `error_code`/`error_detail` 형태와 다르다. 호출자가 사용자 정의 본문만 기대하고 파싱하면 일부 오류에서만 다른 모양을 받는다. `limit` 범위 검증이 바로 그 경로에 걸린다. 기본 422 응답을 같은 형태로 맞출지는 정하지 못했다.

## 랜덤 목록은 seed까지 만들었다가 접었다

랜덤으로 뽑는 목록은 페이지를 넘기면 문제가 생긴다. 요청마다 순서가 달라서 1페이지와 2페이지 사이에 중복이나 누락이 생길 수 있다. seed를 고정해서 같은 순서를 재현하는 방식을 구현하고 실험했다.

결국 쓰지 않았다. 랜덤 동작은 그대로 두고 응답 구조만 `totalCount`/`list`로 통일하기로 했다. 이 목록의 용도가 "넘겨가며 전부 훑기"가 아니라 "그때그때 뽑아 보기"라서, seed 상태를 호출자와 맞추는 복잡함이 얻는 것보다 크다고 봤다. 이건 용도에 대한 판단이어서, 나중에 전체 순회 요구가 생기면 뒤집힐 수 있다.

## 검증은 어디까지 했나

DB에서 직접 SQL을 실행해 쿼리가 돌아가는 건 확인했다. 그런데 이건 앱이 같은 쿼리를 돌린다는 증거가 아니다. 앱에서는 `:limit`, `:skip`이 SQLAlchemy 바인드 파라미터로 넘어가고, 타입 처리가 직접 실행과 다를 수 있다. 직접 실행에서 되는 쿼리가 바인드 경로에서는 안 될 가능성을 배제하지 못했다.

현재 상태는 로컬 커밋과 전달용 패치를 만든 데까지다. 망이 분리된 환경이라 패치 파일로 옮겨야 한다. 실제 앱을 띄워서 `offset`, `limit`, 범위 밖 값을 넣어 보는 검증과 원격 반영은 아직 하지 않았다. 다음에 할 일은 `limit=0`, `limit=301`을 앱에 보내서 어떤 본문이 오는지 확인하는 것이다.
