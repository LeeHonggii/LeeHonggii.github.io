작업 환경이 망으로 나뉘어 있다. 코드를 짜는 쪽에서는 개발 저장소 원격에 push할 수 없다. 코드를 보내려면 커밋을 파일로 만들어 옮겨야 한다. 이날 일은 이 과정에서 두 가지 오류가 서로 다른 원인으로 나온 것을 따로 짚어낸 기록이다.

## 커밋을 파일로 만든다

처음엔 외부 원격 저장소에 한 번 push해서 건네야 하나 싶었다. 그럴 필요가 없었다. `git format-patch`는 로컬 커밋만 있으면 만든다.

```bash
git format-patch <base>..<end> --stdout > test.patch
```

`<base>..<end>` 범위의 커밋이 메일 형식 패치 하나로 합쳐진다. 작성자와 커밋 메시지도 같이 담긴다. 이 파일만 반대편으로 넘기면 된다.

## 적용은 됐다. 그런데 브랜치가 없다

받는 쪽에서 `git am test.patch`를 돌렸더니 오류 없이 끝났다. 커밋도 로그에 보였다.

문제는 `git am`이 지금 체크아웃된 브랜치에 커밋을 쌓는다는 점이었다. 내가 그 브랜치를 확인하지 않았다. 커밋은 `main`에 올라가 있었다. 올리려던 곳은 개발 브랜치였다.

그 상태로 `git push origin develop`을 쳤더니 이런 오류가 나왔다.

```
error: src refspec develop does not match any
```

처음엔 원격이 거절한 줄 알았다. 하지만 메시지를 읽어 보니 `src`, 곧 push의 출발점인 로컬 쪽 참조가 없다는 말이었다. 로컬에 `develop`이라는 브랜치 자체가 없었다. 서버는 요청을 받지도 않은 상태였다.

```bash
git branch -a
```

로컬 브랜치는 `main` 하나였고, `remotes/origin/develop`은 목록에 있었다. 원격 브랜치는 보이는데 그걸 추적하는 로컬 브랜치가 없었던 것이다.

## 추적 브랜치를 만들고 커밋을 옮긴다

```bash
git checkout -b develop origin/develop
git cherry-pick main
git push origin develop
```

원격 `develop`에서 로컬 브랜치를 새로 만들어 추적 관계를 잡고, `main`에 잘못 올라간 수정 커밋을 `cherry-pick`으로 가져왔다. 이때 `main`은 패치 하나만큼 앞서 있었으므로 `cherry-pick main`은 그 끝 커밋 하나를 뜻한다. 패치가 여러 커밋이면 범위로 지정해야 한다. `main`에 남은 커밋은 정리하지 않았다.

## 다른 오류: pre-receive 500

push를 다시 시도하자 이번에는 다른 메시지가 떠서 거절됐다. 원격의 `pre-receive` 훅(push를 받기 전에 서버가 돌리는 검사)이 내부 API를 호출하다 500을 돌려받았다는 내용이었다.

앞의 오류와는 층이 다르다. `src refspec`은 내 로컬 참조 문제이고, 이쪽은 서버가 처리하다 실패한 것이다. 내 쪽에서 고칠 게 없는 메시지처럼 보였다.

브랜치를 맞춘 상태로 다시 push했고 반영됐다. 다만 500이 일시적이었는지, 이전 시도가 추적 브랜치 없이 나간 것과 관련이 있었는지는 가리지 못했다. 서버 로그를 볼 수 없어서 재시도하니 통과했다는 것까지만 안다.

## 같은 날 만든 다른 변경

이 방식으로 옮긴 건 JOIN 참조 오류를 고친 커밋이다. 테이블 이름을 바꾼 뒤 옛 이름이 남은 JOIN을 고쳤고, 실제 DB에서 쿼리를 돌려 확인한 다음 개발 브랜치에 올렸다.

목록 API에 페이지네이션과 전체 건수를 넣은 작업은 여기까지 가지 못했다. 로컬 커밋과 전달용 패치까지만 만들었다. 실제 앱에서 돌려 본 검증과 원격 반영은 이 기록에 없다. 이 패치를 받는 쪽에서 `git am` 전에 `git branch`부터 확인할 것이다.

그리고 pre-receive 500의 원인은 아직 모른다.
