"임베딩부터 붙여야 하지 않나요." 검색 품질 얘기가 나올 때마다 나오는 말이다. 나도 처음엔 그렇게 접근할 참이었다. 수학 콘텐츠를 다루는 추천 시스템이었고, 의미 기반 검색은 언제나 좋아 보이니까.

그런데 로그를 열어본 다음부터 방향이 바뀌었다.

## 먼저 데이터를 본다

개발 기간 동안 쌓인 사용자 입력이 원본 2104건. 중복을 걷어내니 1849건이 남았다. 이 정도면 하루면 다 훑는다. 훑었다.

훑고 나서 든 느낌은 "이건 의미 문제가 아니라 표면 문제구나"였다. 같은 개념을 대여섯 가지 방식으로 친다. "이차방정식", "이차 방정식"(띄어쓴 것), "이차방정식 알려줘", "이차방정 식"(오타 섞인 것), "quadratic". 임베딩(embedding — 텍스트를 고차원 벡터로 변환해 의미 유사도를 재는 기법)은 이 중 뒤쪽 두어 개만 잘 잡아준다. 앞쪽은 오히려 규칙으로 처리하는 게 확실하다.

발견한 변형을 대충 묶어보면 이랬다.

| 변형 유형 | 예시 |
|---|---|
| 요청문 후미 | "함수의 극값 알려줘", "~가르쳐줘" |
| 띄어쓰기 | "이차 방정식", "삼각 함수" |
| 별칭·약어 | "미분" ↔ "도함수" |
| 조사·어미 | "극한의 개념", "극한에 대해" |

빈도까지 계산했지만 절대 수치는 배포 전 시점 값이라 여기 옮기지 않겠다. 중요한 건 분포의 모양이지 자릿수가 아니다.

## Unicode부터 만졌다

가장 먼저 손댄 건 유니코드다. 한국어는 같은 "가"가 NFC(정규형 합성)와 NFD(분해)로 다르게 저장된다. macOS 파일명에서 복사해 오면 대개 NFD, 웹폼에서 들어오면 NFC. 문자열 비교가 조용히 실패한다. 이건 눈으로 보면 절대 못 잡는다.

```python
import unicodedata

def normalize_text(s: str) -> str:
    return unicodedata.normalize("NFC", s.strip())
```

두 줄인데 이걸 넣기 전과 후로 매칭 실패의 성격이 달라졌다. 정확히 몇 퍼센트가 좋아졌는지는 A/B 로그를 남기지 않아 지금 답할 수 없다. 다음에 이런 정규화 계층을 붙일 때는 before/after 카운터를 먼저 심어놓는 걸 규칙으로 삼으려 한다.

## 후미를 자르는 규칙은 좁게

두 번째는 "알려줘/가르쳐줘" 같은 요청문 후미다. 사용자는 검색창을 채팅창처럼 쓴다. 정보량은 앞에 있고 뒤는 상투어다.

```python
import re

_TRAILING_PATTERNS = re.compile(
    r"(알려줘|가르쳐줘|설명해줘|찾아줘|알고싶어|뭐야)\s*$"
)

def normalize_for_match(s: str) -> str:
    s = normalize_text(s)
    s = _TRAILING_PATTERNS.sub("", s).strip()
    return s
```

여기서 유혹이 온다. "~에 대해", "~좀", "~부탁해" 다 넣고 싶어진다. 참았다. 정규식(regular expression)을 확장할수록 오버피팅(overfitting — 학습에 쓴 패턴에만 잘 맞고 새로운 입력에 취약해지는 상태) 위험이 커진다. 어떤 콘텐츠의 정식 제목이 "~에 대해"로 끝날 수도 있다. 나는 로그에서 여러 번 반복 등장한 것만 후보로 뒀다.

## 별칭 맵은 짧게 유지한다

세 번째가 별칭이다. "도함수 → 미분", "확률과통계 → 확률·통계"처럼. 딕셔너리 하나면 되니까 코드는 밋밋하다.

```python
_ALIAS_MAP: dict[str, str] = {
    "도함수": "미분",
    "미적분학": "미적분",
    "확률과통계": "확률·통계",
    # ...
}

def apply_alias_map(s: str) -> str:
    return _ALIAS_MAP.get(s, s)
```

문제는 이 맵이 커지기 시작하면 걷잡을 수 없다는 것이다. 실제로 몇 번, "이것도 넣어달라"는 요청을 받았고, 넣었다가 다른 항목의 매칭을 망친 적이 있다. 그 뒤로는 규칙을 하나 두었다 — 로그에서 반복적으로 등장한 표현만 후보. 한 번 나온 별명은 별명이 아니다. 그냥 그 사람 표현이다.

## 마지막에 부분 문자열 매칭

여기까지 해도 못 잡는 게 남는다. "이차방정식의 풀이 방법"처럼 정규화 후에도 정확히 일치하는 표제가 없는 경우. 이럴 땐 substring 검색으로 후퇴시켰다. 우리 콘텐츠 규모에선 이게 노이즈보다 이득이 컸다.

이 폴백이 임베딩과 가장 비슷한 자리에 있다. 언젠가 여기를 벡터 유사도로 바꿔볼 수는 있다. 다만 순서는 지금도 규칙이 앞이고 임베딩이 뒤일 것 같다. 규칙이 잡는 케이스를 벡터에 맡기면 자원만 쓰고 결과는 비슷하거나 미묘하게 나빠지는 걸 몇 번 봤다.

## 아직 열려 있는 것들

정직하게 남겨두면, 나는 이 파이프라인이 "잘 작동한다"고 말할 근거를 완전하게 가지고 있지 않다. 배포 후 A/B, 매칭 실패율 대시보드, 별칭 맵의 히트/미스 카운터. 이 세 가지가 아직 없다. 다음에 이 계층을 다시 열게 되면 코드보다 먼저 이 세 개를 심을 것이다.

임베딩을 언제 붙일지도 아직 미정이다. 다만 붙인다면 "지금까지 규칙으로 잡던 걸 대체"하는 방식은 아닐 것 같다. 규칙이 못 잡은 잔여를 흡수하는 자리, 그 자리 하나만 노리는 편이 낫다고 지금은 생각한다. 이 판단이 뒤집힐 만한 데이터를 아직 못 봤다. 보면 그때 다시 쓰겠다.
