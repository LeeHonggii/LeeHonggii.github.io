처음에는 테마 파일 하나면 충분하다고 생각했다.

마크다운 원고에서 HTML 덱을 자동 생성하는 도구를 만들면서, 초기 설계는 단순했다. "브랜드 컬러를 CSS 변수로 정의하고, 거기서 모든 걸 끌어다 쓰면 된다." 색상을 바꾸면 전체 덱이 바뀌고, 폰트를 바꾸면 모든 슬라이드가 따라간다. 이 정도면 충분해 보였다.

문제는 실제로 써보기 시작하면서 나왔다.

## 뭔가 어긋나기 시작한 지점

표지 슬라이드와 코드 예시 슬라이드는 같은 CSS 변수를 쓰더라도 근본적으로 **구조 자체가 달라야** 했다. 표지는 중앙에 큰 타이틀 하나, 코드 슬라이드는 왼쪽에 설명 오른쪽에 코드 블록. 이걸 하나의 CSS로 커버하려니 선택자가 점점 복잡해졌다.

더 곤란한 건 다른 방향의 변경이었다. "이번 발표는 timeline 구조로 보여주고 싶다"는 요구가 생겼을 때, 그게 컬러와 완전히 무관한 변경임에도 불구하고 CSS 전체를 들여다봐야 했다.

컬러와 레이아웃이 한 파일 안에 섞여 있으니, 어느 쪽을 건드려도 나머지가 영향을 받을지 불확실했다.

## 분리의 기준

결국 두 가지 질문을 다르게 취급해야 한다는 결론에 도달했다.

"이 덱이 어떤 색과 폰트를 쓰는가" — 이건 브랜드 정체성의 문제다. 컬러 팔레트, 타이포그래피 스케일, 여백 단위, 컴포넌트 기본값. 발표 내용과 무관하게 전사적으로 통일되어야 하는 것들이다.

"이 슬라이드가 어떤 구조로 정보를 배치하는가" — 이건 커뮤니케이션의 문제다. `hero`(임팩트 하나), `split`(텍스트+이미지 양분), `code-focus`(코드가 주인공), `timeline`(순서가 핵심), `card-grid`(항목 나열). 이 선택은 콘텐츠에 따라 슬라이드마다 달라져야 한다.

두 질문의 변경 주기가 다르고, 변경 이유도 다르다. 같은 파일에 둘 이유가 없었다.

## 분리 후 달라진 것

디자인 토큰을 별도 파일(`design.md` 같은 형태)로 빼고, 레이아웃은 슬라이드별로 선택하는 구조로 바꿨다. Marp(마프 — 마크다운을 슬라이드로 변환하는 오픈소스 렌더러)에서는 슬라이드 시작에 `<!-- _class: layout-name -->` 형태로 클래스를 붙이면 해당 슬라이드에만 다른 레이아웃을 적용할 수 있다. 이 메커니즘을 활용해서, 레이아웃 템플릿 디렉터리를 만들고 각 레이아웃은 독립적인 CSS로 관리했다.

사용자가 선택하는 것은 이제 "색상 테마"가 아니라 "발표 페이지 구조"다. 브랜드 컬러는 글로벌 토큰에서 자동으로 물려받는다.

변경이 격리된다는 게 실제로 의미하는 건, "새 레이아웃을 추가해도 기존 슬라이드가 깨지지 않는다"는 확신이다. 이전에는 CSS를 건드릴 때마다 전체 덱을 렌더링해서 눈으로 확인해야 했다. 구조가 섞여 있으면 예측이 불가능하다.

---

아직 정리 안 된 것이 하나 있다. 레이아웃 override가 슬라이드 단위로 가능해지면, 동일한 콘텐츠를 레이아웃만 바꿔서 A/B 비교하고 싶은 욕구가 생긴다. "이 슬라이드를 `split`으로 보면 어떻고 `hero`로 보면 어떤가"를 나란히 렌더링해서 고르게 하는 것. 이게 생성 파이프라인 안에 들어가야 하는 기능인지, 아니면 편집기 레벨의 프리뷰 문제인지가 아직 명확하지 않다.
