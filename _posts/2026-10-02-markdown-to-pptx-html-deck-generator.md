처음엔 파일만 나오면 끝나는 일이라고 생각했다. Markdown을 넣으면 PPTX와 HTML이 나온다. Marp(Markdown을 슬라이드로 바꿔 주는 CLI 도구)가 이미 그걸 해 준다.

```bash
marp deck.md --pptx
marp deck.md --html
```

명령어 두 줄이면 된다. 실제로 막힌 곳은 그 앞뒤였다. 입력으로 들어온 Markdown이 변환 중에 조용히 사라지거나, 파서가 아예 멈추거나, 디자인 파일에서 값 하나가 빠졌다.

## 슬라이드에 안 들어가는 내용은 어떻게 하나

한 슬라이드에 내용이 너무 많으면 선택지가 둘이다. 넘치는 부분을 잘라내거나, 슬라이드를 나눈다.

자르면 레이아웃은 깔끔하다. 하지만 사용자가 쓴 문장이 사라진다. 발표자료를 만드는 사람은 그 문장이 거기 있어야 해서 썼을 것이다. 그래서 삭제하지 않고 슬라이드를 분할해서 수용하는 쪽으로 정했다.

산출물도 PPTX와 HTML만 내보내지 않는다. 원문 Markdown, 변환된 Markdown, 적용된 CSS를 같이 보관한다. 결과물이 이상할 때 어느 단계에서 틀어졌는지 나중에 비교할 수 있어야 한다. 원문과 변환본을 둘 다 남겨 두면 "내용이 빠졌다"는 제보를 받아도 diff 한 번으로 확인할 수 있다.

## 디자인과 레이아웃은 다른 축이다

초기에는 "스타일"을 하나로 뭉쳐서 다뤘다. 브랜드 색과 폰트를 고르면 페이지 구조까지 같이 정해지는 식이었다. 쓰다 보니 둘이 독립적으로 움직여야 했다. 같은 브랜드 색을 쓰면서도 어떤 페이지는 표지형, 어떤 페이지는 2단 비교형이어야 한다.

그래서 둘을 나눴다.

- **브랜드 디자인**: 글로벌 색상과 타이포그래피. 덱 전체에 한 번 적용한다.
- **HTML 레이아웃**: 페이지 구조. 슬라이드마다 고를 수 있다.

고르는 화면에는 디자인 카드와 레이아웃 와이어프레임을 넣었다. 이름만 보고 `two-column`인지 `split-hero`인지 알 수는 없으니, 구조를 그린 그림을 같이 보여 준다. 레이아웃 패턴은 20개까지 늘렸다. 20개가 적절한 숫자인지는 따로 따져 보지 않았다. 필요한 구조가 나올 때마다 추가하다가 거기까지 갔다.

CLI에서는 이렇게 지정한다. 덱 전체에는 `--layout <slug>`를 쓴다. 페이지별로 다르게 하려면 `--per-slide-layouts`에 JSON을 넘긴다. 이 값은 Markdown 안에서 슬라이드 단위 클래스인 `<!-- _class: layout-<slug> -->`로 풀린다. Marp의 `_class` 지시어(해당 슬라이드에만 CSS 클래스를 붙이는 문법)를 쓴 것이라, 레이아웃 선택이 결국 CSS 선택자 하나로 환원된다.

## 파서가 멈췄다

한동안 가장 이상했던 증상은 에러가 아니었다. 아무 일도 안 일어났다. 특정 입력을 넣으면 변환이 끝나지 않고 CPU만 돌았다.

원인은 입력을 읽는 정규식이었다. 정규식의 catastrophic backtracking(매칭 실패 시 가능한 경우의 수를 지수적으로 되짚어 보는 현상)이다. 짧은 입력에서는 멀쩡해서 알아채기 어려웠다. 길거나 모양이 살짝 어긋난 Markdown에서 갑자기 멈췄다.

정규식을 더 정교하게 고쳐 볼 수도 있었다. 하지만 이 파서가 다루는 입력은 사람이 쓴 Markdown이다. 어디가 어긋날지 예측할 수 없다. 그래서 정규식 하나로 문서 전체를 훑는 방식을 버리고, 한 줄씩 읽으며 상태를 들고 가는 라인 기반 파서로 교체했다. 줄 단위로 읽으면 최악의 경우에도 입력 길이에 비례해서 끝난다. 대신 코드가 길어지고 덜 우아해졌다. 멈추지 않는 쪽을 골랐다.

이 과정에서 입력 처리 두 군데를 더 손봤다.

- 디자인 파일의 YAML 블록 문자열(`|`, `>`로 여러 줄을 담는 값)을 `_parseFrontmatterMeta`가 제대로 못 읽어서 디자인 메타데이터가 빠졌다. 값이 비는 게 아니라 필드 자체가 누락되는 형태라, 결과물에서 색이나 폰트가 기본값으로 돌아간 것을 보고서야 알았다.
- frontmatter가 아예 없는 Markdown도 들어온다. 이때는 `_parseMarkdownFallback`이 받아서 본문만으로 슬라이드를 구성한다. frontmatter를 필수로 요구하는 도구는 쓰는 사람이 먼저 포기한다.

## 확인한 것, 확인 못 한 것

5슬라이드짜리 스모크 테스트를 돌렸다. PPTX와 HTML 두 파일이 모두 생성됐고, 경고는 없었다.

이게 전부다. 이 테스트는 파일이 만들어진다는 것만 보여 준다. 다음은 보여 주지 못한다.

- 입력 문장이 전부 출력에 남아 있는가. 분할 방식을 택했지만 긴 문서에서 전수 대조를 한 적은 없다.
- HTML이 실제 모바일 화면에서 반응형으로 동작하는가. 브라우저 폭을 바꿔 보는 정도로도 충분히 확인하지 못했다.
- PPTX를 열었을 때 글자 크기와 줄바꿈이 발표에 쓸 만한가.

"경고 없음"은 경고를 낼 만한 검사가 있었다는 뜻일 뿐이다. 검사하지 않는 항목은 경고도 없다.

## 아직 안 닫힌 것

마지막으로 들어온 제보는 실제 UI에서 생성 버튼을 눌렀을 때 PPTX가 만들어지지 않는다는 것이었다. CLI에서는 파일이 나오는데 UI 경로에서는 나오지 않는다. 진단을 시작한 데까지만 기록이 남아 있고, 원인도 해결 여부도 아직 적을 게 없다.

CLI와 UI가 같은 변환 경로를 타는지부터 다시 봐야 한다. 지금까지 스모크 테스트를 CLI로만 돌렸다는 점이 마음에 걸린다.
