템플릿 목록 API에 페이지네이션을 붙이는 작업이었다. 어렵지 않을 것 같았다. `offset`과 `limit`을 받아서 쿼리에 넘기면 되는 일 아닌가.

그런데 기존 API가 `ORDER BY RAND()`를 쓰고 있었다.

---

`ORDER BY RAND()`는 쿼리가 실행될 때마다 행마다 난수를 뽑아 정렬한다. 1회 실행 안에서는 순서가 고정되지만, **요청이 바뀌면 순서도 바뀐다.**

페이지네이션은 요청이 여러 번 온다는 전제로 작동한다. 1페이지를 받고, 2페이지를 받는다. 그런데 두 요청 사이에 `RAND()`가 다시 섞이면 어떻게 될까.

```sql
-- 1페이지 요청
SELECT * FROM template ORDER BY RAND() LIMIT 30 OFFSET 0;

-- 2페이지 요청 (다음 요청)
SELECT * FROM template ORDER BY RAND() LIMIT 30 OFFSET 30;
```

두 번째 쿼리의 `RAND()`는 첫 번째와 완전히 다른 순서를 만든다. 결과적으로 1페이지에 있던 항목이 2페이지에 다시 나올 수 있고, 반대로 아예 한 번도 노출되지 않는 항목도 생긴다. `offset`이 클수록 이 문제가 심해진다.

구조적으로는 당연한 일이다. `OFFSET n`은 "정렬된 결과에서 앞 n개를 건너뛰어라"는 뜻인데, 정렬 자체가 매번 달라지면 건너뛰는 기준이 없어진다.

---

이걸 피하는 방법 중 하나가 seed 고정이다.

```sql
SELECT * FROM template ORDER BY RAND(:seed) LIMIT 30 OFFSET 30;
```

MySQL 기준으로 `RAND(seed)`에 같은 정수를 넘기면 매번 동일한 순서가 나온다. 세션 단위로 seed를 하나 발급해서 클라이언트가 다음 요청에도 그 seed를 같이 보내면, 한 탐색 세션 안에서는 순서가 흔들리지 않는다.

검증도 간단하다. 같은 seed로 1페이지와 2페이지를 각각 조회하면 겹치는 항목이 0건이어야 한다. 실제로 그렇게 확인했다.

- seed 고정 재현성: 동일 ✓  
- 페이지1 vs 2 중복: 0건 ✓

여기까지는 깔끔하다. 문제는 제품 요구사항이다.

---

랜덤 추천의 의도는 "볼 때마다 다른 것을 보여주는 것"이었다. 세션마다 seed가 다르면 그것도 일정 수준 충족되지만, "같은 사람이 오늘 오전에 봤던 것과 오후에 보는 것이 달라야 한다"는 식의 요구사항과는 seed 방식이 미묘하게 맞지 않는다. seed를 언제 갱신하고 얼마나 유지할 것인지, 클라이언트가 seed를 들고 다니는 방식을 어떻게 노출할 것인지, 이것들이 새로운 설계 질문으로 이어졌다.

그래서 방향을 바꿨다. 랜덤은 그대로 두고, 응답 구조만 페이지네이션 규격에 맞추는 것으로 정리했다. `total`, `offset`, `limit`을 응답에 담되, "순서는 요청마다 달라질 수 있다"는 제약을 API 문서에 명시하는 방식이다.

완전한 해결이 아니라는 건 안다. 중복 없는 탐색이 필요한 유즈케이스라면 이 방식은 맞지 않는다. 다만 지금 요구사항이 그 수준까지 요구하지 않았고, seed 방식의 복잡도를 지금 감수할 이유도 없었다.

---

아직 확인하지 않은 게 하나 있다. 데이터가 많아질수록 `ORDER BY RAND()`의 성능이 급격히 나빠진다. 전체 행에 난수를 할당하고 정렬해야 하기 때문이다. 지금 규모에선 문제가 없지만, 이 부분은 언제 다시 봐야 할 것 같다.
