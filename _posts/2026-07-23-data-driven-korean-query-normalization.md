## 임베딩을 붙이기 전에 로그부터 열었다

추천 파이프라인에 매칭이 자꾸 어긋난다는 얘기가 나왔을 때, 첫 반응은 "임베딩(embedding, 텍스트를 벡터로 바꿔 의미 유사도를 계산하는 기법) 붙이자" 였다. 나도 처음엔 그쪽으로 기울었다. 그런데 붙이기 전에 한 가지만 하고 가자 싶었다. **실제로 사용자가 뭘 어떻게 입력하는지** 로그를 뜯어보는 것.

돌린 스크립트는 단순했다.

```bash
python scripts/analyze_user_inputs_for_normalization.py
```

원시(raw) 로그 2104건, 완전 동일 문자열 중복을 걷어내니 1849건. 중복만으로 10% 넘게 빠졌다는 건, 같은 표현을 그대로 반복해서 치는 사람이 그만큼 많다는 뜻이다. 이 시점에서 이미 감이 왔다. 의미 유사도 문제가 아닐 수도 있겠다는 감.

## 1849건을 그냥 눈으로 읽었다

자동 클러스터링 같은 걸 돌릴 수도 있었지만, 표본이 작아서 그냥 스크롤로 훑었다. 표를 하나 만들면서 유형만 갈랐다.

| 유형 | 예시 |
|---|---|
| 띄어쓰기 | `분수의나눗셈` vs `분수의 나눗셈` |
| 어미 변형 | `풀기`, `풀어보기`, `풀어라` |
| 오타 | `뺄샘`, `팬투미노` |
| 학년·차시 표기 | `4학년 3단원`, `초4-3`, `사학년 세번째 단원` |

의미가 다른 게 아니라 **형태가 다른 것**이었다. 임베딩이 잘 푸는 문제는 "다른 단어로 같은 뜻을 말할 때"인데, 여기 있는 건 대부분 그게 아니었다. 순서가 틀렸다고 판단했다.

## 정규화 함수부터 얹었다

가장 먼저 얹은 건 텍스트 정규화(text normalization). 공백, 대소문자, 유니코드 정규형, 자주 붙는 어미를 한 곳에서 처리한다.

```python
def normalize_text(s: str) -> str:
    s = s.strip().lower()
    s = unicodedata.normalize("NFKC", s)   # 전각 → 반각
    s = re.sub(r"\s+", "", s)              # 공백 제거
    s = re.sub(r"(하기|해보기|풀기|풀어라|이란|이란\?)$", "", s)
    return s
```

이거 하나만으로도 눈에 띄게 많은 질의가 동일 문자열로 붙었다. 여기서 배운 건, "쉬운 걸 먼저 하지 않고 어려운 도구부터 꺼내려던" 내 습관이었다.

## 오타는 딕셔너리가 이긴다

오타·비표준 표기는 임베딩으로 붙이려 하면 오히려 위험하다. `뺄샘` 을 `뺄셈` 이 아니라 `뺄샘물` 같은 엉뚱한 것에 붙일 수 있다. 발견된 케이스는 그냥 매핑으로 못박았다.

```python
ALIAS_MAP = {
    "뺄샘": "뺄셈",
    "팬투미노": "펜토미노",
    "나머지있는나눗셈": "나머지가 있는 나눗셈",
}

def normalize_for_match(s: str) -> str:
    s = normalize_text(s)
    return ALIAS_MAP.get(s, s)
```

이 표는 처음 30개 정도로 시작했는데 1849건을 다 훑고 나니 80개가 넘어갔다. "이걸 딕셔너리로 유지하는 게 지속 가능하냐" 는 의문이 있었지만, 지금 규모에선 이게 가장 안전하고 가장 싸다. 임베딩 모델을 새로 붙이고 인덱스를 관리하는 비용보다, 한 줄 추가하는 비용이 훨씬 작다.

## 통제된 어휘가 있다는 사실을 이용했다

이 도메인은 커리큘럼 단원명이 이미 정해져 있다. 자유 텍스트로 검색하는 게 아니라, **정답 집합이 유한하고 통제돼 있다**. 그렇다면 정규화된 질의가 단원명 어절과 얼마나 겹치는지를 보는 것만으로도 후보를 좁힐 수 있다. 역인덱스(reverse index, 단원명의 핵심 어절을 키로 두고 단원 ID를 값으로 매핑한 구조)를 만들어 두고 서브스트링 포함 여부로 후보를 뽑았다.

임베딩이 아니라 문자열 포함 여부로도 이 도메인에서는 정밀도가 붙는다. **어휘가 통제돼 있기 때문에** 가능한 접근이었고, 이걸 일반 검색 파이프라인에 그대로 이식하면 안 된다. 조건이 붙는 해법이다.

## 퓨샷으로 시작했다가 접은 이야기

솔직히 말하면, 이 구조로 오기 전에 LLM에 퓨샷(few-shot, 몇 가지 예시를 프롬프트에 넣어 원하는 형식으로 답하게 하는 방식) 을 먼저 물렸다. 잘 되는 것 같았다. 그런데 예시에 없는 표현이 들어오면 모델이 **없는 단원명을 그럴듯하게 지어냈다**. 그게 로그에 섞여서 나중에 데이터 품질을 오염시켰다.

퓨샷은 패턴을 추론하게 돕는 도구지 케이스를 고정하는 도구가 아니다. 케이스를 고정할 거면 딕셔너리로 못박아야 한다. 이 구분을 흐리면, 나중에 "왜 이 매칭이 이렇게 나왔는지" 를 아무도 재현하지 못한다.

## 아직 안 푼 것

`4학년 3단원` / `초4-3` / `사학년 세번째 단원` 이 부류는 정규화 함수로도 별칭 맵으로도 예쁘게 안 접힌다. 학년·차시 표기는 결국 파서(parser)를 따로 붙여야 할 것 같은데, 아직 안 붙였다. 이 유형이 전체에서 몇 %를 차지하는지도 정확히 재보지 않았다 — 눈으로 보기엔 무시 못 할 덩어리인데, 정확한 비율은 다음에 다시 스크립트를 돌려 확인해야 한다.

임베딩을 아예 안 쓰겠다는 게 아니다. 형태 노이즈를 걷어낸 다음에 남는, **진짜 의미가 다르게 표현된 케이스**가 얼마나 되는지를 먼저 보고 그때 붙일 생각이다. 순서를 지키고 싶다.
