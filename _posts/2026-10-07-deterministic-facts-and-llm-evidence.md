기존 LLM 분석 코드를 읽으면서 가장 먼저 눈에 들어온 건 프롬프트가 아니었다. 프롬프트에 들어가기 전에 코드가 무엇을 확정해 두는가였다. 학생이 한 페이지(문제 하나)를 푼 기록을 받아 선생님용 짧은 리포트를 만드는 모듈이다. 이 글은 그 코드를 읽고 정리한 학습 노트다. 새로 만든 것은 없고, 새 평가 구조를 구상하면서 가져갈 패턴을 뽑아 두는 글이다.

## 모델에게 넘기는 것과 넘기지 않는 것

출력 칸부터 보면 구조가 보인다.

```python
VERDICTS = ("정답", "부분 정답", "오답", "판단 보류")
RELATIONS = ("같음", "정답이지만 다름", "틀림", "비교 안 함")
TEXT_KEYS = ("한줄", "이해", "과정", "확인_질문", "선생님_할_일")
WRONG_WORDS = ("틀렸", "틀린", "오답", "잘못")
CODE_LIKE = re.compile(r"\bF\d+\b|[A-Z]{2}\d{2}[A-Z]{2,4}|[a-zA-Z]{4,}")
NOT_KOREAN = re.compile(r"[Ѐ-ӿ؀-ۿ฀-๿぀-ヿ一-鿿]")
```

판정과 관계는 닫힌 집합이다. 모델이 "대체로 맞음" 같은 말을 새로 만들 수 없다. 서술 칸(`TEXT_KEYS`)만 자유 문장이다. 숫자나 판정처럼 계산 가능한 쪽은 열거형으로 막아 두고, 모델의 몫은 문장으로 한정했다.

`WRONG_WORDS`, `CODE_LIKE`, `NOT_KOREAN`은 서술 문장을 검사하는 용도로 보인다. 틀렸다는 단어, 내부 번호나 영문 식별자가 새어 나온 흔적, 한국어가 아닌 문자를 거른다. 다만 이 정규식이 호출되는 지점은 가져온 코드가 잘려서 직접 확인하지 못했다. 용도는 이름과 모양으로 추정한 것이다.

## 입력에 식별자를 달아 두기

모델이 보는 입력을 만드는 `build_input`에서 눈여겨본 부분은 사실 목록이다.

```python
lines.append("<사실> 번호 · 내용")
lines += [f"[{f['alias']}] {f['text']}" for f in ev.facts if f["code"] not in SKIP_FACTS]
self.text = "\n".join(lines)
prompt = read_prompt(PROMPT)
self.system = prompt
self.fingerprint = hashlib.sha256((prompt + self.text).encode("utf-8")).hexdigest()[:16]
```

화면 기록에서 뽑은 관찰 하나하나가 `[alias] 내용` 형태로 모델에게 간다. 모델이 근거를 인용하려면 이 번호를 써야 한다. 그러면 리포트의 한 문장이 원자료 어느 지점에서 나왔는지 거꾸로 따라갈 수 있다. 면접에서 "이 문장 근거가 뭐죠?"를 받았을 때 답할 수 있는 구조다.

같은 블록에서 해시도 눈에 띄었다. 지문(fingerprint)은 프롬프트와 입력 텍스트를 합친 SHA-256 앞 16자리다. 프롬프트를 한 글자만 고쳐도 지문이 바뀌고 저장본은 무효가 된다.

## 정답 여부는 코드가 대조한다

여기가 이 글의 제목에 가장 가까운 부분이다.

```python
def answer_groups(self):
    groups, _ = SolutionWay.answers(self.task_id, self.ev.order)
    norm = lambda t: re.sub(r"\s|=.*", "", str(t))
    out = []
    for g in groups or []:
        exprs = {norm(a) for a in g.get("답") or [] if re.fullmatch(r"\d+[+\-×÷]\d+", norm(a))}
        if exprs:
            out.append(exprs)
    return out

# 정답 목록에 식이 있고 학생 화면에 카드 식이 있으면, 정답 여부는 코드가 대조한다(AI 의 「가장 큰/작은」 비교가 실행마다 흔들림)
def verdict_by_code(self, p):
    groups, mine = self.answer_groups(), self.exprs("CARD_EXPR")
    if not groups or not mine:
        return p
    hits = [any(e in g for e in mine) for g in groups]
    code = "정답" if all(hits) else "부분 정답" if any(hits) else "오답"
    # ... (이하 생략)
```

주석이 이유를 직접 적어 두었다. 모델에게 "가장 큰 값과 가장 작은 값"을 비교시켰더니 실행마다 답이 흔들렸다는 것이다. 그래서 정답 목록은 학생 답을 보기 전에 따로 구해 두고, 학생 화면에서 뽑은 식과 집합 대조를 한다. 정답 그룹이 여럿이면 전부 맞았을 때 정답, 일부만 맞았을 때 부분 정답, 하나도 안 맞았을 때 오답이다.

세부 처리 세 가지가 눈에 남았다.

- 식을 비교하기 전에 `norm`으로 공백과 `=` 뒤를 지운다. 같은 식이 표기 차이 때문에 불일치로 나오는 일을 막는다.
- `\d+[+\-×÷]\d+` 꼴만 정답 식으로 인정한다. 이 형태에 안 맞으면 코드는 판정하지 않는다.
- `if not groups or not mine: return p`. 정답 목록이나 학생 식 중 하나라도 없으면 코드는 손대지 않고 모델 판정을 그대로 둔다. 근거가 없는데 오답으로 단정하지 않는 것이다.

마지막 줄이 이 글의 두 번째 주제와 이어진다. 뒤에서 다시 다룬다.

## 저장본을 읽을 때도 코드 값을 다시 얹는다

```python
def load(self):
    p = self.path()
    if not p.exists():
        return None
    d = load_json(p)
    if d.get("fingerprint") != self.fingerprint:
        return None
    self.relation_by_code(d["result"])
    return d
```

지문이 맞는 저장본을 읽는 순간에도 `relation_by_code`로 코드 값을 다시 적용한다. 모델 응답이 저장될 때 한 번만 덮어쓰는 게 아니라 읽을 때마다 덮는다. 나중에 대조 로직이 고쳐지면 저장된 리포트의 판정 관련 값도 새 로직을 따라간다. 모델 출력을 최종값이 아니라 원재료로 대하는 방식이다. `relation_by_code`의 본문은 가져온 코드에 없어서, 정확히 무엇을 덮는지는 확인하지 못했다.

## 평가 불가와 수행 실패

`VERDICTS`에 "판단 보류"가 있고 `RELATIONS`에 "비교 안 함"이 있다. 모범답안이 없으면 입력에 `<모범답안> 없음`이 들어간다. 평가할 근거가 없는 경우를 "오답"과 다른 값으로 둔 설계다.

이 구분이 새 구조에서 중요해질 것 같다. 관찰 근거가 없다는 것은 그 능력이 낮다는 뜻이 아니라 관찰하지 못했다는 뜻이다. 화면에 식이 한 줄도 안 남은 학생을 낮게 평가하면 안 된다. 위 코드의 `return p`가 그 원칙을 코드 수준에서 지키고 있다.

## 아직 정하지 못한 것

여러 활동 유형을 지원하는 평가 구조를 구상하고 있지만, 구현이나 성능 검증은 하지 않았다. 코드를 읽으며 먼저 필요하다고 정리한 것은 세 가지다.

- 활동 유형별 정의
- 유형마다 관찰 가능한 근거의 목록
- 전문가가 매긴 판정 데이터

식을 대조할 수 있는 활동은 이 코드처럼 닫을 수 있다. 정답 식이 없는 활동에서는 무엇을 코드가 확정하고 무엇을 모델에게 맡길지 아직 모른다. 영상 기반 분석도 실험 방향만 논의했다.

평가 품질을 어떻게 잴지도 열려 있다. 이 코드에는 모델 판정과 코드 판정이 얼마나 갈렸는지 세는 부분이 보이지 않았다. 코드가 덮어쓴 비율을 재 보지 않았기 때문에, 모델이 실제로 얼마나 틀렸는지는 모른다. 전문가 판정 데이터가 생기면 그 숫자부터 보고 싶다.
