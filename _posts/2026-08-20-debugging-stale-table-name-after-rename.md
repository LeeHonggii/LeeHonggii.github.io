테이블 이름을 바꾸는 건 쉽다. `ALTER TABLE` 한 줄이면 된다. 문제는 그 한 줄이 닿지 않는 곳에 있다.

---

공개 템플릿 카테고리 조회 API를 손보다가 이상한 걸 발견했다. 코드는 멀쩡해 보였고, ORM 레이어도 오류를 뱉지 않았다. 그런데 응답이 뭔가 비어 있었다. 정확히는 "비어있다"가 아니라 — 카테고리별로 태그 정보가 붙어야 할 자리에 아무것도 없었다.

JOIN을 보니 테이블명이 구버전이었다.

어느 시점에 태그 테이블 이름이 바뀐 적이 있었다. 마이그레이션 스크립트는 실행됐고 DB에는 새 이름만 남아 있는데, 조회 쿼리에는 이전 이름이 그대로 박혀 있었다. Python에서 ORM이 이를 실행할 때 MySQL은 에러를 던지지 않았다 — LEFT JOIN이었기 때문이다. 존재하지 않는 테이블에 LEFT JOIN을 걸면 DB가 어떻게 반응하는지는 엔진마다 다를 수 있지만, 이 경우 응답에서 JOIN 결과가 그냥 NULL로 채워진 채 나왔다. API는 200을 반환했고, 클라이언트는 태그가 없는 템플릿을 받았다.

조용하게 틀린 응답이 나가고 있었던 셈이다.

---

수정 전에 먼저 확인부터 했다. 짐작만으로 커밋을 만들면 나중에 "그게 실제로 문제였냐"는 질문에 답하기 어렵다.

로컬에 DB 스키마 검증 스크립트가 있었다.

```shell
python scripts\check_schema.py
```

이 스크립트가 정확히 무엇을 하는지는 지금 이 글에서 소개할 수 없다 — 코드를 갖고 있지 않으니까. 다만 이 시점에서 내가 확인하려던 건 두 가지였다. 해당 테이블명이 현재 DB에 실제로 존재하는지, 그리고 수정 후 JOIN이 의도한 결과를 돌려주는지. 테이블 존재 여부만 보는 건 충분하지 않다. JOIN이 실제로 붙는지, NULL row가 새어 나오지 않는지까지 실행해봐야 한다.

LEFT JOIN은 특히 그렇다. 조인 대상이 없을 때 에러 대신 NULL을 반환하도록 설계된 문법이라, 오타가 있어도 쿼리 자체는 성공한다. 그래서 "쿼리가 실패하지 않았다"는 것이 "쿼리가 맞다"는 뜻이 아니다.

검증 후 수정 내용은 단순했다. 파일 하나, 테이블명 한 곳.

```shell
git add <product>/mysql/public_project_repository.py
git commit -m "fix: 카테고리 공개캔버스 조회 JOIN 테이블명 수정"
```

커밋 메시지에 수정한 테이블명을 명시했다. 나중에 이 커밋을 다시 볼 때, 또는 같은 패턴이 다른 파일에 있을 때 `git log --all -S "구_테이블명"` 으로 추적할 수 있도록.

---

이 작업 이후에 생각해둬야 할 게 하나 더 있다.

이번에 발견한 건 우연이었다. 응답이 비어있다는 걸 눈으로 확인하다가 JOIN을 들여다봤다. 만약 태그가 원래부터 드물게 붙는 도메인이었다면? NULL이 가득한 응답도 정상처럼 보였을 것이다.

테이블 rename이 발생할 때 코드베이스 전체에서 구 이름을 검색하는 단계가 빠져 있다. 지금은 마이그레이션 스크립트를 만들 때 이 확인을 수동으로 해야 한다. 자동화하거나 CI에 걸어두는 게 맞겠지만, 아직 그렇게 되어 있지 않다.
