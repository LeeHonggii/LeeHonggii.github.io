## AI가 만든 덱은 왜 늘 비어있나

발표자료를 AI에게 맡겨본 사람은 안다. 슬라이드는 나온다. 근데 원본에 있던 표가 사라져 있다. 코드 블록은 "다음 슬라이드 참고"로 대체돼 있다. 세 줄짜리 설명이 세 단어 bullet으로 압축돼 있다.

예쁘긴 하다. 그런데 내가 쓴 내용이 아니다.

이 문제를 그때그때 프롬프트로 우회하는 건 지쳤다. "표 유지해줘", "코드 그대로 넣어줘", "요약하지 말고" — 한 문장 추가할 때마다 결과가 오히려 이상해졌다. 그래서 방향을 뒤집었다. **발표자료 생성은 창작이 아니라 변환이어야 한다.** Markdown 원본을 손대지 않고 슬라이드 포맷으로 옮기는 것, 그것만 잘하면 된다.

어차피 나는 Obsidian에서 글을 쓴다. 같은 `.md` 하나에서 PPTX와 반응형 HTML을 뽑아내는 플러그인을 직접 만들기로 했다.

## 왜 두 엔진을 붙이면 안 되는가

처음엔 무식하게 두 개를 붙이려 했다. PPTX는 pptxgenjs로, HTML은 별도 렌더러로. 그런데 이걸 그리다가 멈췄다.

두 엔진이 같은 Markdown을 각자 해석하면, 슬라이드 경계가 어긋난다. PPTX에서는 3페이지에 있는 표가 HTML에서는 4번째 섹션에 있다. 폰트 크기 기준선이 다르면 텍스트가 잘리는 지점이 다르다. "같은 내용"이라고 우기는 두 산출물이 실제로는 미묘하게 다른 발표가 되는 것이다.

한쪽이 ground truth가 되어야 한다.

## Marp를 공통 계층으로

**Marp** — Markdown Presentation Ecosystem, Markdown을 슬라이드로 바꾸는 오픈소스 도구다. 이 친구가 이미 두 출력을 다 지원한다.

```bash
marp deck.md --pptx
marp deck.md --html
```

같은 소스, 같은 파서, 같은 레이아웃 엔진. 두 산출물이 갈라지는 지점이 없다. 내가 두 엔진을 직접 조율하는 문제가 애초에 사라진다.

플러그인 쪽에서는 이걸 파이썬 래퍼 하나로 감쌌다.

```bash
make_deck.py input.md --mode both --design corporate-blue --layout bento-grid
```

`--mode both`면 PPTX와 HTML을 한 번에 뽑는다. Obsidian 커맨드 팔레트에서 이 스크립트를 호출하는 게 플러그인의 전부다. 얇게 유지했다.

## 디자인과 레이아웃을 왜 분리했나

브랜드 테마가 여러 개다. 레이아웃 패턴도 여러 개다. 이걸 한 축으로 묶으면 "파란 글꼴 + 벤토 그리드", "파란 글꼴 + 좌우 2단", "따뜻한 톤 + 벤토 그리드"... 조합이 폭발한다.

그래서 두 축을 완전히 갈랐다.

- `design.md` 컬렉션 — 색·폰트·브랜드 톤만 정의하는 Marp 테마. 프로젝트에 `theme.css`로 복사돼 PPTX·HTML 양쪽에 붙는다
- layout 패턴 — HTML 전용 반응형 배치. 색과 무관하게 콘텐츠가 어디에 놓이는지만 결정한다

레이아웃은 슬라이드 단위로 Marp directive로 적용한다.

```html
<!-- _class: layout-bento-grid -->
```

디자인을 바꾸는 사람과 레이아웃을 바꾸는 사람이 서로의 파일을 건드리지 않는다. 조합의 폭발은 런타임에 일어나고, 소스에는 두 축이 독립적으로 존재한다.

## 산출물 구조에서 유지한 한 가지 고집

변환기를 만들면서 놓치기 쉬운 게 있다. 원본을 버린다.

```
<project>/_decks/<slug>/
  deck.pptx
  index.html
  deck.md       # Marp directive 붙은 작업본
  theme.css
  source.md     # 원본 입력 그대로
```

`source.md`를 굳이 남긴다. 변환 후 원본이랑 대조할 게 있어야 하기 때문이다. `deck.md`는 이미 Marp가 알아먹을 수 있게 각종 지시자가 붙어 오염돼 있다. 저건 원본이 아니다.

## 내용 유실 검증 — 자동 중단은 안 한다

가장 오래 고민한 부분이다. 변환 후에 원본과 산출물을 비교해서 뭐가 빠졌는지 확인하는 단계.

지금 검증하는 항목:

- 원본 H2 개수 대비 슬라이드 수가 말이 되는지
- 원본에 있던 `|---|` 표 구분자가 산출물에도 남았는지
- 백틱 코드 블록 개수가 맞는지
- 50자 이상 문장을 샘플링해서 HTML 본문에 그대로 있는지

이걸 만들 때 초반 판단이 하나 뒤집혔다. 처음엔 검증 실패 시 변환을 중단시키려 했다. 근데 몇 번 써보니 그게 방해가 됐다. 어떤 유실은 의도적이었다 — 표를 이미지로 대체했거나, 긴 문단을 슬라이드 노트로 옮겼거나.

그래서 방향을 바꿨다. **가시화가 먼저, 중단은 나중.** 검증 실패는 경고 로그로만 남기고 변환은 진행된다. 개발자가 로그를 보고 "이건 괜찮은 유실"인지 "이건 사고"인지 판단한다. 자동 중단은 판단권을 뺏는 방식이었다.

## 아직 안 풀린 것

Marp의 슬라이드 경계 로직이 가끔 사람 기대와 다르다. `---`로 명시적으로 자른 곳 말고, H2가 넘칠 때 자동으로 페이지를 넘기는 규칙이 특히 그렇다. 짧은 슬라이드가 여러 개 이어지면 병합이 안 되고, 긴 슬라이드는 뒤가 잘려나간다. 여기는 아직 검증 로직으로 못 잡는다 — "잘렸다"는 걸 프로그램적으로 감지할 방법을 못 찾았다.

CSS specificity 문제도 남아있다. layout 클래스와 design 테마가 같은 selector를 건드리면 어느 쪽이 이기는지가 슬라이드마다 달라지는 순간이 있다. 이건 다음에 layout 파일을 정리하면서 scope을 다시 잡을 생각이다.

발표자료 도구는 결국 내 내용을 예쁘게 포장하는 게 아니라 그대로 옮기는 역할이어야 한다 — 라는 문장을 마지막에 쓰려다 지웠다. 그건 결론이 아니라 시작 지점의 가정이었고, 아직 이 가정이 얼마나 지켜지고 있는지 나도 다 재보진 못했다.
