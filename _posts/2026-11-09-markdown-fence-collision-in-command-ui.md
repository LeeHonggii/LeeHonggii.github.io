증상은 단순했다. 채팅창에서 긴 명령을 펼쳤더니 명령어 블록이 아니라 그냥 일반 채팅 글처럼 보였다. 회색 코드 박스는 없었고 글자는 본문 폰트였다. 줄바꿈이 일부 사라져 있었고, 중간에 `#` 로 시작하는 줄은 제목처럼 커져 있었다.

명령이 짧을 때는 멀쩡했다. 길고 여러 줄인 명령에서만 깨졌다.

## 첫 의심은 길이였다

"긴" 명령에서만 터지니 접기·펼치기 로직에서 문자열을 자르다가 뭔가 틀어졌다고 생각했다. 그쪽을 한참 봤는데 자르는 지점과 증상이 맞지 않았다. 잘린 결과를 확인해도 깨지는 건 똑같았다.

그래서 "길다"가 아니라 "내용에 뭐가 들었나"로 질문을 바꿨다. 깨지는 명령들을 나란히 놓고 보니 공통점이 있었다. 명령 안에 다시 코드 블록이 들어 있었다. 셸 heredoc 으로 마크다운 파일을 쓰는 명령, 생성된 코드를 통째로 넘기는 명령이 그랬다. 길이는 우연히 따라온 조건이었다. 코드 블록이 들어갈 만큼 긴 명령이었을 뿐이다.

## 원인 추정

명령을 표시할 때 앞뒤를 고정된 백틱 세 개로 감싸고 있었다. 이런 식이다.

````markdown
```
cat > note.md <<'EOF'
예시:
```
echo hi
```
EOF
```
````

마크다운 파서 입장에서는 본문 속 ` ``` ` 한 줄이 곧 닫는 펜스(fence, 코드 블록 경계 표시)다. 첫 블록은 `예시:` 까지만 코드이고, 그 뒤부터는 일반 마크다운으로 파싱된다. 그 아래에서 `echo hi` 는 본문 문단이 되고, 다음 ` ``` ` 는 새 코드 블록을 연다. 이후 짝이 어긋나서 나머지 전체가 반전된다. 화면 전체가 일반 채팅처럼 보인 이유가 이것이다.

CommonMark 규칙상 여는 펜스보다 짧거나 같은 길이의 백틱 줄만 닫는 역할을 한다. 바깥을 백틱 네 개로 감싸면 안쪽의 세 개짜리는 그냥 본문이 된다.

````markdown
````
```
echo hi
```
````
````

이 정도는 알고 있었는데 구현에서는 놓쳤다. 임의의 명령이 들어오는 자리에 펜스 길이를 상수로 박아 둔 것이 문제였다.

"추정"이라고 쓰는 이유가 있다. 깨진 명령 사례들이 모두 이 규칙으로 설명되고 최소 재현도 되지만, 사용자 화면에서 원래 증상이 사라지는 것까지는 아직 보지 못했다.

## 고친 것

본문에서 연속된 백틱의 최장 길이를 구해 그보다 하나 긴 펜스를 만든다. 최소 3개이고, 본문에 백틱 묶음이 없으면 기존과 같은 3개다. 이 계산을 공통 함수 하나로 뺐다.

함수를 따로 뺀 이유는 같은 표현을 쓰는 곳이 렌더링만이 아니었기 때문이다. 코드를 훑어보니 같은 "명령을 펜스로 감싼 문자열"이 세 군데에서 쓰이고 있었다.

- 화면 렌더링
- 클립보드 복사
- 제목 비교 (같은 명령인지 판별하려고 펜스 포함 문자열을 비교)

렌더링만 고치면 복사해 붙여넣은 내용이 화면과 달라지고, 제목 비교는 이전에 만든 항목과 어긋난다. 그래서 세 경로가 모두 공통 함수를 쓰게 바꿨다.

## 확인한 것과 못 한 것

- 펜스 길이 계산에 대한 단위 테스트를 추가했다. 본문에 백틱이 없을 때, 3개일 때, 4개 이상일 때를 다룬다.
- 기존 회귀 테스트는 그대로 통과했다.
- `cargo check --release` 로 릴리스 컴파일도 통과했다.

못 한 것은 이 변경으로 사용자 화면의 증상이 실제로 풀렸는지 확인하는 일이다. 테스트는 문자열 단위에서 맞는 것을 보증할 뿐이고, 앱에 반영된 뒤 같은 명령을 다시 펼쳐서 보는 단계는 당시에 하지 못했다.

## 남은 의문

백틱 외에 `~~~` 펜스를 쓰는 입력이 들어오면 지금 계산은 그것을 보지 않는다. 앞에 들여쓰기가 붙은 펜스 줄이 닫는 줄로 인정되는 경우도 아직 따져 보지 않았다. 지금은 "본문 안의 백틱 묶음"만 기준으로 삼았는데, 그걸로 충분한지는 실제로 입력을 더 돌려 봐야 알 수 있다.
