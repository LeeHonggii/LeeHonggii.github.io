유사도 점수를 뽑는 건 그래도 공식이 있다. 코사인이든 뭐든, 넣으면 숫자가 나온다. 정답이 있으니까 막혀도 검색하면 풀린다.

막힌 건 그 다음이었다.

여러 관점에서 나온 점수들을 어떻게 합칠 것이며, 어떻게 순서를 세울 것이며, 같은 콘텐츠가 화면 세 곳에 뜨는 걸 어떻게 막을 것인가. 이건 검색해도 명쾌한 답이 안 나온다. 서비스마다 다르고, 팀마다 다르고, "그때 그때 달라요"가 정답인 영역이다.

이 글은 추천 파이프라인의 마지막 조립 단계를 만들면서 배운 것들이다. 정확히는, 배웠다기보다는 몇 번 뒤집어엎고 나서야 감이 잡혔던 것들.

## 유사도를 건드리지 마라

처음에는 부스팅(boosting)을 유사도 점수 자체에 섞어 넣었다. "이 콘텐츠는 시리즈 다음 차시니까 유사도에 0.2 더해주자" 같은 식으로.

이게 왜 나쁜 짓인지는 며칠 지나서야 알았다. 디버깅을 할 수가 없다. 어떤 콘텐츠가 왜 위로 올라왔는지 물었을 때, 유사도가 진짜 높았던 건지 부스팅이 얹혀서 올라온 건지 구분이 안 갔다. 로그를 파도 뒤엉킨 숫자만 나왔다.

그래서 원칙을 하나 세웠다.

- 유사도(relevance)는 모델이 낸 값 그대로 보존한다
- 부스팅은 별도 필드로 붙이고, 최종 점수는 곱셈으로 합친다
- 각 단계의 원본 값은 다 남긴다

```python
final_score = relevance * (1 + boost)
```

한 줄이지만, 이 한 줄이 있어야 나중에 "왜 이 순서냐"에 답할 수 있다. `relevance`, `boost`, `final_score` 세 개를 같이 남기니까 리뷰할 때 "이건 유사도 자체가 높았네", "이건 부스팅이 세게 붙었네"가 바로 보였다.

부스팅 규칙은 비즈니스 판단이다. 여기가 은근히 정치적인 영역이라, 어떤 값을 얼마나 줄지는 사람이 앉아서 정해야 한다. 진행 중이던 시리즈의 다음 차시는 크게, 신규 등록은 조금, 이미 본 것은 크게 마이너스. 값은 계속 바뀐다.

## 점수를 더하지 않는다

여러 관점에서 나온 점수를 합칠 때, 처음 떠오르는 건 그냥 더하는 것이다.

$$
\text{score} = w_1 \cdot s_1 + w_2 \cdot s_2 + \dots
$$

이게 왜 위험한지도 직접 겪어보고 알았다. 한 관점의 모델은 정규화된 0~1 값을 뱉고, 다른 관점의 모델은 코사인 유사도를 그대로 뱉는다. 단위가 다르다. 스케일을 맞추는 전처리를 붙이면 되지 않느냐 싶은데, 그게 또 관점마다 분포가 달라서 min-max로 하면 outlier에 흔들리고, z-score로 하면 음수가 나와서 곱셈 파이프라인이랑 안 맞고, 그렇게 하나씩 땜빵을 붙이다 보면 원래 뭘 하려던 건지 잊어버린다.

RRF(Reciprocal Rank Fusion, 역순위 융합)는 이 문제를 우회한다. **점수를 합치지 말고 순위를 합치자**는 아이디어다.

```
rrf_score(item) = Σ 1 / (k + rank_i)
```

`k`는 보통 60을 쓴다 (원 논문 권장값). `rank_i`는 관점 i에서의 순위.

콘텐츠 A가 직무 관점에서 3위, 관심사 관점에서 1위였다면:

```
rrf(A) = 1/(60+3) + 1/(60+1)
       = 0.01587 + 0.01639
       = 0.03226
```

순위가 낮을수록 (숫자가 클수록) 기여가 급격히 작아진다. 어떤 관점에서 1등이었던 항목이 확실히 유리하고, 100등 근처는 사실상 무시된다. 스케일을 맞출 필요가 없다는 게 실무에서 제일 크다. 새 관점을 붙일 때 정규화 전처리를 새로 짤 필요 없이 순위만 매겨서 던져 넣으면 된다.

한 가지 걸리는 게 있다. RRF는 관점 간 중요도를 반영하지 못한다. "직무 관련성이 관심사보다 두 배 중요하다"를 표현하려면 `1/(k+rank)` 앞에 가중치를 붙이는 변종을 쓰거나, 관점별로 후보 개수 자체를 조절해야 한다. 우리 케이스에서는 아직 그럴 만큼 관점 간 우열이 뚜렷하지 않아서, 기본형을 그대로 쓰고 있다. 이건 나중에 다시 볼 문제로 남겨뒀다.

## 화면은 알고리즘이 만들지 않는다

RRF까지 통과시켰다고 끝이 아니었다. 최종 20개를 화면에 얹었더니 어색했다.

상위 20개 중 15개가 같은 카테고리에서 나왔다. RRF가 그렇게 뽑을 만한 이유도 있었다 — 그 카테고리 콘텐츠가 여러 관점에서 골고루 상위였으니까. 알고리즘 관점에서는 맞는 답이었다. 그런데 사용자 화면 관점에서는 틀린 답이었다.

여기서 알고리즘과 화면이 갈라진다는 걸 처음 봤다. 랭킹이 정확한 것과 화면이 자연스러운 건 다른 문제였다.

라운드 로빈(round-robin) 중복 제거는 그 갈라진 틈을 메우는 가장 단순한 장치다. 각 관점에서 한 명씩 돌아가며 아직 뽑히지 않은 것을 하나씩 뽑는다.

```python
seen = set()
result = []

axes = [continue_axis, job_axis, interest_axis]
while len(result) < TARGET_COUNT:
    picked_any = False
    for axis in axes:
        for item in axis.ranked_items:
            if item.id in seen:
                continue
            result.append(item)
            seen.add(item.id)
            picked_any = True
            break
    if not picked_any:
        break
```

각 관점에서 한 개씩 뽑고 다음 관점으로 넘어간다. 한 바퀴 돌면 다시 처음 관점으로. 목표 개수에 도달하거나, 뽑을 게 없으면 멈춘다.

이 방식의 좋은 점은 **한 관점이 아무리 강해도 다른 관점이 최소 지분은 확보한다**는 것이다. "진행 중인 강의 이어보기"가 한 자리, "직무 관련"이 한 자리, "관심사 기반"이 한 자리. 사용자는 세 종류의 이유를 화면에서 동시에 본다.

단점도 명확하다. 관점 A의 3위가 관점 B의 1위보다 어떤 절대적 기준에서 더 좋은 후보였을 수도 있는데, 라운드 로빈은 그걸 무시한다. 다양성을 위해 정확도를 조금 포기하는 거래다. 우리는 이 거래를 받아들였다. 화면이 어색한 것보다는 나았다.

## 아직 못 푼 것

세 단계를 다 조립하고 나니 눈에 띄는 문제가 하나 남았다.

부스팅 값을 지금은 사람이 정한다. 시리즈 다음 차시에 얼마, 신규 콘텐츠에 얼마. 이 값들이 정말 맞는 값인지 아무도 모른다. 클릭률로 검증하려면 A/B 테스트가 필요한데, 트래픽이 그걸 감당할 만큼 나오는지도 아직 재보지 않았다.

RRF의 `k=60`도 마찬가지다. 논문 권장값을 그대로 쓰고 있는데, 우리 데이터 분포에 맞는 값이 따로 있을 가능성이 크다. 이것도 재본 적 없다.

파이프라인이 돌아간다는 것과 파이프라인이 최적이라는 건 다른 이야기다. 지금은 전자까지만 와 있다. 후자는 다음 분기 숙제로 미뤄뒀다.
