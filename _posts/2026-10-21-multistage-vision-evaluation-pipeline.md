기존 평가 파이프라인 코드를 읽으면서 정리한 학습 노트다. 내가 처음부터 짠 코드가 아니라 읽은 코드다. 그래서 "무엇을 하는가"보다 "각 단계가 무엇을 믿고 있는가"를 따라가며 읽었다.

대상은 화면 위에서 도구(저울, 구슬, 막대, 숫자 카드 같은 조작 교구)를 움직여 푸는 수학 문제다. 학생의 풀이는 최종 화면과 조작 기록으로 남는다. 이걸 LLM이 보고 채점한다.

## 이미지가 두 장 있으면 헷갈린다

처음엔 이미지가 "문제 이미지" 하나인 줄 알았다. 실제로는 역할이 다른 두 장이다.

- 문제의 **초기 화면**: 주어진 조건이다. 저울에 뭐가 올라가 있고, 칸이 몇 개인지 같은 것.
- 모범답안의 **최종 화면**: 정답이 채워진 상태다.

최종 화면을 문제 정의에 섞으면 모델은 이미 채워진 답을 "문제의 조건"으로 읽는다. 사람이 보면 당연한 구분인데, 모델에게는 그냥 이미지 두 장이다. 파이프라인이 역할을 말해주지 않으면 구분하지 못한다.

이 구분은 파이프라인 구조에도 그대로 나타난다. 내가 본 설계는 이렇다.

```
문제 정의 → 학생별 판정 → 이벤트 문장화 → 평가 → 코드 확정값 적용 → 리포트 서술
```

같은 문제는 초기 상태의 fingerprint(화면 상태를 요약한 식별값)로 묶어서 문제 정의를 한 번만 만들고 공유한다. 학생별로 달라지는 것은 최종 상태 판정뿐이다. 다만 fingerprint를 만드는 코드는 이번에 읽은 범위에 없었다. 구조는 문서와 호출부에서 확인했을 뿐, 어떤 필드를 해시하는지는 아직 못 봤다.

## "코드가 읽을 수 있는 건 코드가 읽는다"

이미지를 LLM에 통째로 넘기지 않는 부분이 가장 인상적이었다. 화면을 그리는 원본 요소 목록(좌표, 값, 색)이 있으니, 결정적으로 계산되는 값은 코드가 계산해서 문장으로 만든다.

저울 교구가 대표적이다. 접시 양쪽에 올라간 무게를 합산해서 같은지까지 코드가 판정한다.

```python
def plate_weights(elements, start):
    bodies = [e for e in elements if e.get("svgId") == SCALE_BODY]
    out = []
    for b in bodies:
        side = {"왼쪽": [], "오른쪽": []}
        for e in elements:
            if str(e.get("svgId", "")).startswith(SCALE_WEIGHT_PREFIX) and e is not b and e.get("plate") == b.get("id"):
                side["왼쪽" if e["x"] < b["x"] else "오른쪽"].append(float(e.get("value") or e.get("n") or 0))
        w = {k: round(sum(v), 3) for k, v in side.items()}
        out.append(f"접시별: 왼쪽={w['왼쪽']:g}({len(side['왼쪽'])}개), 오른쪽={w['오른쪽']:g}({len(side['오른쪽'])}개) · 무게 같음: {'예' if w['왼쪽'] == w['오른쪽'] else '아니오'}")
    return " / ".join(out)
```

(코드의 `svgId` 값은 일반화한 상수로 바꿨다. 로직은 그대로다.)

LLM은 "왼쪽 접시에 추가 무게가 몇 개 올라갔는지"를 이미지에서 세다가 틀릴 수 있다. 코드가 `왼쪽=3(2개), 오른쪽=3(1개) · 무게 같음: 예` 같은 문장을 만들어주면 모델은 세지 않고 읽기만 한다. 부동소수 비교를 피하려고 `round(..., 3)`을 먼저 거치는 것도 눈에 띄었다.

겹친 카드를 읽는 부분은 더 지저분하고, 그래서 더 배울 게 많았다. 자릿값 카드(100, 10, 1 같은 카드)를 겹쳐 놓으면 하나의 수가 된다. 겹침 여부를 좌표 근접으로 판단한다.

```python
def place_cards(elements, start):
    cards = []
    for e in elements:
        if str(e.get("svgId", "")).startswith(CARD_PREFIX) and str(e.get("value") or "").strip():
            a, b, c, d = extent_of(e) or (0, 0, 0, 0)
            cards.append((int(e.get("n") or 1), int(str(e["value"])[0]) * 10 ** (int(e.get("n") or 1) - 1), c, b))
    if not cards:
        return ""
    groups = []
    for n, v, right, top in sorted(cards, key=lambda c: (c[2], c[3])):
        g = next((g for g in groups if abs(g["right"] - right) < 15 and abs(g["top"] - top) < 30), None)
        if g:
            g["vals"].append(v)
        else:
            groups.append({"right": right, "top": top, "vals": [v]})
    return "자릿값 카드: " + ", ".join(str(sum(g["vals"])) + (f"(겹침: {'+'.join(map(str, sorted(g['vals'], reverse=True)))})" if len(g["vals"]) > 1 else "") for g in groups)
```

오른쪽 끝 좌표 차이 15 미만, 위쪽 좌표 차이 30 미만이면 같은 무리로 본다. 이 15와 30이 어떻게 정해졌는지는 코드에 근거가 없고, 주석도 없다. 화면 해상도나 카드 크기에 묶인 값일 텐데, 아직 확인하지 못했다. 면접에서 물으면 "경험적으로 잡은 값으로 보이고 근거는 확인이 필요하다"고 답할 수밖에 없다.

출력에 `(겹침: 100+20+3)`처럼 합산 내역을 같이 남기는 것은 좋은 습관이라고 생각했다. 나중에 평가 단계나 사람이 "123이 어떻게 나왔지?"를 되짚을 수 있다.

## 초기 화면은 빼기 위한 기준이다

`student_text`가 두 이미지 문제와 가장 직접 닿아 있다.

```python
def student_text(elements, start):
    s0 = {e.get("id") for e in start or [] if e.get("svgId") == "input-text"}
    new = [plain(e.get("text")) for e in elements if e.get("svgId") == "input-text" and e.get("id") not in s0]
    new = [t for t in new if t and t != "텍스트를 입력해 주세요."]
    return ("학생이 쓴 글 상자: " + " / ".join(new)) if new else ""
```

초기 화면에 이미 있던 글 상자 id를 빼고, 기본 안내 문구("텍스트를 입력해 주세요.")도 거른다. 학생이 쓴 것만 남긴다. 초기 상태가 "문제의 조건"이자 "학생이 한 일을 가려내는 기준선"으로도 쓰인다. 막대로 숫자를 만드는 `segment_digits`도 같은 원리라서, 시작 화면의 숫자 칸을 기준으로 읽고 처음 자리에서 옮겨진 막대 수를 센다.

## 모범답안을 모델에게 쓰게 할 때

다른 파일은 실험 스크립트다. 모델에게 문제 이미지(초기 화면 2장까지)를 주고 "정답 척도"를 만들게 한다. 여기서 덧붙인 프롬프트 조각이 흥미로웠다.

```python
ADD2 = """
[교구별 정답 값 꼴]을 지킨다:
- "정답들" 의 항목마다 "꼴" 칸에 [교구별 정답 값 꼴] 중 하나의 이름(예: 판 칸별, 식, 영역 안 개수, 접시별 무게, 자리별 숫자, 모양)을 적고, "답" 은 그 꼴의 모양 그대로 쓴다(설명 글을 섞지 않는다). 설명은 "설명" 칸에 따로 쓴다.
- 정답이 여러 개면 "답" 목록에 같은 꼴로 모두 쓴다.
- "단계" 의 각 단계에 "확인" 칸을 더해, 그 단계가 끝났을 때의 화면을 같은 꼴로 쓴다(예: 판 칸별: 십=6, 일=11). 꼴로 쓸 수 없는 단계(머릿속 생각)는 "확인": "기록 없음".
"""
```

앞에서 본 판독 함수들은 `접시별: 왼쪽=…` 같은 정해진 꼴로 화면을 문장화한다. 모범답안도 같은 꼴로 쓰게 하면 학생 화면과 정답이 같은 언어로 비교된다. 판독 코드의 출력 형식이 정답 형식을 정하는 셈이다. "꼴로 쓸 수 없으면 `기록 없음`"이라는 탈출구를 둔 것도 모델이 억지로 값을 지어내지 못하게 하는 장치로 읽혔다.

실험 구성도 같이 적어둔다. 교구 꼴 목록은 코드가 문제 화면에서 쓰인 교구를 추려 만든다.

```python
RUNS = 5
CORE = [("2-1-3 덧셈과 뺄셈", 2), ("크고 작은 합과 차", 2), ("세 자리 수", 4), ("2-1-3 덧셈과 뺄셈", 5), ("내가 직접", 3), ("내가 직접", 4)]
# ...
text = sw.build_input() + "\n\n[교구별 정답 값 꼴]\n" + answer_forms(tools_in(row), caution=False)
with ThreadPoolExecutor(RUNS) as ex:
    calls = list(ex.map(lambda _: OpenaiChatCompletion(model=MODEL, system=system, user=text,
                        images=sw.images[:2], max_tokens=8000).run(), range(RUNS)))
```

문제 6개를 각각 5번씩 돌리고, 결과에 이전 실행(`old_runs`)을 나란히 저장한다. 같은 입력을 여러 번 돌리는 이유는 흔들림을 보려는 것이다. 이 노트를 쓰는 지금 내 손에는 그 비교 결과가 없다. 5번 중 몇 번이 일치했다는 식의 수치는 쓰지 않는다.

## 평가 이후에도 코드가 이긴다

마지막 한 가지는 순서였다. LLM이 평가를 끝낸 뒤에도 코드로 확정되는 값(예: 위에서 본 무게 합산 같은 것)은 덮어쓸 수 있다. 그리고 리포트를 서술하는 마지막 단계에는 재판정을 맡기지 않는다. 서술 단계의 모델은 앞에서 확정된 결과를 말로 풀기만 한다.

이유를 내 말로 풀어보면, 판정을 여러 단계가 할 수 있으면 단계마다 결론이 달라질 수 있고, 최종 리포트가 앞의 평가와 어긋난 문장을 쓸 수 있다. 평가와 서술을 분리한 것은 이 어긋남을 구조로 막는 선택으로 보인다. 프롬프트 배치도 같은 맥락이다. 공통 스키마와 평가 기준을 앞에, 학생별 데이터를 뒤에 둔다. 앞부분이 학생이 바뀌어도 똑같으니 캐시 효율에도 유리할 텐데, 실제로 캐시가 얼마나 적중하는지는 재보지 않았다.

## 남은 것

- 문제 정의 단계의 fingerprint가 어떤 필드로 만들어지는지 코드를 아직 못 읽었다.
- "코드 확정값이 LLM 평가를 덮어쓰는" 지점의 구현을 직접 확인하지 못했다. 구조 설명에 의존한 부분이다.
- 근접 판정의 15, 30 같은 임계값은 다른 해상도의 문제 화면에서도 맞는지 모른다.
- 교구 판독 함수가 새 교구가 생길 때마다 하나씩 늘어나는 구조인데, 이게 유지보수 가능한 선인지 판단하려면 교구 종류가 몇 개까지 늘어나는지 봐야 한다.

다음엔 평가 단계의 프롬프트와 코드 확정값이 합쳐지는 지점을 읽어볼 생각이다. 거기서 모델의 판단과 코드의 판단이 충돌할 때 어느 쪽 로그가 남는지가 궁금하다.
