작은 모델이 메모리 부족으로 죽었다. 처음엔 내 스크립트 버그라고 생각했다.

추천 모델을 직접 학습시키려고, 후보 모델들을 같은 데이터로 먼저 비교하던 중이었다. 장비는 16GB 메모리의 Apple Silicon Mac 한 대. 평가 데이터 생성기와 모델 실행·채점 스크립트는 직접 짜 둔 상태였고, 측정 대상은 위치 편향, 확률 포화(출력 확률이 0 또는 1 근처로 몰리는 현상), 추천 성능, 지연, 메모리였다.

## 7B도 아닌 모델이 OOM

로그를 보면 모델 크기로는 설명이 안 됐다. 이 정도 크기면 16GB에서 돌아야 하는데 로드 단계에서 실패했다. 같은 모델이 어제는 돌았다.

범인은 모델이 아니었다. 같은 머신에서 다른 대형 모델 서버가 떠 있었고, 그 프로세스가 통합 메모리(Apple Silicon에서 CPU와 GPU가 공유하는 메모리)를 이미 상당량 잡고 있었다. 작은 모델이 들어갈 자리가 없었던 것이다.

그러면 더 곤란한 문제가 생긴다. 이 상태에서 어쩌다 로드에 성공한 모델이 있다면, 그 지연과 메모리 수치는 "모델의 성능"이 아니라 "그날 옆에서 뭐가 돌았는지"를 섞어 담고 있다. 실패한 모델은 눈에 보이지만, 느려지기만 한 모델은 안 보인다. 후자가 더 위험하다고 판단했다.

보완한 것은 단순하다.

- 실행 전에 가용 메모리와 경쟁 프로세스를 확인한다.
- 확인한 시작 상태를 결과 파일에 같이 기록한다.
- 경쟁 프로세스가 있으면 조용히 진행하지 않고 멈춘다.

수치를 고치는 게 아니라, 수치가 어떤 조건에서 나왔는지를 남기는 쪽으로 풀었다.

## 대기열을 하나로

경쟁 프로세스를 사람이 알아서 피하는 방식은 오래 못 간다. 무거운 작업(다운로드, 모델 변환, 평가)을 단일 동시 실행 대기열로 옮겼다. 한 번에 하나만 돈다.

여기서 한 번 더 걸렸다. 다운로드나 전송이 끝났다는 것과, 평가 작업이 대기열에 실제로 등록됐다는 것은 별개의 사건이다. 파일은 다 받았는데 작업이 등록되지 않아서 아무것도 안 도는 상태가 있었다. 완료 신호만 보고 넘어가면 결과가 없다는 사실을 한참 뒤에야 알게 된다. 그래서 두 단계를 따로 확인하게 했다.

## 실험 규약

돌려서 숫자만 나오면 비교가 아니다. 나중에 "이 수치 어떻게 나왔죠"에 답하려면 다음을 같이 남겨야 했다.

- 모델 리비전, 양자화 방식, 실행기, 입력 길이
- 지연, 피크 메모리, 스왑 사용량

입력 길이를 넣은 이유는 메모리와 지연이 길이에 따라 달라지기 때문이다. 스왑을 넣은 이유는 피크 메모리가 멀쩡해 보여도 디스크로 밀려나 느려진 실행을 걸러내기 위해서다.

## 추론이 된다고 학습이 되는 건 아니다

추론이 성공하고 메모리가 여유 있으면 학습도 되겠거니 했다. 틀린 가정이다. 학습에는 역전파(gradient 계산)와 옵티마이저 상태가 얹힌다. 추론 메모리는 하한도 상한도 못 된다.

그래서 학습 쪽은 별도로 재야 한다. 실험에 쓸 옵션 후보는 이렇다.

```bash
--mask-prompt      # 프롬프트 부분은 손실 계산에서 제외
--grad-checkpoint  # 활성값을 저장하는 대신 다시 계산해 메모리를 아낌
--seed             # 반복 실행 비교를 위해 고정
--dequantize       # 양자화된 모델을 되돌려 학습에 쓸 때
```

`--grad-checkpoint`는 메모리를 줄이는 대신 시간을 쓴다. 이 비용이 얼마인지는 아직 재보지 않았다. `--dequantize`는 되돌리는 순간 메모리가 늘어나므로, 추론에서 확인한 수치를 그대로 쓸 수 없다.

## 실행하지 못한 모델은 꼴찌가 아니다

처음엔 모든 모델을 공통 API로 돌릴 계획이었다. 막상 해보니 모델마다 실행기 지원이 달랐다. 어떤 모델은 이 실행기에서 아예 못 돌았다.

이걸 점수 0으로, 혹은 최하위로 표에 넣으면 "이 모델은 성능이 낮다"로 읽힌다. 사실은 "이 환경에서 못 돌렸다"일 뿐이다. 표에서 비워 두고 "비교 누락"으로 표시하기로 했다. 다른 실행기를 쓰면 결과가 달라질 수 있고, 그렇게 되면 실행기 차이가 섞인 비교가 되므로 그것도 기록 대상이다.

참고로 비교 대상 자체도 한 번 바로잡았다. 처음엔 두 후보를 순위를 출력하는 재정렬 모델로 이해하고 있었는데, 확률을 출력하는 판정 모델이었다. 출력 형태가 다르면 같은 척도로 채점할 수 없어서 대상을 수정했다.

## 초기 결과, 그리고 남은 것

여러 모델을 돌린 초기 비교에서 확인된 건 두 가지다. 모델 크기가 성능을 보장하지 않았고, 데이터 유형별로 결과가 달랐다. 그 이상의 수치를 여기 적을 만큼 반복 측정은 하지 못했다.

자체 데이터로 학습하는 단계는 아직 끝나지 않았다. 최종 모델도 정하지 못했다. 학습 메모리를 실측했을 때 지금 후보 중 몇 개가 16GB 안에 들어올지, 그리고 그때도 경쟁 프로세스 확인이 충분할지는 해봐야 안다.
