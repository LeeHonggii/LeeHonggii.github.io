에이전트가 파일을 고칠 때마다 채팅 피드에 도구 실행 이벤트가 쌓인다. 처음엔 이걸 빨강(삭제)·초록(추가) 두 색으로 칠한 diff 블록으로 보여주는 걸로 충분하다고 생각했다. 실제로 쓰기 시작하니 읽을 수가 없었다.

## 같은 변경이 두 번 나온다

가장 먼저 눈에 띈 건 중복이었다. 파일 하나를 수정했는데 카드가 두 장 떴다. 도구 호출은 실행 전 이벤트와 완료 이벤트가 각각 피드에 들어오는데, 둘이 같은 입력을 담고 있어서 화면에서는 똑같은 변경이 두 번 보였다.

단순히 하나를 버리면 되는 게 아니었다. 완료 이벤트가 없는 경우가 있다. 실행 중이거나 중간에 끊긴 호출이다. 이때 실행 전 이벤트까지 버리면 변경이 화면에서 사라진다.

그래서 입력 내용으로 fingerprint(이벤트를 식별하는 지문 문자열)를 만들어 `renderFeed()` 에서 같은 지문끼리 묶었다. 규칙은 단순하다. 완료 이벤트가 있으면 그걸 보여주고, 없으면 실행 전 이벤트를 그대로 둔다. 지문을 어떤 필드 조합으로 만들었는지, 같은 파일을 같은 내용으로 두 번 연속 수정하는 경우 하나로 합쳐지지 않는지는 별도로 검증하지 않았다. 이 부분은 아직 의심이 남아 있다.

## 접으면 아무것도 안 보인다

중복을 없애도 카드가 길었다. 접어두면 파일 경로만 남아서, 펼쳐보기 전에는 무슨 변경인지 알 수 없었다. 그래서 `_extractChangePreview()` 를 넣었다. Edit·MultiEdit·Write 세 종류의 입력에서 변경된 첫 줄을 꺼내 접힌 카드 제목 옆에 붙인다. 입력 모양이 도구마다 달라서 추출 분기를 따로 둬야 했다.

펼친 쪽도 손봤다. 상세 코드는 기본 30줄만 보여주고 "더 보기"로 나머지를 연다. 그래도 한 줄이 아주 긴 코드가 있어서 `max-height: 420px` 로 높이 상한을 걸었다. 30줄이라는 값은 화면에서 보면서 정한 것이고, 근거가 되는 측정은 없다.

## 색이 안 나오는 이유는 라이브러리가 없어서였다

가독성 문제 중 가장 오래 헤맨 건 구문 강조였다. diff 렌더러(`_renderEditDiff(..., inp.file_path)`)는 파일 경로로 언어를 판별해 Prism으로 칠하도록 되어 있었다. 코드는 맞는데 화면에는 색이 없었다.

한참 렌더링 쪽을 의심하다가, 런타임에 Prism 자체가 로드되어 있지 않다는 걸 발견했다. 렌더러가 라이브러리 존재를 암묵적으로 가정하고 있었던 것이다. 번들을 고쳐 Prism을 넣는 방법도 있었지만, 환경이 바뀔 때마다 같은 일이 반복될 것 같았다. 대신 `_simpleHighlight` 라는 정규식 기반 폴백을 만들어, Prism이 없으면 키워드·문자열·주석 정도만이라도 칠하게 했다. Prism만큼 정확하지는 않다. 정규식이라 중첩 문자열 같은 경계 케이스는 틀릴 수 있다.

## 배경색이 토큰 색을 먹고 있었다

강조가 살아난 뒤에야 다른 문제가 보였다. 추가·삭제 행의 배경이 진해서 구문 토큰 색이 묻혔다. 초록 배경 위의 초록 문자열은 읽히지 않는다. 변경 배경을 옅게 낮추니 토큰 색과 변경 표시가 함께 보였다. 빨강·초록만으로는 부족하다는 제목의 뜻이 이거다. 변경 여부와 코드 구조를 동시에 전달해야 했다.

## 남은 것

세션 단위로 카드를 묶는 기능도 생각했다. 한 번의 작업에서 같은 파일을 여러 번 고친 카드를 하나로 모으는 식이다. 구현이 끝났다고 확인하지 못했다. 지금 상태로는 파일을 열 번 고치면 카드가 열 장 뜬다. fingerprint 중복 제거가 실제로 어떤 입력에서 틀리는지부터 먼저 확인해볼 생각이다.
