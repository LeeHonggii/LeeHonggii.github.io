AI에게 발표자료를 만들어 달라고 하면 자꾸 요약이 나온다. 10페이지 분량의 내용을 5페이지로 줄이면서 "핵심만 추렸습니다"라고 한다. 문제는, 내가 필요한 건 요약본이 아니라 원문의 구조를 유지한 슬라이드라는 점이다. 삭제된 내용이 뭔지조차 알기 어렵다.

그 불편함에서 이 도구가 시작됐다.

---

## 버리지 않는다는 원칙

핵심 결정은 하나였다. **재작성하지 않는다.** 원문 Markdown의 헤딩 구조를 그대로 슬라이드 단위로 매핑한다.

`##` 하나가 슬라이드 하나가 된다. 내용이 짧으면 1:1. 내용이 길어서 한 슬라이드에 안 들어오면 1:N으로 분할한다. 분할할 때 기준은 간단하다 — 코드 블록, 표, 단락 경계를 자르지 않는다. 문장 중간에서 페이지가 끊기는 일은 없어야 했다.

AI가 개입하는 지점은 슬라이드 화자 노트 생성이나 레이아웃 힌트 정도다. **본문 텍스트 자체를 AI가 재작성하게 두지 않는다.** 이것만으로도 콘텐츠 유실의 대부분을 막을 수 있다고 봤다.

---

## 단일 소스, 두 가지 출력

원문 Markdown 하나에서 PPTX와 반응형 HTML을 동시에 뽑는 구조를 목표로 삼았다. Marp(Markdown Presentation Ecosystem — Markdown을 슬라이드로 변환하는 CLI 도구)가 이 역할을 한다.

```
marp deck.md --pptx
marp deck.md --html
```

출력 디렉토리는 슬라이드 단위로 격리했다.

```
_decks/<slug>/
├── deck.pptx
├── index.html
├── deck.md       # Marp 변환용 중간 파일
├── theme.css
└── source.md     # 원문 그대로
```

`source.md`가 있다는 게 중요하다. 나중에 재생성이 필요할 때 원문이 항상 같은 위치에 있어야 해시 비교로 멱등성(idempotency — 같은 입력에는 같은 출력이 나오는 성질)을 보장할 수 있다. 원문이 안 바뀌었다면 굳이 다시 생성하지 않는다.

---

## 검증 레이어: 생성 후 빠진 게 있는지 확인한다

생성 자체보다 이 부분에 더 공을 들였다.

슬라이드가 만들어진 다음, 원문에 있던 세 가지를 산출물에서 다시 찾는다.

- **코드 블록**: ` ``` ` 로 감싸진 블록이 원문에 있었다면 PPTX·HTML에 그게 남아있는지
- **표**: `|` 로 시작하는 Markdown 테이블이 살아있는지
- **긴 문장**: 원문에서 일정 글자 수 이상의 단락이 있었다면, 잘리지 않고 어딘가에 존재하는지

이 검증이 통과 못 하면 파이프라인이 멈춘다. 경고가 아니라 오류다. "일단 나오긴 했는데 내용이 빠졌어요"를 사람이 나중에 알아차리는 구조는 쓸모가 없다고 판단했다.

---

## 아직 못 정한 것

분할 기준이 애매한 케이스가 있다. 코드 블록이 원문에서 60줄이면 어떻게 할까. 한 슬라이드에 다 올리면 글씨가 안 보이고, 쪼개면 문맥이 끊긴다. 지금은 "분할하되 레이아웃 경고를 내라"는 쪽으로 기울어 있는데, 실제로 써보기 전까진 맞는 선택인지 모르겠다.

화자 노트 자동 생성도 마찬가지다. 원문 내용을 그대로 노트로 내리면 발표자가 보기엔 너무 길고, AI한테 요약을 맡기면 처음의 원칙과 충돌한다. 이 부분은 아직 열려 있다.
