AI로 수학 문항을 생성하는 작업에서 "원하는 문제가 안 나온다"는 얘기가 나왔다. 처음 든 생각은 단순했다. 입력 메타데이터가 부족하니 학습 목표, 관찰된 오류, 대표 오답 같은 항목을 더 넣으면 되겠다는 것이었다.

이 글은 그 생각을 그대로 실행하지 않고 먼저 따져 본 과정의 기록이다. 결론부터 적으면, 메타데이터가 생성 품질을 높이는지는 **아직 검증하지 못했다.** 생성 실험은 크레딧 부족으로 한 번 실패했다. 충전 후에는 API 연결이 되는지만 확인했다. 아래는 실험 전에 정리한 설계 쪽 이야기다.

## 먼저 데이터가 어디 있는지부터

메타데이터를 설계하려면 학생 활동 기록이 어디에, 어떤 구조로 저장되는지 알아야 했다. 그래서 여러 데이터베이스의 스키마와 JSON 필드를 훑는 조회 스크립트를 먼저 만들었다.

중간에 막힌 곳이 있었다. 활동 기록이 압축 문자열로 저장돼 있었는데, 문자열 앞에 형식을 알리는 접두어가 붙어 있었다. 이걸 모르고 통째로 복호화하니 오류가 났다. 접두어를 떼고 풀자 복원된 데이터가 기존 분석 코드의 입력 구조와 그대로 호환됐다. 새 변환 계층을 만들 필요가 없다는 것까지 확인하고 나서야 메타데이터 설계로 넘어갈 수 있었다.

## 항목을 늘리기 전에 "어느 출력 필드를 받치나"

메타데이터 후보는 금방 모였다. 학습 목표, 연결 단위개념, 관찰된 오류, 대표 오답 같은 것들이다. 그런데 항목을 나열하다 보니 질문이 바뀌었다. 이 항목이 **최종 출력의 어느 부분을 뒷받침하는가?**

- 학습 목표는 문제의 의도를 정한다.
- 대표 오답은 선택지(오답 보기)의 근거가 된다.
- 관찰된 오류는 어떤 함정을 문제에 넣을지 정한다.

출력 필드와 연결되지 않는 항목은 모델에게 읽을거리만 늘린다. 원하는 방향으로 끌어 주지는 못한다.

같은 패턴을 다른 실험에서 이미 써 본 적이 있다. 학생 기록을 단계별로 판정하는 단계표 생성 실험인데, 문항 생성 코드는 아니다. 활동 메타데이터를 프롬프트용 글로 조립하는 함수가 있다.

```python
# 실증 문제집에는 활동별 오개념 칸이 없다(새 메타 양식의 새 칸) — 시험용 가정값, 실제 메타데이터가 오면 바꾼다
ACT_MIS = {11: ["M05"], 12: ["M04", "M06"]}

def meta(t):
    """활동 메타데이터(연결 단위개념·활동 오개념)를 글로 만든다 — 학생 진단 오개념이 아니라 활동에 붙은 것."""
    c = t.ctx
    ids = ACT_MIS.get(t.page.get("order"), [])
    mis = " / ".join(f"{m['id']} 「{m['name']}」 — {m.get('report', '')}" for m in WB.get("misconceptions") or [] if m["id"] in ids) or "없음"
    return f"[연결 단위개념] {c.get('unit')} 「{c.get('unit_name')}」\n[메타 오개념] {mis}\n[활동 목표] {c.get('goal')}"
```

돌아보면 이 함수가 보여 주는 게 두 가지다. 하나는 메타데이터가 `[연결 단위개념]`, `[메타 오개념]`, `[활동 목표]`라는 이름 붙은 칸으로 프롬프트에 들어간다는 점이다. 칸이 이름을 가지니 지침에서 "이 칸의 것만 쓴다"고 참조할 수 있다. 다른 하나는 맨 위 주석이다. 활동별 오개념 칸이 원본 자료에 없어서 **가정값으로 채워 둔 것**이다. 시험은 돌릴 수 있지만, 이 가정값으로 얻은 결과를 실제 메타데이터의 효과로 읽으면 안 된다.

## 지침이 막고 있으면 항목을 늘려도 소용없다

같은 실험의 시스템 프롬프트에는 이런 규칙이 있다.

```python
TABLE_SYS = """수학 활동 하나의 「단계표」를 만든다. ...
규칙:
- 단계는 학생이 화면에서 실제로 하게 되는 조작 순서로 3~5개. 첫 단계는 반드시 「과제 받아들이기·첫 표상」...
- 오개념은 [메타 오개념] 목록 안의 것만 쓴다. 다른 오개념을 새로 만들지 않는다.
- 단계마다 [메타 오개념] 목록을 **하나씩 모두** 보고, 설명 가운데 이 단계 조작에서 드러나는 말이 있으면 「오개념들」에 넣는다. ...
- 「근거」는 그 오개념 설명의 말을 **원문 그대로 인용**. ...
JSON 으로만: {"steps": [{"id": "S1", "name": "단계 이름", "기대 조작": "…", "알 수 있는 것": "...", "오개념들": [{"id": "...", "근거": "설명 인용", "보일 조작": "…", "핵심": "…"}]}]}"""
```

여기서 메타데이터는 입력인 동시에 **허용 목록**이다. 목록에 없는 오개념은 출력에 못 나온다. 그러니 메타데이터를 늘리는 일이 곧 모델의 선택 범위를 정하는 일이 된다.

반대 방향의 문제도 있다. 문항 생성에서 지침이 특정 유형을 금지하고 있거나, 출력 스키마에 필요한 관계를 담을 칸이 없다면 어떨까. 예를 들어 "이 오답이 이 오개념에서 나왔다"는 연결을 스키마가 표현하지 못하면, 대표 오답을 아무리 정교하게 넣어도 그 관계는 출력에 남지 않는다. 입력을 고치기 전에 현재 쓰는 프롬프트와 스키마의 버전, 그리고 거기 걸린 제약부터 대조해야 하는 이유다. 이 대조는 아직 끝내지 못했다.

## 샘플은 채점 기준인가, 생성 입력인가

설계하다가 가장 늦게 정리된 질문이 이것이었다. 기준 샘플 문항을 어떻게 쓸 것인가.

처음에는 샘플을 **평가 기준**으로만 보았다. 생성 입력에서 샘플을 빼고 메타데이터만으로 만든 결과를 샘플과 비교하면, 메타데이터의 효과가 깨끗하게 보일 거라고 생각했다. 그래서 샘플을 제외한 비교 실험을 준비했다.

그런데 이후 요구 사항을 다시 확인해 보니, 샘플도 생성 입력이었다. 샘플 없이 만든 결과는 실제 운영 조건과 다르다. 준비해 둔 비교 실험은 설계를 수정해야 했다. 평가 기준으로 쓸 샘플과 생성에 넣을 샘플을 분리해야 하고, 그러면 같은 샘플이 양쪽에 쓰여 비교가 오염되지 않는지도 따져야 한다.

전문가 검수 범위도 같은 문제와 이어져 있다. 검수자가 샘플을 기준으로 본다면 생성 입력에 같은 샘플이 들어간 결과는 유리하게 평가될 수 있다.

## 지금 상태

- 생성 실험 코드와 입력 조건은 준비했다.
- 첫 실행은 크레딧 부족으로 실패했다.
- 충전 후에는 API 연결만 확인했다. 생성 결과는 아직 하나도 보지 못했다.
- 메타데이터 항목이 문항 품질을 개선하는지는 **확인이 필요하다.**

다음에는 샘플 역할을 분리하도록 비교 실험을 고치고, 현재 프롬프트와 출력 스키마가 금지하는 문항 유형이 없는지 먼저 대조한 뒤에 돌려 볼 생각이다. 가정값으로 채운 오개념 칸을 실제 메타데이터로 바꿀 수 있을지는 아직 모르겠다.
