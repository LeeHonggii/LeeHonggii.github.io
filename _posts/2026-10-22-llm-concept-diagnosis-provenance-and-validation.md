기존에 있던 멀티모달 평가 파이프라인을 읽는 중이었다. 학생이 화면에서 만든 풀이 흔적과 활동 이력이 들어가서, 문제 정의, 답안 판정, 평가를 거쳐 리포트가 나오는 구조다. 실제 실행 순서를 따라가다 보니 리포트에 찍히는 "선개념 / 본개념 / 후개념" 목록이 어디서 오는지 확인하고 싶어졌다.

결론부터 말하면, 교육과정 데이터베이스를 조회해서 가져온 값이 아니었다. 이 목록은 모델이 생성할 수 있는 값이다. 교사가 입력해 주지 않으면 모델이 사전학습 지식으로 채운다. 이 글은 그 사실을 알게 된 뒤 "리포트의 어떤 문장을 얼마나 믿을 수 있나"를 다시 정리한 학습 노트다.

## 목록이 만들어지는 자리

프롬프트가 요구하는 출력 형태는 이렇다.

```json
"concepts": {
  "pre":  ["이 문제를 풀기 전에 이미 알고 있어야 하는 개념"],
  "core": ["이 문제로 익히게 하려는 개념"],
  "post": ["이걸 익히면 다음에 배우게 되는 개념"]
}
```

스키마는 칸만 정의한다. 값을 어디서 가져오라는 지시가 없다. 이 칸이 "교육과정에서 조회한 결과"인지 "모델이 그럴듯하게 만든 결과"인지는 출력만 봐서는 구분되지 않는다.

내가 처음 놓친 부분이 여기였다. 리포트에는 "선개념: 자릿값의 이해"처럼 단정적인 문장이 나온다. 읽는 사람은 어떤 기준표와 대조했다고 받아들이기 쉽다. 실제로는 모델이 문제 텍스트를 보고 "이 문제면 이런 개념이 필요하겠지" 하고 쓴 것일 수 있다. 틀렸다는 뜻이 아니다. 근거의 종류가 다르다는 뜻이다.

기준이 만들어지는 경로를 나눠 보면 이렇다.

- 교사가 입력한 기준을 채택하는 경로
- 교사 입력이 없어서 모델이 생성하는 경로

두 경로의 결과물은 같은 칸에 같은 모양으로 들어간다. 그래서 어느 경로로 만들어졌는지를 값과 함께 남겨야 한다고 생각했다. 교사가 준 기준이면 그렇게 표시하고, 모델이 만든 기준이면 "생성됨"이라고 드러내야 한다.

## 코드가 확정하는 것과 모델이 추론하는 것

이 파이프라인에서 관찰 쪽은 비교적 단단하다. 화면의 좌표를 읽어서 어떤 칸에 무엇이 놓였는지를 코드가 계산한다. 정답 항목과 화면 판독 글을 맞대는 부분이 대표적이다. 설계 의도는 클래스 설명에 그대로 적혀 있다.

```python
class Matcher:
    """정답 항목 값과 화면 판독 글을 맞대 일치·불일치·맞댈 수 없음(None)을 낸다 —
    판정이 아니라 판정 AI 에 주는 사실. 모르면 None, 틀린 「불일치」를 내지 않는다."""
```

세 값을 내는 구조가 핵심이다. 모르는 것을 `False`로 내보내지 않고 `None`으로 남긴다. 불일치를 잘못 단정하는 쪽이 일치를 놓치는 쪽보다 해롭기 때문이다. 코드는 사실만 넘기고 판정은 AI가 한다.

「또는」으로 갈리는 답을 처리하는 분기에서도 같은 원칙이 보인다.

```python
@staticmethod
def alternatives(p):
    # 「답 칸1=3 또는 4」 → 「답 칸1=3」, 「답 칸1=4」 — 값 쪽만 「또는」으로 갈린 꼴
    if " 또는 " not in p:
        return None
    alts = [a.strip() for a in p.split(" 또는 ")]
    head = re.match(r"^(.*?[=:]\s*)", alts[0])
    return [a if (head is None or re.search(r"[=:]", a)) else head.group(1) + a for a in alts]
```

```python
alts = Matcher.alternatives(p)
if alts:
    res = [Matcher.part(a, reading) for a in alts]
    return True if True in res else None if None in res else False
```

대안 중 하나라도 맞으면 `True`다. 하나라도 판독 불가면 `None`이다. 전부 확실히 아닐 때만 `False`가 나온다. 판독이 불확실한 대안이 섞여 있는데 `False`를 내면, 맞았을 수도 있는 답을 틀렸다고 못 박게 된다. 그래서 `None`이 `False`보다 우선한다.

한편 칸별 개수가 정확히 맞는지 보는 `board_ok`는 모든 자리의 수를 정확히 비교한다. 여기에는 모델이 끼어들 틈이 없다. 코드가 확정한 값이고, 같은 입력이면 항상 같은 결과가 나온다.

이 부분은 "학생이 화면에서 무엇을 했는가"에 관한 이야기다. 같은 파이프라인에 있어도 "학생이 어떤 오개념을 가졌는가"는 이 코드가 풀어 주지 않는다.

## 규칙을 만드는 일과 해당 여부를 판단하는 일

오개념 쪽을 읽으면서 두 작업이 섞여 있다는 걸 깨달았다.

1. 오개념 규칙을 만든다. 예를 들면 "이런 식으로 놓으면 이런 오개념이다" 같은 기준이다.
2. 학생의 행동이 그 규칙에 해당하는지 판단한다.

2번은 관찰이다. 화면에 실제로 남은 흔적에 근거하고, 위에서 본 코드가 일부를 확정해 준다. 1번은 다르다. 규칙 자체가 모델의 생성물이면, 2번이 아무리 정확해도 "그 규칙이 교육적으로 타당한가"는 보장되지 않는다.

처음에는 규칙마다 출처와 관찰 근거를 같이 남기면 신뢰 문제가 해결된다고 생각했다. 그런데 이건 절반만 맞다. 출처 표시는 이 판단이 어디서 왔는지를 알려 준다. 판단이 맞는지는 알려 주지 않는다. "모델이 생성한 규칙, 학생의 이 행동에 근거"라고 적혀 있어도, 규칙이 틀렸다면 근거가 아무리 충실해도 진단은 틀린다.

## 권한 설정이지 정확성이 아니다

이 시스템에는 두 가지 권한 설정이 있다. 교사 입력이 있으면 그것을 기준으로 채택한다. 코드가 계산한 값은 판정으로 고정한다. 둘 다 설계로서 합리적이다. 다만 둘 다 "누구 말을 따를 것인가"를 정하는 규칙이다. 따른 결과가 교육적으로 맞다는 뜻이 아니다.

교사가 입력한 기준도 틀릴 수 있다. 코드가 고정한 값도 규칙이 틀리면 정확하게 틀린 값이다. 권한 구조는 책임 소재를 분명하게 해 줄 뿐이다.

## 정확성은 어디서 확인하나

교육적 정확성을 보려면 비교 대상이 필요하다. 교사가 같은 사례에 직접 내린 판정 모음, 즉 골드셋이다. 시스템 판정과 교사 판정의 일치도는 가중 카파(weighted kappa)로 잴 수 있다. 가중 카파는 우연히 일치할 확률을 빼고, 등급이 서로 가까운 불일치는 덜 감점해서 계산하는 일치도 지표다.

이번에 대화로 확인한 결과, 이 검증은 지금 공백이다. 골드셋이 없고, 일치도를 잰 적도 없다. 그래서 "진단이 얼마나 정확한가"라는 질문에는 지금 수치로 답할 수 없다. 이 글에도 정확도나 일치도 수치는 넣지 않았다. 재 본 적이 없기 때문이다.

## 영상으로 가면 달라질까

관찰 근거가 화면 결과물에 한정된다는 점도 걸렸다. 풀이 과정을 영상으로 받으면 어떤 순서로 풀었는지, 어디서 망설였는지까지 볼 수 있다. 그런 실험을 하려면 어떤 데이터를 어떤 조건으로 모아야 하는지를 정리해 제안했다. 다만 거기까지다. 영상 처리는 구현하지 않았고, 실험 결과도 없다. 영상이 오개념 진단 정확도를 올려 줄지는 아직 모른다.

한 가지 걸리는 점이 남아 있다. 영상에서 얻은 관찰이 늘어도, 그 관찰을 해석하는 규칙이 여전히 모델의 생성물이라면 앞에서 말한 공백이 그대로 남는다. 골드셋을 먼저 만들지, 영상 실험을 먼저 할지는 아직 정하지 못했다.
