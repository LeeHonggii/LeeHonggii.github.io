프롬프트를 다섯 번쯤 고쳤을 때 멈췄다. 예시를 늘리고, 역할을 부여하고, 출력 포맷을 조였는데 추천은 여전히 어긋났다. "분수의 나눗셈"이라고만 물어도, "5학년 2학기"만 물어도, 둘 다 물어도, 결과의 질이 제각각이었다. 규칙성이 없다는 게 이상했다. 뭔가를 프롬프트가 아닌 다른 층에서 잘못 짜고 있다는 뜻이었다.

## 파이프라인을 다시 그려봤다

당시 그래프는 이런 모양이었다.

```
validate → extract_keywords → filter_templates → recommend
```

깔끔해 보인다. 어떤 입력이 들어오든 같은 노드를 탄다. 문제는 이 "같은 노드"가 서로 다른 성격의 입력에 대해 같은 일을 한다는 점이다.

`extract_keywords` 노드는 사용자 원문에서 키워드를 뽑는 LLM 호출이었다. "3학년 2학기 국어" 같은 입력이 들어오면 이 노드는 뭘 할까. 아무것도 안 뽑아도 될 텐데, 노드는 자기 일을 해야 한다고 믿는다. LLM은 무언가를 반환한다. "국어", "학습", "3학년" 같은 것들. 이게 다음 단계 `filter_templates` 로 흘러가서 학년·단원 필터와 AND로 엮인다. 학년 필터 하나만 걸었으면 맞았을 후보군이, 억지로 뽑힌 키워드 때문에 엉뚱하게 좁혀진다.

반대 방향도 있었다. "분수의 나눗셈 설명 자료" 같은 순수 키워드 요청에는 학년 정보가 없다. 그런데 필터 단계는 학년이 없으면 전 학년을 훑는다. 후보군이 과도하게 넓어지고, 그 위에서 최종 LLM이 아무리 고심해도 이미 진창을 밟은 뒤다.

돌이켜 보면 이건 프롬프트 문제가 아니었다. **입력의 성격이 다른데 같은 파이프를 통과시킨 게 문제였다.**

## 입력을 세 갈래로 갈랐다

초입에 분류 노드를 하나 넣었다. 학년/차시만 있으면 A, 키워드만 있으면 B, 둘 다 있으면 C. 이후 노드들은 `input_type` 을 보고 자기가 뭘 해야 하는지 판단한다.

| 유형 | 조건 | 필터 전략 |
|------|------|-----------|
| A | 학년/차시만 | curriculum 인덱스로 단원 필터 |
| B | 키워드만 | FTS(Full-Text Search) — 인덱스 기반 전문 검색 |
| C | 둘 다 | 단원 필터 ∩ 키워드 매칭 |

LangGraph — 노드와 엣지로 LLM 워크플로를 그래프로 정의하는 프레임워크 — 의 조건부 엣지로 그리면 이렇게 된다.

```
validate → resolve_input_type
              ├── [A] → curriculum_filter → recommend
              ├── [B] → fts_search        → recommend
              └── [C] → curriculum_filter + fts_search → merge → recommend
```

A 경로에서는 `extract_keywords` 를 아예 타지 않는다. 필요 없는 LLM 호출이 사라졌고, "3학년 2학기"에서 억지로 뽑힌 잡음이 필터를 오염시키던 문제가 원천에서 없어졌다. B 경로는 그 반대다. 학년 필터를 걸지 않으니 검색 범위가 애초에 좁아질 이유도, 넓어질 이유도 없이 사용자 의도만 따른다.

## 그 다음이 사실 더 중요했다

분기만으로는 부족했다. 최종 추천 노드는 여전히 사용자 원문 한 줄만 받고 있었다.

```python
prompt = f"사용자 질문: {user_input}\n추천해주세요."
```

"분수의 나눗셈"이라는 다섯 글자로 LLM이 5학년 2학기 맥락을 알아내리라 기대한 셈이다. 알아낼 수도 있다. 그런데 그건 LLM이 도박을 잘한 것이지, 우리가 시스템을 잘 짠 게 아니다. 앞 노드에서 이미 학년·단원·개념을 다 알고 있으면서 그걸 안 넘겨줬다는 게 지금 보면 이상하다.

맥락을 구조화해서 넘기도록 바꿨다. 학년, 학기, 단원명, 추출된 개념을 각각 필드로 담아 프롬프트에 명시한다. 이 변경 이후 A와 C 경로의 결과가 눈에 띄게 안정됐다. 눈에 띄게, 라고 쓴 건 정성적인 판단이라 그렇다. 이 시점에 정량 지표를 만들어두지 않은 게 아쉽다.

## 남은 것

이 글을 쓰면서도 아직 못 푼 게 하나 있다. C 경로의 merge 로직이다. 단원 필터로 나온 후보와 FTS 검색으로 나온 후보를 합칠 때, 지금은 교집합을 우선하고 부족하면 합집합으로 넓힌다. 그런데 "부족하면"의 기준을 몇 건으로 잡을지가 여전히 감이다. 이 임계값을 사용자 로그로 재보고 싶은데 아직 못 재봤다.

프롬프트를 고칠 것인가, 파이프라인을 고칠 것인가. 이 둘은 손이 가는 방향이 완전히 다르다. 프롬프트는 눈에 보이고 즉시 고쳐진다. 파이프라인은 그래프를 다시 그려야 하고 노드 계약을 다시 정해야 한다. 그래서 처음 다섯 번은 프롬프트를 만졌다. 여섯 번째에 그래프를 그렸어야 했다.
