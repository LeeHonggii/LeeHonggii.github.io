## 처음엔 앞자리로 충분한 줄 알았다

직무 코드 체계는 계층이 예쁘게 잘려 있다. 2자리, 4자리, 6자리. 대분류·중분류·소분류·세분류가 접두어로 딱딱 붙는다. 그래서 처음 유사도를 짤 때 자연스러운 규칙이 나왔다 — 6자리가 같으면 1.0, 4자리가 같으면 0.7, 2자리가 같으면 0.4.

한동안 이걸로 굴렸다. 문제가 없어 보였다. 코드가 같은 범주에 있으면 관련 콘텐츠, 아니면 관련 없는 콘텐츠. 규칙이 단순해서 디버깅도 쉬웠다.

그런데 실제 학습 이력을 훑다가 어색한 것들이 눈에 들어왔다. 마케팅 기획 쪽 사람이 데이터 분석 콘텐츠를 끝까지 봤다. 웹 개발 쪽 사람이 UX 설계 강의로 이어갔다. 코드 앞자리는 서로 다른데, 사용자는 두 개를 붙여서 소비하고 있었다.

## 분류 체계는 협업 패턴을 담지 않는다

한참 뒤에야 정리된 문장이 이거다. **분류 코드는 "이 직무가 무엇을 하는가"를 담지, "어떤 직무들이 붙어서 일하는가"를 담지 않는다.** 표준을 만든 사람이 잘못한 게 아니라, 애초에 그 목적으로 만든 게 아니다.

예를 들어 `05010101 사업기획`과 `20010301 빅데이터 분석`은 대분류부터 다르다. prefix 매칭으로는 유사도 0. 그런데 현장에서 이 둘은 한 프로젝트 안에서 마주 앉아 일한다. 반대로 같은 4자리 안에 있어도 실무에서 거의 안 엮이는 세분류 쌍도 있다. 4자리 매칭은 너무 넓고 균질하다 — 진짜 붙어서 일하는 쌍과, 그냥 같은 서랍에 들어있는 쌍을 구분하지 못한다.

여기서 하고 싶었던 건 하나였다. **"같은 서랍"이 아니라 "같이 일하는"을 신호로 쓰고 싶다.**

## AI로 보완관계를 뽑되, 원본은 절대 안 건드린다

이건 구현보다 운영 원칙이 먼저 정해진 결정이었다. 표준 코드 자체는 외부에서 관리되고, 개정이 들어온다. 그 위에 우리가 만든 관계를 덧칠해두면 개정이 왔을 때 뭐가 원본이고 뭐가 우리 손댄 건지 구분이 안 된다. 나중에 나 아닌 다른 사람이 이 코드를 열었을 때, 그게 원본이라고 착각하고 다른 판단을 내릴 위험이 크다.

그래서 표준 코드 테이블은 그대로 두고, LLM이 뽑은 보완관계는 별도 파일 하나에 몰아서 넣었다. 대략 이런 형태다.

```json
{
  "05010101": {
    "related_codes": ["20010301", "20010302", "05020201"],
    "relation_type": "complementary",
    "generated_by": "llm",
    "confidence": 0.82,
    "updated_at": "2026-07-10"
  }
}
```

LLM에는 세분류의 직무 설명과 능력단위 요소만 입력으로 줬다. 코드 자체는 힌트로 주지 않았다 — 숫자가 가까우면 관련이 있을 거라고 착각하는 걸 막고 싶었다. 출력은 코드 쌍과 신뢰도, 그리고 왜 그렇게 판단했는지의 짧은 근거. 근거는 저장은 하지만 점수 계산에는 안 쓴다. 나중에 사람이 검수할 때만 본다.

`updated_at` 필드는 재처리 범위를 자르기 위해서다. 표준이 개정되면 영향받은 코드가 포함된 쌍만 다시 돌린다. 전체를 재처리하는 건 비용도 문제고, 이미 검수를 통과한 쌍을 날리는 낭비다.

## 점수 순서를 뒤집었다 — 보완관계가 4자리보다 위

기존 유사도 함수는 이랬다.

```python
def sim_ncs(src, tgt):
    if src == tgt:
        return 1.0
    if src[:4] == tgt[:4]:
        return 0.7
    if src[:2] == tgt[:2]:
        return 0.4
    return 0.0
```

보완관계를 넣을 자리를 어디에 둘지가 이 글에서 제일 오래 고민한 부분이다. 처음에는 4자리 매칭 아래에 뒀다 — 0.7보다 낮은 0.6 정도. 표준 분류가 여전히 더 강한 신호일 거라고 생각했다.

그런데 결과를 보고 뒤집었다. 4자리 매칭은 그 안의 세분류 전부를 균질하게 끌어당긴다. 그 중에는 실제로 관련 없는 쌍도 섞여 있다. 반면 LLM이 뽑은 보완관계는 직무 설명을 읽고 골라낸 쌍이라 노이즈가 상대적으로 적다. 무차별 넓은 신호와 좁고 선별된 신호가 붙었을 때, 신뢰도가 일정 수준 이상이면 후자를 위로 두는 게 맞다.

```python
def sim_ncs(src, tgt, relations):
    if src == tgt:
        return 1.0
    if is_complementary(src, tgt, relations):
        return 0.8
    if src[:4] == tgt[:4]:
        return 0.7
    if src[:2] == tgt[:2]:
        return 0.4
    return 0.0


def is_complementary(src, tgt, relations):
    entry = relations.get(src)
    if not entry:
        return False
    if entry.get('confidence', 0) < 0.7:
        return False
    return tgt in entry.get('related_codes', [])
```

`confidence < 0.7`이면 관계 자체를 없는 걸로 친다. 이 임계값은 초기에 0.5로 뒀다가 올렸다. 낮게 두면 LLM이 애매하게 뽑은 쌍까지 신호에 섞이면서 오히려 추천이 산만해졌다. 신호 하나를 더 쓰는 것보다, 확실한 신호만 쓰는 게 나았다.

## 그리고 이건 로직 한 조각이라는 것

이 `sim_ncs`가 추천 점수의 전부가 아니다. 실제 서비스 코드에서는 여러 유사도가 합쳐진다. 콘텐츠 자체의 메타 유사도, 사용자 행동으로 뽑은 전이 관계, 학습 이력 기반 필터. 대략 이런 식으로 얽혀 있다.

```python
@lru_cache(maxsize=config.POOL_CACHE_SIZE)
def _content_sim(tenant_id: str) -> ContentSimilarity:
    return ContentSimilarity(_inst_pool(tenant_id))


@lru_cache(maxsize=1)
def _relation() -> RelationMatrix:
    return RelationMatrix.load(
        Path(__file__).resolve().parent / 'relation_matrix.json'
    )
```

`ContentSimilarity`는 콘텐츠 메타(제목·태그·직무 코드) 기반 유사도를 담고, `RelationMatrix`는 방금 이야기한 보완관계 파일을 로드한 객체다. 둘은 서로 다른 라이프사이클을 갖는다 — 콘텐츠는 회사별로 풀이 다르니 테넌트마다 캐시하고, 보완관계는 표준 코드 위에 얹혀 있으니 프로세스 전체에서 하나만 쓴다.

이 분리가 지금 이 글의 주제와 이어진다. 보완관계는 특정 회사·특정 사용자에 종속되지 않고, 직무 체계 자체에 붙는 지식이다. 그래서 테넌트별로 나눠 갖지 않고 전역 하나로 두는 게 자연스러웠다. 만약 회사마다 "우리 조직에서는 이런 협업 패턴이 강하다"는 정보가 나중에 붙는다면, 그건 별도 레이어로 얹어야 한다. 지금 파일에 섞으면 다시 원본 오염 문제가 반복된다.

행동 기반 전이는 또 다른 이야기다. 같은 코드에서는 이런 식으로 뽑고 있다.

```python
outgoing: dict[str, int] = {}
pair_users: dict[tuple[str, str], set[str]] = {}
for uid, seq in by_user.items():
    if len(seq) < 2:
        continue
    for i, src in enumerate(seq[:-1]):
        outgoing[src] = outgoing.get(src, 0) + 1
        for dst in seq[i + 1:i + 1 + _TRANSITION_WINDOW]:
            if dst == src:
                continue
            pair_users.setdefault((src, dst), set()).add(uid)
```

이건 사용자가 실제로 A를 보고 나서 B를 봤다는 시퀀스 데이터에서 뽑는 관계다. LLM 보완관계와 목적이 겹치는 것 같지만 성격이 다르다. 이쪽은 데이터가 충분히 쌓여야 신뢰할 수 있고 (`_PEER_MIN_SUPPORT = 5`), 신규 콘텐츠나 신규 직무 코드에는 아직 신호가 없다. LLM 관계는 그 빈 공간을 채우는 역할에 가깝다. 데이터가 없어도 직무 설명만 있으면 뽑을 수 있으니까.

## 남아있는 것

솔직히 말하면 이 `sim_ncs = 0.8`이라는 숫자가 정말 맞는지는 아직 답을 못 냈다. 4자리 매칭 위에 두는 방향은 맞다고 보지만, 0.8인지 0.75인지 0.85인지는 실험이 필요하다. 지금은 감으로 정한 값이고, 클릭·완료율과의 상관을 아직 재보지 않았다.

한 가지 더 걸리는 건 LLM이 뽑은 관계의 편향이다. 모델은 자기가 학습한 데이터의 직무 상식을 반영한다. 그래서 IT나 마케팅처럼 온라인에 이야기가 많이 쌓인 직무 쌍은 그럴듯한 관계가 잘 나오는데, 자료가 얇은 도메인은 관계가 얕게 나오거나 아예 안 나온다. 이건 confidence 필터만으로는 못 잡는다 — 자신있게 얕은 관계를 뱉을 수 있으니까.

그래서 다음에 볼 건 두 가지다. 첫째는 실제 사용자 행동으로 이 관계들이 검증되는지, 둘째는 LLM이 잘 못 뽑는 도메인을 어떻게 인지하고 신호를 낮출지. 뒤엣것은 아직 방법이 안 보인다.
