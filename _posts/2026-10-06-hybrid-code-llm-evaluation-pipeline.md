기존 멀티모달 평가 코드를 읽으면서 가장 먼저 한 일은 실행 순서를 종이에 옮기는 것이었다. 프롬프트 문구를 보기 전에 "이 케이스가 들어와서 저장될 때까지 누가 무엇을 하는가"부터 적었다. 입력은 이미지와 활동 이력이다. 출력은 평가와 리포트다.

순서는 이랬다.

```
정규화 → 활동 문장화 → (코드 계산 + 프롬프트 조립) → LLM 평가
→ 코드 확정값 적용 → 리포트 서술 → 저장
```

코드 안에서는 `promptPiece → assess → applyCodeFacts → render-both` 같은 이름으로 흩어져 있었다. 이 글은 이 순서에서 **코드 확정값 적용**이라는 한 칸이 왜 필요한지를 정리한 학습 노트다.

## LLM이 낸 숫자를 믿지 않는 칸

LLM 평가의 흔한 사고는 모델이 계산을 틀리는 것이다. 더 곤란한 쪽은 모델이 계산을 맞게 해 놓고, 서술하다가 다른 값을 말하는 경우다.

이 코드는 그 문제를 프롬프트를 잘 쓰는 쪽으로 풀지 않았다. 코드가 계산할 수 있는 값은 코드가 계산하고, 모델 응답이 돌아오면 그 값을 **덮어쓴다**. 이게 `applyCodeFacts` 단계다. 덮어쓰고 나면 해당 수치와 판정은 모델이 뭐라고 했든 일관된다.

한계도 분명하다. 덮어쓰기는 코드가 아는 값에만 효과가 있다. 모델이 쓴 나머지 추론, 예컨대 "이 학생은 이런 오개념이 있어 보인다" 같은 문장의 정확성은 이 단계가 보장하지 않는다. 그건 다른 방식으로 다뤄야 한다.

## "코드가 계산한 정답"은 어디까지 가능한가

비슷한 분할을 실험용 코드에서도 볼 수 있었다. 초등 수학 활동에서 "숫자 카드로 가장 큰 수를 만드는 식"을 학생이 맞게 만들었는지 판정하는 실험이다. 문제 단위 입력을 만드는 클래스가 정답 집합을 코드로 미리 만든다.

```python
def build_truth(self):
    self.truth = {}
    if self.spec["kind"] != "구성":
        op = self.spec["op"]
        self.truth["계산"] = {f"{a}{op}{b}={a + b if op == '+' else a - b}" for a, b in self.spec["items"]}
        return self.truth
    prob = PlaceValueProblem(self.spec["digits"], self.spec["shape"])
    for goal in self.spec["goals"]:
        value, best = prob.best(goal)
        self.truth[goal] = {f"{s['a']}{prob.op}{s['b']}" for s in best}
    return self.truth
```

문제 유형이 단순 계산이면 식과 값을 코드로 바로 만든다. "구성" 유형, 곧 큰 수·작은 수 만들기이면 `PlaceValueProblem.best` 가 목표(`max`/`min`)별 최적 식 집합을 돌려준다. 정답이 하나가 아니라 **집합**인 점이 중요하다. 모범답안은 여러 정답 중 하나일 뿐이라서, 모범답안과 문자열이 다르다고 오답 처리하면 안 된다.

이 코드는 정답 집합을 만드는 쪽이다. 학생 답을 이 집합과 비교해 판정을 확정하는 쪽은 이 파일에 없다. 그건 다른 파일에 있을 것이고, 이 글에서 보여줄 근거가 없다.

## 모델에게 넘기는 사실도 골라서 준다

학생 쪽 입력도 같은 원칙이다. 화면 기록에서 코드가 뽑은 사실(`facts`) 중 식·과정에 해당하는 코드만 골라 문장으로 만든다.

```python
STUDENT_FACTS = ("CARD_EXPR", "EXPR_LOG", "PEN_LOG", "PROCESS", "HANDWRITING", "NO_HANDWRITING")

class StudentInput:
    def get_facts(self):
        self.facts = [f["text"] for f in self.ev.facts if f["code"] in STUDENT_FACTS]
```

화이트리스트 한 줄이다. 증거 묶음에는 이보다 많은 종류의 사실이 들어 있는데, 학생이 실제로 한 일에 해당하는 것만 통과시킨다. 문제 쪽 정보(모범답안 식 등)가 학생 관찰 근거에 섞여 들어가면, 모델은 학생이 하지도 않은 걸 근거로 인용할 수 있다. `NO_HANDWRITING` 같은 "없음"을 나타내는 코드가 따로 있는 것도 눈에 띄었다. 비어 있음도 근거로 전달한다.

## 판정 프롬프트가 코드의 구멍을 메우는 방식

판정 시스템 프롬프트에서 인상 깊었던 건 규칙이 "정답/오답을 맞혀라"에 그치지 않고 **무엇이 판정을 올리지 못하는지**를 적는다는 점이다.

```python
JUDGE_SYSTEM = """너는 초등 수학 활동의 학생 기록을 읽고 판정하는 교사 보조다.
- 판정은 **최종 답**을 지시문의 조건으로 본다. 모범답안과 식이 달라도 조건을 만족하면 정답이다.
- 정답 = 최종 답이 조건을 모두 만족 / 부분 정답 = 답이 여러 개인 문제에서 최종 답 일부만 맞음 / 오답 = 최종 답이 틀림.
- 확인_필요 = 최종 답이 틀린 부분이 있는데, 과정 기록에 그 부분의 정답을 만든 적이 있으면 true. 이때 과정 칸에 정답을 찾았다가 수정했다고 쓴다. 과정 중 정답은 판정을 올리지 않는다.
- 모범답안과 다르지만 정답이면 「틀렸다」고 쓰지 말고 「모범답안과 풀이(식)가 다르다」고만 쓴다.
JSON 하나로만 답한다:
{"판정":"정답|부분 정답|오답","확인_필요":false,"모범답안과":"같음|정답이지만 다름|틀림","과정":"...","근거":"...","선생님께":"..."}"""
```

"과정 중 정답은 판정을 올리지 않는다"가 핵심이다. 학생이 중간에 맞는 식을 만들었다가 지웠다면 그 사실은 `확인_필요` 플래그와 서술로 남기고, 판정 등급은 최종 답으로만 정한다. 출력 스키마가 JSON으로 고정돼 있어서 코드가 각 필드를 따로 검증하고 덮어쓸 수 있다.

## 코드가 못 구하는 정답은 모델에게 두 번 묻는다

모든 문제의 정답을 코드로 만들 수는 없다. 실험 코드에는 "가장 큰/작은" 비교 판단을 모델이 자주 틀리는 문제를 고치려는 조건들이 있다.

```python
JUDGE = {
    "J0": ("그대로", "말 + 코드가 읽은 식 (11 실험 최선 조건)"),
    "J1": ("다른 배치 비교", "가장 큰/작은 조건이면 다른 배치를 직접 만들어 비교하라는 규칙 추가"),
    "J2": ("두 단계", "1단계: 지시문 조건의 정답 값을 먼저 구함 → 2단계: 그 값을 붙여 판정"),
    "J3": ("예시 한 개", "다른 숫자로 푼 판정 예시 하나 추가"),
    "J4": ("지시문 앞뒤", "데이터 뒤에 지시문을 한 번 더"),
}
```

```python
if cond == "J2":
    s1 = OpenaiChatCompletion(model=self.model, system=STEP1, user=f"<지시문> {case.ev.instruction()}", max_tokens=3000).run()
    extra = s1.parsed
    for k in usage:
        usage[k] += s1.usage.get(k) or 0
    user = text + "\n<먼저 구한 정답 (참고, 학생 답 판정에 사용)> " + json.dumps(extra, ensure_ascii=False)
call = OpenaiChatCompletion(model=self.model, system=system, user=user, max_tokens=4000).run()
```

J2는 정답을 먼저 구하는 단계를 학생 답과 분리한다. 학생 답을 보기 전에 조건만으로 정답을 만들게 하면, 학생 답에 끌려가 "맞아 보인다"고 판정하는 일을 줄일 수 있을 거라는 가설이다. 이것 역시 코드가 정답을 갖고 있을 때의 대체재다. 코드 계산이 가능하면 J2의 1단계는 필요 없다.

각 실험 행에 `verdict_ok`와 `answer_score`를 정답 데이터(gold)와 비교해 남기는 구조이고, 토큰·시간도 단계별로 합산한다. 다만 이 글을 쓰는 시점에 내가 가진 자료에는 조건별 결과표가 없다. 어느 조건이 나았는지는 **적지 않는다.** 숫자를 직접 다시 뽑아 보기 전에는 말할 수 없다.

## 평가와 서술을 갈라 놓은 이유

파이프라인 후반부에서 평가 단계는 식별자가 붙은 관찰 근거를 인용해야 한다. 서술(리포트) 단계는 그 평가 결과를 받아 글만 쓰고 재판정하지 않는다. 역할이 섞이면 서술하다가 판정이 슬쩍 바뀐다. 갈라 두면 바뀐 게 어느 단계인지 추적할 수 있다.

프롬프트 구성에서 확인한 것은 두 가지다.

- 정적 지시와 스키마를 앞에, 사례별 데이터를 뒤에 둔다. 앞부분이 케이스마다 같으니 캐시도 기대할 수 있다. 다만 이 코드에서 캐시 적중을 실제로 쟀는지는 확인하지 못했다.
- 근거가 없는 블록은 빈 제목만 남기지 않고 통째로 생략한다. 빈 `<관찰 근거>` 블록은 모델에게 "근거가 있어야 한다"는 압력으로만 작용한다.

## 아직 풀리지 않은 것

가장 신경 쓰이는 건 선개념·오개념 쪽이다. 학생이 어떤 오개념을 가졌는지에 대한 서술은 검증된 지식 조회에서 나오지 않는다. 모델이 추론해서 만든 문장이다. 코드로 덮어쓸 수도 없다. 그래서 전문가가 입력한 기준과, 학생 기록에서 실제 관찰된 근거를 구분해서 표시해야 한다는 걸 알게 됐다.

이 구분을 바탕으로 새 평가 시스템의 기획 초안을 써 보았다. 활동 유형별로 관찰 가능한 것이 무엇인지, 전문가 자문이 필요한 항목은 무엇인지, 평가 기준 중 정해지지 않은 부분은 어디인지를 나눠 적은 정도다. 구현은 하지 않았고, 영상 입력 실험도 끝내지 못했다.

덮어쓰기가 보장하지 못하는 나머지 추론을 어떻게 검증할지는 아직 답이 없다. 다음에는 오개념 서술 한 가지만 골라 전문가가 직접 채점해 보는 쪽으로 가려 한다.
