처음엔 잘 됐다. 그게 문제였다.

프롬프트에 예시 몇 개를 박아두니 LLM이 척척 답을 뱉었다. "전체와 부분의 관계 이해"가 들어오면 `분수`, "수 모으기 활동"이 들어오면 `모으기`. 데모에서는 이보다 깔끔할 수 없었다. 문제는 실사용자 입력이 쌓이면서 시작됐다.

## 표면 패턴을 정답이라고 착각하기 시작한 모델

퓨샷(few-shot, 프롬프트에 소수의 입출력 예시를 포함해 모델을 유도하는 방식)은 프로토타입에는 최적이다. 그런데 예시가 곧 모델의 판단 기준이 되어버리는 순간이 온다.

내가 넣어둔 예시는 이런 식이었다.

```
입력: "전체와 부분의 관계 이해"
키워드: ["분수"]
```

특정 학년, 특정 단원에서는 맞는 답이었다. 그런데 초등 저학년의 "전체와 부분으로 나눠 세기"라는 완전히 다른 맥락의 입력이 들어와도 모델은 여전히 `분수`를 뱉었다. "전체와 부분"이라는 표면 문자열만 보고 있었던 것이다.

"수 모으기 활동" 같은 어색한 입력에는 `모으기`라는 존재하지도 않는 키워드가 튀어나오기 시작했다. 이 시점에서 나는 두 가지를 깨달았다.

하나. **예시로 박아둔 정답이 일반화를 막는다.** 모델은 예시 분포 근처에서는 강력하지만, 조금만 벗어나면 표면 패턴을 정답으로 확신한다.

둘. **LLM에게 키워드를 창작할 자유를 주면 안 된다.** 자유를 주는 순간 인덱스에 없는 단어가 태연하게 반환된다.

## LLM을 분류기로 강등시키기

그래서 구조를 이렇게 뒤집었다.

```
사용자 입력
   ↓
정규화 사전 (별칭 → 표준어)
   ↓
역인덱스에서 실제 존재하는 후보 목록 확보
   ↓
LLM: "이 후보 중 골라라"
```

LLM은 이제 생성기가 아니라 분류기다. 언어 이해력은 살리되, 출력은 항상 사전에 검증된 집합 안에 머문다. "분수의 덧셈"과 "분수 더하기"를 같은 키로 묶는 별칭 처리를 미리 해두지 않으면, 역인덱스 조회 단계에서 후보가 빈 리스트로 떨어져 버린다. 이 별칭 사전이 없을 때는 LLM 프롬프트가 아무리 정교해도 무너졌다.

## 이 결정이 시스템 전체에 어떤 흔적을 남겼는가

이 판단은 키워드 추출 한 층에만 그친 게 아니었다. 추천 엔진 전반에서 "LLM이 자유롭게 값을 만드는 지점을 최소화한다"는 방침으로 확장됐다.

예를 들어 최종 추천을 뽑아내는 로직은 모두 상수화된 가중치와 명시적 캡(cap)으로 통제된다. LLM이 아니라 사람이 읽고 조정할 수 있는 숫자들이다.

```python
MATRIX = {
    'job': {'level': 0.6, 'self': 0.2, 'trend': 0.2},
    'career': {'level': 0.4, 'self': 0.2, 'trend': 0.4},
    'company': {'level': 0.4, 'self': 0.4, 'trend': 0.2},
}

BOOST_MAX = 1.0
BOOST_SERIES_NEXT = 1.0
BOOST_SERIES_FUTURE = 0.20
BOOST_RELATION = 0.20
BOOST_PEER = 0.15

CAP_SERIES = 2
CAP_STRAND = 4
CAP_NCS6 = 3
```

세 개의 추천 목적(직무·커리어·회사)마다 축(level, self, trend)의 비중이 다르고, 부스팅과 다양성 캡이 명시적으로 걸려 있다. 이 값들이 지금 최적이라고 주장할 생각은 없다. 다만 **"이 숫자를 왜 이렇게 두었는가"에 답할 수 있는 상태**가 LLM 자유 창작보다 훨씬 방어 가능하다는 게 지금까지의 결론이다.

사용자 성향(캐릭터)에 따라 축 비중을 살짝 흔드는 미세 조정도 마찬가지다.

```python
CHARACTER_AXIS_DELTA = {
    '트렌드 적응가': {
        'job': {'trend': 0.04, 'level': -0.04},
        'career': {'trend': 0.06, 'level': -0.04, 'self': -0.02},
        'company': {'trend': 0.05, 'level': -0.02, 'self': -0.03},
    },
    '실무 적용가': {
        'job': {'self': 0.04, 'trend': -0.04},
        'career': {'level': 0.03, 'trend': -0.03},
        'company': {'self': 0.03, 'trend': -0.03},
    },
    # ...
}
```

캐릭터마다 축을 얼마나 밀고 당길지를 코드에 박아둔 이유는 단순하다. LLM에게 "이 사람은 트렌드형이니까 적당히 반영해줘" 같은 지시를 넘기는 순간, 매번 다른 결과가 나오고 재현이 안 된다. **재현 가능하지 않은 로직은 튜닝할 수 없다.**

토큰 정규화도 조사 스트리퍼 하나까지 명시했다.

```python
_TOK = re.compile(r'[가-힣a-zA-Z0-9]+')
_JOSA = re.compile(r'(으로|에서|에게|한테|까지|부터|처럼|보다|이나|의|을|를|은|는|이|가|에|와|과|도|로|만|나)$')

def _strip_josa(t: str) -> str:
    if len(t) >= 3:
        m = _JOSA.search(t)
        if m and m.start() >= 2:
            return t[:m.start()]
    return t
```

이 처리를 LLM에 맡길 수도 있었다. 하지만 "곱셈으로"와 "곱셈"이 같은 토큰으로 묶이는가는 검색 리콜에 직접 영향을 주는 결정이고, 그런 결정은 LLM의 그날 컨디션에 맡길 수 없다.

## 모른다고 말할 수 있는 상태

또 하나 바꾼 것은, 모호한 입력에 대해 **억지 답을 하지 않는 상태**를 명시적으로 뒀다는 점이다.

```json
{
  "status": "needs_clarification",
  "clarification_reason": "입력이 여러 단원에 걸쳐 있어 특정 키워드로 좁히기 어렵습니다."
}
```

`needs_clarification`은 실패 코드가 아니다. "지금 확신이 없다"고 모델이 스스로 말하는 상태다. 이걸 도입하고 나서야 프론트 쪽에서 "재질문 UI"라는 옵션이 생겼다. 이전에는 모든 입력에 대해 무언가를 뱉었기 때문에, 낮은 신뢰도의 추천이 그대로 사용자에게 노출되고 있었다.

억지 답변이 신뢰를 갉아먹는 속도는 생각보다 빠르다. 차라리 "다시 물어봐 주세요"가 낫다.

## 아직 남은 것

솔직히 말하면, 후보 집합 자체의 품질은 아직 끝난 얼(結) 이야기가 아니다. 별칭 사전은 지금도 사람이 손으로 채우고 있고, 역인덱스에 없는 신규 개념이 사용자 입력으로 들어왔을 때 이걸 "미확인 개념"으로 자동 격리해두는 파이프라인은 아직 없다. 지금은 그런 입력이 조용히 `needs_clarification`으로 흡수되고 있을 뿐이다.

캐릭터별 축 델타값도 감으로 잡은 초기값에 가깝다. 캐릭터별로 실제 클릭·완주율 로그를 붙여 이 값을 뒤에서 학습으로 밀어내는 게 다음 숙제인데, 그 전에 로깅 스키마부터 다시 봐야 한다. 이 글을 쓰는 지금 시점에서는 아직 못 재본 숫자다.
