처음 이 문제를 만났을 때 나는 완전히 잘못된 방향을 잡고 있었다.

콘텐츠에 태그가 없었다. 추천 신호를 만들려면 무언가 붙여야 했고, 나는 익숙한 걸 꺼냈다. 카테고리로 묶어서 TF-IDF(Term Frequency-Inverse Document Frequency — 단어 빈도 역문서빈도) 돌리고, 상위 키워드를 태그로 심는 방식. 반나절 만에 파이프라인이 돌아갔다. 결과도 그럴싸했다.

그런데 몇 건을 눈으로 훑다가 멈췄다.

"회의 퍼실리테이션"을 다루는 콘텐츠와 "재무제표 읽는 법"을 다루는 콘텐츠가 둘 다 `["업무", "성과", "조직"]` 이라는 똑같은 태그를 달고 있었다. 같은 "비즈니스" 버킷에 들어갔기 때문이다. 추천 엔진 입장에서 이 둘은 사실상 구별이 안 된다.

내가 만든 건 태그가 아니라 **카테고리를 한 번 더 반복한 라벨**이었다.

## 통계는 개별성을 지운다

TF-IDF 자체가 나쁜 건 아니다. 문제는 내가 그걸 **콘텐츠 묶음** 위에 얹었다는 것이다. 문서 하나에 대해 특징 단어를 뽑는 게 아니라, 카테고리 안의 문서 100개를 합쳐놓고 공통 단어를 뽑으니 정작 튀는 단어들이 죽었다. 개별 콘텐츠의 정체성이 카테고리 평균으로 수렴했다.

물론 문서 단위로 돌릴 수도 있었다. 그런데 그러기엔 원본 데이터가 너무 얇았다. 콘텐츠 테이블에 제목만 있고 본문 요약이 없는 경우가 많았고, 어떤 건 제목조차 "리더십 과정 3차" 같은 사내 관리용 문구였다. 이런 텍스트에서 통계로 뽑히는 건 노이즈밖에 없다.

여기서 판단이 뒤집혔다. **문서가 얇을수록 사람(혹은 LLM)이 맥락을 채워 읽어야 한다.** 통계는 텍스트가 두꺼울 때 쓰는 도구지, 텍스트가 없을 때 쓰는 도구가 아니었다.

## 별도 메타 테이블로 뽑아낸 이유

원본 콘텐츠 테이블에 컬럼을 추가하는 방향은 처음부터 접었다. LLM이 뱉을 속성 — 키워드 배열, strand(주제 계열), 청중 태그 — 은 원 스키마의 관심사가 아니었고, 재생성이 잦을 예정이었다.

그래서 별도 테이블(`content_meta` 라고 부르자)을 만들고 콘텐츠 PK를 외래키로 물렸다. 한 콘텐츠 = 한 메타 레코드.

upsert 는 `ON DUPLICATE KEY UPDATE` 로 뒀다. 이건 취향이 아니라 필수였다. LLM 배치는 반드시 어딘가에서 깨진다. 같은 항목을 두 번, 세 번 돌려도 결과가 같아야(멱등성 — idempotency) 재처리 스크립트를 겁 없이 돌릴 수 있다.

## 진짜 문제는 "재처리를 어떻게 설계하느냐"였다

LLM 호출을 1,000건 루프에 그냥 물리면 안 된다는 건 안다. 그건 상식이다. 근데 배치를 어떻게 쪼개고, 실패를 어디에 남기고, 다음 회차가 뭘 집어야 하는지 — 이걸 처음에 대충 잡았다가 두 번 갈아엎었다.

최종적으로 정착한 구조는 이렇다.

```
data/content_meta/
  batch_001.json      ← 성공 결과 아카이브 (건드리지 않음)
  batch_002.json
  ...
  partial.json        ← 다음 회차가 집을 재처리 대상
```

`batch_N.json`은 **불변 아카이브**로 뒀다. 언제 어떤 프롬프트로 어떤 응답이 나왔는지 나중에 추적하려면 성공한 것도 남겨야 한다. `partial.json`은 반대로 **매 회차마다 갈아치우는 워킹셋**이다.

이 분리가 왜 중요했냐면, 두 파일이 섞이면 "얼마나 처리됐냐"와 "뭐가 남았냐"를 둘 다 놓친다. 초기에 한 파일에 다 쓰다가 재처리하면서 성공 결과를 덮어쓴 적이 있다. 그때 아카이브를 분리해야겠다고 결심했다.

## 빈 결과를 "성공"으로 분류하는 실수

가장 오래 잡아먹은 버그는 이거였다. LLM 응답이 JSON 파싱은 됐는데 `keyword_tags: []` 인 경우. 처음엔 이걸 정상으로 취급해서 DB 에 그대로 넣었다.

몇 주 뒤 추천 결과를 뜯어보다가, 어떤 콘텐츠들이 아예 추천 후보에서 사라져 있는 걸 발견했다. 원인을 따라가 보니 태그 배열이 비어서 유사도 계산 단계에서 스코어가 0으로 떨어져 있었다. 파이프라인은 조용히 성공했고, 결과만 조용히 망가져 있었다.

기준을 다시 세웠다.

| 응답 상태 | 처리 |
|---|---|
| 정상 (`keyword_tags` 1개 이상) | `batch_N.json` 저장 → DB upsert |
| `keyword_tags` 가 빈 배열 | `partial.json` 으로 이동, 재처리 대기 |
| JSON 파싱 실패 | 원문 응답 로그로 남기고 `partial.json` |

재처리할 때 프롬프트를 다시 손댔는데, 여기서 배운 게 하나 있다. **맥락을 더 주는 것보다 출력 조건을 강하게 조이는 게 훨씬 잘 먹혔다.** "이 콘텐츠는 어떤 성인학습자를 위한 것인지 고려해서..." 같은 문장을 앞에 붙이는 것보다, "반드시 keyword_tags 를 1개 이상 반환하라. 빈 배열은 허용되지 않는다" 를 명시하는 편이 실패율을 뚝 떨어뜨렸다.

지금 생각해보면 당연하다. 모델은 지시가 애매하면 애매한 결과로 도망친다. 빈 배열은 그중에서도 가장 안전한 도망이다.

## 추천 엔진이 이 메타를 실제로 어떻게 쓰는가

메타 테이블이 왜 필요했는지는 결국 소비자를 봐야 이해가 된다. 추천 엔진 쪽에서 이 데이터를 물어오는 지점은 대략 이렇다.

```python
@lru_cache(maxsize=config.POOL_CACHE_SIZE)
def _inst_pool(tenant_id: str) -> dict:
    return {cid: c for cid, c in _company_pool(tenant_id).items()
            if c.get('content_type') == 'INSTITUTION' and c.get('has_meta')}


@lru_cache(maxsize=config.POOL_CACHE_SIZE)
def _content_sim(tenant_id: str) -> ContentSimilarity:
    return ContentSimilarity(_inst_pool(tenant_id))
```

`has_meta` 플래그가 여기서 게이트키퍼다. 메타가 아직 안 붙은 콘텐츠는 유사도 풀에 아예 들어가지 않는다. 처음엔 "일단 다 넣고 태그 없는 건 스코어 낮게"로 갔다가, 유사도 매트릭스가 노이즈로 오염되는 걸 보고 게이트를 아예 앞으로 당겼다.

한 콘텐츠에 대해 어떤 레코드를 대표로 쓸지도 골라야 한다. 같은 원본 콘텐츠(`origin_content_pk`)에서 파생된 버전이 여러 개 있을 때, 그중 메타 정보가 가장 풍부한 걸 대표로 쓴다.

```python
def _info_score(c: dict) -> int:
    return (2 if c.get('keyword_tags') else 0) \
         + (1 if c.get('ncs_code') else 0) \
         + (1 if c.get('title') else 0)


@lru_cache(maxsize=config.POOL_CACHE_SIZE)
def _uuid_map(tenant_id: str) -> dict:
    pool = _company_pool(tenant_id)
    m: dict[str, str] = {}
    for cid, c in pool.items():
        u = c.get('content_uuid')
        if not u:
            continue
        if u not in m or _info_score(c) > _info_score(pool[m[u]]):
            m[u] = cid
    return m
```

가중치 (2, 1, 1) 은 감(感)이다. 재보고 정한 게 아니라, "키워드가 없으면 나머지는 사실상 의미 없다"는 판단을 반영해 키워드에만 2를 줬다. 이 부분은 언젠가 실제 추천 클릭률과 붙여서 튜닝해야 하는데, 아직 못 했다.

여기서 눈에 띄는 게 하나 있다. `_info_score` 는 메타의 **존재 여부**만 본다. 내용 품질은 안 본다. 이건 의도된 것인데, LLM 생성 태그의 품질을 다시 LLM 없이 평가하기 시작하면 그 로직 자체가 또 다른 통계 뭉개기가 될 것 같아서 접었다. 나중에 사람 리뷰 샘플링 파이프라인을 만들 계획이지만 아직 안 만들었다.

## 아직 못 푼 것

배치가 지금은 안정적으로 돈다. 실패 항목은 partial 에 쌓이고, 재처리 회차에서 소진된다. 여기까진 됐다.

남은 문제가 두 개 있다.

하나는 **strand(주제 계열) 라벨의 일관성**이다. 같은 콘텐츠를 두 번 돌리면 한 번은 "자기관리"로, 다른 한 번은 "커리어개발"로 라벨링되는 경우가 있다. 라벨 후보를 고정 enum 으로 프롬프트에 명시하고 있는데도 그렇다. 모델이 흔들리는 건지, 콘텐츠 자체가 애매한 경계에 있는 건지 아직 판별을 못 했다.

다른 하나는 앞서 말한 **가중치 (2, 1, 1) 의 근거**다. 지금은 그냥 그렇게 두고 있고, 실제로 이 가중치가 추천 CTR(Click Through Rate — 클릭률) 에 어떻게 반응하는지 재보지 않았다. 재봐야 한다.

통계로 뭉개는 걸 멈추려고 시작한 일이었는데, 결국 그 위에 또 다른 판단이 얹혀 있고 그 판단은 아직 통계로 검증되지 않았다. 우습지만 그렇다.
