슬라이드는 이미 확정돼 있었다. 7장. 다시 만들 시간은 없었다.

발표 대상은 비개발자 의사결정권자였고, 내가 설명해야 할 것은 추천 엔진의 내부 구조였다. 손에 든 노트에는 RRF(Reciprocal Rank Fusion — 여러 순위 목록을 하나의 순위로 합치는 융합 방법)와 축별 가중치, CombSUM/MNZ 같은 단어들이 어지럽게 적혀 있었다. 그 단어들이 그대로 청중 앞에 나가면 안 된다는 것 정도는 알고 있었다.

## 슬라이드는 못 바꾼다, 그러면 대본이 슬라이드를 따라가야 한다

발표 준비의 기본기는 "슬라이드 다음에 대본"이지만, 슬라이드가 잠긴 순간 그 순서가 뒤집힌다. 나는 슬라이드를 고칠 게 아니라, 슬라이드가 이미 던져놓은 질문에 대본을 맞춰야 했다.

7장을 다시 열어놓고, 각 장이 청중에게 **어떤 질문을 던지고 있는지**를 먼저 적었다.

```
1. 왜 이 시스템이 필요했나
2. 추천을 어떤 관점으로 판단하나
3. 각 관점은 어떻게 점수가 되나
4. 여러 점수를 어떻게 합치나
5. 특수 조건은 어떻게 얹나
6. 실제로 어떤 결과가 나오나
7. 다음은
```

이걸 먼저 쓰고 나니 대본이 훨씬 쉬워졌다. 슬라이드의 시각적 요소를 억지로 설명하지 않아도 됐다. 청중은 어차피 그림을 보면서 내 목소리로 이 질문에 답을 듣는다.

## 그런데 슬라이드 2번이 문제였다

내부적으로 추천은 네 갈래로 나온다. 코드로는 이렇게 생겼다.

```python
_RECO_EXAMPLE = {
    "tenant_id": "TENANT_A",
    "user_id": "user-001",
    "mode": "preeval+history",
    "axes": {
        "job": [_ITEM_EXAMPLE],
        "career": [_ITEM_EXAMPLE],
        "company": [_ITEM_EXAMPLE],
        "best": [_BEST_EXAMPLE],
    },
    ...
}
```

`job`, `career`, `company`, `best`. 개발자끼리는 이대로 부른다. 그런데 이 네 단어를 그대로 슬라이드 옆에서 말하는 순간 청중은 세 번째 단어에서 이미 놓친다. `company` 는 회사 이름 얘기가 아니라 "그 회사 안에서 선호되는 것" 이라는 뜻인데, 처음 듣는 사람에겐 그 매핑이 안 된다.

그래서 대본용 어휘를 별도로 정해뒀다. 코드 안에서는 `job/career/company/best` 그대로 두고, 입 밖으로 나갈 때만 바꿔 말하기로.

| 코드 | 발표 대본 |
|---|---|
| job | 직무에 맞는 것 |
| career | 지금 커리어 단계에 맞는 것 |
| company | 회사에서 많이 보는 것 |
| best | 종합해서 상위인 것 |

이걸 미리 정해두는 게 중요했다. 발표 도중에 매번 번역하려고 하면 반드시 어느 순간 `career` 라고 그냥 말해버린다. 한 번 삐끗하면 청중은 그때부터 다른 축들도 영어인 줄 안다.

## 계산 얘기를 언제 꺼내느냐

가장 오래 고민한 게 슬라이드 4번, 점수를 합치는 부분이었다. 내부 로직으로는 각 축의 순위를 RRF로 합치고, `best` 축은 별도로 CombSUM/MNZ 계열의 융합 점수를 쓴다. 응답 스키마에도 그대로 남는다.

```python
_BEST_EXAMPLE = {
    ...
    "best_score": 1.0,
    "rrf_score": 1.0,
    "axis_ranks": {"job": 1, "career": 1, "company": 1, "next": 1},
    "reasons": ["종합 상위"],
}
```

`best_score`, `rrf_score`, `axis_ranks`. 정직하게 이 필드를 하나씩 설명하려 들면 5분이 사라진다. 그리고 5분 뒤 청중은 "그래서 왜 저 콘텐츠가 위에 있는 건가요" 를 다시 묻는다.

초안에는 "Why → What → How" 순서로 가라고 적어뒀었는데, 실제로는 그것보다 한 겹 더 있었다. **What 자체를 두 층으로 쪼개는 것.** 청중에게 필요한 What은 "네 축의 순위를 합쳐서 하나의 순위를 만든다" 까지고, RRF 라는 이름과 수식은 필요할 때만 꺼내는 예비 카드다.

그래서 실제 발표에서는 이렇게 갔다.

- 먼저 "사람이 콘텐츠를 고를 때 보는 기준이 네 가지" 라고 말하고 (Why)
- "그래서 우리도 네 갈래로 각각 순위를 낸다" 라고 보여준 뒤 (What, 얕은 층)
- "네 순위를 하나로 합치는 게 이 마지막 목록이다" 라고 결론을 먼저 던지고 (What, 결론)
- 질문이 들어오면 그때 "합치는 방법은 순위 융합이라는 방식인데" 로 들어갔다 (How, 조건부)

질문이 안 들어오면 How는 안 꺼낸다. 이게 제일 어려웠다. **내가 아는 걸 안 말하는 것.**

## 실제로 발표 뒤에 남은 것

발표가 끝나고 받은 질문 중에 "가중치는 어떻게 정했나요" 가 있었다. 이건 사실 대본에 없는 질문이었는데, 나는 여기서 처음으로 `preeval_payload` 얘기를 꺼냈다.

```python
def preeval_payload(self) -> dict | None:
    prefs = [t.label for t in self.topics if t and t.label]
    job = _label(self.job)
    if not (job or prefs):
        return None
    return {
        'job': job,
        'sub': _label(self.sub_job),
        'career': _label(self.career),
        'prefs': prefs,
        'character': _label(self.learner_type),
        'scores': self.scores,
    }
```

가중치는 사실 사용자가 사전평가에서 뭘 얼마나 채웠느냐에 따라 조건부로 달라진다. `job` 도 없고 `prefs` 도 없으면 아예 사전평가를 안 쓰고 이력만 본다. 이 로직을 짧게 풀어놓으니, 오히려 "그럼 신입은 어떻게 되나요" 라는 다음 질문이 자연스럽게 붙었다. 그게 내가 슬라이드 7번에서 하려던 얘기였다. 질문이 나 대신 다음 장을 넘겨준 셈이다.

발표가 잘 됐다고 말하기는 어렵다. 슬라이드 5번에서 한 번 헤맸고, `axis_ranks` 를 설명하려다 결국 "네 축에서 각각 몇 등이었는지" 라고 다시 말했다. 준비한 대체어 표에 이건 없었다. 다음번엔 표를 좀 더 두껍게 짜야 한다.

그리고 아직 못 푼 게 하나 있다. 응답에 딸려 나가는 `_level_board`, `_competency`, `_xp_scale` 같은 내부 필드들 — 저것들을 어떤 자리에서, 누구에게, 어느 수준까지 열어 보여야 하는지는 이번 발표에서 손도 못 댔다. 다음 라운드에서 볼 문제다.
