목록 API에 페이지네이션과 seed 기반 랜덤 정렬을 붙이던 날이었다. 서버는 문제없이 떠 있었다. 문법 검사도 통과했다. 그런데 API 문서 화면에서 `offset`, `limit`이 보이지 않았다.

## 처음 짠 구조

요구사항은 단순했다. 목록을 페이지 단위로 자르고, 정렬은 seed로 고정되는 랜덤으로 한다. seed가 같으면 같은 순서가 나오니 페이지를 넘겨도 항목이 겹치거나 빠지지 않는다.

입력은 이렇게 나눴다.

- 페이지 관련 값(`offset`, `limit`)은 Pydantic 모델 하나로 묶은 쿼리 모델
- `seed`는 그 옆에 별도 쿼리 파라미터로 선언

모델이 이미 있으니 `seed`만 하나 더 얹는 게 가장 작은 변경이라고 생각했다. 코드 리뷰에서도 이상해 보이지 않는 모양이다.

## 증상

서버는 에러 없이 올라왔고 문법 검사(컴파일 단계)도 깨끗했다. 문제는 생성된 API 문서였다. 모델 필드가 개별 쿼리 파라미터로 펼쳐지지 않았다. 입력 계약이 조용히 사라진 셈이다.

예외가 없으니 단서가 없었다. 클라이언트가 값을 보내도 서버가 그걸 기대하는 파라미터로 인식하는지 확인할 방법이 문서 스키마뿐이었다. 스키마를 열어본 게 우연히 발견의 계기였다.

## 고친 방법

`seed`를 쿼리 모델 안으로 옮겼다. 쿼리 입력이 모델 하나로 통일되자 `offset`, `limit`, `seed`가 각각 개별 파라미터로 노출되는 것을 확인했다.

원인을 정확히 짚지는 못했다. 내가 쓰던 FastAPI 환경에서는 쿼리 모델과 별도 쿼리 파라미터를 함께 선언했을 때 이런 일이 생겼다는 것까지만 관찰했다. 이걸 FastAPI 전반의 제약이라고 쓰지는 않겠다. 버전을 바꿔가며 재현해본 것도 아니고 릴리스 노트를 대조한 것도 아니다. 모델 쿼리 파라미터를 지원하는 버전 범위나 혼용 시 동작은 문서로 확인이 필요하다. 이 글은 한 환경에서 본 사례다.

## 문법 검사가 못 잡는 것

이번에 배운 건 "서버가 뜬다"와 "입력 계약이 맞다"가 별개라는 점이다. 문법은 코드가 파이썬으로서 유효한지만 본다. 어떤 파라미터가 외부에 노출되는지는 프레임워크가 런타임에 만드는 스키마에 있다. 그래서 확인 단위를 바꿨다.

- 생성된 스키마에서 파라미터 목록 확인
- 경계값을 실제로 넣어 입력 검증 동작 확인

경계값은 이렇게 점검했다.

- `offset=0` → 422
- `limit=301` → 422 (상한 초과)
- `seed=-1` → 422

`offset`이 1부터 시작하는 페이지 번호라서 0이 거부된다. 그래서 건너뛸 개수는 이렇게 계산했다.

```text
skip = (offset - 1) * limit
```

`offset=1`이면 skip이 0, 그다음 페이지는 `limit`만큼씩 밀린다. 이름이 `offset`이라 흔히 쓰이는 "건너뛸 개수" 의미와 다르다는 점이 헷갈릴 수 있다. 이름 때문에 클라이언트가 `offset=0`부터 시작할 가능성이 있다. 그 경우 422를 받는다.

## 남은 것

페이지네이션 변경은 SQL 단위로 검증을 마쳤다. 아직 못 한 게 둘이다.

- 앱 전체를 띄운 통합 검증. 스키마가 맞다는 것과 실제 요청이 끝까지 정상 동작한다는 것은 다른 문제다.
- 클라이언트와의 API 계약 합의. `offset`이 페이지 번호라는 의미와 422 기준을 상대 쪽이 같은 뜻으로 읽는지 확인하지 못했다. 이름을 `page`로 바꾸는 게 맞는지도 아직 결정하지 않았다.

응답에서 `status`를 제거한 것도 같은 계약의 일부라 문서는 고쳤지만, 받는 쪽이 이 필드에 의존하고 있는지는 확인 전이다.
