노트 시스템에 수백 개의 파일이 쌓이다 보면 어느 순간부터 검색이 이상해진다. 쿼리를 던졌는데 결과 상위가 전부 하나의 파일로 채워진다. 열어보면 회의록이나 작업 로그를 몇 달치 이어붙인 16MB짜리 Markdown이다. 전문 검색(full-text search) 엔진 입장에서는 이 파일 하나가 수천 개의 토큰을 공급하는 공해 소스다. 가장 관련 있는 짧은 파일들이 순위 밖으로 밀려난다.

해결책은 두 가지였다. 색인에서 제외하거나, 검색에 걸릴 수 있는 작은 요약 아티팩트로 교체하거나. 전자는 내용 자체를 버리는 거라 싫었다. 후자를 택했다.

---

## 파일을 통째로 넘기면 안 되는 이유

Gemma 같은 로컬 LLM(Large Language Model, 대규모 언어 모델)의 컨텍스트 창은 길어야 수십 킬로바이트 수준이다. 16MB짜리 파일을 통째로 넘기는 건 불가능하다. GPU 메모리에서 그냥 뻗는다.

그래서 Map-Reduce 전략을 썼다. Map-Reduce는 원래 분산 처리 개념인데, 여기서는 단순히 이렇게 쓴다.

- **Map**: 파일을 섹션 단위로 나눠 각 섹션을 LLM에게 요약시킨다
- **Reduce**: 섹션 요약들을 다시 모아 전체 마스터 요약을 한 번 더 만든다

나누는 기준은 Markdown 헤더(`#`, `##`, `###`)다. 문서 구조가 이미 섹션 경계를 정의해놓고 있으니 별도 분할 로직이 필요 없다. 헤더가 없거나 섹션이 비정상적으로 긴 경우엔 청크 크기 상한으로 자른다.

## 멱등성 문제: mtime보다 SHA-256

파이프라인을 처음 짤 때 "파일이 수정됐으면 재처리"를 mtime(수정 시각)으로 판단했다. 이게 생각보다 불안정하다. 파일 시스템 동기화, 에디터 자동 저장, 심지어 일부 백업 툴이 mtime을 건드린다. 내용이 바뀌지 않았는데 재처리가 트리거되고, 요약이 멀쩡히 있는데 LLM 호출이 또 나간다.

SHA-256 해시 기반으로 바꿨다. 파일 바이트를 읽어 해시를 구하고, 이전 처리 때 저장한 해시와 비교한다. 내용이 실제로 바뀌지 않으면 처리를 건너뛴다. 개념적으로는 이런 흐름이다.

```
original_hash = sha256(file_bytes).hexdigest()
if original_hash == stored_hash:
    skip  # 내용 동일, 재처리 불필요
```

실제 구현은 이 한 줄보다 당연히 복잡하지만, 핵심 판단이 여기 있다. mtime은 "언제 쓰였냐"를 보지만 해시는 "무엇이 쓰였냐"를 본다.

배치 처리 중에 파일이 갑자기 덮어씌워질 때도 이 방식이 더 안전하다. 처리 시작 시점의 해시와 처리 완료 시점의 해시를 비교해 저장할지 말지 결정할 수 있다.

## Gemma 호출에서 thinking 모드를 끈 이유

Gemma의 thinking 모드(추론 단계를 내부적으로 확장하는 기능)는 복잡한 추론 문제에선 효과가 있다. 그런데 요약 태스크에는 오히려 방해가 됐다.

두 가지 문제가 있었다.

**속도.** 수십 개의 섹션을 순서대로 처리하는 파이프라인에서 섹션 하나당 thinking 토큰이 수백 개씩 붙으면 처리 시간이 배로 늘어난다. 요약이 목적인데 thinking 출력은 어차피 버린다.

**JSON 파싱 안정성.** 출력을 구조화된 JSON으로 받으려 했는데, thinking 모드에서는 LLM이 thinking 블록과 실제 응답 블록을 섞어 내보내는 경우가 있었다. 파싱이 실패하면 그 섹션의 요약이 통째로 날아간다. thinking을 끄면 출력이 깔끔해지고 파싱 실패율이 크게 줄었다.

요약 태스크는 창의적 추론이 필요한 게 아니라 "이 텍스트에서 핵심만 뽑아라"에 가깝다. thinking이 도움이 되는 영역이 아니었다.

## 결과물의 구조

파이프라인이 끝나면 원본 파일 옆에 요약 Markdown이 생긴다. 이 파일은 원본보다 수십 배 작고, 전문 검색 색인에는 이 요약 파일만 걸린다. 원본은 `.txt`로 확장자를 바꿔 색인 경로 밖으로 뺀다.

요약 파일 안에는 마스터 요약 외에 섹션별 요약도 함께 들어간다. 검색에서 히트됐을 때 어느 섹션이 관련 있는지 바로 보이게 하기 위해서다.

CLI는 단순하게 만들었다.

```
summarize_large <file>
```

파일을 넘기면 해시 확인 → 섹션 분할 → Map 요약 → Reduce 요약 → 결과 저장까지 자동으로 돈다. 이미 처리된 파일이면 "변경 없음"을 출력하고 끝난다.

---

아직 해결 못 한 게 있다. 섹션이 수십 개인 파일의 Reduce 단계에서 섹션 요약을 전부 이어붙이면 그게 또 컨텍스트 한계를 넘어선다. 지금은 섹션 요약도 다시 청킹해서 2단 Reduce를 돌리는데, 이게 맞는 구조인지 확신이 없다. 계층이 깊어질수록 정보 손실이 누적된다. 원본에서 한 번에 중요한 걸 뽑는 게 낫지 않냐는 생각도 드는데, 그러려면 로컬 모델 컨텍스트 창이 지금보다 훨씬 커야 한다.
