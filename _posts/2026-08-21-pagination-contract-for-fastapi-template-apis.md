페이지네이션은 어느 언어, 어느 프레임워크에서도 "쉬운 것"으로 취급된다. 사실 틀린 말은 아니다. 문제는 **쉬운 것들이 맞닿을 때** 생긴다.

NestJS로 짜둔 API 계약을 FastAPI로 옮기는 작업이었다. 프론트엔드는 이미 기존 스펙을 바라보고 있었고, 응답 구조도 바꾸는 게 목표였다. 작업 전에 예상한 공수와 실제 공수가 꽤 달랐다.

---

## offset이 "페이지 번호"인 API

처음부터 이상했다. NestJS 쪽 `PaginationDto`는 `offset`과 `limit`을 받는데, 프론트가 넘기는 `offset=1`은 **첫 번째 페이지**를 의미했다. DB의 `OFFSET 1`이 아니었다.

그러니까 이 API에서 `offset`은 사실 `page`다. 이름이 잘못 붙은 것인지, 아니면 처음부터 그렇게 정의한 것인지는 모르겠다. 히스토리를 더 파야 알 수 있는데, 어차피 프론트가 그렇게 쓰고 있으니 그 의미로 구현해야 했다.

변환식은 단순하다.

```
skip = (offset - 1) * limit
```

`offset=1, limit=30`이면 `skip=0`, 즉 처음 30개. `offset=2`면 30번째부터. 이 계산 자체는 한 줄이지만, **이게 의도된 설계였는지 확인하는 데 더 오래 걸렸다.**

## 응답 구조 교체

기존 응답은 이렇게 생겼다고 전달받았다.

```json
{
  "status": "success",
  "count": 7,
  "templates": [...]
}
```

바꿔야 하는 구조는 이렇다.

```json
{
  "totalCount": 7,
  "list": [...],
  "main_tool": "SM02PB"
}
```

차이가 세 가지다:

- `count` → `totalCount` — 이름만 바뀐 게 아니다. 이게 **페이지네이션 이전 전체 개수**임을 명시적으로 정의했다. 즉 한 페이지에 30개를 보여줘도 `totalCount`는 276일 수 있다.
- `templates` → `list` — 엔드포인트마다 배열 키가 달랐던 걸 통일했다.
- `status` 필드 제거 — 이게 제일 크다.

`status: "success"` / `status: "fail"`을 body에 넣는 패턴은 HTTP 상태코드의 의미를 반쯤 무시하는 구조다. 200으로 내려오는데 `status: "fail"`인 응답은 클라이언트 쪽에서 두 번 확인해야 한다. 이번에 그걸 정리했다. 이제 실패는 4xx/5xx로 내려오고 body에는 `error_code`와 `error_detail`이 들어간다.

## FastAPI Pydantic 쿼리 모델의 함정

FastAPI에서 쿼리 파라미터를 묶을 때 Pydantic 모델을 쓰면 깔끔하다. `PaginationParams` 같은 이름으로 `offset`, `limit`을 묶고 `Depends()`로 주입하는 방식이다.

문제는 **다른 쿼리 파라미터와 함께 쓸 때** 생긴다.

엔드포인트 하나에 `main_tool` 같은 path parameter 외에 쿼리 파라미터가 따로 있고, 거기에 `Depends(PaginationParams)`까지 붙이면 FastAPI가 자동으로 "펼쳐줄 것"이라고 기대하게 된다. 실제로는 상황에 따라 파라미터가 제대로 바인딩되지 않는 경우가 있었다.

이게 FastAPI 자체의 버그인지, 특정 버전에서만 생기는 문제인지, 아니면 내가 어딘가 잘못 쓴 건지는 아직 확실히 정리하지 못했다. 일단 그 부분은 명시적으로 파라미터를 선언하는 방식으로 우회했다. 재현 조건을 좁히는 게 다음 숙제다.

## 랜덤 정렬과 페이지네이션은 사실 충돌한다

랜덤 템플릿 목록 API가 따로 있었다. `ORDER BY RANDOM()` 같은 방식으로 정렬하고 결과를 주는 엔드포인트다.

여기에 페이지네이션을 붙이면 이상해진다. 2페이지를 요청할 때 DB가 다시 랜덤 정렬을 하면, 1페이지에서 봤던 항목이 2페이지에 다시 나올 수 있다. 반대로 영영 안 나오는 항목도 생긴다.

이 API의 `totalCount: 276`은 실제로 DB에 있는 전체 개수를 그대로 반환하는 것이고, 프론트가 페이지네이션 UI를 그리기 위해 쓴다. 하지만 2페이지를 눌렀을 때 정합성이 보장되지 않는다는 걸 스펙 문서에 명시해야 하는지, 아니면 구현 방식을 바꿔야 하는지는 프론트와 한 번 더 얘기해야 할 것 같다.

---

응답 구조 교체와 실패 처리 변경은 마무리됐다. Pydantic 쿼리 모델 바인딩 문제는 재현 조건을 더 좁혀야 하고, 랜덤 정렬 + 페이지네이션 정합성 이슈는 결정이 남아 있다.
