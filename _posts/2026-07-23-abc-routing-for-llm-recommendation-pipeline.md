처음엔 흐름이 하나였다. 사용자 입력이 들어오면 LLM이 키워드를 뽑고, 그 키워드로 콘텐츠 풀을 좁히고, 남은 후보에서 추천을 골랐다. 깔끔해 보였다.

돌려보니 그렇지 않았다.

어떤 질의는 학년이 다른 콘텐츠가 섞여 나왔다. 어떤 질의는 LLM이 너무 많이 뽑아서 필터가 지나치게 좁아졌다. 처음엔 LLM 프롬프트를 만졌다. 예시를 늘리고, 출력 형식을 강제하고, "학년은 키워드에 포함하지 말라"고 명시했다. 조금 나아졌다가 다시 무너졌다. 다른 입력 유형에서 또 다르게 무너졌다.

문제는 LLM 실력이 아니라 **구조**였다는 걸 늦게 알아챘다. 서로 성격이 다른 입력을 하나의 경로로 강제하고 있었다.

## 두 종류의 입력이 섞이는 순간

- `중2 1학기 방정식 단원 문제풀이 도구` — 학년·학기·단원명이 명시된 입력
- `연립방정식 그래프로 보여주는 거` — 개념만 있는 입력

앞쪽 입력을 LLM에 그대로 던지면 "중2", "1학기", "방정식"이 전부 키워드로 나온다. 이 키워드를 텍스트 매칭에 쓰면 학년 조건이 문자열 매칭에 섞여 들어가서, 조건이 과하게 좁아지거나 반대로 학년이 다른 콘텐츠가 딸려온다. LLM 입장에선 다 그냥 단어일 뿐이니까.

두 입력은 처리 방식 자체가 달라야 했다. 앞쪽은 정보가 이미 구조화되어 있으니 규칙 기반으로 조회하면 되고, 뒤쪽은 자유로운 자연어니까 LLM이 필요하다.

## 분기의 기준

| 유형 | 조건 | 후보 생성 |
|------|------|-----------|
| A | 학년·단원 정보만 있음 | 커리큘럼 역인덱스 직접 조회 |
| B | 개념 키워드만 있음 | LLM 키워드 추출 → 전문 검색 |
| C | 둘 다 포함 | A + B 결합 |

기준을 세우고 나서 원칙이 한 줄로 정리됐다. **구조화 정보는 규칙으로, 모호한 자연어만 LLM으로.** LLM에게 학년을 알아채라고 시키지 않고, 학년은 파서가 뽑아서 필터 조건으로 넘기고, LLM은 나머지—오타·별칭·자유 표현—만 담당한다.

## 판별을 노드 하나로 뽑는다

LangGraph로 짜면서 처음엔 분기 로직을 기존 노드 안에 묻어뒀다. 테스트가 지옥이었다. LLM 호출이 앞에 물려 있으니 단위 테스트마다 mock이 필요했고, 분기 조건이 바뀔 때마다 그래프 전체를 다시 돌려봐야 했다.

판별을 독립 노드로 꺼내자 문제가 사라졌다.

```python
def resolve_input_type(state: PipelineState) -> PipelineState:
    has_grade = state.parsed_grade is not None
    has_keywords = len(state.extracted_keywords) > 0

    if has_grade and not has_keywords:
        state.input_type = "A"
    elif not has_grade and has_keywords:
        state.input_type = "B"
    else:
        state.input_type = "C"
    return state
```

LLM 호출이 없다. 순수 함수다. 입력만 넣어서 분기 결과를 곧바로 검증할 수 있다. 이후 conditional edge로 나눈다.

```python
graph.add_conditional_edges(
    "resolve_input_type",
    lambda s: s.input_type,
    {"A": "curriculum_lookup", "B": "keyword_search", "C": "hybrid_search"},
)
```

판별 노드를 뽑은 게 실제로 가장 크게 도움이 된 변경이었다. 코드 라인 수로는 작지만, 이후 모든 디버깅이 "어느 분기에서 무너졌는가"로 시작할 수 있게 됐다.

## 최종 추천 프롬프트에서도 같은 실수

C 타입에서 한 번 더 걸렸다. 분기까지는 잘 나눴는데, 최종 추천을 만드는 LLM 프롬프트에 사용자 원문만 넣었다. 그러면 LLM이 학년 맥락을 자꾸 흘렸다. 이미 파싱해둔 학년 정보를 프롬프트에서 다시 자연어로 파악하라고 시키고 있었던 셈이다.

프롬프트에 구조 필드를 명시적으로 붙였다.

```
사용자 질의: {original_query}
학년: {grade}  학기: {semester}
단원명: {unit_name}  학습 개념: {learning_concept}
후보 목록: {candidates}
```

앞단에서 뽑은 걸 뒷단에서 또 흐리게 만들지 않는다. 파이프라인의 어느 단계든 이미 구조화된 정보는 구조화된 채로 넘긴다.

## 남아 있는 것

분기를 나눈 뒤 눈으로 훑는 수준에선 오염이 확실히 줄었다. 문제는 그걸 수치로 증명하지 못한 상태라는 것이다. 실제 질의 로그가 1849건 쌓여 있는데 아직 유형별로 분류해서 각 분기의 정확도를 비교하지 못했다. B 분기의 LLM 키워드 추출은 여전히 편차가 커 보이고, C 분기에서 A와 B를 어떻게 가중치로 섞을지도 지금은 그냥 반반이다.
