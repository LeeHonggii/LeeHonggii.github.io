`json.loads`가 통과하면 끝이라고 생각했다. 키워드 추출 결과를 추천 쪽에서 가져다 쓰기 시작하면서 그 생각이 깨졌다.

추천 계산은 키워드를 라벨로 취급한다. 같은 개념이 "분수의 덧셈", "분수 덧셈", "덧셈(분수)"로 갈라져 나오면 JSON은 멀쩡해도 라벨로는 쓸 수 없다. 형식은 맞는데 계약은 깨진 상태다. 그래서 키워드 추출 코드를 손봤다. 출력이 JSON인지만 보지 않고, 미리 정해 둔 어휘 목록 안에 있는 값인지도 확인한다.

## 한 파일에 섞여 있던 것을 넷으로 쪼갰다

처음 코드는 프롬프트 조립, API 호출, 응답 파싱, 어휘 비교가 한 흐름 안에 섞여 있었다. 지금은 호출·추출·검증·어휘 모듈로 나눠 놓았다.

- **호출**: 모델에 요청을 보내고 응답 원문을 돌려준다.
- **추출**: 입력에서 프롬프트를 만들고 응답을 키워드 목록으로 바꾼다.
- **검증**: 형식과 어휘를 확인한다.
- **어휘**: 통제어휘(controlled vocabulary, 허용된 라벨만 모아 둔 닫힌 목록) 자체를 들고 있다.

어휘를 따로 뺀 이유는 단순하다. 어휘는 바뀌는 데이터이고 검증 로직은 안 바뀌는 코드다. 둘이 같은 파일에 있으면 어휘 한 줄을 고칠 때마다 로직을 건드리게 된다.

## "형식 검증"이 이미 하는 일

같은 저장소의 다른 스크립트에, 형식 층을 어떻게 막았는지 보여 주는 코드가 있다. 키워드 추출기가 아니라 진단 문항을 한 번 생성해 보는 실험용 프로브다. 이 글의 주제인 어휘 검증 코드는 아니고, 형식 검증이 어디까지 해 주는지 보여 주는 용도로만 가져왔다. 식별자는 일반화했다.

```python
def run(self):
    from openai import OpenAI, OpenAIError
    t0 = time.perf_counter()
    try:
        with OpenAI(api_key=KEY, timeout=300, max_retries=0) as client:
            r = client.chat.completions.create(
                model=MODEL, reasoning_effort="low", max_completion_tokens=16000,
                response_format={"type": "json_object"},
                messages=[{"role": "system", "content": Guide.text()},
                          {"role": "user", "content": self.user}])
        self.usage.update(calls=1, input_tokens=r.usage.prompt_tokens,
                          output_tokens=r.usage.completion_tokens)
        ch = r.choices[0]
        self.raw = ch.message.content or ""
        if ch.finish_reason != "stop":
            raise ValueError(f"응답 중단: {ch.finish_reason}")
        self.parsed = json.loads(self.raw)
    except OpenAIError as e:
        self.usage["calls"] = 1
        self.error = f"{type(e).__name__}: {str(e)[:300]}"
    except (ValueError, TypeError) as e:
        self.error = str(e)[:300]
    self.usage["elapsed_ms"] = int((time.perf_counter() - t0) * 1000)
    return self
```

이 함수에서 신경 쓴 건 세 군데다.

`response_format={"type": "json_object"}`는 모델이 JSON 문법을 지키게 하는 옵션이다. 거기까지만 보장한다. 키 이름이나 값의 의미는 보장하지 않는다.

`finish_reason != "stop"` 검사는 `json.loads`보다 먼저 돈다. 토큰 상한에 걸려 잘린 응답은 JSON이 중간에 끊겨 파싱 에러로 나온다. 그런데 원인은 형식이 아니라 길이다. 파싱 에러만 보면 프롬프트를 의심하게 된다. 그래서 중단 사유를 먼저 에러로 올린다.

실패해도 예외를 던지지 않고 `error`와 `raw`를 객체에 남긴다. 실험 도구라서 한 건이 실패해도 나머지 조건을 계속 돌려야 하고, 실패 원문도 나중에 봐야 한다. `max_retries=0`으로 SDK의 자동 재시도를 꺼 둔 것도 같은 이유다. 재시도가 안 보이는 곳에서 일어나면 호출 횟수를 셀 수 없다.

## 이 함수가 통과시키는 것

위 코드를 통과한 응답은 "문법이 맞는 JSON이고, 끝까지 생성됐다"는 것만 증명한다. 키워드를 이 경로로 뽑는다면 아래 응답도 통과한다.

```json
{"keywords": ["분수 덧셈", "통분 하기", "분모가 다른 분수의 합"]}
```

문법은 맞고 키 이름도 맞다. 그런데 어휘 목록에 없는 문자열일 수 있다. 위 코드 어디에도 이걸 걸러내는 줄이 없다. 추천 계산이 이 값을 키로 조회하면 조용히 비어 있는 결과가 돌아온다.

그래서 검증 모듈에는 두 번째 관문을 뒀다. 파싱된 키워드 각각이 어휘 모듈의 허용 집합에 속하는지 본다. 이 관문은 코드를 길게 인용할 게 없다. 집합 소속 비교이고, 어려운 건 로직이 아니라 그 비교를 파이프라인의 어디에 두느냐였다. 호출 직후가 아니라 추출 다음, 외부로 내보내기 전에 둔다. 그래야 외부 추출 API로 같은 일을 시킬 때도 같은 관문을 지난다.

## 외부 API와 맞출 기준

추출을 별도 API로 노출하는 연동도 염두에 두고 있다. 그래서 실제 입력으로 돌려 본 검증 결과와, 입력·응답 규격 문서를 같이 준비했다. 응답 규격에는 키워드가 어휘 목록의 값이라는 조건을 명시했다. 호출하는 쪽이 "JSON이 왔으니 믿는다"로 가지 않게 하려는 것이다.

이 글에는 실제 입력으로 돌린 결과의 수치를 싣지 않는다. 어휘에서 벗어난 응답이 몇 퍼센트였는지는 아직 정리해서 재보지 않았다. 숫자를 대충 쓰느니 비워 두는 쪽이 낫다.

## 아직 정하지 못한 것

어휘에 없는 값이 나왔을 때 어떻게 할지는 아직 확정하지 못했다.

- 그 키워드만 버린다. 이러면 한 문서의 키워드가 조용히 줄어든다.
- 전체를 재요청한다. 비용이 늘고, 같은 값이 또 나올 수도 있다.
- 가장 가까운 어휘로 매핑한다. 편하지만 모델이 틀린 걸 코드가 덮어 주는 셈이 된다.

세 번째가 가장 끌리는데, 그게 제일 위험해 보인다. 어휘 밖 값이 자주 나온다면 그건 검증 문제가 아니라 프롬프트나 어휘 설계 문제일 수 있다. 먼저 실제 입력에서 어휘를 벗어나는 빈도부터 세어 봐야 정할 수 있을 것 같다.
