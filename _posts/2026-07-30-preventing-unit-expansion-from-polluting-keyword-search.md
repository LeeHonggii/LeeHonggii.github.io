로그를 넘기다가 손이 멈췄다. 사용자가 "가르기" 관련 활동을 원했는데, 상단에 "모으기"가 앉아 있었다. 수학적으로 정반대인 두 개념. 오탈자도 동의어도 아니다. 뭔가 조용히 망가져 있었다.

## 처음 의심한 곳은 틀렸다

키워드 인덱싱을 먼저 뒤졌다. "모으기" 활동에 "가르기" 태그가 잘못 붙어 있는 줄 알았다. 아니었다. 태그는 깨끗했다. 그러면 왜 걔가 위로 올라왔지.

스코어링 로그를 열어 보고서야 알았다. "모으기"는 **직접 키워드 매칭으로 뽑힌 게 아니라, 단원 확장(unit expansion)으로 여러 번 걸려서** 올라와 있었다. 같은 단원에 속한 다른 활동을 후보로 끌어오는 로직인데, 취지는 좋다. 직접 매칭만 보면 후보가 얕으니까 관련 단원까지 넓혀서 다양성을 준다.

문제는 점수였다.

## 확장이 직접 신호를 이길 수 있는 구조였다

당시 스코어링은 대략 이런 모양이었다. — 정확한 상수는 다르지만 구조는 이거였다.

```python
if keyword in template.keywords:
    score += 3
if unit in expanded_units:
    score += 3
```

직접 매칭 +3, 확장 매칭 +3. 같은 무게. 확장이 한 활동에 대해 여러 경로로 걸릴 수 있는 구조라, "모으기" 같은 활동이 확장으로 두세 번만 잡히면 직접 매칭 한 번을 이겨 버렸다. 확장이 **보조 신호가 아니라 주 신호로 바뀌는** 순간이 있었던 거다.

이게 왜 조용한 버그냐면, 에러가 안 난다. 500도 없고 422도 없다. 그냥 "왜 이게 여기 있지" 하는 결과만 조용히 쌓인다.

## 고치는 방향은 위계를 코드에 박아 두는 것

수정은 상수 이름부터 다시 지었다. 신호 종류마다 크기가 눈에 보이게.

```python
SCORE_DIRECT_KEYWORD = 10
SCORE_TEXT_MATCH     = 5
SCORE_UNIT_EXPANSION = 1
```

직접 키워드는 10, `description`·`learning_goal` 같은 텍스트 필드 매칭은 5, 단원 확장은 1. 확장 매칭이 직접 매칭을 넘으려면 열 번 걸려야 한다. 실제 데이터에서 그런 경우는 거의 없다. 원하는 건 확장이 순위를 뒤집는 게 아니라, **직접 신호가 부족할 때 후보를 얕지 않게 채워 주는 것**이었으니까.

텍스트 필드 매칭(+5)을 중간에 끼운 게 의외로 컸다. 키워드 필드는 사람이 손으로 붙인 태그라 누락이 잦다. `description` 안에 "가르기"라는 단어가 들어 있으면 그건 우연이 아니라 실제 관련성이다. 직접 매칭보다는 약하지만, 확장보다는 훨씬 강한 신호로 취급한다.

## 테스트를 먼저 깨뜨려 두고 고쳤다

상수를 눈대중으로 만지면 다른 케이스가 무너진다. 그래서 실패 케이스부터 이름을 박아 뒀다.

```python
def test_b_path_direct_match_outranks_unit_expansion():
    direct = score_template(activity_a, ["가르기"], expanded_units)
    expansion_only = score_template(activity_b, ["가르기"], expanded_units)
    assert direct > expansion_only
```

먼저 빨간 줄을 켜두고 상수를 조정하니 수렴이 빨랐다. 회귀 여부도 이 이름으로 남는다. 나중에 누가 확장 점수를 올리려 할 때, 이 테스트가 "그거 예전에 왜 낮췄는지" 물어봐 준다.

## 남은 것

이 버그를 잡으면서 확실해진 건, **확장 로직의 역할은 "보강"이지 "우선순위"가 아니다** 라는 것. 룰 기반 확장은 편리해서 자꾸 무게가 실리는데, 그 순간 추천 품질은 에러 없이 조용히 뭉개진다.

아직 못 본 게 있다. 텍스트 매칭 +5가 정말 적정한지는 재보지 않았다. `description`이 긴 활동이 우연히 여러 키워드를 품고 있어서 과대평가되는 케이스가 있을 것 같은데, 실제 분포를 아직 안 뽑아 봤다. 다음에 열어 볼 파일은 그 쪽이다.
