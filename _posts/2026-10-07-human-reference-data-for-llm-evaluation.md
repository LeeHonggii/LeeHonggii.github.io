기존 LLM 분석 코드를 읽으면서 실행 순서를 따라가 봤다. 학생이 남긴 활동 기록 한 페이지가 문제 정의, 답안 판정, 활동 이력 평가, 선생님용 리포트로 넘어가는 흐름이다. 읽다 보니 "테스트가 통과한다"는 말이 이 코드에서 무엇을 보증하는지 다시 따져보게 됐다.

이 글은 그 정리다. 새 평가 엔진을 만들어 검증한 이야기가 아니다. 구현도 성능 검증도 아직 안 했다.

## 코드가 판정하는 부분과 모델이 판정하는 부분

페이지 하나를 처리하는 클래스는 입력을 문자열로 조립해서 모델에 한 번 보낸다. 지시문, 쓰인 교구, 화면 글, 코드가 미리 뽑아둔 사실 목록이 들어간다. 정답 목록이 있으면 같이 넣는다.

그런데 이 클래스 안에는 모델 판정을 코드가 덮어쓰는 구간이 따로 있다.

```python
def answer_groups(self):
    groups, _ = SolutionWay.answers(self.task_id, self.ev.order)
    norm = lambda t: re.sub(r"\s|=.*", "", str(t))
    out = []
    for g in groups or []:
        exprs = {norm(a) for a in g.get("답") or [] if re.fullmatch(r"\d+[+\-×÷]\d+", norm(a))}
        if exprs:
            out.append(exprs)
    return out

# 정답 목록에 식이 있고 학생 화면에 카드 식이 있으면, 정답 여부는 코드가 대조한다(AI 의 「가장 큰/작은」 비교가 실행마다 흔들림)
def verdict_by_code(self, p):
    groups, mine = self.answer_groups(), self.exprs("CARD_EXPR")
    if not groups or not mine:
        return p
    hits = [any(e in g for e in mine) for g in groups]
    code = "정답" if all(hits) else "부분 정답" if any(hits) else "오답"
    # ... (이하 생략)
```

주석이 이유를 그대로 적고 있다. 「가장 큰 수」 같은 비교를 모델에게 맡기면 실행할 때마다 결과가 흔들렸다는 것이다. 그래서 정답 식 집합과 학생 화면의 카드 식이 모두 있을 때만 집합 포함 여부를 코드로 계산한다. 정규식으로 `숫자 연산자 숫자` 모양만 걸러서 비교하고, 한쪽이라도 없으면 `return p`로 모델 결과를 그대로 둔다.

이 구간은 단위 테스트로 잡을 수 있다. 입력이 같으면 출력이 같고, 기대값을 손으로 적을 수 있다. 타입 검사와 이런 회귀 테스트가 통과하면 안심이 되는 이유다.

다만 그 안심이 덮는 범위는 좁다. 이 함수가 안 건드리는 쪽, 즉 식이 없거나 정답 목록이 없는 페이지에서 모델이 준 판정과 한 줄 평, 학생이 왜 막혔는지에 대한 서술은 테스트가 답해주지 않는다.

## 캐시는 재현성을 주지만 정확성은 안 준다

같은 입력이면 저장본을 쓴다. 지문(fingerprint)은 프롬프트와 입력 텍스트를 이어 붙여 해시한 값이다.

```python
self.system = prompt
self.fingerprint = hashlib.sha256((prompt + self.text).encode("utf-8")).hexdigest()[:16]

def load(self):
    p = self.path()
    if not p.exists():
        return None
    d = load_json(p)
    if d.get("fingerprint") != self.fingerprint:
        return None
    self.relation_by_code(d["result"])
    return d
```

프롬프트를 한 글자라도 고치면 지문이 바뀌어 저장본이 무효가 된다. 프롬프트 변경이 결과에 반영되는 구조라서, 전후 비교를 하기에는 좋은 토대다.

하지만 지문이 바뀌었다는 것은 결과가 달라질 수 있다는 뜻일 뿐이다. 달라진 결과가 더 맞는지는 이 구조 어디에도 없다. 저장본을 읽어올 때 `relation_by_code`를 다시 거치는 것도 같은 맥락이다. 코드로 계산할 수 있는 관계는 코드가 다시 채운다. 그 밖의 모델 서술은 저장된 그대로 나간다.

## 집계는 판정이 맞다는 가정 위에 서 있다

활동 단위 리포트는 페이지별 판정을 모아 선생님에게 "먼저 볼 학생"을 알려준다.

```python
NEEDS_HELP = ("오답", "부분 정답")

@staticmethod
def one_line(rows):
    done = [r for r in rows if all(p["판정"] for p in r["pages"])]
    if not done:
        return "아직 AI 분석 전입니다."
    help_ = [r["student"] for r in done if any(p["판정"] in NEEDS_HELP or p["확인_필요"] for p in r["pages"])]
    line = f"{len(done)}명 중 " + (f"{', '.join(help_)} 학생을 먼저 확인해 보세요." if help_ else "모두 정답에 도달했습니다.")
    if len(done) < len(rows):
        line += f" (분석 전 {len(rows) - len(done)}명)"
    return line
```

이 함수는 문장이 자연스럽게 나오도록 잘 짜여 있다. 분석 전인 학생 수까지 따로 적는다. 그래도 "모두 정답에 도달했습니다"라는 문장이 참인지는 아래 단계의 판정이 맞았을 때만 성립한다. 읽기 좋은 리포트와 맞는 평가는 다른 층에 있다. 이번에 가장 크게 정리된 지점이 여기다.

판정 값 자체도 눈여겨볼 만하다. `정답 / 부분 정답 / 오답 / 판단 보류` 네 개인데, 앞의 셋은 정도가 있는 순서형처럼 보이고 `판단 보류`는 그 줄에 놓이지 않는다. 이 점은 아래 일치도 지표를 고를 때 걸린다.

## 그래서 필요한 것: 전문가 판정과 참조 데이터

모델이 부여한 점수가 타당한지 보려면 사람 쪽 기준이 먼저 있어야 한다. 정리하면 이렇다.

- 활동 유형별로 무엇을 평가하는지 정의한다.
- 그 판단의 근거가 되는, 화면에서 관찰 가능한 단서를 정한다.
- 전문가가 같은 기록에 매긴 판정을 모아 참조 데이터셋으로 만든다.
- 프롬프트를 바꾸기 전후로 같은 참조 데이터에 돌려 비교한다.

일치도 지표는 대상에 맞춰 골라야 한다.

- 단순 일치율은 "같은 칸에 얼마나 들어갔나"만 본다. 범주가 명목형이면 이쪽으로 충분하다. 우연히 맞는 몫을 걷어내지는 않는다.
- 가중 카파는 틀린 정도에 가중치를 준다. 정답을 부분 정답으로 본 것과 정답을 오답으로 본 것을 다르게 센다. 순서형 점수에 맞는다.
- 위의 `판단 보류`는 순서 위에 놓기 애매하다. 순서형으로 볼지, 보류를 따로 떼어 볼지는 아직 정하지 못했다.

한 가지 함정도 적어둔다. 선생님이 리포트를 승인하거나 수정한 기록은 참조 데이터 후보로 쓸 수 있다. 하지만 승인율을 정확도로 읽으면 안 된다. 그럴듯한 리포트는 훑어보고 승인하기 쉽다. 승인율이 높다는 것은 읽을 만하다는 신호이지, 평가가 맞는다는 신호가 아니다. 수정 기록에서 무엇이 바뀌었는지는 참조 후보가 되지만, 승인만 한 건은 따로 취급해야 한다.

## 아직 안 한 것

- 참조 데이터셋이 없다. 위의 지표는 아직 한 번도 돌려보지 않았다.
- 코드로 덮어쓰는 구간과 모델에 맡기는 구간이 실제 페이지에서 각각 얼마나 되는지 재보지 않았다. 이 비율을 모르면 회귀 테스트가 지켜주는 범위도 모른다.
- 영상 기반 분석에서 관찰 가능한 근거를 어디까지 정의할 수 있을지는 실험 방향만 논의한 단계다.

참조 데이터를 몇 건부터 만들어야 지표가 의미를 가질지도 아직 모른다. 이건 먼저 소량으로 전문가 판정을 받아보고 판단해야 할 것 같다.
