발표자료를 만들 때 "스타일"을 고른다는 게 무슨 의미인지 오래 헷갈렸다.

처음에는 테마를 고른다는 뜻이라고 생각했다. 폰트, 배경색, 강조색. 그런데 Marp(Markdown 텍스트를 슬라이드로 변환하는 도구) 기반으로 HTML 발표 페이지를 생성하는 흐름을 만들다 보니, 실제로 사용자가 원하는 건 색이 아니라는 걸 알게 됐다. 그들이 원하는 건 **이 슬라이드를 어떻게 나눌 것인가** 였다.

---

발단은 간단했다. Markdown 한 벌에서 PPTX와 HTML 발표 페이지를 동시에 뽑는 흐름을 만들고 있었고, HTML 쪽에서 "어떤 레이아웃으로 만들어 드릴까요?"라는 선택지를 UI에 넣으려 했다. 처음 설계한 선택지 목록은 이랬다.

- 밝은 테마
- 어두운 테마
- 심플 테마

당연히 쓸모없었다. 색이 다른 슬라이드를 세 개 보여줘봤자 사용자는 뭘 골라야 할지 알 수가 없다. 내용이 어떤 **형태**로 배치되는지를 보여줘야 한다.

그때부터 레이아웃 패턴 단위로 다시 분류하기 시작했다.

---

## 레이아웃을 분리한다는 것

결국 정착한 방식은 `deck_layouts/` 디렉토리 아래에 레이아웃별 폴더를 두고, 각 폴더에 두 가지 파일을 함께 두는 구조다.

```
00_System/deck_layouts/
  hero/
    LAYOUT.md       # 이 레이아웃의 사용 방법, 변수, 예시
    wireframe.svg   # 레이아웃의 시각적 미리보기
  bento-grid/
    LAYOUT.md
    wireframe.svg
  timeline/
    LAYOUT.md
    wireframe.svg
  code-focus/
    LAYOUT.md
    wireframe.svg
```

`LAYOUT.md`는 이 레이아웃이 어떤 상황에 맞는지, Marp에서 어떻게 활성화하는지, 어떤 변수를 받는지를 담는다. `wireframe.svg`는 실제 내용 없이 영역 배치만 보여주는 와이어프레임이다.

이 구조를 택한 이유는 하나다. 사용자가 코드 템플릿을 직접 열어보지 않아도 결과물의 형태를 판단할 수 있어야 한다. 발표자료 생성 UI에서 레이아웃을 고를 때, 색 견본이 아니라 `wireframe.svg`를 미리보기로 보여주면 된다.

---

## Marp에서의 연결

Marp는 슬라이드별로 CSS 클래스를 지정하는 방식을 지원한다. 레이아웃 이름을 클래스 이름으로 매핑하면, 발표 전체에 기본 레이아웃을 적용하면서도 특정 슬라이드만 다르게 만들 수 있다.

```markdown
<!-- _class: layout-bento-grid -->

## 이번 주 작업 분류

- 신규 기능 3건
- 버그 수정 7건
- 문서 업데이트 2건
```

`layout-bento-grid`는 콘텐츠를 격자형으로 배치하는 패턴이다. 여러 항목이 나란히 보여야 할 때 쓴다. `layout-hero`는 큰 제목과 한 문장 요약이 화면 중앙에 위치하는 표지형이고, `layout-code-focus`는 코드 블록이 좌우 전체를 차지하고 설명이 하단에 붙는다.

이걸 슬라이드별로 지정하는 CLI 플래그도 만들었다.

```bash
--per-slide-layouts '{"2":"code-focus","3":"timeline"}'
```

JSON 형태로 슬라이드 번호와 레이아웃 이름을 매핑하면, 생성 시점에 해당 슬라이드에만 클래스를 주입한다. 전체 덱의 기본 레이아웃은 `--layout`으로 따로 지정할 수 있다.

## 와이어프레임이 생각보다 중요했다

레이아웃 선택 UI에서 가장 오래 고민한 게 이 부분이었다.

처음에는 레이아웃 이름(`bento-grid`, `timeline` 등)을 드롭다운으로 보여줬다. 이름만으로는 직관적이지 않다는 피드백이 나왔다. 그 다음엔 설명 텍스트를 붙였다. 역시 읽지 않았다.

SVG 와이어프레임을 옆에 두고 나서야 선택이 빨라졌다. 내용이 없는 사각형들의 배치만 보여줘도, 사람은 "아, 이건 코드 설명 슬라이드 구조네"를 바로 파악한다. 텍스트 설명은 보조 수단이지 주 수단이 아니었다.

와이어프레임을 SVG로 만든 건 단순한 이유다. 확대해도 깨지지 않고, 다크 모드에서도 색 반전 없이 쓸 수 있고, 파일 크기가 작다.

---

레이아웃 패턴이 지금 네 개인데, 이게 적당한 수인지는 아직 모르겠다. 실제로 자주 쓰는 건 `hero`와 `code-focus` 두 개뿐이고, `bento-grid`는 내용이 많을 때만 가끔 나온다. `timeline`은 만들어두긴 했는데 아직 실사용 케이스를 못 봤다.

콘텐츠 누락 검증도 아직 미완이다. Markdown을 슬라이드로 쪼갤 때 레이아웃에 따라 허용 가능한 글자 수가 달라지는데, 지금은 그걸 변환 후에야 눈으로 확인해야 한다. 자동으로 경고를 띄우거나 레이아웃을 제안하는 로직을 붙이려고 했는데 아직 손을 못 댔다.
