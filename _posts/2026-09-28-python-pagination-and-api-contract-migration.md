단순히 목록에 페이지네이션 파라미터를 추가하는 작업이라고 생각했다. 그런데 끝나고 보니 응답 필드 의미, 실패 표현 방식, 기본 동작까지 건드렸다. 처음에 예상한 것보다 계약 변경의 범위가 컸다.

---

## `offset`이 무엇을 뜻하는가

먼저 파라미터 이름부터 결정이 필요했다. 흔히 `offset`을 SQL의 행 오프셋으로 쓰는 경우가 있다. 0부터 시작하고, `OFFSET 30`이면 "31번째 행부터"라는 뜻이다.

그런데 호출자 쪽 인터페이스는 TypeScript로 이미 정의되어 있었다.

```typescript
interface PaginationQuery {
  offset?: number;
  limit?: number;
}
```

여기서 `offset`은 페이지 번호였다. 1부터 시작하는 1-based 페이지. SQL의 행 오프셋과 이름이 같지만 의미가 다르다.

Python 쪽에서는 이걸 SQL에 넘기기 전에 변환해야 했다.

```python
skip = (offset - 1) * limit
```

그리고 쿼리는 이렇게 된다.

```sql
LIMIT :limit OFFSET :skip
```

이름 하나가 두 가지 의미로 쓰이고 있다는 게 처음엔 불편했다. 하지만 호출자가 이미 이 네이밍으로 붙어 있었기 때문에, Python 내부에서 변환하는 것으로 정리했다. 인터페이스를 바꾸면 더 큰 계약 변경이 된다.

---

## 개수가 두 개가 된 이유

이전 응답은 단순했다. 조건에 맞는 항목을 전부 리스트로 내려줬다.

페이지네이션을 붙이면서 응답 구조가 바뀌었다.

```typescript
interface PaginationResponse<T> {
  totalCount: number;
  list: T[];
}
```

`totalCount`는 필터 조건에 맞는 전체 개수다. `list`에 담긴 항목 수와 다르다. 예를 들어 조건을 만족하는 항목이 150개인데 `limit=30`이면, `list.length`는 30이고 `totalCount`는 150이다.

이 구분이 왜 필요한가. 클라이언트가 "총 몇 페이지인지"를 계산하려면 전체 개수가 있어야 한다. `list.length`만으로는 마지막 페이지인지 알 수 없다.

문제는 전체 개수를 얻으려면 쿼리를 두 번 날려야 한다는 것이다. 한 번은 실제 데이터, 한 번은 `COUNT(*)`. 규모가 크지 않은 상황이라 일단 두 번 날리는 방식으로 뒀는데, 이게 나중에 부담이 될지는 아직 재보지 않았다.

그리고 여기서 놓치기 쉬운 계약 변경이 있다. 이전까지 이 API는 필터 조건에 맞는 항목을 **전부** 내려줬다. 이제는 기본값인 30개만 내려준다. `limit` 파라미터를 명시하지 않으면 동작이 바뀐다. 호출자가 이걸 모르고 있다면 조용한 버그가 된다.

---

## `status` 필드를 없앴다

응답에 `status` 필드가 있었다. 성공과 실패를 이 필드로 구분하는 방식이었다. HTTP 상태코드를 200으로 유지하면서 body 안에서 성공/실패를 표현하는 패턴이다.

이번에 이걸 제거하고 HTTP 상태코드로 실패를 표현하도록 수정했다. 실패면 4xx, 성공이면 200. body에는 성공 데이터만 담는다.

이 변경에서 확인해야 했던 것이 두 가지였다.

하나는 기존 오류 응답 형식. 프로젝트에는 `error_code`와 `error_detail`로 실패를 표현하는 커스텀 형식이 이미 있었다. 이걸 따라야 했다.

다른 하나는 FastAPI의 기본 422 응답. FastAPI는 요청 파라미터 검증 실패 시 422를 내려주는데, 이 응답 형식이 위의 커스텀 형식과 다르다. 별도 핸들러를 달지 않으면 같은 4xx여도 body 구조가 달라진다. 지금 422 핸들러가 있는지 확인이 필요한 상태로 남겨뒀다.

## 랜덤 목록과 seed 고정

목록 중 일부는 랜덤으로 섞어서 반환하는 엔드포인트가 있었다. 페이지네이션을 붙이면 문제가 생긴다. 첫 번째 페이지와 두 번째 페이지 요청 사이에 순서가 바뀌면 항목이 겹치거나 빠진다.

해결책으로 seed 고정을 실험했다. 요청 시 seed를 파라미터로 받고, 같은 seed면 같은 순서를 보장하는 방식이다.

결국 채택하지 않았다. 이 엔드포인트는 매 요청마다 다른 순서를 의도적으로 보여주는 용도였다. seed 고정은 그 목적과 맞지 않았고, 클라이언트도 페이지 간 연속성을 필요로 하지 않았다. 대신 응답 형식만 다른 엔드포인트와 통일했다.

---

남은 것이 있다. SQLAlchemy 바인드 실행이 실제로 제대로 도는지 앱 수준에서 검증하지 않았다. 쿼리를 직접 실행해서 확인했지만, 앱을 올려서 실제 HTTP 요청으로 흐르는 경로는 아직이다. 422 핸들러 문제도 같이 봐야 한다.
