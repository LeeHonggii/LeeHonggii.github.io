기존 멀티모달 평가 코드를 읽으면서 "이미지를 넣으면 평가 리포트가 나온다"는 한 줄이 실제로는 어떤 순서로 도는지 따라가 봤다. 입력과 출력을 단계마다 적고, 어느 값을 코드가 계산하고 어느 값을 LLM이 추론하는지 표시한 시퀀스 문서를 만들었다. 이 글은 그 정리다.

미리 말해 두면 영상 쪽은 아직 아무것도 검증하지 못했다. 맨 끝에 적었다.

## 설명용 단계와 실제 실행 순서는 다르다

처음 그린 그림은 깔끔했다. 문제 정의, 학생 답안 판정, 루브릭 평가, 리포트 생성이 일렬로 이어졌다. 코드를 따라가니 이 그림은 설명용이었다.

- 비전 분석과 리포트 생성은 **별도 실행**이다. 한 번의 호출 체인이 아니다.
- 활동을 문장으로 바꾼 뒤에 평가 프롬프트를 조립하는데, 이 시점에 코드 계산이 돈다.
- 계산값은 평가 응답에 반영된다. 서술은 그다음에 생성된다.

단계 이름은 개념 순서이고, 계산이 어디서 끼어드는지는 실행 순서를 봐야 보인다. 둘을 한 그림에 섞어 놓고 읽으면 "LLM이 계산했겠지"라고 넘겨짚게 된다. 시퀀스 문서를 따로 만든 이유가 이것이다.

## 이미지 세 장은 역할이 다르다

문제 하나에 화면이 세 종류 들어온다.

- 문제 초기 화면
- 모범답안 화면
- 학생 최종 화면

이 세 장을 "이미지 3장"으로만 넘기면 모델은 모범답안 화면에 놓인 배치를 문제 조건으로 읽을 수 있다. 정답이 이미 깔린 화면이니 그럴 만하다. 그래서 문제 정의 단계에서 이미지마다 역할을 명시해야 한다. 초기 화면만 문제의 조건이고, 모범답안은 정답 기준이다.

화면에서 추출한 텍스트도 이미지와 같이 준다. 문장은 텍스트로, 배치는 이미지로 읽으면 서로 빈틈을 메워 준다. 이 효과를 따로 측정하지는 않았다. 설계상의 이유일 뿐이다.

## 문제 정의를 분리하면 얻는 것과 잃는 것

문제 정의와 학생 답안 대조는 갈라 놓았다. 공통 문제 정의를 한 번 만들고, 학생이 여럿이면 재사용한다. 학생마다 문제를 새로 해석하지 않으니 기준이 같다.

대신 약점이 생긴다. 초기 화면 복원이 틀리면 그 오류가 모든 학생 분석에 똑같이 번진다. 학생별로 따로 정의했다면 해석이 흩어졌겠지만, 같은 문제가 서로 다른 기준으로 분석되는 일이 생길 수 있다. 분리하는 쪽을 택했으니, 공통 정의가 맞는지 검증하는 단계가 필요하다. 지금 그 검증은 없다.

## 선개념·오개념 목록은 어디서 오나

이 부분은 읽기 전에 오해하고 있었다. 선개념·오개념 목록이 교육과정 데이터를 조회해서 나올 거라고 생각했는데, 실제로는 교사가 입력하거나 모델이 추론한 값이었다.

두 가지를 구별해야 한다.

- 개념 목록의 **출처**: 교사 입력인지 모델 추론인지
- 개념 목록의 각 항목을 학생이 가졌다는 **판정 근거**: 학생 화면의 무엇을 보고 그렇게 판정했는지

리포트에 "이 학생은 ○○ 오개념이 있다"고 적혔을 때, 목록이 권위 있는 데이터에서 왔다는 인상을 주면 안 된다. 목록은 후보이고, 학생에 대한 판정은 화면 근거가 따로 있어야 한다.

## 코드가 확정하는 값은 어떤 모양인가

이 파이프라인의 계산 코드를 그대로 가져올 수는 없다. 대신 같은 저장소의 이웃 모듈 하나가 이 원칙을 잘 보여 줘서 가져온다. 이미지 경로가 아니라 풀이 과정을 프레임 단위로 받아 수 모형(자리값 블록) 조작을 사실로 펴는 분석기다. 식별자는 일반화했다.

가장 먼저 눈에 띈 건 개수를 세는 기준이다.

```python
# 판에 담긴 모형은 판의 격자가 정본이다 — 판 사이를 옮길 때 재생된 모형 요소는 갱신되지 않는 경우가 있다
@staticmethod
def kind_counts(elements):
    n = [0] * len(PLACE)
    for e in elements:
        if is_board(e):
            for row in BaseTenTrace.grid(e):
                for k, c in enumerate(row[:len(PLACE)]):
                    n[k] += c
        elif is_block_tool(e) and not e.get("connectedBoardId") and isinstance(e.get("shapeType"), int) and 0 <= e["shapeType"] < len(PLACE):
            n[e["shapeType"]] += 1
    return n
```

판에 올라간 모형은 개별 요소를 세지 않고 판의 격자 값을 센다. 주석에 이유가 있다. 모형을 판 사이로 옮길 때 재생된 요소가 갱신되지 않는 경우가 있어서, 요소를 세면 이중으로 세거나 빠뜨린다. 판에 연결되지 않은 낱개 모형만 요소로 센다.

여기서 "무엇이 정본인가"를 정하는 것이 곧 계산의 정확도다. LLM이 화면을 보고 "백 모형이 몇 개쯤 있네"라고 말하는 방식과는 신뢰의 종류가 다르다. 다만 이 정본 선택이 맞는지는 데이터가 아니라 위 주석에 적힌 관찰에 의존한다. 이 글을 쓰면서 그 관찰을 다시 확인하지는 않았다.

그다음은 프레임 사이 개수 변화를 조작의 종류로 분류하는 함수다.

```python
@staticmethod
def change(d):
    for k in range(len(PLACE) - 1):
        lo, hi = d[k], d[k + 1]
        rest = [x for j, x in enumerate(d) if j not in (k, k + 1)]
        if any(rest):
            continue
        if hi > 0 and lo == -10 * hi:
            return {"kind": "합치기", "label": f"{PLACE[k]} 모형 {-lo}개 → {PLACE[k + 1]} 모형 {hi}개"}
        if hi < 0 and lo == -10 * hi:
            return {"kind": "쪼개기", "label": f"{PLACE[k + 1]} 모형 {-hi}개 → {PLACE[k]} 모형 {lo}개"}
    if any(x < 0 for x in d) and not any(x > 0 for x in d):
        return {"kind": "덜어 냄", "label": " · ".join(f"{PLACE[k]} 모형 {-x}개" for k, x in enumerate(d) if x < 0)}
    if any(x > 0 for x in d) and not any(x < 0 for x in d):
        return {"kind": "더 놓음", "label": " · ".join(f"{PLACE[k]} 모형 {x}개" for k, x in enumerate(d) if x > 0)}
    return None
```

합치기(받아올림)는 인접한 두 자리에서 낮은 쪽이 정확히 10배만큼 줄고 높은 쪽이 늘고, 나머지 자리는 변하지 않을 때만 성립한다. 쪼개기(받아내림)는 그 반대다. 어느 쪽에도 안 맞는데 증가만 있거나 감소만 있으면 "더 놓음"이나 "덜어 냄"이다. 증가와 감소가 섞여 있으면 `None`을 돌려준다.

마지막 `None`이 내가 이 함수에서 제일 좋게 본 부분이다. 애매하면 추측해서 이름을 붙이지 않고 이벤트 없음으로 둔다. 이름 붙이는 일은 이 값을 받은 LLM에게 맡길 수 있지만, 사실이 아닌 값을 사실처럼 넘기는 일은 막는다.

이 분류가 맞다는 것도 코드를 읽고 논리를 확인한 것이지, 실제 데이터로 재 본 결과는 아니다. 앞의 정본 선택과 마찬가지다.

## 최종 서술에는 재판정을 맡기지 않는다

이 구조를 파이프라인에 대입하면 이렇게 나뉜다. 학생이 무엇을 했는지는 코드가 계산해서 확정한다. 그 값을 평가 응답에 반영한 뒤에야 서술 단계가 돈다. 서술 단계의 일은 이미 정해진 판정을 읽기 좋은 말로 쓰는 것이다. 판정을 뒤집을 권한은 없다.

서술 단계에 판정까지 맡기면 같은 학생이 리포트를 다시 뽑을 때마다 결론이 달라질 수 있다. 그래서 선을 그었다.

그렇다고 코드로 고정한 값이 안전한 것은 아니다. 위 `kind_counts`처럼 입력 기준(무엇을 정본으로 삼는가)이 틀리거나 계산 규칙이 현실과 어긋나면, 고정된 값은 틀린 채로 일관되게 나온다. LLM의 흔들림은 눈에 띄지만 코드의 오류는 조용하다. 확정한 값에는 별도 검증이 따라붙어야 한다.

## 아직 안 한 것

- 풀이 영상을 이미지 프레임으로 바꿔 분석하는 경로를 논의만 했다. 구현도 검증도 없다. 프레임을 몇 장 뽑을지, 이벤트를 어떻게 잡을지는 정하지 않았다.
- 초기 화면 복원이 틀렸을 때 공통 문제 정의가 얼마나 흔들리는지 재보지 않았다.
- 계산값이 틀렸을 때 서술 단계가 그것을 알아챌 방법이 지금은 없다. 알아채게 하는 것이 맞는지부터 정해야 한다. 서술이 재판정하지 못하게 막아 둔 설계와 부딪히기 때문이다.
