여러 활동 유형을 지원하는 새 평가 시스템을 구상하다가, AI가 내놓은 표 하나를 그대로 믿을 뻔했다. 그 표가 어디서 틀렸는지 적어 둔다.

## 표는 깔끔했다

기존 파이프라인은 이미 있었다. 이미지 분석, 활동 이력의 문장화, 평가, 리포트 생성 순서다. 코드와 문서를 따라가며 실제 실행 순서와 데이터 흐름부터 정리했다. 여기까지는 확인한 사실이다.

그다음 "활동 유형이 늘어나면 평가는 어떻게 붙이나"를 AI와 같이 구상했다. 돌아온 답이 표였다. 유형 A는 기존 루브릭의 이 항목, 유형 B는 저 항목에 연결하는 식이다. 표는 깔끔했고 바로 쓸 수 있어 보였다.

사용자가 이 표에서 멈춰 세웠다. 이 연결은 누가 검증한 것이냐는 질문이었다. 답은 아무도 없다였다. 표는 요구사항이 아니라 AI가 제안한 가설이었다. 내가 "정리됐다"고 받아들이는 순간 가설이 사양서처럼 굳을 참이었다. 그래서 해당 연동은 미정으로 되돌렸다.

## 유형 이름은 평가 목표가 아니다

표가 틀린 이유를 따져 보니 단순했다. 하나의 활동 안에 비교, 구성, 조작 같은 행동이 겹쳐 있다. 유형 이름을 붙이면 그중 하나만 대표로 남는다. 어떤 활동이 정말 "비교"를 평가하려는 것인지는 이름으로 정해지지 않는다. 전문가에게 조작적 정의(무엇이 관찰되면 그 능력이 있다고 볼지)와 경계 사례를 받아야 정해진다. 아직 받지 못했다.

## 로그에 없는 능력은 프롬프트로 못 만든다

더 근본적인 문제는 입력이었다. 학생 수행에서 관찰되는 것은 좌표 이동, 답칸 상태 같은 이벤트다. 평가하고 싶은 능력 중에는 설명의 논리성, 표현의 의미처럼 이벤트로는 보이지 않는 것이 있다. 프롬프트를 아무리 다듬어도 로그에 없는 정보는 나오지 않는다. 나오는 것처럼 보이면 모델이 지어낸 것이다.

기존 코드는 이 문제를 이미 의식하고 있었다. 판단 모델에게 물을 때 보기를 이렇게 구성한다.

```python
Q_MARK = "코드가 학생 기록에서 찾은 [표시]가 [오개념]대로 생각해서 생긴 흔적인지 고른다. [표시 구간]·[앞뒤 사건]·[답 칸 제출]에 있는 사실만 근거로 쓴다."
OPT_MARK = [
    ("오개념", "학생이 이 오개념대로 생각해 이 표시를 만들었다 — 표시가 오래 머물렀거나, 끝까지 남았거나, 답으로 냈다"),
    ("다른이유", "표시는 생겼지만 이 오개념의 흔적이 아니다 — 옮기는 도중 잠깐 생긴 상태, 아직 놓지 않은 조각, 문제를 바르게 풀려고 만든 상태"),
    ("판단불가", "사실이 모자라 가를 수 없다"),
]
```

표시를 찾는 일은 코드가 하고, 모델은 "이 표시가 그 오개념의 흔적인가"만 고른다. 질문에 "있는 사실만 근거로 쓴다"는 제약을 걸고, 보기에는 `판단불가`를 반드시 넣었다. 입력이 모자라면 모른다고 말할 출구를 열어 둔 것이다. 처음에는 이게 방어 코드 정도로 보였다. 지금 보면 "입력에 없는 능력은 평가하지 않는다"는 원칙을 코드로 옮긴 것이다.

출구는 선택지에만 있지 않다. 확률이 낮을 때도 판단불가로 떨어뜨린다.

```python
def pick(self, state, name, question, opts):
    """판단 모델에 한 번 묻는다. 가장 높은 확률이 UNSURE 아래면 판단불가로 둔다."""
    self.calls += 1
    try:
        _, resp = model_client.ask(state, {name: {"type": "choice", "instructions": question, "criteria": dict(opts)}}, "rule_tree",
                                   transport=lambda p: model_client.http_transport(p, timeout=120))
    except Exception as e:
        self.errors.append(f"{name}: {type(e).__name__}: {e}"[:200])
        return "판단불가", {}
    a = (resp.get("answers") or {}).get(name) or {}
    probs = {k: round(float(v), 3) for k, v in (a.get("probabilities") or {}).items()}
    top = a.get("choice") or (max(probs, key=probs.get) if probs else "판단불가")
    if top not in dict(opts) or (probs and probs.get(top, 1) < UNSURE and "판단불가" in dict(opts)):
        top = "판단불가"
    return top, probs
```

호출이 실패해도 예외를 던지지 않고 `판단불가`와 에러 기록을 남긴다. 보기에 없는 답이 와도, 확률이 `UNSURE`(기본 0.5, 환경변수로 조절) 아래여도 같은 곳으로 간다. 모델이 자신 없을 때 억지로 하나를 고르게 하지 않으려는 구조다. 0.5라는 임계값이 적절한지는 따로 재본 적이 없다. 설정 기본값일 뿐이다.

## 영상 경로는 아직 제안일 뿐이다

관찰 가능한 정보가 부족하면 영상에서 프레임을 뽑아 넣자는 안이 나왔다. 아이디어로는 자연스럽다. 하지만 구현하지 않았고 검증하지도 않았다. 화면 영상만으로 설명이나 사고 근거가 확보되는지는 다른 질문이다. 화면에 풀이가 보여도 왜 그렇게 했는지는 안 보일 수 있다. 이것도 직접 해 보기 전에는 모른다.

## 골드셋을 어떻게 만들었고, 왜 틀릴 수 있는가

그래서 우선 과제는 프롬프트가 아니라 전문가와 실제 사례를 같이 보며 라벨링하는 일이 됐다. 평가 기준과 골드셋(정답으로 취급하는 기준 데이터)을 같이 만드는 작업이다. 교사가 고친 이력은 검토를 거치면 골드셋 후보가 될 수 있다. 다만 교사 수정이 전부 정답은 아니라서 검토 단계는 필요하다.

기존 저장소에도 손으로 만든 기준표 채점기가 있다. 구조는 이렇다.

```python
# 기준표를 「보임이어야 함(Y) / 보이면 안 됨(N)」으로 옮긴 것
EXPECT = {
    "unit_a": {"case-01-p11": {"A-M05": "N"}, "case-11-p11": {"A-M05": "Y"}, ...},
    "unit_b": {f"case-{s}-p13": {"B-M04": "Y" if s == "03" else "N", "B-M06": "N"}
               for s in ("01", "02", "03", "05", "07", "10", "08", "11")},
    # ...
}


def score(unit, rule_dir):
    """규칙 고정본 하나로 기준표 기록을 판정해(AI 호출 0) 보임/아님을 맞댄다."""
    # ... 규칙을 불러 각 사례를 판정
    rows = []
    for c in cases:
        r = Judge(c, load_rule(o), store).run(leaf=False)
        exp = next(v for k, v in EXPECT[unit].items() if c.endswith(k))
        for m, want in exp.items():
            got = r["act"].get(m, "")
            rows.append({"case": c[-16:], "mis": m, "want": want,
                         "got": got, "ok": got.startswith("보임") == (want == "Y")})
    return rows
```

`leaf=False`로 모델 호출 없이 규칙만 판정해 기준표와 맞댄다. 코드가 계산하는 부분과 모델이 추론하는 부분을 갈라 둔 덕에 이 채점이 가능하다. 그리고 기준표 자체가 틀릴 수 있다는 흔적이 원본 주석에 남아 있다. 한 사례는 기준표를 만들 때 한쪽 색 화살표만 보고 놓쳐서 "보임"이 맞다고 나중에 고쳤다. 손으로 만든 골드셋도 오류가 섞인다. 전문가 라벨링이라고 다르다고 볼 이유가 없다.

여기서 판정이 보임/아님의 이진이라 단순 일치 개수를 세는 걸로 충분하다. 새 시스템의 점수가 순서 있는 등급이라면 이야기가 다르다. 한 단계 틀린 것과 세 단계 틀린 것을 같게 셀 수 없으니 가중 κ(순서 오차에 가중을 주는 일치도 지표)를 써야 한다. 명목형 분류라면 일반 κ가 맞다. 어떤 지표를 쓸지는 점수의 성격부터 정해야 나온다. 이 부분도 아직 정하지 못했다.

## 아직 남은 것

신규 평가 엔진과 영상 분석 경로는 기획 단계다. 구현 완료로 쓸 수 있는 건 없다. 위의 채점기가 실제로 몇 건을 맞혔는지는 이 글에서 인용할 만큼 정리한 값이 없어서 적지 않는다.

지금 가장 걸리는 건 전문가에게 가져갈 첫 질문이다. 겹치는 행동 중 무엇을 이 활동의 평가 대상으로 삼을지, 그 경계 사례 몇 개를 어떻게 고를지를 정해야 한다. 아직 못 정했다.
