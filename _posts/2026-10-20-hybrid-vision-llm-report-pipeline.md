기존 리포트 파이프라인을 인수받아 읽다가 가장 먼저 부딪힌 질문은 "이 리포트의 숫자는 누가 정하는가"였다. 비전 모델이 화면을 보고, LLM이 평가하고, 또 LLM이 문장을 쓴다. 단계마다 모델이 끼어 있으니 정답 여부 같은 숫자까지 모델이 말하는 구조일 거라고 짐작했다. 코드를 따라가 보니 아니었다.

이 글은 그 추적 노트다. 새로 만든 것이 아니라 이미 있는 시스템을 이해한 기록이다.

## 먼저 정정한 것: 비전 분석은 리포트 실행 안에 없다

처음에는 케이스 하나를 처리할 때 화면 이미지를 보는 단계가 같이 돈다고 생각했다. 틀렸다. 비전 전처리와 리포트 생성은 **별도 실행**이다.

비전 쪽이 하는 일은 "문제 정의"를 만드는 것이다. 입력은 두 장이다.

- 문제의 초기 화면
- 모범답안의 최종 화면

이 두 장으로 문제가 무엇을 묻는지(`task`, `intent`), 어떤 개념이 걸려 있는지(`concepts`), 어떤 오개념 규칙이 있는지(`misconceptionRules`), 문제 유형(`problemType`)과 정답(`answer`)을 뽑는다. 모델이 확신이 없는 부분은 `confidence`와 `uncertainNotes`로 따로 남긴다. 학생의 최종 화면은 이 정의가 만들어진 **뒤에**, 정의를 기준으로 판정된다.

두 장의 역할을 나눈 이유가 있다고 이해했다. 정답 화면을 문제 화면과 섞어 한 번에 보여주면, 모델이 정답의 배치를 "문제가 요구하는 조건"으로 읽어버릴 수 있다. 초기 화면은 문제를, 모범답안 화면은 정답을 — 입력 단계에서 역할을 분리해 두면 정답 배치가 문제 정의에 스며드는 것을 막는다. 여기에 화면 요소에 저장된 텍스트도 추출해 이미지와 함께 준다. 이미지만으로는 읽기 애매한 글자를 보완하기 위해서다.

## 캐시 키가 초기 장면이라는 것의 함정

문제 정의는 초기 장면의 fingerprint(장면 내용을 요약한 식별값)로 공유·캐시된다. 같은 문제를 푼 학생이 100명이면 정의는 한 번만 만들고 재사용한다. 합리적이다.

문제는 "초기 장면"을 어디서 복원하느냐다. 학생의 활동 기록은 프레임의 연속으로 저장되고, 첫 프레임을 초기 장면으로 쓴다. 이 복원이 학생의 조작에 오염되면 — 예컨대 첫 프레임이 이미 조작이 반영된 상태라면 — 같은 문제인데 fingerprint가 학생마다 갈라진다. 기준이 학생마다 달라지는 것이다. 이번 조사에서 이 위험을 확인했지만, 실제 데이터에서 얼마나 자주 일어나는지는 **아직 재보지 않았다.**

실제로 데이터를 파다가 만난 문제는 더 단순했다. 활동 기록이 압축 저장돼 있었는데, 문자열 접두사 때문에 압축 해제가 실패하고 있었다. 접두사 처리를 고치고 나서야 원본 화면 상태와 조작 이력이 보였다. 그리고 보이기 시작하자 분석 전에 걸러야 할 것들도 같이 보였다. 시험 삼아 넣은 데이터가 섞여 있었고, 기록이 빠진 케이스도 있었다. 건수는 세지 않았다.

## 케이스 하나가 지나가는 순서

코드를 따라가며 정리한 순서는 이렇다.

```
normalize → promptPiece → 코드 계산·입력 조립 → assess → applyCodeFacts → render-both → 저장
```

1. **normalize**: 기록을 정규화한다.
2. **promptPiece**: 조작 이력을 문장으로 바꾼다.
3. **코드 계산·입력 조립**: `solveOptimum`, `computeCorrectness` 같은 함수가 평가 입력을 만드는 도중에 돈다. 정답 여부와 최적해 같은 값은 여기서 이미 정해진다.
4. **assess**: LLM이 평가한다.
5. **applyCodeFacts**: 코드가 확정한 값을 평가 결과 위에 덮어쓴다.
6. **render-both**: 리포트 서술을 생성한다.
7. 저장.

내가 틀렸던 지점은 3번과 4번의 순서였다. 계산이 LLM 평가 뒤에 검산처럼 붙을 줄 알았는데, 실제로는 평가 **입력을 조립하는 도중**에 돈다. LLM은 이미 계산된 값을 받아 판단하고, 그 뒤에 5번에서 한 번 더 코드 값이 우선권을 갖는다. 같은 값에 코드가 앞뒤로 두 번 걸리는 셈이다. 모델이 정답 여부를 다르게 말해도 최종 결과에는 코드 값이 남는다.

다만 이 저장소에서 내가 직접 열어본 건 이 순서를 따라가기 위해 참고한 일부이고, `solveOptimum`·`computeCorrectness`·`applyCodeFacts` 본문의 세부 로직은 이 글에서 인용하지 않는다. 함수 이름과 호출 위치는 확인했으나 내부 계산 방식은 따로 정리가 필요하다.

## 코드가 확정하는 값, 모델이 추론하는 값

이 설계에서 가장 마음에 든 건 경계가 명시적이라는 점이다.

평가 단계에는 관찰 근거마다 ID를 붙여 준다. 모델이 "이 학생은 이런 오개념이 있다"고 판정하면, 그 판정이 어느 관찰에서 나왔는지 ID로 되짚을 수 있다. 서술 단계(`render-both`)에는 반대로 **재판정을 금지**한다. 문장을 쓰는 모델이 슬쩍 판정을 바꾸지 못하게 한다. 관찰·판정·서술이 서로의 일을 하지 않게 칸막이를 친 구조다.

같은 맥락에서 이번에 기록 안의 규칙 기반 판독 코드도 읽었다. 조건 종류별로 판독값을 내는 부분이다.

```python
def value(self, cond):
    t = cond["type"]
    if t == "group_shape_equals_group":
        start, gs = self.groups0()
        now = self.cells(self.f)
        a = [now[i] for i in gs[cond["group"] - 1] if i in now]
        return canon(a) == canon([start[i] for i in gs[cond["target"] - 1]])
    if t == "group_moved_count":
        start, gs = self.groups0()
        now = self.cells(self.f)
        return sum(1 for i in gs[cond["group"] - 1] if now.get(i) != start.get(i))
    if t == "support_counts":
        return list(on_supports(self.f, self.s["item"], self.s["support"], self.s["reach"])[0])
    # ... (items_left, items_created, stick_number, sticks_moved 생략)
    raise ValueError(t)
```

판독 **종류**는 범용이고, 어떤 교구를 어떤 값과 비교할지는 규칙 JSON이 정한다. 비교는 별도 함수가 연산자(`==`, `<=`, `in`, `pairs_equal` 등) 테이블로 처리한다.

```python
def ok(self, cond):
    v = self.value(cond)
    op, want = cond["op"], cond.get("value")
    return {"==": lambda: v == want, "<=": lambda: v is not None and v <= want, ">=": lambda: v is not None and v >= want,
            "in": lambda: v in want, "true": lambda: v is True,
            "pairs_equal": lambda: v is not None and all(v[a] == v[b] for a, b in want)}[op]()
```

`None`을 허용하는 연산자마다 `v is not None`을 따로 걸어둔 게 눈에 띈다. 숫자 판독이 실패했을 때(`stick_number`가 숫자 아닌 배치에서 `None`을 돌려준다) 비교가 예외 대신 거짓이 되게 하려는 것으로 읽었다. 판독 실패를 "오답"과 같은 값으로 취급해도 되는지는 별개 문제이고, 거기서 뭉개지는 정보가 있을 것 같다.

단계 판정은 규칙의 단계 목록을 순서대로 훑으며 `when` 조건이 전부 참인 마지막 단계를 현재 단계로 삼는 방식이다. 이 코드는 규칙 JSON을 외부에서 받는 실험용 프로브이고, 위 리포트 파이프라인 본체와 같은 코드는 아니다. 같은 철학, 즉 상태 판정을 모델이 아닌 코드에 맡기는 쪽의 예로 읽었다.

## 선개념·오개념: 어디까지 판정할 수 있나

선개념(학생이 이미 갖고 있는 개념)과 오개념의 **출처**를 구분하는 것도 이번에 정리한 부분이다. 오개념 규칙은 문제 정의 단계에서 비전 모델이 제안한다. 즉 규칙 자체가 모델의 추론이다. 화면 상태가 그 규칙에 맞는지는 코드로 확인할 수 있어도, 그 규칙이 정말 학생의 사고 오류를 가리키는지는 화면 기록만으로는 판정이 안 된다. 같은 배치를 만든 두 학생의 이유가 다를 수 있다. 이 한계는 리포트 문장에서 얼마나 조심스럽게 쓰이는지 다음에 확인해야 한다.

## 끝나지 않은 것

화면 녹화 영상을 입력으로 쓰는 별도 실험도 논의했다. 필요한 데이터가 무엇인지(프레임 샘플링 간격, 조작 이력과의 시간 정렬 등)까지만 이야기했고 구현도 검증도 하지 않았다. 지금 기록 기반 파이프라인이 이미 조작 이력을 문장으로 바꿔 주는데, 영상이 그 위에 무엇을 더 주는지 아직 모르겠다. 먼저 그걸 어떻게 재야 할지부터 정해야 한다.

초기 장면 오염 건도 남았다. fingerprint가 갈라지는 케이스가 실제 데이터에 얼마나 있는지, 시험 데이터와 누락 기록을 걸러낸 뒤에 세어볼 생각이다.
