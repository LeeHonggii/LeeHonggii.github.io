다른 언어로 만들어진 서비스의 목록 API를 FastAPI로 옮기는 일이었다. 요청 DTO(Data Transfer Object, 요청·응답 형태를 정의한 객체)를 그대로 가져오는 작업이라 금방 끝날 줄 알았다. 실제로는 이름 하나, 정렬 하나, 응답 필드 하나가 전부 호출자와 얽혀 있었다.

## offset은 offset이 아니었다

전달받은 계약에는 `offset`과 `limit`이 있었다. 이름만 보면 행 오프셋(건너뛸 행 수)이다. 그런데 계약대로라면 `offset`은 **1부터 시작하는 페이지 번호**였다. `offset=2&limit=30`은 "31번째 행부터"가 아니라 "2페이지, 30개씩"이라는 뜻이다.

이름이 헷갈려도 계약이 우선이라고 판단했다. 이미 호출하는 쪽이 그 의미로 값을 보내고 있을 것이기 때문이다. 내부에서만 변환했다.

```
skip = (offset - 1) * limit
```

SQL에는 `LIMIT :limit OFFSET :skip`으로 바인딩한다. 외부 이름은 계약을 따르고, 내부 변수 이름은 `skip`으로 달리해서 코드를 읽는 사람이 둘을 혼동하지 않게 했다. 이름을 바로잡는 건 호출자와 합의가 끝난 뒤의 일이라 이번에는 건드리지 않았다.

`limit`에는 기본값과 최댓값 검증을 넣었다. 응답은 전체 개수와 현재 페이지 목록을 분리했다.

```json
{"totalCount": 100, "list": [], "seed": 8231}
```

(`list`가 빈 배열인 건 형태만 보이려는 예시다.)

## 랜덤 정렬과 페이지네이션은 서로 모른다

이 목록은 랜덤 순서로 보여주는 API였다. 요청마다 `ORDER BY RAND()`를 실행하면 1페이지와 2페이지가 서로 다른 셔플 결과에서 잘린다. 1페이지에서 본 항목이 2페이지에 또 나오고, 어떤 항목은 어느 페이지에도 나오지 않을 수 있다. 제목 그대로의 현상이다.

그래서 서버가 `seed`를 정해 응답에 실어 보내고, 호출자가 다음 요청에서 그 값을 그대로 돌려주게 했다. MySQL의 `RAND(seed)`는 같은 seed로 같은 수열을 만든다.

```
ORDER BY RAND(seed)
?offset=2&limit=30&seed=8231
```

첫 요청에는 seed가 없으니 서버가 만들고, 이후 요청은 받은 seed를 쓴다. 상태를 서버에 두지 않고 호출자에게 맡기는 구조다.

## SQL로 확인한 것, 못 한 것

MySQL에서 직접 쿼리를 돌려서 세 가지를 봤다.

- 같은 seed로 두 번 실행하면 같은 순서가 나온다.
- 같은 seed의 1페이지와 2페이지 사이에 겹치는 항목이 없다.
- seed를 바꾸면 순서가 달라진다.

여기서 멈춘다. 이건 "그 시점의 그 데이터, 그 실행 계획에서" 확인한 결과다. 페이지를 넘기는 사이에 행이 추가·삭제되면 같은 seed여도 순서가 밀린다. 실행 계획이 바뀌었을 때 `RAND(seed)`가 행을 평가하는 순서가 그대로일지도 확인하지 않았다. 순서 안정성을 일반적으로 보장한다고 쓸 수는 없다.

## 앱 쪽 검증은 끝나지 않았다

직접 SQL 검증과 앱을 통한 검증은 다르다. 앱에서는 SQLAlchemy가 `limit`, `skip`, `seed`를 바인드 파라미터로 넘기고, 그 위에 HTTP 계층이 있다. 이 구간의 통합 검증은 대화가 끝난 시점까지 하지 못했다. 바인드된 `RAND(:seed)`가 리터럴 seed와 같은 수열을 내는지부터 확인해야 한다.

작업 중에 FastAPI 쿼리 모델에서 파라미터가 의도와 다르게 노출되는 문제도 하나 고쳤다.

## 응답에서 status를 빼면 생기는 일

이번 변경에는 응답의 `status` 필드 제거와 오류의 HTTP 상태 코드 전환도 포함됐다. 문서는 거기에 맞춰 고쳤다. 다만 호출자가 `status` 값으로 성공 여부를 판단하고 있었다면, 필드가 사라지는 순간 그 판정이 깨진다. 기본 `limit`을 바꾼 것도 마찬가지다. 값을 안 보내던 호출자는 갑자기 다른 개수를 받는다.

코드는 바꿨고 문서도 바꿨지만, 호출자와의 계약 합의는 아직 남아 있다. 지금 확인된 건 SQL 수준의 동작뿐이다. `offset`이 페이지 번호라는 해석과 `status` 제거를 호출자가 실제로 받아들이는지는 아직 모른다.
