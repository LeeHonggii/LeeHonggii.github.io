기존 LLM 평가 파이프라인을 코드와 문서로 거슬러 올라가며 읽고 있었다. 순서는 이미지 분석, 활동 이력 문장화, 평가, 리포트 생성이다. 그 과정에서 한 가지 질문에서 손이 멈췄다.

리포트에 "이 학생은 이 선개념이 부족하다", "이런 오개념이 보인다"라고 적혀 있다. 이 개념 목록은 어디서 온 걸까?

## 목록은 어디서 오는가

따라가 보니 구조는 단순했다. 교사가 개념을 입력하면 그 값을 쓴다. 입력이 없으면 모델이 문제를 보고 직접 만든다. 프롬프트가 요구하는 출력 형태는 대략 이렇다.

```json
{
  "concepts": {
    "pre":  ["이 문제를 풀기 전에 이미 알고 있어야 하는 개념"],
    "core": ["이 문제로 익히게 하려는 개념"],
    "post": ["이걸 익히면 다음에 배우게 되는 개념"]
  },
  "misconceptionRules": [
    { "observation": "학생이 이렇게 하면", "gap": "이것이 부족한 것으로 본다" }
  ]
}
```

내가 읽은 범위에서는 이 값이 어딘가의 교육과정 데이터베이스와 대조되는 단계를 찾지 못했다. 목록에 있는 개념이 실제 교육과정에 있는지 검증하는 코드도 없었다. 모델이 사전학습으로 알고 있는 지식이 곧 출처다. "확인되지 않았다"는 건 "없다"와 다르다. 내가 못 찾았을 수도 있다. 다만 못 찾았다는 사실 자체가 중요했다. 리포트를 읽는 사람은 그 목록을 교육과정 기준처럼 받아들일 수 있기 때문이다.

문제는 이 출력이 그럴듯하다는 점이다. 선개념, 본개념, 후개념이라는 3단 구조는 교육적으로 자연스러워 보인다. 자연스러워 보이는 것과 검증된 것은 다르다.

## 목록을 정하는 일, 이해했는지 판단하는 일

처음엔 이렇게 생각했다. 교사가 개념 이름을 직접 입력하게 하면 해결되지 않을까.

반만 맞았다. 목록의 출처는 분명해진다. 하지만 "학생이 그 개념을 이해했는가"는 여전히 비어 있다. 입력으로 관찰되는 건 학생의 행동이다. 어디를 눌렀고, 무엇을 옮겼고, 어떤 답을 냈는지다. 평가하려는 건 능력이다. 개념 이름과 행동 사이에는 연결 기준이 따로 필요하다. 이름만 교사가 정해 주면 이 공백은 그대로 남는다.

`misconceptionRules`가 바로 그 연결 자리다. 스키마를 다시 보면 `observation`(관찰 행동)과 `gap`(그래서 부족하다고 본다)을 이어 붙인 한 줄짜리 가설이다. 행동이 규칙과 일치해도 "그 해석이 교육적으로 맞는가"는 별개의 질문이다. 규칙은 일치 여부를 확인하는 장치다. 규칙 자체가 타당한지 검증해 주지는 않는다.

## 코드가 사실을 정하고, 모델은 갈림길에서만

저장소에는 오개념 규칙이 걸린 뒤 판정하는 부분이 있었다. 이쪽은 역할 분리가 꽤 신경 써서 되어 있었다. 코드가 학생 기록에서 표시를 찾고, 그 표시가 정말 오개념의 흔적인지 애매한 경우에만 모델에게 보기 중 하나를 고르게 한다.

```python
Q_MARK = ("코드가 학생 기록에서 찾은 [표시]가 [오개념]대로 생각해서 생긴 흔적인지 고른다. "
          "[표시 구간]·[앞뒤 사건]·[답 칸 제출]에 있는 사실만 근거로 쓴다.")
OPT_MARK = [
    ("오개념",   "학생이 이 오개념대로 생각해 이 표시를 만들었다 — 표시가 오래 머물렀거나, 끝까지 남았거나, 답으로 냈다"),
    ("다른이유", "표시는 생겼지만 이 오개념의 흔적이 아니다 — 옮기는 도중 잠깐 생긴 상태, "
                "아직 놓지 않은 조각, 문제를 바르게 풀려고 만든 상태"),
    ("판단불가", "사실이 모자라 가를 수 없다"),
]
```

보기 세 개 중 `다른이유`와 `판단불가`가 눈에 들어왔다. 표시가 있다고 오개념이 되는 게 아니다. 옮기는 도중에 잠깐 생긴 상태일 수도 있고, 바르게 풀려고 만든 중간 상태일 수도 있다. 질문 자체가 "[표시 구간]·[앞뒤 사건]·[답 칸 제출]에 있는 사실만 근거로 쓴다"로 묶여 있어서, 모델이 사전지식으로 사정을 그럴듯하게 채워 넣는 길을 막아 둔다. 판단 근거의 출처를 입력된 사실로 한정하는 장치다.

그리고 모델이 모른다고 말할 수 있는 길을 열어 둔 것이 `판단불가`다.

```python
def pick(self, state, name, question, opts):
    """한 번 묻는다. 가장 높은 확률이 UNSURE 아래면 판단불가로 둔다."""
    self.calls += 1
    try:
        _, resp = judge_client.ask(state, {name: {"type": "choice",
                                                  "instructions": question,
                                                  "criteria": dict(opts)}}, "rule_tree",
                                   transport=lambda p: judge_client.http_transport(p, timeout=120))
    except Exception as e:
        self.errors.append(f"{name}: {type(e).__name__}: {e}"[:200])
        return "판단불가", {}
    a = (resp.get("answers") or {}).get(name) or {}
    probs = {k: round(float(v), 3) for k, v in (a.get("probabilities") or {}).items()}
    # ... usage 누적 생략
    top = a.get("choice") or (max(probs, key=probs.get) if probs else "판단불가")
    if top not in dict(opts) or (probs and probs.get(top, 1) < UNSURE and "판단불가" in dict(opts)):
        top = "판단불가"
    return top, probs
```

여기서 마음에 든 건 실패 처리의 방향이다. 호출이 예외로 끝나도, 모델이 보기에 없는 답을 내도, 최고 확률이 `UNSURE` 미만이어도 전부 `판단불가`로 떨어진다. 오류를 "다른이유" 같은 그럴듯한 값으로 메우지 않는다. 에러 메시지는 따로 모은다. 모르는 것이 정답처럼 보이는 값으로 둔갑하지 않게 하는 구조다.

한계도 적어 둔다. `UNSURE`의 기본값은 0.5인데, 이 값을 어떤 데이터로 맞췄는지는 내가 읽은 범위에서 확인하지 못했다. 모델이 내는 확률이 보정(calibration, 낸 확률이 실제 적중률과 맞는 정도)되어 있다는 근거도 못 찾았다. 임계값이 있다는 것과 그 임계값이 검증됐다는 것은 별개다. 로컬 모델 쪽 `LocalPicker`는 같은 질문을 여러 번 물어 고른 비율을 확률로 쓴다. 표본 3번의 비율은 확률이라기보다 투표 결과에 가깝다.

## 기준표도 사람이 옮긴 것이다

이 판정이 맞는지는 `기준표`와 대조해서 본다. 채점 스크립트에는 기준표 내용을 "보임이어야 함(Y) / 보이면 안 됨(N)"으로 옮긴 기대값이 하드코딩되어 있다. 규칙 고정본을 AI 호출 없이 돌려 보고, 기대값과 맞는지 센다. 아래는 식별자를 일반화해서 줄인 것이다.

```python
# 기준표를 「보임이어야 함(Y) / 보이면 안 됨(N)」으로 옮긴 것
# 한 칸은 기준표 작성 때 한쪽 색만 보고 놓친 것을 나중에 바로잡았다 (주석에 이유를 남김)
EXPECT = {
    "unit_a": {"case_01": {"M05": "N"}, "case_02": {"M05": "N"}, "case_11": {"M05": "Y"},
               "case_01_p12": {"M04": "Y", "M06": "N"}, },
    "unit_b": {f"case_{s}": {"M04": "Y" if s == "03" else "N", "M06": "N"}
               for s in ("01", "02", "03", "05", "07")},
    # ...
}

def score(unit, rule_dir):
    """규칙 고정본 하나로 기준표 기록을 판정해(리프 없이, AI 호출 0) 보임/아님을 맞댄다."""
    # ... 환경 변수 설정과 모듈 재적재 생략
    rows = []
    for c in T.S.CASES:
        r = T.Judge(c, T.load_rule(order), store).run(leaf=False)
        exp = next(v for k, v in EXPECT[unit].items() if c.endswith(k))
        for m, want in exp.items():
            got = r["act"].get(m, "")
            rows.append({"case": c[-16:], "mis": m, "want": want, "got": got,
                         "ok": got.startswith("보임") == (want == "Y")})
    return rows
```

`leaf=False`, 즉 AI 호출 0이라는 점이 중요하다. 규칙이 사실을 제대로 잡는지를 모델 변동 없이 따로 잰다. 모델이 끼는 판정은 이 숫자에 섞지 않는다.

한편 `EXPECT` 위의 주석이 이 글 주제와 정확히 맞닿아 있다. 기준표를 만들 때 파란 화살표만 보고 빨간 화살표의 빈 점을 놓쳐서, 학생 한 명의 기대값을 나중에 `N`에서 `Y`로 고쳤다. 사람이 만든 기준표도 틀린다. 틀렸을 때 그 사실이 코드 옆에 남아 있다는 게 다행이었다. 기준표가 정답이라고 믿고 모델 판정을 "오답"으로 셌다면 이 오류는 모델 탓으로 기록됐을 것이다.

그리고 이 기준표는 한 사람이 눈으로 본 기록을 옮긴 것이다. 여러 전문가가 독립적으로 라벨을 달고 일치도를 잰 골드셋은 아니다. 채점 결과로 "기준표 일치 몇 건 중 몇 건"이 출력되지만, 이 글에 쓸 수 있는 실행 결과 수치는 갖고 있지 않아 적지 않는다. 있더라도 그건 "코드가 기준표를 얼마나 재현하느냐"이지 "기준표가 교육적으로 맞느냐"가 아니다.

## 출처를 남기는 쪽으로

세 갈래 출처가 섞이고 있었다. 교사가 준 기준, 비전 모델이 이미지에서 만든 기준, 그 위에 모델이 한 번 더 추론한 것. 지금 구조에서는 최종 리포트로 올라가면 셋 다 같은 문장 모양이 된다. 새 평가 시스템을 구상하면서 정한 건, 각 값에 어디서 왔는지를 붙여 끝까지 들고 가는 것이다. 코드로 확정한 판정이라도 그 코드에 연결된 평가 기준이 타당한지는 보장하지 않는다. 그래서 "코드가 확정"과 "기준이 검증됨"을 서로 다른 필드로 둬야 한다.

여러 활동 유형을 지원하는 신규 평가 엔진과 영상 분석 경로는 아직 기획 단계다. 구현한 게 아니다. 여기까지는 읽고 정리한 것이고, 만든 것은 없다.

남은 건 전문가 기준이다. 선개념·오개념 목록을 누가 어떤 절차로 확정할지, 골드셋을 몇 명이 어떤 형식으로 달지 아직 정하지 못했다. 그 전까지 모델이 만든 오개념 규칙은 가설이라고 표시해 두는 게 맞는 것 같은데, 표시를 단 가설이 리포트에서 얼마나 무겁게 읽힐지는 아직 모른다.
