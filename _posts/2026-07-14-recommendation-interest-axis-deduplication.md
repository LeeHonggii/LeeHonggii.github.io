추천 결과 상위 10개가 전부 같은 얼굴이었다.

처음엔 후보 풀이 좁은 줄 알았다. 회사별로 콘텐츠 수가 다르니까, 특정 회사에서 그런 쏠림이 있을 수 있다고 생각했다. 그런데 큰 회사에서도 똑같이 나왔다. 후보는 수천 건인데 상위 10개가 다 "데이터 분석 · 파이썬 · 실무 튜토리얼" 이었다.

## 축을 세 개로 나눈 게 문제였다

우리 추천은 네 갈래로 나간다. 직무(job), 관심(career), 선호(company), 그리고 이 셋을 CombSUM/MNZ로 합친 best. 스키마에도 그대로 박혀있다.

```python
"axes": {
    "job": [_ITEM_EXAMPLE],
    "career": [_ITEM_EXAMPLE],
    "company": [_ITEM_EXAMPLE],
    "best": [_BEST_EXAMPLE],
},
```

축을 나눈 이유는 명확했다. 사용자에게 "왜 이 콘텐츠가 추천됐는지" 갈래별로 보여주고 싶었다. UI에서도 축별로 슬라이드가 나뉜다. best는 세 축의 순위를 랭크 기반으로 합쳐 종합 상위를 뽑는다.

문제는 여기서 시작됐다. 세 축이 서로 다른 "관점"이라고 믿고 설계했는데, 실제로 계산해보면 셋 다 같은 신호를 다시 세고 있었다.

사용자가 "IT·개발·데이터" 직무에 관심 주제로 "데이터 분석"을 골랐다고 하자. 그러면 직무축이 데이터 콘텐츠를 밀어올린다. 관심축도 데이터 콘텐츠를 밀어올린다. 선호축은 학습 이력에서 유사도를 뽑는데, 이 사용자의 이력도 이미 데이터 쪽이다. 세 축이 전부 같은 방향을 가리킨다.

랭크 합산이라 값의 스케일 문제는 없다. 그런데도 상위가 쏠린다. 세 축에서 모두 1~5위에 든 콘텐츠는 best에서도 1위가 될 수밖에 없기 때문이다. 다양성이 사라진 게 아니라, 애초에 다양성이 만들어지지 않고 있었다.

## "축은 나눴는데 관점은 안 나눠졌다"

이걸 깨달은 순간이 있었다. 로그를 보다가, 특정 사용자의 세 축 상위 10개가 8개나 겹치는 걸 봤다. 겹칠 수 있다. 그런데 8개는 이상하다. 그렇다면 축을 세 개로 나눈 의미가 뭐지?

축을 나눈다는 건 서로 다른 정보를 본다는 거다. 그런데 지금 구조는:
- 직무축 = f(직무 라벨, 콘텐츠 키워드)
- 관심축 = f(관심 주제 라벨, 콘텐츠 키워드)
- 선호축 = f(이력 콘텐츠 키워드, 후보 콘텐츠 키워드)

세 함수의 입력이 다르지만, 결국 다들 "콘텐츠 키워드"라는 같은 축에 사영된다. 사용자가 이미 가진/좋아하는 키워드 집합을 세 번 재구성해서 세 번 세고 있는 것.

## 시드 키워드를 빼면 무엇이 남는가

관심축을 다시 정의하기로 했다. 관심축은 "사용자가 아직 안 본 관점"을 보여주는 축이어야 한다. 그러려면 사용자가 이미 가진 키워드는 빼고 계산해야 한다.

말은 쉬운데, 어디서 빼야 하는가가 애매했다. 후보 콘텐츠의 키워드에서 빼면 후보 자체가 사라진다. 시드(이력) 쪽에서 빼면 시드가 비어버리는 사용자가 생긴다.

결국 이렇게 정리했다. 관심축의 시드는 "이력에서 등장한 키워드 집합"이 아니라, "이력 콘텐츠와 유사하지만 사용자가 아직 안 본 키워드"로 재구성한다. 즉 이력 → 유사 콘텐츠 확장 → 그중 사용자가 안 본 것들의 키워드 → 이걸 시드로 삼는다.

직무축과 선호축은 안 건드렸다. 그건 원래 "이미 가진 것 기반"이 맞다. 관심축만 성격을 바꿨다.

## 재보지 않은 것

이 변경이 실제로 다양성을 얼마나 늘렸는지는 아직 정량으로 확인하지 못했다. Hit@10, MRR 같은 오프라인 지표는 이 변경에 대해 오히려 나빠질 수 있다 — "정답"이 결국 사용자가 이미 좋아하는 것 근처인 벤치마크에서, 안 본 관점을 밀어올리면 정답에서 멀어지기 때문이다.

그래서 정량 지표만으로는 판단이 안 서고, 정성 리뷰가 필요하다. 상위 10개 중 얼마나 관점이 갈리는지, 사용자별로 눈으로 보고 판단해야 한다. 이 부분은 아직 데이터를 모으는 중이다.

## 아직 안 푼 것

선호축(company)이 남았다. 이 축은 같은 회사 안에서 다른 사용자들의 이력 패턴을 본다. 그런데 같은 회사 사람들은 대체로 비슷한 콘텐츠를 듣는다. 그래서 이 축도 결국 "많이 들은 것"으로 수렴한다. 관심축을 고친 방식이 여기에도 통할지, 아니면 회사 축은 다른 접근이 필요할지 모르겠다.

축을 나눴다고 관점이 나뉜 게 아니라는 것. 이걸 처음부터 알았다면 축 설계를 다르게 시작했을 것 같다. 지금은 이미 API 스키마가 네 갈래로 굳어있어서, 뒤에서 각 축의 정의만 조용히 바꿔가는 중이다.
