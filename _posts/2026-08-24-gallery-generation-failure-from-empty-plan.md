갤러리 생성이 계속 실패했다. 로그에는 이미지를 못 찾았다는 메시지가 남았고, 처음엔 이미지 검색 API 쪽을 의심했다. 외부 서비스 응답이 바뀌었거나, 쿼리 포맷이 어긋났거나.

그런데 로그를 더 파고들수록 이상했다. 이미지 검색 API 호출 자체가 없었다. 실패한 게 아니라 시도를 안 한 것이었다.

---

일단 500 에러부터 잡아야 했다. 실패한 생성 작업의 상태를 조회하는 API가 응답을 못 내고 있었는데, 원인이 황당했다. 작업이 실패하면 에러 메시지를 DB JSON 필드에 평문으로 저장하는데, 상태 조회 쪽에서 그 필드를 무조건 `json.loads` 로 역직렬화하려 했다. 평문 문자열이 들어오면 당연히 `JSONDecodeError`. 생성 실패가 조회 실패를 연쇄로 일으키는 구조였다.

이건 고쳤다. 그래도 생성 실패 자체는 여전했다.

---

다음으로 추론(inference) 호출이 아예 안 된다는 걸 확인했다. OpenAI API 키 자체는 유효했다. 만료된 키가 아니었다. 크레딧이 소진된 상태였다. 키가 살아있어도 크레딧이 없으면 추론 호출은 전부 실패한다. 하드코딩된 API 키가 코드베이스 곳곳에 19곳 박혀 있었고, 이걸 환경변수로 일괄 교체했다.

이제 추론은 됐다. 그래도 갤러리 생성은 여전히 빈 결과를 냈다.

---

여기서 다시 처음 질문으로 돌아왔다. 이미지 검색이 왜 호출 안 됐는가.

코드를 따라가 보면, 갤러리를 만드는 루틴은 대략 이렇게 돌았다. LLM에게 입력 문서를 주면 plan이 생성되고, plan 안의 `subheadings` 배열을 순회하면서 각 소제목마다 이미지를 검색하는 구조였다.

```
for sub in self.subheadings:
    # 각 소제목으로 이미지 검색
```

`subheadings`가 비어 있으면 루프는 0번 실행된다. 이미지 검색이 한 번도 안 되는 건 당연한 결과였다. 문제는 왜 `subheadings`가 빈 배열이었냐는 것이다.

plan이 제대로 생성되지 않았다. LLM에 넘긴 입력 문서 자체가 부실했고, 추론이 소제목을 뽑아낼 만한 내용이 없었다. 결과는 `list_of_subheadings = []`.

---

그런데 이미 이 사실을 알고 있는 게 있었다. LLM 자신이었다.

plan 생성 단계에서 LLM은 `input_document_check`와 `input_user_requests_check`라는 플래그를 응답에 포함하고 있었다. 입력 문서가 충분한지, 사용자 요청이 처리 가능한 수준인지를 LLM이 스스로 판단해서 `True` / `False` 로 돌려주는 방식이었다. 이번 케이스에서 두 플래그 모두 `False`였다.

```
input_document_check = False
input_user_requests_check = False
```

백엔드는 이 값을 DB에 저장했다. 저장만 하고, 읽지 않았다. 플래그가 `False`여도 다음 단계로 그냥 넘어갔다. 이미지를 찾으러 가는 척 했지만, 찾으러 갈 소제목 목록 자체가 없었다.

---

결국 실패 경로는 이랬다.

입력이 부실 → LLM이 입력 품질 검증 실패로 판단 → plan에 소제목 없음 → 이미지 검색 루프 0회 실행 → `found_images`가 채워지지 않음 → 갤러리 생성 실패

이미지 검색 API는 처음부터 문제가 없었다.

---

수정 방향은 명확하다. `input_document_check` 또는 `input_user_requests_check` 가 `False`면 이후 단계를 중단하고 사용자에게 입력 보완을 요청해야 한다. 저장해둔 플래그를 실제로 소비하는 코드가 필요하다.

다만 아직 확인이 필요한 부분이 있다. 두 플래그를 LLM이 얼마나 정확하게 판단하는지다. 입력이 충분한데도 `False`를 돌려주거나, 반대로 빈 문서를 `True`로 통과시키는 케이스가 얼마나 되는지 아직 재보지 않았다. 플래그를 강제 게이트로 쓰기 전에 이 정확도를 먼저 측정해야 한다.
