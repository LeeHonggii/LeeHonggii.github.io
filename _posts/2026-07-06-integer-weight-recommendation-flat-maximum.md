## "왜 0.62냐"

리뷰 자리에서 그 질문을 받았을 때 잠깐 멍했다. `0.62`, `0.21`, `0.11`. 오프라인 지표를 기준으로 그리드 서치를 돌려서 나온 값이었고, 나는 그걸 그대로 배포했다. 근거를 대라면 "그리드 서치가 그렇게 뽑았다"밖에 없었다.

그게 답이 안 된다는 건 물어본 사람도 알고 나도 알았다. 그리드 서치가 왜 하필 그 조합에서 최댓값을 냈는지, 옆에 있던 `0.60 / 0.22 / 0.11` 조합은 얼마나 나빴는지, 나는 설명할 수 없었다.

## 흔들어봤더니

궁금해서 가중치를 조금씩 흔들어봤다. 상위 K개 추천 순서가 얼마나 바뀌는지 보려고.

거의 안 바뀌었다.

`0.62 / 0.21 / 0.11` 을 `6/9, 2/9, 1/9` (≈ `0.667 / 0.222 / 0.111`) 로 바꿔도 상위권 순서는 사실상 동일했다. 두 번째 자리 소수점을 지우고 정수비로 바꿔도 결과가 같다는 뜻이다.

처음엔 실험 설정을 의심했다. 후보 풀이 너무 좁아서 그런가, 점수 스케일이 이미 뭉쳐 있어서 그런가. 그런데 여러 tenant, 여러 사용자군에서 반복해도 결과는 비슷했다.

## Flat maximum

찾아보니 이건 이름이 있는 현상이었다. **Flat maximum** — 선형 결합(linear combination) 모델에서 가중치를 어느 정도 범위 안에서 흔들어도 목적함수 값이 거의 변하지 않는 구간이 넓게 퍼져 있다는 관찰. Dawes & Corrigan (1974) 이 사람 판단 모델을 비교하면서 지적한 게 유명하다.

요지는 이렇다. 선형 결합 모델의 예측력은 **각 신호의 서열 구조** 에서 대부분 온다. 가중치의 소수점 두 자리를 정밀하게 맞추는 데서 오는 이득은 생각보다 작다. "A가 B보다 중요하고, B가 C보다 중요하다"만 맞으면, `0.62/0.21/0.11` 이든 `6/2/1` 이든 나오는 순서는 비슷하다.

내가 그리드 서치로 찾아낸 `0.62` 는 최적점이 아니라 **평탄한 봉우리 위의 아무 점** 이었던 셈이다.

## 정수비로 바꿨다

바꾼 뒤 감각이 완전히 달라졌다.

`6:2:1` 은 소리 내어 읽을 수 있다. "주축이 6, 보조 2, 약한 신호 1." 리뷰에서 누가 물으면 "이 축이 6배 무겁게 들어간다" 라고 답하면 된다. `0.62` 는 그렇게 못 한다.

운영도 편해졌다. 보조 축을 조금 더 태우고 싶으면 `6:3:1` 로 밀어보면 된다. 소수점 시절엔 하나를 건드리면 나머지 두 개를 정규화하느라 계산기를 꺼내야 했다. 사실 `raw_weight / sum(raw_weights)` 한 줄이지만, 리뷰에서 "이 0.21 이 왜 0.23 이 됐지?" 라는 질문이 나오는 순간부터 피곤해진다.

## 그런데 서비스는 정수비만 있는 게 아니다

이 이야기의 결말이 "다 정수비로 통일했다" 는 아니다. 실제 서비스 코드는 훨씬 지저분하다. 축이 하나가 아니라 여러 개고, 축마다 성격이 다르다.

우리 서비스는 사용자 한 명에게 **네 갈래(job, career, company, best)** 로 추천을 나눠 보낸다.

```python
_RECO_EXAMPLE = {
    "tenant_id": "tenant_a",
    "user_id": "user-001",
    "mode": "preeval+history",
    "axes": {
        "job": [_ITEM_EXAMPLE],
        "career": [_ITEM_EXAMPLE],
        "company": [_ITEM_EXAMPLE],
        "best": [_BEST_EXAMPLE],
    },
    "diagnostics": {
        "preeval_applied": True, "history_input": 5, "history_matched": 5,
        "fallback_axes": [], "warnings": [],
    },
}
```

앞의 세 축은 각자 자기 기준으로 점수를 낸다. 여기까지는 축 내부에서 "인기도 : 적합도 : 최신성" 같은 재료를 섞는 문제고, 이 자리에서 `6:2:1` 같은 정수비를 쓰기 시작한 것이다. "무엇이 얼마나 중요한가"에 이름을 붙일 수 있는 자리.

그런데 마지막 `best` 축은 성격이 다르다. 세 축의 결과를 다시 합쳐서 "종합 상위" 를 뽑는 자리다. 여기서 세 축을 또 `?:?:?` 정수비로 섞기 시작하면, 아까 리뷰에서 받은 질문이 그대로 돌아온다. **"왜 job 이 career 보다 2배 무겁죠?"**

## Best 축에서는 RRF 로 도망갔다

그래서 best 는 가중치 논쟁을 피하는 방법을 골랐다. 순위 기반 결합, 그 중에서도 CombSUM/MNZ 와 RRF (Reciprocal Rank Fusion).

```python
_BEST_EXAMPLE = {
    # ... 콘텐츠 메타 ...
    "rank": 1,
    "best_score": 1.0,
    "rrf_score": 1.0,
    "axis_ranks": {"job": 1, "career": 1, "company": 1, "next": 1},
    "reasons": ["종합 상위"],
}
```

RRF 는 각 축에서 어떤 아이템의 **순위** 만 보고 `1 / (k + rank)` 로 점수를 매겨 더한다. 축들의 점수 스케일이 서로 달라도 상관없고, 축 하나가 극단적으로 큰 값을 뱉어도 다른 축을 짓누르지 않는다. 무엇보다, 축 간 가중치를 명시적으로 정하지 않아도 된다.

이게 flat maximum 논의랑 붙는 지점이 있다. 축 내부에서는 "이 신호가 저 신호보다 몇 배 중요한지" 를 사람이 말할 수 있으니 정수비로 쓴다. 축 사이에서는 그 정당화가 훨씬 약하니, 아예 가중치를 끄고 순위만 본다. **어디에서 가중치를 세게 잡고 어디에서 놓아버리는지가 지금 내가 신경 쓰는 지점이다.**

`axis_ranks` 를 응답에 같이 실어두는 것도 이 맥락이다. "이 아이템이 best 에 뜬 건 job=1 career=1 company=1 이라서요" 를 리뷰 자리에서 바로 짚을 수 있다. `0.62` 를 설명하지 못했던 시절의 반작용이다.

## 남은 것

정수비로 바꾸고 나서 사실 성능 지표는 크게 안 움직였다. 그게 flat maximum 이 말하는 그대로다 — 원래 안 움직였을 자리였다.

바뀐 건 대화의 결이다. 리뷰에서 "왜 이렇게 무겁게 뒀냐" 를 답할 수 있게 됐고, 다음 이터레이션에서 어디를 밀어볼지 손가락으로 짚을 수 있게 됐다.

아직 안 정리된 것도 있다. 축 내부에서도 정말로 "6배 중요" 라고 말할 근거가 있는지, 아니면 그것도 그냥 내가 붙인 이야기인지, 사용자 세그먼트별로 이 서열이 뒤집히는 구간이 있는지. RRF 의 `k` 값은 왜 지금 값을 쓰고 있는지도 다시 볼 차례다. 이건 그리드 서치로 도망갈 문제가 아니라, 축을 하나씩 열어서 다시 물어야 하는 문제다.
