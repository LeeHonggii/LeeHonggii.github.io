증상은 단순했다. 채팅에 긴 명령을 코드 블록으로 보여 주는 칸이 있다. 그 명령을 펼치면 중간부터 글자 모양이 바뀐다. 코드 폰트였던 줄이 갑자기 일반 본문 폰트가 되고, 어떤 줄은 굵게, 어떤 줄은 제목처럼 커진다. 명령이 중간에 끊긴 게 아니다. 내용은 다 있는데 **절반만 코드 블록 안에 있고 나머지는 채팅 본문으로 풀려 나온다.**

처음엔 길이 문제인 줄 알았다. "긴 명령"에서만 생겼으니까. 길이 제한이나 접기/펼치기 상태 버그를 의심했다. 그런데 짧은 명령도 특정 내용이면 똑같이 깨졌다. 공통점은 길이가 아니라 **명령 안에 Markdown 코드 울타리가 들어 있다는 것**이었다. 예를 들어 이런 명령이다.

````markdown
```
echo "다음 내용을 파일에 저장"
cat > README.md <<'EOF'
```python
print("hello")
```
EOF
```
````

바깥 울타리(fence, 코드 블록의 시작·끝을 표시하는 백틱 줄)는 백틱 3개다. 안쪽 내용에도 백틱 3개짜리 줄이 있다. Markdown 파서는 안쪽의 첫 ``` 를 "바깥 블록을 닫는 줄"로 읽는다. 그 뒤부터는 일반 본문이다. 그러다 다음 ``` 가 나오면 이번엔 새 코드 블록이 열린다. 그래서 코드와 본문이 번갈아 뒤집힌다. 화면에서 본 증상이 정확히 이 모양이었다.

## 규칙은 이미 있었다

CommonMark 규칙을 다시 읽었다. 닫는 울타리는 **여는 울타리와 같은 문자이고, 길이가 같거나 더 길어야** 한다. 반대로 말하면 안쪽에 백틱 3개가 나와도 바깥이 4개면 닫히지 않는다.

````markdown
`````
```python
print("hello")
```
`````
````

해법은 Markdown 쪽에 이미 있었다. 고칠 것은 우리가 명령을 감싸는 쪽이었다. 울타리를 항상 3개로 하드코딩해서 감싸고 있었다.

## 고친 방향

내용 안에 연속된 백틱이 최대 몇 개까지 나오는지 센다. 바깥 울타리는 그보다 하나 더 길게, 단 최소 3개로 잡는다. 이 계산을 한 곳에 모아 공통 함수로 만들고, 코드 블록으로 감싸는 곳이 모두 그 함수를 쓰게 바꿨다.

여기서 이 글에 실제 소스를 싣지 않는 이유를 밝혀 둔다. 이 글을 쓸 때 내가 가진 자료에는 그 함수의 실제 코드가 없었다. 구조를 기억에 의존해 다시 써서 "이게 원본"이라고 내놓고 싶지 않았다. 위 설명이 판단의 전부다.

감싸는 곳이 여러 군데라는 점이 중요했다. 화면에 그리는 경로만 고치면 끝나지 않았다.

- **복사**: 코드 블록을 복사할 때도 Markdown으로 다시 감싸서 내보내는 경로가 있었다. 여기가 3개 고정이면 화면은 멀쩡한데 붙여넣은 결과가 깨진다.
- **제목 비교**: 블록의 제목(첫 줄 등)을 비교하는 처리도 울타리 형태를 가정하고 있었다. 울타리 길이가 가변이 되면 그 가정이 틀어진다.

한 곳만 고쳤다면 "고쳤는데 복사하면 또 깨진다"를 나중에 만났을 것이다. 공통 함수로 뽑은 이유가 이거다. 울타리를 정하는 코드가 두 곳에 있으면 언젠가 하나만 고쳐진다.

## 확인한 것, 못 한 것

단위 테스트와 회귀 테스트를 추가했고, `cargo check --release` 로 컴파일이 통과하는 것까지 봤다. 테스트에는 안쪽에 ``` 가 있는 경우, ```` 가 있는 경우, 백틱이 없는 경우를 넣었다.

하지만 **실제 화면에서 처음 본 그 증상이 사라졌는지는 그때 확인하지 못했다.** 테스트는 "감싸는 함수가 맞는 문자열을 만든다"까지만 보증한다. 화면에 그리는 파서가 그 문자열을 어떻게 읽는지, 펼침 상태에서 다른 경로를 타는지는 따로 눈으로 봐야 한다. 빌드한 앱에서 위의 예제 명령을 실제로 펼쳐 보는 일이 아직 남아 있다.

## 남은 의심

울타리 길이를 늘리는 방식은 내용이 어떤 백틱 묶음을 갖고 있든 동작한다. 다만 **틸데(`~~~`) 울타리나 들여쓰기 코드 블록이 섞인 내용**은 내가 따로 시험하지 않았다. 백틱 길이만 세는 함수라면 거기엔 영향이 없을 것 같지만, "없을 것 같다"는 확인이 아니다. 다음에 화면을 볼 때 이것도 같이 넣어 볼 생각이다.
