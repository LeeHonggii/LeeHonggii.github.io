Markdown으로 슬라이드를 만드는 도구를 오래 쓰다 보면 어느 순간 벽에 부딪힌다. 색상 팔레트를 아무리 정성 들여 잡아도, 모든 슬라이드가 결국 "제목 하나 + 본문 하나" 형태에서 못 벗어난다는 것.

발표 콘텐츠는 그렇게 균질하지 않다. 큰 사진 한 장으로 밀어붙여야 할 슬라이드가 있고, 왼쪽에 설명 오른쪽에 코드를 나란히 놓아야 이해되는 슬라이드가 있다. 어떤 페이지는 지표 여섯 개를 격자로 뿌려야 하고, 어떤 페이지는 시간축으로 흘러야 한다. 이걸 한 벌의 테마 CSS에 다 우겨넣는 순간, 브랜드 색을 바꾸려다 레이아웃까지 갈아엎게 된다.

## 계층을 두 개로 쪼갠 이유

처음 만든 테마에는 컬러 변수, 폰트 스택, 슬라이드 그리드 규칙이 한 파일에 다 들어 있었다. 브랜드 하나 바꿔달라는 요청이 오면 그리드 규칙까지 손대야 했다. 반대로 새 레이아웃 하나를 실험해보려면 브랜드 색이 들러붙어 있어서 손이 안 나갔다.

그래서 아예 계층을 이렇게 뜯었다.

| 계층 | 담는 것 | 위치 |
|---|---|---|
| 디자인 시스템 | 컬러, 타이포, 간격 변수 | `design.md` 한 벌 |
| 레이아웃 템플릿 | 슬라이드 내부 HTML 구조 | `deck_layouts/<name>/` |

디자인 시스템은 CSS 변수(`--color-primary`, `--font-heading` 같은 것들)로만 존재한다. 색을 직접 쓰는 곳은 없다. 레이아웃 템플릿은 그 변수를 가져다 쓰기만 하고, 자기 파일 안에 hex 값을 박지 않는다. 이 규칙 하나만 지키면 브랜드가 바뀔 때 레이아웃 파일들은 통째로 무관해진다.

## 레이아웃을 파일로 관리한다는 것

한 레이아웃은 폴더 하나다. 그 안에 두 파일만 있다.

```
deck_layouts/
├── hero/
│   ├── LAYOUT.md
│   └── wireframe.svg
├── split/
├── bento-grid/
├── timeline/
└── device-mockup/
```

`LAYOUT.md`에는 "이 레이아웃이 언제 필요한지", "슬라이드에 어떤 클래스를 붙이는지", "어떤 슬롯을 채워야 하는지"를 적었다. `wireframe.svg`는 생성 UI에서 미리보기로 쓴다. 새 레이아웃을 추가할 때 파이썬 코드 어디도 손대지 않아도 되게 만드는 게 목적이었다. 명세와 이미지, 두 파일만 던져 넣으면 그 순간부터 선택 가능한 옵션이 된다.

슬라이드 하나에 붙이는 방식은 Marp의 `_class` 지시어를 그대로 활용했다.

```markdown
<!-- _class: layout-split -->

## API 설계 원칙

왼쪽에 들어갈 설명 텍스트

---right---

컬럼 나눔 마커 뒤에 코드나 이미지
```

`layout-split`이 붙은 슬라이드만 좌우 그리드로 렌더링되고, 나머지는 아무 영향도 받지 않는다. 이 부분에서 한 번 크게 데인 적이 있는데, `layout-*` 클래스가 다른 슬라이드에까지 새 나가서 절반이 안 보이는 사고가 있었다. Shell CSS가 스코프된 CSS를 덮어써버려서 그랬다. 그 뒤로는 레이아웃 클래스를 슬라이드 컨테이너에만 붙이고, 셀렉터에 `:not()` 가드를 항상 껴놓는다.

## CLI에서 두 가지 방식

덱 생성 스크립트는 레이아웃 지정을 두 층위로 받는다. 전체 기본값과 개별 오버라이드.

```bash
make_deck.py --layout hero
```

이러면 모든 슬라이드가 `hero`를 기본으로 깔고 시작한다. 개별 슬라이드에서 `_class`로 다른 걸 지정하면 그게 이긴다.

```bash
make_deck.py --per-slide-layouts '{"2":"bento-grid","3":"timeline"}'
```

JSON으로 슬라이드 번호와 레이아웃을 매핑한다. 2번은 격자, 3번은 타임라인, 나머지는 기본값. Markdown 본문은 한 줄도 안 건드리고 시각화만 실험할 수 있다는 게 이 구조의 실제 이득이었다. 같은 콘텐츠를 세 가지 다른 배치로 뽑아 놓고 어떤 게 잘 읽히는지 옆에 두고 비교하기 좋다.

## HTML이 반응형이 되는 지점

HTML 출력은 처음부터 뷰포트 단위(`vw`, `vh`)와 CSS Grid로만 짰다. 픽셀 고정은 어디에도 없다.

```css
.layout-bento-grid .slide-content {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(28vw, 1fr));
  gap: 2vh 2vw;
}
```

`auto-fit`과 `minmax` 조합이 카드 개수에 맞춰 열을 알아서 접었다 폈다 해준다. 카드가 세 개면 3열, 여섯 개면 자동으로 두 줄. 창을 좁혀도 무너지지 않고 재배치된다.

PPTX 출력은 이 세계에 못 들어온다. 슬라이드마다 좌표를 픽셀로 못 박아야 하니 반응형이라는 개념이 성립하지 않는다. 그런데 이게 오히려 역할이 갈리는 계기가 됐다. PPTX는 인쇄와 공유용, HTML은 화면 발표와 웹 링크 공유용. 하나를 두 매체에서 다르게 소비한다는 감각.

## 남은 것

레이아웃을 파일로 뜯어놓고 나서 생긴 진짜 변화는, 이 도구를 "슬라이드 만드는 것"이 아니라 "콘텐츠를 여러 배치로 렌더링하는 것"으로 보게 됐다는 점이다. 새 레이아웃을 하나 추가하는 비용이 파일 두 개로 줄었다.

아직 못 푼 게 있다. 슬라이드 하나 안에서 두 레이아웃을 섞고 싶을 때가 종종 있는데 — 위쪽 절반은 hero, 아래쪽은 bento 같은 — 지금 구조로는 슬라이드 단위 이하로 못 쪼갠다. 이걸 슬롯 기반으로 다시 파야 할지, 아니면 그 정도는 그냥 손으로 HTML을 쓰라고 두는 게 맞는지 아직 판단이 안 섰다.
