title: "랜덤 추천 API에 페이지네이션을 붙이면 왜 중복이 생길까"
date: 2026-09-04 17:00:00 +0900
categories: [Backend]
tags: [pagination, sql, fastapi, api-design]
---

`totalCount`와 `list`를 응답에 실어 달라는 요청이 들어왔다. 기존 랜덤 추천 엔드포인트는 그냥 배열을 반환하고 있었고, 클라이언트가 "더보기"를 구현하려면 페이지네이션 포맷이 필요하다는 거였다. 간단해 보였다. `offset`과 `limit`을 받아서 `LIMIT :limit OFFSET :offset`을 붙이면 끝 아닌가.

문제는 이미 쿼리 끝에 이게 달려 있었다는 것이다.

```sql
ORDER BY RAND()
LIMIT :limit OFFSET :offset
```

이 두 줄을 함께 쓰면 안 된다.

---

`ORDER BY RAND()`는 쿼리가 실행될 때마다 새 시드로 섞는다. 1페이지를 요청하면 DB가 전체 행을 한 번 섞고 앞 30개를 내려준다. 2페이지를 요청하면 DB가 **다시** 섞는다. 그 결과 `OFFSET 30`부터 시작하더라도 1페이지에 나왔던 항목이 다시 나오거나, 반대로 영영 안 나오는 항목이 생긴다.

`totalCount`를 276이라고 응답해 놓고 실제로는 중복과 누락이 뒤섞인 목록을 내려주는 셈이다.

```json
{ "totalCount": 276, "list": [...] }
```

숫자는 맞는데 내용을 신뢰할 수 없는 API가 된다.

---

해결책은 크게 두 갈래다.

**seed를 고정하는 방법.** MySQL은 `RAND(seed)` 형태로 시드를 받는다.

```sql
ORDER BY RAND(:seed)
LIMIT :limit OFFSET :offset
```

처음 요청 때 서버가 seed를 하나 만들어 응답에 실어 보내고, 클라이언트는 다음 페이지 요청마다 그 seed를 함께 보낸다. 같은 seed면 같은 순서가 보장되니 페이지를 넘겨도 중복이 생기지 않는다.

단점은 클라이언트가 상태를 들고 다녀야 한다는 것이다. seed를 잃어버리거나 요청을 새로 시작하면 순서가 바뀐다. 캐싱도 까다로워진다. 그리고 같은 seed는 영원히 같은 순서다 — 사용자가 앱을 다시 열어도 목록이 그대로라면 "랜덤"이라는 느낌이 사라진다.

**랜덤을 포기하지 않는 방법.** 응답 포맷만 페이지네이션 규격에 맞추되, `offset`이 0이 아닌 경우는 아예 막거나 경고를 문서에 명시한다. 실질적으로는 "1페이지 한정 랜덤"이다. 클라이언트가 "더보기"를 원하면 오프셋을 올리는 대신 처음부터 다시 요청해서 새로운 랜덤 목록을 받는다.

이쪽은 구현이 단순하다. 서버 상태도 없고 seed 관리도 없다. 대신 사용자 입장에서 "2페이지"가 존재하지 않는다. 무한 스크롤처럼 끝없이 내려가는 UI라면 쓸 수 없다.

---

팀과 얘기해서 지금 클라이언트는 단순 목록 노출이고 페이지를 넘기는 UX가 아니라는 걸 확인했다. 필요한 건 응답 포맷이지 실제 다중 페이지 탐색이 아니었다. 그래서 `offset=0`만 유효하고 나머지는 `limit`만 조절하는 방향으로 정리했다.

`totalCount`는 필터 조건을 맞추는 전체 행 수를 따로 조회해서 채웠다. 순서는 여전히 `RAND()`다.

---

작업하면서 하나 더 걸렸다. FastAPI에서 쿼리 파라미터를 Pydantic 모델로 선언할 때 `Query(...)` 어노테이션을 필드 기본값으로 써야 하는데, 클래스 변수처럼 그냥 타입만 적으면 FastAPI가 쿼리 파라미터로 인식하지 않고 request body를 기대한다. GET 엔드포인트에 body가 오면 당연히 422가 난다.

```python
# 이렇게 쓰면 body로 인식된다
class Params(BaseModel):
    offset: int = 0
    limit: int = 30

# 이렇게 써야 쿼리 파라미터로 잡힌다
class Params(BaseModel):
    offset: int = Query(default=0, ge=0)
    limit: int = Query(default=30, ge=1, le=100)
```

문서엔 나와 있는 내용인데, 기존 코드가 섞여 있으니 어느 쪽이 맞는지 헷갈렸다.

---

seed 방식은 아직 구현하지 않았다. 지금 요구사항엔 필요 없지만, 나중에 진짜 다중 페이지 랜덤 탐색이 필요해지면 seed를 어디 저장할지부터 다시 정해야 한다 — 클라이언트 쿠키인지, 서버 캐시인지, 아니면 아예 순서 보장을 포기하고 다른 방식으로 가는지.
