퓨샷(few-shot) 예시를 하나 더 박으면 그날은 고쳐진 것처럼 보였다. "분수 알려줘"가 "분수의 덧셈"에 안 붙으면, 프롬프트에 예시를 추가했다. 다음 날 로그를 보면 그 예시가 붙인 케이스만 맞고 옆에 나란히 서 있는 비슷한 표현은 그대로 틀렸다. 퓨샷은 일반화가 아니라 암기라는 걸, 나는 프롬프트를 몇 번 더 늘려본 뒤에야 인정했다.

## 로그를 dedupe하고 나서야 문제가 다르게 보였다

문제를 다시 보려고 사용자 질의 로그를 중복 제거(dedupe)해서 빈도순으로 정렬했다. LLM이 틀린 이유가 임베딩 거리 문제라고 생각했었는데, 상위에 쌓인 오답의 상당 부분이 그 이전 단계 — 표면 문자열이 안 맞아서 후보에 못 든 케이스였다.

| 입력 | 기대 매칭 | 실제 문제 |
|------|----------|----------|
| `분수의덧셈` | 분수의 덧셈 | 띄어쓰기 없음 |
| `직사각형 넓이구하기` | 직사각형의 넓이 | 조사 누락, 어미 변형 |
| `소수점 곱하기` | 소수의 곱셈 | 도메인 별칭 |
| `곱하기` | 곱셈 | 구어체 |

임베딩 모델을 바꿀 문제도, 리랭커를 붙일 문제도 아니었다. 그 앞 단계에서 이미 후보가 잘려 있었다.

## 정규화를 세 층으로 나눈 이유

한 함수에 다 몰아넣고 싶은 유혹이 있었는데, 층을 나눈 건 **어디까지 지우고 어디서부터 원본을 지킬지**가 층마다 달랐기 때문이다.

가장 바깥 층은 표면 정규화다. 유니코드, 공백, 구두점만 만진다.

```python
import re, unicodedata

def normalize_text(s: str) -> str:
    s = unicodedata.normalize("NFC", s)   # 자모 분리 방지
    s = s.strip().lower()
    s = re.sub(r"\s+", " ", s)            # 연속 공백 → 단일 공백
    s = re.sub(r"[^\w\s]", "", s)         # 구두점 제거
    return s
```

`NFC` 정규화는 macOS에서 붙여넣기한 텍스트나 파일명에서 온 문자열이 섞일 때 결정적이었다. 눈으로는 같은 "가"인데 바이트가 달라 캐시 키가 갈라진다. 이걸 안 하면 이후 층이 아무리 정교해도 캐시 히트가 새어나간다.

두 번째 층은 매칭 점수를 낼 때만 쓰는 정규화다. 조사·어미를 잘라낸다.

```python
def normalize_for_match(s: str) -> str:
    s = normalize_text(s)
    endings = ["의", "을", "를", "이", "가", "은", "는", "에서", "하기", "구하기"]
    for e in endings:
        if s.endswith(e):
            s = s[:-len(e)]
            break
    return s.strip()
```

`endings` 목록을 처음엔 좀 더 공격적으로 뒀다가 사고를 쳤다. "나누기"에서 "기"를 잘라 "나누"가 되니 "나누어떨어지다" 같은 옆 개념에 붙었다. 그래서 후행 매치만 하고, 한 번 잘리면 멈추고, 목록도 로그에 실제로 나오는 것만 보수적으로 유지한다. 감으로 늘리지 않는다.

세 번째 층은 별칭 맵이다. 구어체를 사전상 용어로 치환한다.

```python
ALIAS_MAP = {
    "곱하기": "곱셈",
    "나누기": "나눗셈",
    "더하기": "덧셈",
    "빼기": "뺄셈",
    "소수점": "소수",
}

def apply_alias_map(text: str) -> str:
    for alias, canonical in ALIAS_MAP.items():
        text = text.replace(alias, canonical)
    return text
```

한때 이걸 프롬프트로 처리하려고 했다. "'곱하기'는 '곱셈'과 같다"를 시스템 프롬프트에 설명하면, 이번 요청에서만 그럴듯하게 지켜지고 다음 요청에서 흔들렸다. 별칭 맵으로 옮기고 나서는 결정론적이고, 실패 시 어디를 봐야 할지 명확하다. LLM한테 시킬 일이 아니었다.

## 어디에 적용할지가 사실 더 중요했다

정규화 자체보다 이걸 파이프라인 어디에 꽂을지가 오래 걸렸다.

캐시 키에는 두 번째 층까지 적용한 문자열을 쓴다. 같은 뜻인데 다른 표면으로 들어온 질의가 캐시를 못 맞추는 낭비가 컸다. 후보 검색 — 임베딩이 놓친 걸 FTS5(SQLite Full-Text Search 5, 전문 검색)로 fallback할 때 — 에는 세 층을 다 통과시킨 텍스트를 넣는다. 어미 잘린 표현이 인덱스에 더 잘 걸린다.

반대로 LLM 프롬프트에는 사용자가 실제로 친 문장을 그대로 넘긴다. 정규화된 문자열을 넣어봤더니 답이 어색해졌다. "분수의덧셈 알려줘" 같은 원문의 뉘앙스가 삭제되면 모델이 어조를 못 잡는다. 정규화는 시스템 내부에서만, 사람 얼굴 앞에는 원본. 이 규칙이 지금까지 흔들린 적이 없다.

## 아직 못 푼 것

어미 목록을 늘려도 되는지 아직 자신이 없다. 지금은 후행 한 개만 잘라내는데, 이중 어미("~하기가", "~구하기를")를 만나면 여전히 놓친다. 재귀로 잘라내면 위험하고, 형태소 분석기를 얹기엔 라이센스·속도 문제가 있다. 다음에 로그를 다시 뒤질 때 이 유형이 얼마나 남아 있는지 재는 것부터 하려 한다.

별칭 맵도 아직 손으로 유지 중이다. 로그에서 자동으로 후보를 뽑아 리뷰 큐로 보내는 스크립트를 만들다 말았다. 자동 추가는 위험해서 사람 검수를 남기려는데, 그 검수를 내가 계속 할 수 있는지가 관건이다.
