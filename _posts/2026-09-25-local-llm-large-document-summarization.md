컨텍스트 윈도우보다 큰 문서를 로컬 모델에 그냥 넣으면 잘린다. 아니면 모델이 에러를 낸다. 이걸 처음 만났을 때 "그냥 청크 나눠서 넣으면 되겠지"라고 생각했다. 반은 맞고 반은 틀렸다.

---

## 문서를 어떻게 나눌 것인가

무작정 n토큰 단위로 자르면 문단이 절반에서 끊긴다. 그 상태에서 요약하면 문맥이 없어서 모델이 이상한 말을 한다. Markdown 기반 문서라면 헤더가 자연스러운 경계다. `#`, `##` 수준에서 섹션을 나누면 각 청크가 의미 단위를 유지한다.

문제는 테이블이다. 수백 행짜리 Markdown 테이블이 섹션 하나에 통째로 들어 있으면 그 섹션만 혼자 컨텍스트를 초과한다. 이 경우엔 샘플링을 택했다. 전체 행을 다 넣는 게 아니라 일부만 뽑아서 넘긴다. 당연히 원문의 모든 정보가 요약에 담기지는 않는다. 이 점은 명확히 해둬야 한다. "대표 샘플로 패턴을 요약한다"는 것이지 "전체를 압축한다"가 아니다.

흐름은 이렇다.

```
입력 문서
  → Markdown 헤더 기준 섹션 분할
  → 대형 테이블이 있는 섹션은 행 샘플링
  → 섹션별 부분 요약 생성 (Map)
  → 부분 요약들을 하나로 병합 (Reduce)
  → 최종 구조화 요약 저장
```

Map-Reduce라는 이름은 분산 처리 맥락에서 나온 용어인데, 여기서는 순차 실행이지만 개념은 같다. 각 청크를 독립적으로 요약하고, 나중에 합친다.

---

## JSON 파싱이 처음부터 안 됐다

구조화 요약이라고 했는데, 요약 결과를 JSON 형태로 받으려 했다. 모델 출력을 바로 파싱했더니 계속 실패했다. 로그를 보면 응답 자체가 오고 있었다. 내용도 얼추 맞았다. 그런데 JSON으로 파싱이 안 됐다.

문제를 좁히기 위해 파이프라인을 거치지 않고 모델을 직접 호출해봤다. 그랬더니 잘 됐다. 파이프라인 어딘가에서 출력이 달라지고 있었다.

결국 두 가지를 바꿨다. 하나는 호출 경로를 모델 전용 함수로 분리한 것. 다른 하나는 추론 모드(reasoning mode)를 끈 것이다. 추론 모드는 모델이 내부적으로 생각하는 과정을 출력에 포함시키는데, 이 "생각" 부분이 JSON 앞뒤에 끼어들었을 가능성이 있다.

바꾸고 나서 파싱이 됐다. 그런데 두 가지를 동시에 바꿨기 때문에 어느 쪽이 원인이었는지 확정하지 못했다. 추론 모드 하나만 끄고 다시 실패를 재현해보지 않았다. 시간이 없어서 넘어갔는데, 사실 이건 한번 확인해둬야 한다.

---

## 같은 파일을 두 번 처리하지 않으려면

파이프라인을 반복 실행하다 보면 이미 요약한 파일을 또 처리하는 일이 생긴다. 로컬 LLM 추론은 느리다. 바뀌지 않은 파일을 다시 넣는 건 순수한 낭비다.

SHA-256 해시를 썼다. 원문 내용의 해시를 처음 요약할 때 저장해두고, 다음 실행 때 현재 파일의 해시와 비교한다. 같으면 건너뛴다.

실제로 28개 파일을 대상으로 재실행했을 때 전부 건너뛰어서 약 3.7초에 끝났다. 어느 것도 내용이 안 바뀌어 있었기 때문이다. 해시 비교 자체는 거의 시간을 안 잡아먹는다.

주의할 점은 파일명이 아니라 내용 기준이라는 것. 파일을 옮기거나 이름을 바꿔도 내용이 같으면 건너뛴다. 반대로 파일명이 같아도 내용이 달라지면 다시 처리한다. 의도한 동작이다.

## 아직 안 풀린 것

마지막에 발표자료 생성 기능을 붙이는 작업을 했다. Markdown 요약을 받아서 PPTX로 만드는 흐름인데, 파서 문제와 메타데이터 누락은 수정했지만 실제 PPTX 파일이 제대로 나오는지는 끝까지 확인을 못 했다. 로그상으로는 생성 단계까지 가는데, 파일 자체를 열어보는 과정이 빠졌다.
