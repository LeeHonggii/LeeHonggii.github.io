목록 API에 페이지네이션을 붙이는 일은 작아 보였다. 파라미터 두 개 추가하고, 쿼리에 `LIMIT`을 걸고, 응답에 전체 개수를 얹으면 된다. 실제로 코드 diff는 작았다. 그런데 바뀐 것은 코드보다 **호출자와 맺은 약속** 쪽이 훨씬 많았다.

이 글은 그 약속이 어디서 바뀌었는지를 적은 기록이다. 코드를 길게 싣는 글은 아니다. 인용할 수 있는 건 한 줄짜리 식과 쿼리 조각 정도고, 나머지는 판단에 대한 이야기다.

## 전달받은 DTO의 `offset`은 오프셋이 아니었다

시작은 다른 쪽에서 넘어온 요청 DTO였다. 필드 이름이 `offset`이라 당연히 "건너뛸 행 수"로 읽었다. 그런데 의미를 확인해 보니 **1부터 시작하는 페이지 번호**였다.

이름과 의미가 어긋난 채로 SQL에 그대로 넘기면 첫 페이지가 통째로 사라지거나, 페이지 번호가 행 번호로 해석되어 엉뚱한 구간이 조회된다. 에러도 안 난다. 그래서 SQL로 넘길 값은 따로 계산했다.

```text
skip = (offset - 1) * limit
```

```sql
LIMIT :limit OFFSET :skip
```

DTO의 `offset`은 건드리지 않았다. 외부에서 받은 계약이라 이름을 바꾸면 호출자가 깨진다. 대신 계산한 값은 `skip`이라는 다른 이름으로 두어서, 코드를 읽을 때 "페이지 번호"와 "행 오프셋"이 섞이지 않게 했다.

페이지 번호가 1부터이므로 `offset=0`은 `skip`이 음수가 된다. 이 값을 경계 케이스로 잡아 모델 검증 단계에서 걸러지는지 봤다.

## 기본값이 곧 응답 크기가 된다

`limit`은 기본 30, 허용 범위 1~300으로 정했다. 상한을 둔 이유는 단순하다. 상한이 없으면 페이지네이션이 아니다. `limit=301`이 거절되는지도 같은 방식으로 확인했다.

문제는 기본값이다. 파라미터를 안 보내던 기존 호출자는 예전에는 전체 목록을 받았다. 이제는 **30건만** 받는다. 호출 코드는 한 줄도 안 바뀌었는데 받는 데이터가 줄어든다. 에러도 없고, 응답 형태도 그대로다. 그래서 가장 늦게 발견될 종류의 변화다.

호출자가 다음 페이지를 요청해야 나머지를 받는다. 이걸 문서와 호출 예시에 적었지만, 문서를 읽지 않는 호출자가 있다는 건 안다. 실제로 전체 목록에 의존하던 호출자가 몇 곳인지는 아직 전수 확인하지 못했다.

## `count`가 다른 숫자가 되었다

응답 필드도 바꿨다. `count`와 `templates`를 `totalCount`와 `list`로 바꿨다.

```json
{ "totalCount": 100, "list": [] }
```

이름 변경보다 중요한 건 숫자의 의미다. 예전 `count`는 **이번 응답에 담긴 항목 수**였다. 지금 `totalCount`는 **필터 조건에 맞는 전체 항목 수**다. 페이지를 넘기면 `list`의 길이는 최대 30인데 `totalCount`는 그대로다.

이름이 바뀌었으니 옛 이름을 쓰던 호출자는 어차피 깨져서 눈에 띈다. 위험한 쪽은 반대다. 이름을 그대로 두고 의미만 바꿨다면 조용히 틀린 값으로 돌았을 것이다. 필드 이름을 바꾼 건 호환성을 깨는 비용이 아니라, 의미가 바뀐 걸 호출자에게 알리는 수단이기도 했다.

## 성공과 실패를 `status` 필드로 알리지 않기로 했다

같은 작업에서 응답의 `status` 필드를 빼고 HTTP 상태코드로 성공·실패를 구분하게 바꿨다. 전에는 HTTP 200에 본문의 `status`로 결과를 알렸다. 이러면 호출자는 응답 코드를 보고, 본문을 파싱하고, 다시 `status`를 봐야 한다.

호출하는 쪽은 이렇게 단순해진다.

```text
!response.ok
```

이 조건 하나로 실패 분기가 끝난다. 호출 예시와 문서도 이 기준으로 고쳤다.

예외가 하나 남았다. health check의 `status`는 그대로 뒀다. 이건 요청의 성공 여부가 아니라 서비스 상태를 나타내는 값이라 성격이 다르다고 봤다. 다만 "주요 API는 빠졌는데 이것만 남은" 상태라 문서에서 헷갈릴 여지는 있다.

## 쿼리 모델이 파라미터를 못 읽었다

FastAPI에서 쿼리 파라미터를 모델로 묶어 받는 부분에서, 모델의 파라미터가 제대로 인식되지 않는 문제가 있었다. 이 부분도 같이 고쳤다. 원인을 일반화해서 설명할 만큼 파고들지는 않았다. 여기서는 "페이지네이션 파라미터가 실제로 모델에 들어오는지"를 별도로 확인해야 했다는 정도만 남긴다.

## 랜덤 목록: 고정 seed를 시도했다가 되돌렸다

랜덤 순서로 돌려주는 목록 API가 하나 있었다. 여기에 페이지네이션을 붙이면 문제가 생긴다. 요청마다 순서가 다르면 1페이지와 2페이지 사이에 항목이 중복되거나 빠질 수 있다. 그래서 고정 seed를 실험했다. 같은 seed면 순서가 같으니 페이지 경계가 안정된다는 계산이었다.

결국 되돌렸다. 매 요청의 랜덤성을 유지하는 쪽을 택했다. 이 API는 애초에 "매번 다른 걸 보여주는" 용도라, 순서를 고정하면 기능 자체가 바뀐다고 판단했다. 대신 응답 형식은 다른 목록 API와 같은 `totalCount`/`list`로 통일했다.

이 선택의 대가는 안다. 랜덤 목록에서 페이지를 넘기면 이전에 본 항목이 다시 나올 수 있다. 그게 허용 가능한지는 호출하는 화면이 어떻게 쓰는지에 달려 있고, 나는 아직 그쪽을 확인하지 못했다.

## 어디까지 확인했고 어디가 남았나

확인한 것은 두 가지다. 요청 모델의 검증이 경계값을 의도대로 다루는지, 그리고 위의 `LIMIT`/`OFFSET` 쿼리를 DB에 직접 실행했을 때 기대한 구간이 나오는지.

확인하지 못한 것이 있다. **실제 앱에서 SQLAlchemy 바인드 파라미터가 DB 드라이버를 거쳐 `:limit`, `:skip`으로 제대로 전달되는지**는 아직 보지 못했다. 직접 실행한 SQL은 문자열이 들어간 상태이고, 앱 경로는 바인딩을 거친다. 둘이 같다고 가정하고 있을 뿐이다.

변경은 로컬 커밋까지만 했다. 앱과 DB를 연결해 돌려 보는 검증과 원격 반영이 남아 있다. 다음에 할 일은 그 환경에서 `offset=0`, `limit=301`, 그리고 기본값만 보내는 호출을 실제로 한 번씩 쏴 보는 것이다. 그리고 기본값 30 때문에 데이터가 줄어드는 호출자가 있는지 찾는 일은, 아직 방법도 정하지 못했다.
