학생이 문제를 푸는 동안 화면에서 한 조작 기록이 어딘가에 저장돼 있을 텐데, 어디인지 몰랐다. 이번 작업은 그걸 찾는 일이었다. 처음엔 반나절이면 되겠다 싶었다.

## 문서를 믿고 시작한 게 첫 실수

접속 정보가 적힌 오래된 문서가 있었고, 거기 적힌 데이터베이스에 붙었다. 테이블도 있고 데이터도 들어 있었다. 마지막으로 쌓인 날짜가 꽤 최근이라 "여기가 현재 쓰는 곳이구나" 하고 넘어가려 했다.

그런데 일부 행의 날짜가 최근이라는 건 그 DB가 지금 쓰이는 곳이라는 증거가 못 된다. 나는 그 둘을 같은 말로 취급하고 있었다. 확인 방법은 단순했다.

```sql
SHOW DATABASES;
```

스키마 목록을 실제로 펼쳐보니 문서에 없던 것들이 여럿 있었다. 활동 기록이 사는 곳은 문서가 가리키던 쪽이 아니라 다른 스키마일 가능성이 보였다. 이후로는 문서에 적힌 위치를 가설로만 두고, 스키마 목록과 테이블 구조를 직접 열어보는 쪽으로 방향을 바꿨다.

## ID로 찾으면 0건

찾고 있던 대상은 특정 학생의 한 번의 풀이였다. 그 풀이를 가리키는 짧은 ID 값이 있어서, ID처럼 생긴 컬럼들을 훑으며 그 값을 검색했다. 결과는 0건이었다.

여기서 "이 DB에는 없다"로 결론 내렸다면 거기서 끝났을 것이다. 하지만 ID 컬럼에 없다는 것과 데이터가 없다는 것은 다른 이야기다. 참조는 URL 문자열 안에 들어 있을 수도 있고, 긴 텍스트 컬럼 안에 있을 수도 있고, JSON 필드 안쪽에 있을 수도 있다. 기록 본체 자체가 JSON 한 덩어리로 저장돼 있을 가능성도 있었다.

그래서 검색 범위를 짧은 컬럼에서 URL, 긴 텍스트, JSON으로 넓혔다. 이 방향 전환이 이번 작업에서 가장 값어치 있었던 판단이었다고 생각한다. 실제로 기록 본체는 JSON 필드 안에 있었다.

## 개인정보를 뿌리지 않고 JSON 구조를 보는 법

JSON 필드를 찾고 나서 `SELECT *`로 한 줄 열어보고 싶은 충동이 있었다. 이 필드에는 학생 이름 같은 개인정보가 섞여 있다. 터미널에 통째로 찍으면 로그와 화면에 그대로 남는다.

그래서 값이 아니라 모양을 먼저 봤다. 순서는 이랬다.

1. 페이지 종류별로 몇 건씩 있는지 센다.
2. 종류별로 어떤 키 경로가 있는지 본다.
3. 종류마다 예시를 한 건만, 필요한 부분만 본다.

이렇게 하면 어떤 종류의 화면이 있고, 각각 어떤 키를 가지는지 알 수 있다. 개인정보는 한 번도 통째로 출력하지 않았다.

이 과정에서 이름 필드가 한 겹이 아니라 중첩된 위치에 들어 있다는 것도 알게 됐다. 나중에 추출 쿼리를 짤 때 최상위 키만 보고 마스킹하면 빠뜨렸을 것이다.

## 압축된 기록은 열리지 않았다

기록 본체는 압축된 문자열이었다. 해제를 시도했지만 실패했다. 한동안 압축 방식이 다른가 의심했는데, 원인은 훨씬 사소했다. 문자열 앞에 접두사가 붙어 있었고, 해제 함수는 그걸 압축 데이터의 일부로 읽고 있었다. 접두사를 떼고 넘기니 열렸다.

열린 JSON 안에서 확인한 필드는 `elements`, `penElements`, `historyStack`, `viewBox`였다. 화면에 놓인 요소, 펜으로 그린 선, 조작 이력, 캔버스 영역이다. 이 중 `historyStack` 덕분에 최종 화면뿐 아니라 풀이 도중 어떤 상태를 거쳤는지까지 볼 수 있었다.

나중에 이 구조를 기반으로 매 순간의 화면 상태를 읽는 작업을 했다. 아래는 그 단계에서 쓴 코드의 일부다. 식별자는 일반화했다. 탐색 단계의 결과물이 어떻게 쓰이는지 보여주려고 넣었다.

```python
# 블록 종류 = shapeType (0 일·1 십·2 백·3 천)
# 놓인 칸 = connectedBoardIdx (0 이 일의 자리)
PLACE = {0: "일", 1: "십", 2: "백", 3: "천"}
BLOCK, BOARD = "BLOCK_SVG", "BOARD_SVG"


def boards(f, names):
    out = {}
    for e in f["elements"]:
        if e.get("svgId") == BOARD:
            m = e.get("elements") or []
            places = {PLACE[c]: sum(row) for c, row in enumerate(m) if sum(row)}
            wrong = [f"{PLACE[c]}의 자리 칸에 {PLACE[u]} 모형 {k}개"
                     for c, row in enumerate(m)
                     for u, k in enumerate(row) if k and c != u]
            out[names.get(e["id"], e["id"][:5])] = {"n": e.get("n"), "칸": places, "다른 자리": wrong}
    return out


def where(e, names):
    b = e.get("connectedBoardId")
    if not b:
        return "판 밖"
    c = e.get("connectedBoardIdx")
    return f"{names.get(b, b[:5])} {PLACE.get(c, c)}의 자리 칸"
```

`elements` 안의 `elements`는 판의 칸마다 블록 종류별 개수를 담은 2차원 배열이다. 행 인덱스가 놓인 칸, 열 인덱스가 블록 종류다. 두 값이 다르면 "십 모형이 일의 자리 칸에 놓였다" 같은 오개념 후보가 된다. 구조를 모르면 이 비교는 불가능했을 것이다. 반대로 말하면, 탐색 단계에서 키 경로를 먼저 정리해둔 덕에 이 코드가 짧아졌다.

## 추출 전에 점검한 것들

기록을 읽을 수 있게 된 뒤에도 바로 분석으로 넘어가지 않았다. 몇 가지가 걸렸다.

- 테이블 목록에서 보이는 행 수는 추정치다. 정확한 값은 `COUNT`로 따로 집계해야 한다. 나는 처음에 추정치를 그대로 믿을 뻔했다.
- 시험 삼아 넣은 데이터가 섞여 있었다. 분석 대상에 들어가면 통계가 오염된다.
- 기록이 아예 없는 건이 있었다. 풀이는 했는데 저장이 안 됐거나, 저장 경로가 달랐을 수 있다. 원인은 아직 구분하지 못했다.

## 아직 남은 것

이 기록을 기존 LLM 리포트 파이프라인의 입력과 대조해봤다. 비전 분석, 코드 계산, 평가, 서술 생성이 실제로 어떤 순서로 돌고 각자 무엇을 하는지 코드로 추적했다. 선개념과 오개념이 어디서 나오는지, 그리고 기록만으로는 어디까지 판정할 수 있는지의 한계도 구분해봤다.

화면 녹화 영상을 입력으로 쓰는 별도 실험도 논의했다. 어떤 데이터가 필요한지 정리하는 데까지만 갔고, 구현도 검증도 하지 않았다. 시험 데이터와 누락 건이 전체에서 얼마나 되는지도 아직 세지 않았다. 다음에 할 일은 그 숫자부터 확인하는 것이다.
