date: 2026-09-03 17:00:00 +0900

---

페이지네이션을 붙이고 나서 Swagger UI를 열었더니 `offset`과 `limit`이 보이지 않았다.

422도 없고, 500도 없었다. API 호출 자체는 됐다. 그냥 파라미터가 문서에서 사라져 있었다.

---

작업 배경은 간단했다. 목록 API에 페이지네이션을 추가하면서 기존 응답 구조도 같이 정리했다. `count/templates` 형태를 `totalCount/list`로 바꾸고, `status` 필드를 빼고 HTTP 상태코드만 남기는 식이었다. 그 과정에서 쿼리 파라미터도 정리했는데, 이 순간부터 이상한 일이 시작됐다.

기존에 `offset`, `limit` 파라미터를 개별로 선언하던 방식에서, Pydantic 모델로 묶어서 받는 방식으로 바꿨다. FastAPI에서 Pydantic 모델을 쿼리 파라미터로 쓰는 건 익숙한 패턴이다. 모델 클래스를 선언하고 의존성으로 주입하면, FastAPI가 모델 필드 각각을 쿼리 파라미터로 펼쳐준다(flatten). 이게 안 되면 에러라도 나야 하는데, 에러가 없었다.

처음엔 Swagger UI 캐시 문제라고 생각했다. 강제 새로고침해도 달라지지 않았다. 그 다음엔 OpenAPI 스키마 자체를 확인했다.

```
python scripts\check_schema.py
```

자동화 스크립트로 생성된 OpenAPI JSON을 파싱해서 각 엔드포인트에 선언된 파라미터 목록을 뽑아보니 확실했다. `offset`과 `limit`이 없었다. 다른 엔드포인트에선 멀쩡히 보이는 항목들이.

---

파라미터가 왜 사라졌는지를 역으로 추적했다. 비슷한 다른 엔드포인트와 선언 방식을 비교했을 때 차이가 하나 있었다. 문제 있는 엔드포인트는 Pydantic 쿼리 모델과 별도 쿼리 파라미터를 **같은 함수 시그니처에 혼재**해서 선언하고 있었다.

FastAPI는 쿼리 파라미터를 여러 방식으로 받을 수 있다. Pydantic 모델을 `Depends()`로 주입하는 방식, 각 파라미터를 `Query()`로 직접 선언하는 방식. 문제는 이 둘을 섞어 쓸 때였다. 특정 조건에서 FastAPI가 모델의 필드를 개별 쿼리 파라미터로 펼치지 않고 모델 자체를 body로 인식하거나, 아예 OpenAPI 스키마에서 누락시키는 동작이 있었다. 에러는 없고, 동작도 "겉으로는" 됐다. 파라미터를 명시하지 않으면 기본값이 들어가고, 기본값 범위 안에서 호출하면 별 문제없이 응답이 나왔으니까.

`limit=301`을 넘겼을 때 422가 나온다는 걸 확인했을 때 비로소 검증 로직 자체는 살아있다는 걸 알았다. Pydantic 모델 안의 유효성 검사는 동작하고 있었다. OpenAPI 문서에만 파라미터가 안 보였던 거다.

---

수정은 단순했다. 혼재해서 쓰던 파라미터들을 Pydantic 모델 하나로 통합했다. 랜덤 추천 API에서 쓰이던 `seed` 파라미터도 함께 같은 모델 안으로 넣었다. 이렇게 하니 FastAPI가 모델 필드 각각을 올바르게 쿼리 파라미터로 인식하고, Swagger UI에서도 `offset`, `limit`, `seed`가 전부 보이기 시작했다.

스키마 확인 스크립트를 다시 돌렸다. 이번엔 파라미터가 다 있었다.

---

이 버그가 불편한 이유는 에러가 없다는 거다. FastAPI가 틀렸다고 알려주지 않는다. 기본값이 있으면 앱은 돌아간다. OpenAPI 스키마를 꼼꼼히 보지 않으면 프론트엔드에 스펙을 잘못 전달하거나, QA 단계에서 파라미터가 없는 채로 테스트가 통과될 수 있다.

FastAPI 버전이나 Pydantic v1/v2에 따라 이 동작이 달라지는지는 아직 체계적으로 확인하지 못했다. 지금 쓰는 버전에서는 재현됐고 수정됐다는 것까지만 안다.
