기존 멀티모달 평가 코드를 읽는 중이었다. 학생이 푼 화면 이미지와 활동 이력을 모델에 넣고, 판정과 리포트를 받는 파이프라인이다. 입력에서 리포트까지 데이터가 어디로 흐르는지 따라가다가 한 군데서 멈췄다.

리포트에 "선개념(prior concept)"과 "오개념(misconception)" 항목이 있었다. 그 값이 어디서 왔는지 코드에서 답이 안 나왔다.

## 코드가 계산하는 것, 모델이 추론하는 것

이 코드는 둘을 꽤 깔끔하게 나눠 놓았다. 카드 식이 모범답안과 몇 자리 일치하는지, 목표 식을 몇 개 달성했는지는 코드가 센다. 그 값으로 근접도 곡선을 그린다. 곡선은 첫 화면에서 이미 맞은 몫을 빼고 0~1로 정규화한다.

```python
class Normalized:
    @staticmethod
    def series(curve):
        if not curve:
            return None
        m0, tot = curve[0]["matched"], curve[0]["total"]
        if tot - m0 <= 0:
            return None
        return [{"t": c["t"], "v": max(0.0, min(1.0, (c["matched"] - m0) / (c["total"] - m0)))} for c in curve]
```

처음부터 다 맞은 화면은 분모가 0이 되니 `None`으로 돌려보낸다. "근접도 1.0"이라는 값을 만들어 내지 않는다는 뜻이다. 이쪽은 숫자의 출처가 분명하다. 입력이 같으면 결과도 같고, 어느 카드가 몇 개 맞았는지 거슬러 올라가 확인할 수 있다.

반면 `판정`, `루브릭`, `전략`, `오개념`, `선개념`은 모델 호출 결과다. 같은 리포트에 실려 있어도 성격이 다르다. 코드가 센 값은 관찰이고, 모델이 낸 값은 해석이다.

## 선개념 목록은 어디서 오는가

모델에게 문제 화면을 주고 이 문제에 필요한 개념을 뽑으라고 하면, 대략 이런 모양의 답이 나온다.

```json
{"concepts":{"pre":["선행 개념"],"core":["목표 개념"],"post":["후속 개념"]}}
```

읽기에는 교육과정 DB를 조회한 결과처럼 보인다. 그런데 내가 확인할 수 있는 건 모델이 화면을 보고 사전학습 지식으로 만들어 냈을 가능성이다. 둘 다 같은 JSON 필드에 같은 모양으로 담기기 때문에, 리포트만 읽어서는 구분이 안 된다. 틀린 목록이라는 말이 아니다. 그럴듯하지만 검증된 사실로 취급할 근거는 아직 없다는 말이다.

오개념도 마찬가지다. 모델은 이런 형태로 규칙을 만든다.

```json
{"observation":"관찰 가능한 행동 조건","gap":"해당 행동에서 의심하는 개념적 어려움"}
```

관찰 조건과 의심되는 어려움을 짝지은 규칙이다. 이 규칙의 출처(전문가가 쓴 것인지, 모델이 생성한 것인지)와, 그 규칙에 실제 학생의 행동이 들어맞았다는 근거는 별개의 두 가지다. 한 필드에 섞어 두면 나중에 "모델이 이 학생에게 오개념이 있다고 했다"가 "이 학생에게 오개념이 있다"로 읽힌다.

그리고 관찰을 규칙과 대조하는 단계를 LLM이 하고 있다면, 그 대조도 틀릴 수 있다. 규칙이 전문가 것이어도 마찬가지다.

## 전문가가 개념 이름을 넣어 주면 해결되는가

처음엔 그렇게 생각했다. 평가할 개념을 전문가가 직접 입력하게 하면 가설 문제가 사라질 거라고 봤다. 반만 맞았다.

"어떤 개념을 평가할 것인가"는 전문가가 정할 수 있다. 하지만 "이 학생이 그 개념을 이해했는가"는 다른 질문이다. 개념 이름이 검증됐다고 해서 그 이름에 대한 학생 판정까지 검증되는 건 아니다. 입력 쪽의 신뢰가 출력 쪽으로 넘어가지 않는다.

## 재현성은 타당도가 아니다

저장소에는 같은 기록을 AI에 여러 번 다시 돌려 항목별 일치 비율을 재는 스크립트가 있다. 저장본은 건드리지 않고 웹과 같은 입력, 같은 검사로 다시 호출한다.

```python
ITEMS = ["판정", "확인_필요", "모범답안과", *[f"루브릭:{k}" for k in RUBRIC], "전략", "오개념", "선개념"]

    @staticmethod
    def values(fb, rv):
        out = {"판정": fb.get("판정"), "확인_필요": fb.get("확인_필요"), "모범답안과": fb.get("모범답안과")}
        for k in RUBRIC:
            out[f"루브릭:{k}"] = ((rv.get("루브릭") or {}).get(k) or {}).get("점수")
        out["전략"] = tuple(sorted({t["태그"] for t in rv.get("전략") or []}))
        out["오개념"] = tuple(sorted({m["id"] for m in rv.get("오개념") or []}))
        out["선개념"] = tuple(sorted((c["개념"], c["신호"]) for c in rv.get("선개념") or []))
        return out
```

오개념은 id 집합, 선개념은 `(개념, 신호)` 쌍의 집합으로 바꿔 정렬한 튜플로 비교한다. 순서만 다른 답을 불일치로 세지 않으려는 처리다. 항목마다 "같은 값이 나온 비율"을 잰다.

다만 이 측정이 보여주는 건 모델이 같은 입력에 같은 소리를 하는가, 하나뿐이다. 여러 번 같은 오개념을 지목해도 그 오개념이 맞다는 증거는 되지 않는다. 일관되게 틀리는 모델도 일치율은 높게 나온다. 이 글에 일치율 숫자는 없다. 돌린 결과를 내가 여기에 옮겨 적지 않았고, 안 읽은 숫자를 지어 쓰고 싶지도 않다.

그래서 일치율은 "불안정한 항목을 찾는 도구"로만 쓸 수 있다. 낮은 항목은 의심할 이유가 되지만, 높은 항목이 믿어도 된다는 보증은 아니다.

## 남겨 둔 제안

내가 정리한 방향은 이렇다.

- 선개념·오개념 필드에 출처 태그를 붙인다. "전문가 입력", "모델 생성 가설", "코드가 센 값"이 같은 모양으로 섞이지 않게 한다.
- 오개념은 규칙의 출처와 이 학생에게서 실제 관찰된 근거를 따로 저장한다. 둘을 잇는 대조가 LLM 판단이면 그것도 표시한다.
- 전문가가 같은 기록에 매긴 판정을 모아, 모델 판정과의 일치도를 잰다. 이게 있어야 타당도 이야기를 시작할 수 있다.

세 번째가 제일 무겁다. 전문가 판정 데이터는 지금 없고, 몇 건이면 일치도를 말할 수 있는지도 아직 모른다.

이 코드를 읽은 뒤 다양한 활동 유형을 받는 새 평가 시스템의 기획 초안을 잡았다. 영상 분석과 새 입력 경로가 거기 들어 있는데, 아직 검토 단계고 구현된 건 없다. 영상에서는 "관찰"이 무엇인지부터 다시 정의해야 해서, 위의 출처 분리가 그대로 통할지도 확인하지 못했다.
