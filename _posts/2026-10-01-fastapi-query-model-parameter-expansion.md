목록 API에 페이지네이션을 붙이고 있었다. `offset`, `limit`, 전체 건수. 랜덤 목록에는 `seed`도 하나 더 넣기로 했다. 같은 seed면 같은 순서로 나오게 하려는 생각이었다.

문법 검사는 깨끗하게 통과했다. 서버도 떴다. 그런데 API 문서 화면을 열어 보니 쿼리 파라미터 칸에 `offset`과 `limit`이 없었다.

## 증상

페이지네이션 파라미터는 Pydantic 모델 하나에 묶어 두었다. 쿼리 파라미터를 모델로 선언하면 모델의 필드가 개별 쿼리 파라미터로 펼쳐지길 기대한다. 여기서 "펼친다"는 `?offset=0&limit=20`처럼 모델 필드 하나하나가 URL 쿼리 문자열의 키로 노출된다는 뜻이다. 그런데 `seed`를 모델 밖의 별도 쿼리 파라미터로 함께 선언한 엔드포인트에서는 이 펼침이 일어나지 않았다. 문서에는 `seed`만 보였다.

에러는 없었다. 이 점이 제일 나빴다. 타입 검사도 린트도 통과한다. 파라미터 계약만 조용히 어긋나 있었다. 클라이언트가 `offset=0`을 보내도 그 값은 어디에도 바인딩되지 않을 수 있는 상태였다.

## 처음 의심한 것

모델 정의를 먼저 봤다. 필드 이름이 틀렸나, 기본값 때문인가, 제약 조건 때문인가. 아니었다. 모델 단독으로 선언한 엔드포인트에서는 같은 모델이 멀쩡히 펼쳐졌다.

그러면 달라진 건 `seed` 하나였다. 모델 파라미터와 단일 쿼리 파라미터를 같은 시그니처에 같이 두는 조합. 이 조합에서만 모델이 개별 파라미터로 인식되지 않았다. 내가 쓰던 환경에서 관찰한 결과다. 다른 버전이나 다른 선언 방식에서도 똑같은지는 확인하지 않았다. 프레임워크 버그라고 단정할 근거도 없고, 내가 선언을 잘못 쓴 것일 수도 있다. 원인을 소스까지 내려가 확인하지는 않았다.

## 고친 방법

`seed`를 쿼리 모델 안으로 옮겼다. 모델 하나가 `offset`, `limit`, `seed`를 모두 갖고, 시그니처에는 모델만 남겼다. 그러자 세 필드가 개별 쿼리 파라미터로 정상 노출됐다.

이유를 설명할 수 있는 수정은 아니다. 조합을 바꿨더니 되돌아왔다는 수준이다. 그래서 이 글에는 "이렇게 하면 된다"가 아니라 "이 환경, 이 선언 조합에서 이렇게 보였다"까지만 적는다.

## 문법 검사로는 못 잡는 것

이번에 배운 건 검증 방법이었다. 코드가 돌아가는지와 계약이 맞는지는 별개다. 그래서 확인을 두 겹으로 했다.

- 생성된 API 스키마를 열어 파라미터 목록을 직접 봤다. 코드가 아니라 서버가 실제로 내보내는 명세다. 여기서 `offset`과 `limit`이 빠져 있는 걸 처음 확인했고, 수정 후 세 개가 다 있는 것도 여기서 확인했다.
- 경계값으로 실제 요청을 보냈다. 하한인 `offset=0`, 상한 바로 위인 `limit=301`, 범위 밖인 `seed=-1`. 정상 값은 통과하고 범위를 벗어난 값은 거절되는지 봤다. 파라미터가 인식되더라도 검증 제약이 같이 붙어 있는지는 따로 봐야 한다. 모델 필드가 펼쳐지지 않았다면 이 제약도 같이 사라졌을 수 있기 때문이다.

## 그리고 seed는 없어졌다

결말이 좀 허무하다. seed 고정 방식은 구현하고 실험까지 했지만, 최종적으로 랜덤 동작을 그대로 두기로 했다. 응답 구조만 다른 목록 API와 통일했다. 실패도 `status` 필드가 아니라 HTTP 상태코드로 표현하도록 코드와 문서를 고쳤다.

그래서 문제를 일으킨 `seed` 파라미터는 지금 코드에 없다. 남은 건 쿼리 모델이 실제로 어떤 형태로 노출되는지 스키마로 확인한다는 습관이다.

## 아직 안 한 것

페이지네이션 변경은 로컬 커밋과 전달용 패치를 만드는 데까지만 갔다. 망이 분리된 환경이라 패치로 옮겨야 했다. 최종 앱 환경에서 목록 API가 의도대로 도는지 확인하지 못했고, 원격 반영이 끝났다는 기록도 없다.

`seed`를 뺀 지금의 선언에서 `offset`과 `limit`이 계속 정상 노출되는지는 스키마를 다시 열어 보려 한다. 이 현상이 다른 버전에서도 나오는지는 재현해 본 적이 없다. 그건 아직 모른다.
