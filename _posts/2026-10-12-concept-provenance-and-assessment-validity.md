멀티모달 평가 코드를 처음부터 끝까지 읽었다. 문제 정의 → 학생 답안 판정 → 루브릭 평가 → 리포트 생성 순서다. 입력과 출력이 어디서 어디로 흐르는지 시퀀스 문서로 그리는 게 목적이었다. 그리다가 그림 한 군데가 계속 찜찜했다.

"선개념"과 "오개념" 목록이 어디서 오는가.

## 목록은 조회한 게 아니었다

처음엔 교육과정 데이터에서 가져오는 줄 알았다. 문제마다 "이 문제를 풀려면 이런 개념이 필요하다"는 목록이 붙어 있으니 어딘가에 매핑 테이블이 있겠거니 했다. 읽어 보니 없었다. 목록은 두 군데서 나왔다.

- 교사가 개념 이름을 직접 입력한다.
- 입력이 없으면 모델이 문제를 보고 추론해서 만든다.

교육과정 자료를 조회하는 경로는 이 코드에 없었다. 모델이 만든 목록은 사전학습 지식에서 나온 것이다. JSON 스키마를 지켜 출력하니 형식은 멀쩡하다. 하지만 형식이 맞는 것과 내용이 맞는 것은 다른 문제다. "받아올림이 있는 덧셈에는 자릿값 개념이 선행된다" 같은 문장은 그럴듯하게 나오고, 그럴듯하다는 사실 자체가 검증이 되지는 않는다.

여기서 나는 두 가지를 같은 작업으로 뭉뚱그리고 있었다.

1. 이 문제에 필요한 개념이 무엇인가를 **생성**하는 일
2. 이 학생이 그 개념을 이해했는가를 **판단**하는 일

1번은 모델이 잘하는 일이다. 그럴듯한 목록은 얼마든지 나온다. 2번은 학생의 행동에서 근거를 가져와야 한다. 1번이 잘 돌아간다고 2번이 되는 게 아니다. 오히려 1번의 매끄러움이 2번의 빈약함을 가린다.

## 오개념 규칙은 가설이다

오개념 쪽은 더 조심해야 했다. "학생이 십의 자리에 일 모형을 놓았다 → 자릿값 개념이 부족하다" 같은 규칙은 **관찰된 행동과 개념 부족을 이어 붙인 가설**이다. 실제 행동과 일치할 수는 있다. 그래도 교육적으로 검증된 진단이라고 부를 수는 없다. 같은 행동이 부주의, 조작 도구의 사용법 미숙, 풀이를 소리 내어 설명하다 생긴 실수에서도 나올 수 있다.

그럼 교사가 개념 이름을 직접 넣으면 해결되는가. 절반만 그렇다. 기준의 **출처**는 분명해진다. 누가 정했는지 안다. 하지만 학생이 그 기준을 충족했는지는 여전히 별개의 판단이다. 개념 이름이 "자릿값"이어도, 학생의 어떤 관찰 가능한 행동이 그 이름에 연결되는지가 비어 있으면 판정은 다시 모델의 추론으로 돌아간다.

## 코드가 사실만 말하는 부분

이 코드베이스에서 그 구분이 비교적 깔끔하게 나뉘는 곳이 있었다. 수 모형 조작을 분석하는 모듈이다. 모형판의 격자를 정본으로 삼아, 자리마다 어떤 모형이 몇 개 놓였는지를 코드가 직접 센다.

```python
@staticmethod
def place_facts(g):
    facts = []
    for i, row in enumerate(g[:len(PLACE)]):
        own = row[i] if i < len(row) else 0
        if own >= 10:
            facts.append(f"{PLACE[i]}의 자리에 {PLACE[i]} 모형 {own}개 — 10개 이상")
        for j, c in enumerate(row[:len(PLACE)]):
            if j != i and c:
                facts.append(f"{PLACE[i]}의 자리에 {PLACE[j]} 모형 {c}개")
    return facts
```

출력은 "십의 자리에 일 모형 3개" 같은 문장이다. "자릿값을 모른다"는 말은 어디에도 없다. 판정이 아니라 관찰이다. 다음 단계의 LLM이 이 사실을 받아 해석하더라도, 입력은 코드가 계산한 값이라 되짚어 볼 수 있다.

프레임 사이의 개수 변화에서 합치기·쪼개기를 읽는 부분도 같은 성격이다.

```python
@staticmethod
def change(d):
    for k in range(len(PLACE) - 1):
        lo, hi = d[k], d[k + 1]
        rest = [x for j, x in enumerate(d) if j not in (k, k + 1)]
        if any(rest):
            continue
        if hi > 0 and lo == -10 * hi:
            return {"kind": "합치기", "label": f"{PLACE[k]} 모형 {-lo}개 → {PLACE[k + 1]} 모형 {hi}개"}
        if hi < 0 and lo == -10 * hi:
            return {"kind": "쪼개기", "label": f"{PLACE[k + 1]} 모형 {-hi}개 → {PLACE[k]} 모형 {lo}개"}
    # ... (덜어 냄 / 더 놓음 분기)
```

일 모형 10개가 사라지고 십 모형 1개가 생겼을 때만 "합치기"라고 부른다. 인접한 두 자리 외에 다른 변화가 섞여 있으면 이벤트로 인정하지 않는다. 조건이 엄격해서 놓치는 경우는 있을 수 있지만, 있지도 않은 합치기를 만들어 내지는 않는다. 해석을 모델에 넘기기 전에 코드가 걸러 두는 층이다.

격자를 정본으로 삼는 주석도 있었다. 판 사이로 모형을 옮길 때 재생된 요소가 갱신되지 않는 경우가 있어서, 요소를 세지 않고 격자를 센다는 내용이다. 입력 데이터의 어느 쪽을 믿을지 정한 결정이고, 이런 결정이 쌓여야 "근거"라는 말에 무게가 생긴다.

다만 이 모듈은 어디까지나 **관찰**을 만든다. 이 관찰이 어떤 개념의 이해 여부로 이어지는 연결은 이 파일에 없다. 내가 읽은 범위에서는 그 연결이 LLM 쪽에 있다.

## 출처를 남기자는 쪽으로

시퀀스 문서에서 값마다 색을 달리했다. 코드 계산값, 교사 입력, 모델 생성. 그리고 이 세 출처가 최종 리포트에서는 구분 없이 한 문장으로 섞여 나온다는 점이 눈에 들어왔다. "학생은 받아올림 개념이 부족하다"는 문장이 교사가 정한 기준에서 코드가 센 값으로 확인된 것인지, 모델이 짐작한 것인지 읽는 사람은 알 수 없다.

그래서 후속으로 잡은 것은 이렇다. 아직 하나도 구현하지 않았다.

- 개념·판정마다 출처 태그(교사/모델/코드)를 보존한다.
- 교사가 직접 판정한 골드셋을 만들고, 시스템 판정과 가중 카파(순서가 있는 등급 사이의 일치도를 보는 지표)로 비교한다.

골드셋은 아직 없다. 일치도 수치는 당연히 없고, 지금 판정이 얼마나 믿을 만한지는 **측정하지 않았다.**

## 영상 쪽은 논의만 했다

풀이 과정을 영상으로 받아 프레임 이미지로 바꿔 분석하자는 이야기도 나왔다. 수 모형 조작이 이미 프레임 단위로 처리되고 있어서 자연스러운 방향이긴 하다. 하지만 이 경로의 구현도, 검증 결과도 없다. 프레임에서 뽑은 관찰이 지금의 격자 기반 사실만큼 믿을 만한지도 모른다. 격자는 정본이 있었지만 영상에는 그런 정본이 없다.

그 점이 제일 걸린다. 코드가 센 값이라는 이유로 신뢰하던 층이, 이미지로 가면 모델이 읽은 값으로 바뀐다. 그때도 같은 태그를 붙일 수 있을지는 아직 모르겠다.
