노트 뭉치를 쌓아두는 파일 하나가 있다. 회의록, 링크 덤프, 리서치 조각, 반쯤 쓰다 만 문단. 몇 달치가 쌓이니 16MB가 됐다. 그래프뷰가 무거워지고, 전문 검색을 돌리면 이 한 파일이 결과의 절반을 먹었다.

한 줄 요약본만 노출하고 원본은 인덱스에서 빼면 되는 문제였다. 로컬에 Gemma를 띄워두고 있으니 "그냥 넣어서 요약본 하나 뽑자" 로 시작했다. 그게 첫 오판이었다.

## 통째로 안 들어간다

Gemma 3 27B 의 컨텍스트는 128K 토큰. 16MB Markdown 은 한·영 혼합 기준 어림잡아도 100만 토큰이 넘는다. 물리적으로 안 들어간다.

"그러면 앞부분만 잘라 넣자" 로 넘어갔다. 이게 두 번째 오판이었다. 앞 10만 토큰은 전체의 10% 도 안 된다. 나머지 90% 를 버리고 만든 요약을 "문서 요약" 이라고 부를 수는 없다. 게다가 컨텍스트가 꽉 차면 응답이 중간에 잘리는 빈도가 눈에 띄게 올라간다. JSON 스키마를 걸어놔도 소용 없다 — 응답 자체가 완성되지 않으니까.

여기서 "어떻게 통째로 넣지" 를 붙잡고 있던 걸 그만두고, "어떻게 쪼갤지" 로 문제를 갈아탔다.

## 쪼갤 때는 글자 수가 아니라 헤더로

처음엔 N글자마다 잘랐다. 결과가 이상했다. 문단 중간이 잘리면 Gemma 가 "이 섹션은 불완전한 문장으로 시작됩니다" 같은 걸 요약 첫 줄에 쓴다. 요약이 아니라 파일 상태를 보고하고 있는 거다.

Markdown 은 이미 저자가 의미 단위를 표시해둔 문서다. `#`, `##` 헤더. 이걸 경계로 삼는 게 자연스럽다. 헤더 단위로 잘라 붙이다가 누적 토큰이 목표치를 넘으면 청크를 확정하고 다음 청크를 시작한다. 목표는 10K~20K 토큰. 더 작게 하면 청크 수가 폭발해 Reduce 단계가 다시 무거워지고, 더 크게 하면 응답 안정성이 떨어진다.

한국어 토큰 추정은 대충 잡았다. 4자 ≈ 1토큰. 정확할 필요 없다. 안전마진만 있으면 된다.

## thinking 을 꺼야 JSON 이 들어온다

Map 단계는 청크마다 부분 요약을 뽑는 것. 이때 걸린 함정이 하나 있었다.

Gemma 의 thinking(추론 노출) 옵션을 켜두면, JSON 스키마를 강제해도 응답 앞에 `<think>...</think>` 블록이 붙어 나온다. 파서는 그걸 JSON 이 아니라고 판단한다. "지시가 명확한" 작업 — 요약, 분류, 추출 — 에서는 thinking 이 오히려 방해다. 모델이 생각을 정리할 여지 자체가 필요 없는 작업이니까.

`think=False` + `format=<JSON schema>` 조합으로 옮기고 나서 파싱 실패가 확 줄었다. 정확히 몇 % 였는지는 재보지 않았다. 재봤어야 했는데, 그 시점엔 "된다/안 된다" 만 눈으로 보고 넘어갔다. 다음에 이런 파이프라인을 다시 짜면 파싱 실패율을 카운터로 남겨둘 생각이다.

각 청크에서 뽑는 스키마는 `title`, `summary`, `keywords` 세 필드 정도. 통합 단계에서 재조합할 수 있는 최소 단위로만.

## Reduce 는 놀랍도록 조용하다

Map 이 끝나면 청크 수만큼의 요약 딕셔너리가 남는다. 부분 요약의 총 토큰은 원문의 한 자릿수 퍼센트 수준으로 줄어 있어서, Reduce 는 컨텍스트 걱정 없이 단일 호출로 끝난다. 부분 요약들을 그대로 이어 붙여 "이걸 하나의 노트로 통합해줘" 만 시키면 된다.

여기서 재미있는 관찰이 하나 있었다. Map 단계에서 keywords 를 뽑아두면 Reduce 단계 프롬프트에 그걸 함께 넣어줄 수 있다. 모델이 "이 청크가 어떤 주제였는지" 를 자기 요약문 밖에서 한 번 더 확인할 수 있어서, 통합본에서 특정 청크가 통째로 누락되는 사고가 줄어든다 — 는 인상을 받았다. 정량 측정은 아니다. 몇 번 돌려보고 눈으로 본 정도.

## 남은 것

원본은 `.md` → `.txt` 로 확장자를 바꿔서 인덱서에서 제외했다. Gemma 가 뽑아준 통합 요약본만 `.md` 로 남긴다. 검색과 그래프뷰가 조용해졌다.

아직 정리 못 한 것도 있다.

하나는 청크 병렬화. Map 단계는 서로 독립이라 병렬로 돌려도 되는데, 로컬 Ollama 인스턴스는 동시 요청을 몇 개 받아줄 수 있는지 아직 안 재봤다. 두 개 띄웠을 때 첫 요청이 눈에 띄게 느려졌다는 인상만 있고, 숫자는 없다.

또 하나는 청크 경계에서 잘려나가는 맥락. 헤더 분할이라 문단 중간은 안 자르지만, "앞 섹션에서 정의한 용어가 뒷 섹션에서 반복 사용되는" 경우엔 뒤 청크의 요약이 그 용어를 모른다. 부분 요약끼리 keyword 를 공유하는 걸로 어느 정도 완화되긴 하는데, 완전히 해결된 느낌은 아니다. 다음에 이 파이프라인을 다시 열면 여기부터 볼 것 같다.

Map-Reduce 는 분산 처리 세계의 오래된 이름이지만, 로컬 LLM 의 컨텍스트 제약을 우회하는 데 그대로 맞는다. 큰 문서를 마주할 때 "어떻게 다 넣지" 에서 "어디서 자르고 어떻게 다시 붙이지" 로 질문을 바꾸는 것 — 이번엔 그 지점에서 시간을 가장 많이 벌었다.
