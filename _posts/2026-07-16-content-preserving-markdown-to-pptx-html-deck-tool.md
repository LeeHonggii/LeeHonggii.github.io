처음엔 AI가 게으른 줄 알았다.

10페이지짜리 기술 문서를 넘기고 "발표자료로 만들어줘"라고 하면, 결과 슬라이드에는 원문의 표 하나가 "상세 내용은 문서 참고"라는 한 줄로 요약되어 있곤 했다. 코드 블록은 통째로 사라지고, 근거로 넣은 인용은 세 개가 하나로 합쳐져 있었다.

프롬프트를 바꿔봤다. "요약하지 마", "원문 그대로 넣어", "표를 지우지 마". 그때그때 조금씩 나아지긴 했는데, 문서가 길어지면 다시 같은 짓을 했다. 문장 두 개로 강제할 수 있는 문제가 아니었다.

## AI 탓이 아니라 파이프라인 탓이었다

한참 씨름하고 나서 관점을 뒤집었다. AI가 요약하는 게 문제가 아니라, **요약할 여지를 주는 파이프라인 구조가 문제**였다. "이 문서를 슬라이드로 만들어줘"라는 요청 자체가 AI에게 "네가 판단해서 압축해"라는 재량을 준다.

그래서 재량을 뺏기로 했다. 파이프라인이 지켜야 할 규칙을 세 줄로 못박았다.

- 원본 문장을 짧게 다시 쓰지 않는다
- 코드 블록, 표, 리스트 항목은 하나도 지우지 않는다
- 한 슬라이드에 다 안 들어가면 슬라이드를 늘린다

세 번째가 핵심이다. 내용을 버리는 대신 슬라이드 수를 늘리라는 뜻. AI에게 "요약 vs 그대로"의 선택지를 주는 게 아니라, "1장에 담기 vs N장으로 쪼개기"의 선택지만 남긴다. 후자에서는 무엇을 버릴지 판단할 여지가 없다.

## 왜 Marp였나

한 소스에서 PPTX와 HTML을 동시에 뽑고 싶었다. 회사 미팅에서는 PPT를 열어야 하고, 외부 공유용으로는 링크 하나 보내면 되는 반응형 HTML이 편했다. 두 산출물이 미묘하게 어긋나는 건 최악이었다 — 발표할 때 슬라이드에는 있는 표가 공유 링크에는 없으면, 그 순간부터 "어느 게 최신이죠?" 소리를 듣게 된다.

Marp는 Markdown을 특수 주석과 `---` 구분자로 슬라이드로 변환하는 도구다. 매력은 단순함이었다. **입력이 하나면 출력이 두 개여도 내용은 같다.** PPTX와 HTML이 갈라질 이유 자체가 없어진다.

```bash
marp deck.md --pptx
marp deck.md --html
```

이 두 줄이 파이프라인의 심장이다. 나머지는 다 이 둘을 감싸는 껍데기다.

## 디자인과 레이아웃을 분리한 이유

처음엔 디자인·레이아웃·색상·폰트를 한 CSS 파일에 다 몰아넣었다. 그러다 어느 날 "색은 A 브랜드 그대로 쓰되 슬라이드 배치만 그리드로 바꿔달라"는 요청을 받았다. CSS 한 파일에서 색만 남기고 나머지를 다 갈아엎어야 하는 상황. 그때 분리했어야 한다는 걸 알았다.

지금은 두 개의 관심사가 따로 논다.

- **design** — 색상 팔레트, 폰트, 여백의 기준값. 브랜드마다 하나씩
- **layout** — 슬라이드 안에서 콘텐츠를 어떻게 배치할지. grid, two-column, full-width 같은 것들

CLI에서 두 개를 독립적으로 고른다.

```bash
python make_deck.py source.md --mode both --design brand_a --layout grid
```

`--design`을 바꿔도 배치는 그대로, `--layout`을 바꿔도 색은 그대로. 이 분리가 있어야 "브랜드 A 그리드 버전", "브랜드 A 2단 버전", "중립 톤 그리드 버전"을 조합으로 만들 수 있다. 안 나눠놨으면 조합마다 CSS 파일을 하나씩 만들었을 거다.

## 산출물 구조에서 배운 것

산출물을 이렇게 뽑아낸다.

```
_decks/<slug>/
├── source.md
├── deck.md
├── theme.css
├── deck.pptx
└── index.html
```

여기서 `source.md`를 왜 남기느냐가 처음엔 안 자명했다. `deck.md`가 있는데 원본을 굳이? 한 번 지워봤다가 크게 후회했다.

`deck.md`는 Marp 문법으로 이미 슬라이드가 나뉜 상태다. `---` 구분자, `<!-- -->` 주석, 특수 클래스가 다 붙어있다. 여기서 디자인을 갈아엎으려고 하면 슬라이드 경계에 갇힌다. "이 세 슬라이드를 하나로 합치고 싶다"거나 "레이아웃을 바꾸면서 슬라이드 나누는 지점을 다시 잡고 싶다"는 순간, `deck.md`는 시작점으로 못 쓴다. 이미 결정이 박혀있어서.

`source.md`는 슬라이드 경계 없는 순수 원본이다. 디자인을 갈아엎을 때마다 여기서 다시 시작한다. 원본을 "절대 수정 안 함" 상태로 봉인해두는 것 — 이게 재변환의 자유도를 지켜준다.

## 검증 단계, 정확히는 실패 단계

파이프라인 마지막에 검증 단계를 붙였다. 원본에서 코드 블록, 표, 일정 길이 이상의 문장을 뽑아내고, 그것들이 PPTX와 HTML 양쪽에 실제로 존재하는지 확인한다.

중요한 건 "확인한다"가 아니라 **"실패하면 파이프라인이 멈춘다"**는 부분이다. 처음엔 유실된 항목을 경고로만 찍고 넘어갔다. 그랬더니 아무도 경고를 안 봤다. 로그 스크롤 위쪽에 노란 글씨로 "표 2개 유실"이라고 적혀 있어도, 다들 PPTX를 열어보고 "됐네" 하고 넘어갔다. 며칠 뒤 발표 자리에서 "이 표 원본에 있던 거 아니었어?" 소리가 나왔다.

지금은 유실이 하나라도 잡히면 exit code로 죽는다. 조용한 성공보다 시끄러운 실패가 낫다. 어차피 발표 전에 알아야 할 사실이라면 지금 아는 게 낫다.

## 남아있는 문제

지금 파이프라인은 "내용이 다 옮겨졌는가"는 잡아내는데, "옮겨진 자리가 적절한가"는 못 본다. 표 하나가 폭 좁은 슬라이드에 꾸겨넣어져서 텍스트가 3px로 렌더링돼도, 검증 단계는 "존재함"으로 통과시킨다. 사람 눈에는 실패인데 파이프라인 눈에는 성공이다.

여기부터는 시각 검증의 영역이라 텍스트 매칭으로 못 잡는다. Playwright로 렌더링 스크린샷을 찍고 폰트 크기·오버플로우를 판단하는 쪽을 다음에 붙여볼 생각인데, 아직 어디까지 자동화가 유의미한지 감이 안 잡힌다. 사람이 마지막에 한 번 넘겨보는 것보다 나은 지점이 어디인지 — 이건 좀 더 만들어보고 알 것 같다.
