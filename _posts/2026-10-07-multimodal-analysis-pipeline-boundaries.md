기존 LLM 분석 코드를 인수받아 읽는 중이다. 처음엔 문서에 적힌 순서대로 "문제 이미지 → 문제 정의 → 답안 판정 → 활동 평가 → 리포트"라고 머릿속에 그렸다. 코드를 따라가 보니 이 순서는 설명용이었다. 실제 호출은 다른 순서로, 다른 지점에서 일어났다. 읽으면서 정리한 것을 남긴다.

여기서 다루는 시스템은 학생이 화면에서 조작한 기록(한 페이지에 문제 하나)을 AI에 넘기고, 교사용 짧은 리포트를 받는 구조다. 새 평가 엔진을 만든 이야기가 아니다. 기존 코드를 읽고 이해한 이야기다.

## 화면이 세 종류다

입력으로 쓰이는 화면은 하나가 아니었다.

- 문제의 초기 화면: 문제가 처음 어떻게 놓여 있었는지
- 모범답안의 최종 화면: 정답이 어떤 모양인지
- 학생의 최종 화면: 학생이 어디까지 만들었는지

세 장을 한꺼번에 "이미지"로 묶어 던지면 모델이 어느 것을 근거로 말하는지 흐려진다. 코드에서도 모범답안은 있을 때만 "이미지 2"로 지칭하고, 없으면 없다고 명시한다. 입력 조립부를 보면 이 구분이 드러난다.

```python
def build_input(self):
    ev = self.ev
    tools = sorted({e["name"] for e in ev.elements if e.get("tool") and e.get("name") and e.get("kind") not in ("text", "background")})
    lines = [f"<활동> {self.title}", f"<지시문> {html.unescape(ev.instruction())}", f"<쓰인 교구> {', '.join(tools) or '없음'}",
             f"<모범답안> {'있음 (이미지 2)' if self.has_model else '없음'}", "<화면 글> 위에서 아래 순"]
    lines += [f"- {html.unescape(t['text'])}" for t in ev.texts()]
    # ...
```

이미지만 주지 않고, 화면에서 추출한 텍스트를 "위에서 아래 순"으로 같이 준다. 이미지는 배치와 공간 관계를 보여 주고, 텍스트는 문장을 정확히 보여 준다. 한쪽만으로는 둘 다 얻을 수 없어서 겹쳐 준 것으로 이해했다. 다만 텍스트만 줬을 때나 이미지만 줬을 때와 비교해 얼마나 나아지는지는 이 저장소에서 확인하지 못했다. 재 본 적 없다.

## 정답 목록은 학생 답을 보기 전에 만든다

가장 오래 들여다본 부분은 분기다.

```python
way = SolutionWay.confirmed(self.task_id, self.ev.order)
if way:
    lines.append("<선생님이 확인한 풀이 방식 기준> " + json.dumps(way, ensure_ascii=False))
else:
    groups, status = SolutionWay.answers(self.task_id, self.ev.order)
    if groups:
        lines.append(f"<정답 목록 — 학생 답을 보기 전에 따로 구한 것({status}, 선생님 미확인)> " + json.dumps(groups, ensure_ascii=False))
        lines.append("최종 답이 정답 목록에 있는지 하나씩 맞춰 보고 판정한다.")
```

문제 정의(이 문제의 정답이 무엇인가)와 개별 답안 판정(이 학생의 답이 거기에 들어가는가)이 분리되어 있다. 학생마다 "정답이 뭐지?"를 새로 추론하게 하면 같은 문제인데 학생에 따라 기준이 달라질 수 있다. 그래서 문제 정의는 문제당 한 번 만들어 공유하고, 판정 호출에는 결과만 넘긴다.

선생님이 확인한 기준이 있으면 그것이 우선이고, 없으면 AI가 따로 구한 목록을 쓰되 "선생님 미확인"이라는 꼬리표를 프롬프트에 그대로 단다. 신뢰 수준을 모델에게도 숨기지 않는 설계다.

공통 정의를 공유하는 방식에는 약점이 보인다. 문제의 초기 상태를 잘못 복원하면 그 한 번의 오류가 같은 문제의 모든 판정 기준으로 번진다. 개별 판정이 아무리 정교해도 기준 자체가 틀어져 있으면 소용없다. 실제로 이런 사고가 났는지는 코드로 확인하지 못했다. 구조상 가능한 전파 경로라는 얘기다.

## 캐시 키에 입력 전체가 들어간다

위 조립 결과는 그대로 캐시 키가 된다.

```python
prompt = read_prompt(PROMPT)
self.system = prompt
self.fingerprint = hashlib.sha256((prompt + self.text).encode("utf-8")).hexdigest()[:16]

def load(self):
    p = self.path()
    if not p.exists():
        return None
    d = load_json(p)
    if d.get("fingerprint") != self.fingerprint:
        return None
    self.relation_by_code(d["result"])
    return d
```

프롬프트와 입력 텍스트를 합쳐 해시한다. 정답 목록 줄도 `self.text` 안에 있으므로, 문제 정의가 바뀌면 지문(fingerprint)이 달라져 저장본이 자동 무효화된다. 프롬프트를 고쳐도 마찬가지다. 별도의 무효화 로직 없이 "입력이 같으면 같은 결과"라는 규칙만 지킨다.

한계도 있다. 키에는 이미지가 들어가지 않는다. 텍스트와 사실 목록이 같은데 이미지만 달라지는 경우가 있다면 저장본이 재사용된다. 그런 경우가 실제로 생기는지는 아직 모른다. 해시는 16자리로 잘라 썼는데, 충돌 가능성을 따진 흔적은 코드에서 못 찾았다.

## 코드가 계산할 수 있는 건 코드가 한다

읽다가 주석 한 줄에서 멈췄다.

```python
# 정답 목록에 식이 있고 학생 화면에 카드 식이 있으면, 정답 여부는 코드가 대조한다(AI 의 「가장 큰/작은」 비교가 실행마다 흔들림)
def verdict_by_code(self, p):
    groups, mine = self.answer_groups(), self.exprs("CARD_EXPR")
    if not groups or not mine:
        return p
    hits = [any(e in g for e in mine) for g in groups]
    code = "정답" if all(hits) else "부분 정답" if any(hits) else "오답"
    # ... (이하 생략)
```

모델이 "가장 큰 값 / 가장 작은 값" 같은 비교를 실행마다 다르게 답했고, 그래서 집합 포함 여부는 코드로 옮겼다는 기록이다. 정답 목록의 각 묶음마다 학생 식이 하나라도 포함되는지 보고, 전부 맞으면 정답, 일부면 부분 정답, 없으면 오답으로 바로 정한다. 모델에게 맡기는 건 코드가 확정할 수 없는 쪽, 즉 과정 설명과 이해 수준의 서술이다.

이 함수가 끝까지 어떻게 `p`를 덮어쓰는지는 내가 받은 코드가 잘려 있어서 읽지 못했다. 위 조건(`code != "정답"` 일 때 `확인_필요`를 세운다)까지만 확인했다.

코드로 계산한 사실과 모델의 추론이 섞여 있는 리포트에서는, 어느 칸이 어느 쪽에서 왔는지가 오류를 추적하는 첫 단서가 된다.

## 집계 쪽은 의외로 단순하다

활동 단위 리포트는 개별 저장본을 모아 보여 주는 쪽이다. 한 줄 요약도 LLM이 아니라 규칙이다.

```python
NEEDS_HELP = ("오답", "부분 정답")

@staticmethod
def one_line(rows):
    done = [r for r in rows if all(p["판정"] for p in r["pages"])]
    if not done:
        return "아직 AI 분석 전입니다."
    help_ = [r["student"] for r in done if any(p["판정"] in NEEDS_HELP or p["확인_필요"] for p in r["pages"])]
    line = f"{len(done)}명 중 " + (f"{', '.join(help_)} 학생을 먼저 확인해 보세요." if help_ else "모두 정답에 도달했습니다.")
    if len(done) < len(rows):
        line += f" (분석 전 {len(rows) - len(done)}명)"
    return line
```

여기서 놀랐다. 활동 이력 평가라고 해서 모델이 한 번 더 도는 줄 알았는데, 이 한 줄은 저장된 판정을 읽어 규칙으로 만든다. `search_by_task` 도 `PageFeedback(...).saved` 만 읽어 오고, 저장본이 없으면 호출하지 않고 "분석 전"으로 센다. 화면을 여는 것만으로는 모델이 호출되지 않는 구조다.

`확인_필요`가 켜진 학생은 판정이 정답이어도 "먼저 확인" 목록에 들어간다. 이 조건이 `or` 로 묶여 있어서, 코드 대조와 모델 판정이 어긋난 경우를 놓치지 않는다.

## 설명 순서와 실행 순서

정리하면 이렇다. 문서의 흐름은 "이미지 → 문제 정의 → 판정 → 평가 → 리포트"였다. 코드에서는 리포트 화면이 저장본을 읽는 것이 먼저고, 판정 호출은 입력 지문이 저장본과 어긋날 때만 일어난다. 문제 정의는 판정 입력을 조립하는 도중에 불려 온다. 그래서 오류를 찾을 때는 단계 이름보다 호출 지점과 데이터 의존성을 따라가야 했다. 어느 줄이 누구의 출력을 읽는지를 봐야 한다.

## 아직 못 한 것

새 구조를 구상하고 있다. 여러 활동 유형을 한 평가 틀로 지원하려는 것인데, 지금은 유형 정의, 화면에서 관찰할 수 있는 근거의 종류, 전문가가 붙인 판정 데이터가 먼저 필요하다는 정리까지만 했다. 영상 기반 분석과 평가 품질 측정은 어떻게 실험할지 논의한 단계다. 구현도 성능 검증도 하지 않았다.

기준 데이터가 없는 상태에서 "판정이 맞다"를 어떻게 말할지는 아직 답이 없다. 위에서 읽은 "선생님 미확인" 꼬리표가 그 데이터를 모으는 입구가 될 수 있을지, 다음에 코드를 더 읽고 따져 볼 생각이다.
