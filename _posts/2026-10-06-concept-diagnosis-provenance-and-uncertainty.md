기존 멀티모달 평가 코드를 읽다가 프롬프트 필드 하나에서 멈췄다. `틀린_길`이다. 학생 답을 보기 전에 "이 문제에서 학생이 어떻게 틀릴 수 있는지"를 모델이 먼저 적게 하는 칸이다. 결과물은 꽤 그럴듯하다. 그런데 이 목록이 어디서 왔는지 코드에서 짚어 보니 확인된 근거가 없었다.

이 글은 그 발견을 정리한 학습 노트다. 새 시스템을 구현한 기록은 아니다. 기존 코드를 분석하고 새 평가 시스템 기획 초안에 반영할 원칙을 세운 단계까지만 다룬다.

## 학생 답을 보기 전에 오개념을 쓰게 하는 프롬프트

문제(활동 페이지)마다 "풀이 방식 기준"을 만드는 프롬프트다. 식별자는 일반화했다.

```python
WAY_SYSTEM = """너는 초등 수학 활동의 「풀이 방식 기준」을 쓰는 수학교육 전문가다. 학생 답을 보기 전에, 이 문제를 푸는 방법과 정답이 나오는 원리를 정리한다.
- 지시문의 조건을 만족하는 답이 여러 개면 빠짐없이 모두 적는다.
- 모범답안은 여러 정답 중 하나의 예시일 수 있다.
JSON 하나로만 답한다:
{"정답_원리":"...","정답들":[{"무엇":"...","식":["..."]}],"최소_조작":"...",
"전략_수준":[{"수준":"낮음|중간|높음","모습":"..."}],"정답쪽_신호":["..."],
"틀린_길":[{"모습":"...","왜":"...","지도":"..."}]}"""
```

입력은 지시문과 모범답안 식뿐이다. 선택적으로 `MATERIALS`가 붙는다. CCSS Progressions, CGI 전략, 국내 평가기준 상·중·하 같은 일반 틀을 발췌한 텍스트다.

여기서 정리가 필요했다. `MATERIALS`는 문제와 무관한 일반 틀이다. 이 문제에서 학생들이 실제로 흔히 겪는 오개념 DB가 아니다. 자료에는 "예상하기"라는 관행 설명이 들어 있다. 학생이 어떤 오개념·오류를 보일지 예상하라는 내용이다. 모델은 그 지침을 따라 `틀린_길`을 채운다. 교육과정 데이터를 조회하는 단계는 코드 어디에도 없다. 그래서 `틀린_길`은 모델이 사전학습 지식과 주어진 틀로 **만든 가설**이다. "이 학년 이 단원의 검증된 오개념 목록"이 아니다.

내용이 틀렸다는 뜻은 아니다. 대체로 맞을 수도 있다. 다만 맞는지 확인한 사람이나 데이터가 이 파이프라인에 없다. 출력 JSON에도 이 칸이 가설이라는 표시가 없다. `정답_원리`와 `틀린_길`이 같은 모양의 문자열로 나란히 놓여 있다.

## 코드가 계산하는 것은 다른 층이다

같은 파일에서 정답 집합은 모델에 맡기지 않는다.

```python
def build_truth(self):
    self.truth = {}
    if self.spec["kind"] != "구성":
        op = self.spec["op"]
        self.truth["계산"] = {f"{a}{op}{b}={a + b if op == '+' else a - b}" for a, b in self.spec["items"]}
        return self.truth
    prob = PlaceValueProblem(self.spec["digits"], self.spec["shape"])
    for goal in self.spec["goals"]:
        value, best = prob.best(goal)
        self.truth[goal] = {f"{s['a']}{prob.op}{s['b']}" for s in best}
    return self.truth
```

"가장 큰 합을 만드는 배치"는 전수 탐색(`prob.best`)으로 구한다. 이 값에는 출처를 물어볼 필요가 없다. 같은 입력이면 같은 답이 나오고 틀렸으면 코드 버그다.

학생 기록도 같은 방식으로 걸러 모델에 넘긴다.

```python
STUDENT_FACTS = ("CARD_EXPR", "EXPR_LOG", "PEN_LOG", "PROCESS", "HANDWRITING", "NO_HANDWRITING")

def get_facts(self):
    self.facts = [f["text"] for f in self.ev.facts if f["code"] in STUDENT_FACTS]
```

화면에서 코드가 읽어 낸 사실 중 식·과정에 해당하는 코드만 통과시킨다. 모델은 "학생이 이 카드를 이 순서로 놓았다"를 추론하지 않고 받는다. 그래서 층이 둘로 갈린다.

- **관찰한 사실**: 코드가 계산하거나 읽은 것. 정답 집합, 학생의 식, 필기 유무.
- **생성한 가설**: 모델이 쓴 것. 정답 원리 설명, 전략 수준, 틀린 길.

## 가설을 만드는 일과 학생에게 적용하는 일은 다르다

처음엔 `틀린_길`을 생성하게 한 뒤 학생 기록을 대조하면 오개념 진단이 되는 줄 알았다. 이 구조에는 불확실성이 두 번 들어간다.

1. 규칙 생성: 모델이 오개념 후보를 쓴다. 근거는 모델의 지식이다.
2. 규칙 적용: 학생 행동이 그 후보에 해당하는지 판단한다. 이 판단도 LLM이 한다.

판정 프롬프트는 이렇게 생겼다.

```python
JUDGE_SYSTEM = """너는 초등 수학 ... 학생 기록을 읽고 판정하는 교사 보조다.
- 판정은 **최종 답**을 지시문의 조건으로 본다. 모범답안과 식이 달라도 조건을 만족하면 정답이다.
- 정답 = 최종 답이 조건을 모두 만족 / 부분 정답 = 답이 여러 개인 문제에서 최종 답 일부만 맞음 / 오답 = 최종 답이 틀림.
- 확인_필요 = 최종 답이 틀린 부분이 있는데, 과정 기록에 그 부분의 정답을 만든 적이 있으면 true. ...
JSON 하나로만 답한다:
{"판정":"정답|부분 정답|오답","확인_필요":false,"모범답안과":"같음|정답이지만 다름|틀림","과정":"...","근거":"...","선생님께":"..."}"""
```

이 프롬프트에서 눈에 띄는 설계가 있다. 판정 기준은 "최종 답이 조건을 만족하는가"뿐이고, 과정 중에 정답을 만든 적이 있어도 판정을 올리지 않는다. 대신 `확인_필요`라는 플래그로 사람에게 넘긴다. 판정이 모호할 때 모델이 확신하는 척하지 않게 막는 장치다. 이 부분은 불확실성을 설계에 넣은 좋은 예로 읽혔다.

다만 내가 받은 코드는 중간에서 잘려 있다. 판정 단계에 `틀린_길`이 실제로 입력되는지는 확인하지 못했다. 입력된다면 "이 학생의 행동이 가설 규칙 X에 해당한다"는 판단이 LLM 대 LLM 대조가 된다. 입력되지 않는다면 `틀린_길`은 교사용 참고 서술로만 남는다. 어느 쪽인지 다시 읽어 봐야 한다.

## 기획 초안에서 바꾸려는 것

새 평가 시스템 초안에서는 개념 이름을 전문가가 입력하는 방식을 검토했다. 이러면 기준의 출처는 분명해진다. 모델이 그럴듯하게 만든 목록이 아니라 누가 정했는지 남는 목록이 된다. 하지만 이것이 학생이 그 개념을 습득했다는 판정을 자동으로 주지는 않는다. 개념 이름 하나는 아직 관찰 가능한 무엇이 아니다.

그래서 개념마다 "학생이 이렇게 하면 이것이 부족한 것으로 본다"는 관찰 기준을 붙이는 형태를 구상했다. 초안 단계의 스키마 형태는 이 정도다. 구현된 코드가 아니다.

```json
{ "observation": "학생이 이렇게 하면", "gap": "이것이 부족한 것으로 본다" }
```

관찰 기준이 코드로 판정 가능한 모양이면(예: 십의 자리에 작은 수를 놓았다) 코드가 먼저 적용한다. 거기까지는 위 `build_truth`와 같은 층이다. 여기에 출력마다 `origin`(전문가가 입력했나, 모델이 생성했나)과 `basis`(어떤 관찰 사실에 근거했나)를 남기는 방안을 적어 뒀다. 이것도 아직 구현하지 않았다.

## 풀리지 않은 것

출처 표기와 코드 우선 적용은 추적 가능성을 높인다. 누가 이 기준을 썼고 어떤 관찰에서 나온 판정인지 되짚을 수 있다. 그렇다고 그 기준이 학생의 실제 이해를 대표한다는 보증은 되지 않는다. "십의 자리에 작은 수를 놓았다"는 관찰이 정말 자릿값 개념의 부족인지, 단순 실수인지, 카드 배치 방식에 익숙하지 않아서인지는 코드로도 모델로도 알 수 없다.

그 검증은 교육 전문가 자문과 실제 학생 데이터가 있어야 한다. 활동 유형별로 무엇이 관찰 가능한지도 아직 정리하지 못했다. 영상 입력 실험도 끝나지 않았다. 평가 기준 중 확정 못 한 항목은 초안에 "미정"으로 남겼다. 지금 확실한 것은 생성된 가설과 관찰된 사실을 같은 모양의 칸에 두면 안 된다는 점 하나다.
