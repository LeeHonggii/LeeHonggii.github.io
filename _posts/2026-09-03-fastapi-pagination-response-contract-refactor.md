---

API 계약이라는 건 처음엔 사소해 보인다. 응답에 `status: "success"` 하나 더 붙어 있는 게 뭐가 문제냐고. 근데 클라이언트가 두 곳이 넘어가기 시작하면 이야기가 달라진다.

---

계기는 간단했다. 프론트엔드 쪽에서 실패 응답을 처리하는 방식이 엔드포인트마다 달랐다. 어떤 곳은 HTTP 상태코드를 보고, 어떤 곳은 응답 body 안의 `status` 필드를 봤다. 둘 다 `200`으로 내려오면서 body에 `status: "error"`가 들어오는 케이스도 있었다. 모니터링 입장에서는 최악이다. 4xx, 5xx가 찍혀야 알람이 울리는데, 모든 게 200으로 오면 조용히 실패한다.

그래서 방향을 정했다. **성공 여부는 HTTP 상태코드로만 판단한다.** 응답 body에서 `status` 필드를 제거하고, 실패 시에는 FastAPI의 `HTTPException`으로 적절한 4xx/5xx를 내린다. body는 데이터만 담는다.

---

목록 API 응답 구조도 같이 손봤다. 기존엔 `count`와 `templates`로 내려오던 걸 `totalCount`와 `list`로 바꿨다. 이름 자체보다 `totalCount`의 정의가 더 중요했는데 — 이건 **페이지네이션 이전 전체 개수**다. 지금 페이지에 몇 개가 있는지가 아니라, 이 쿼리 조건에 맞는 전체 행 수.

프론트에서 페이지 수를 계산할 때 이 숫자가 필요하다. `Math.ceil(totalCount / limit)` 이 되어야 하니까. 만약 `totalCount`가 현재 페이지 개수를 가리키면 마지막 페이지가 언제인지 알 방법이 없다.

---

페이지네이션 파라미터로는 `offset`과 `limit`을 받기로 했다. 여기서 착각하기 쉬운 부분이 있다. 이름이 `offset`이라 SQL의 `OFFSET` — 즉 건너뛸 행 수 — 로 해석하기 쉬운데, 이 API에서 `offset`은 **1-based 페이지 번호**다.

실제 SQL에 넘기는 skip 값은 이렇게 계산된다:

```
skip = (offset - 1) * limit
```

1페이지면 skip = 0, 2페이지면 skip = 30(limit=30일 때). 클라이언트가 `offset=1`을 보내면 첫 번째 페이지를 달라는 뜻이고, 행 번호 1번부터 달라는 뜻이 아니다. 이게 합의가 안 되면 클라이언트는 2페이지를 보여줘야 할 때 `offset=30`을 보내고, 서버는 그걸 31페이지로 해석한다.

---

엔드포인트 형태는 이렇게 확정했다:

```
GET /templates-by-tool/{main_tool}?offset=1&limit=30
```

응답은:

```json
{
  "totalCount": 7,
  "list": [...],
  "main_tool": "SM02PB"
}
```

`main_tool`을 응답에 echo하는 건 디버깅할 때 요청이 제대로 라우팅됐는지 눈으로 확인하기 편하다는 이유였다. 문서에도 넣었다.

---

골치 아팠던 건 **랜덤 추천 API에 페이지네이션을 붙이는 부분**이었다.

`ORDER BY RAND()`와 페이징은 근본적으로 충돌한다. 첫 번째 요청에서 무작위로 섞인 순서가, 두 번째 요청에서는 다시 섞이기 때문이다. 사용자가 2페이지를 요청했을 때, 1페이지에 나왔던 항목이 또 나올 수 있고 일부는 영원히 안 나올 수도 있다.

해결책은 크게 두 가지였다. seed를 고정해서 같은 세션 내에서는 순서를 유지하는 방식, 아니면 랜덤성은 포기하고 출력 형식(totalCount/list)만 페이지네이션 계약에 맞추는 방식. 요구사항을 다시 확인했고, 결국 랜덤 추천 자체의 성격상 "페이지를 넘기며 탐색한다"는 유스케이스가 없다는 걸 확인했다. 형식만 맞추는 쪽으로 조율했다.

---

이 작업은 코드를 얼마나 썼느냐보다 계약을 얼마나 명확하게 말로 정의했느냐가 작업량의 대부분이었다. `offset`이 뭘 의미하는지, `totalCount`가 언제 기준인지, 실패 응답은 어디서 판단하는지. 이게 문서에 없으면 구현은 맞아도 사용은 틀린다.

아직 남은 건 있다. 랜덤 추천에 seed 기반 고정 순서를 언젠가 붙여야 하는지 — 지금은 유보했지만 서비스가 커지면 다시 꺼낼 질문이다.
