다른 언어로 만들어진 API 계약을 Python(FastAPI)으로 옮기는 일을 맡았다. 계산식 몇 줄이면 끝날 줄 알았다. 실제로는 파라미터 하나가 Swagger 문서에서 통째로 사라졌고, 응답 형식과 성공 판별 방식까지 건드려야 했다.

## offset은 offset이 아니었다

전달받은 규격에는 `offset`과 `limit`이 있었다. 이름만 보고 `OFFSET offset`으로 쓰면 되겠다고 생각했다. 규격을 끝까지 읽어 보니 `offset`은 행 오프셋이 아니라 **1부터 시작하는 페이지 번호**였다. SQL에 넘길 값은 따로 계산해야 한다.

```python
skip = (offset - 1) * limit
```

```sql
LIMIT :limit OFFSET :skip
```

이름이 같은 값을 그대로 SQL에 넣으면 1페이지를 요청해도 첫 `limit`개를 건너뛴다. 에러도 없다. 데이터만 조용히 어긋난다.

이 때문에 `offset=0`이 입력 경계가 된다. 페이지 번호가 1부터라면 0은 거부해야 한다. 0을 그대로 계산하면 `skip`이 음수가 되고, DB에 따라 오류가 나거나 다르게 동작한다. 그래서 하한 검증을 넣었다. `limit`도 상한을 넘기는 값(`limit=301` 같은 경우)이 거부되는지 확인했다.

## 반환 개수와 전체 개수는 다른 값이다

기존 응답은 조회된 항목만 돌려주는 형태였다. 페이지네이션을 제대로 하려면 클라이언트가 전체 건수를 알아야 해서, 응답을 아래 모양으로 바꿨다.

```json
{ "totalCount": 100, "list": [] }
```

`list`의 길이는 `limit` 이하다. `totalCount`는 조건에 맞는 전체 대상 수이고, 이 값을 채우려면 `COUNT` 쿼리가 따로 필요하다. 쿼리를 추가하고 API 문서도 같이 고쳤다. 응답 필드 이름만 바꾸고 문서를 두면 호출자가 `list`의 길이를 전체 건수로 착각하기 쉽다.

## 모델 필드가 파라미터로 노출되지 않았다

이 글의 제목이 된 문제다. 쿼리 파라미터를 Pydantic 모델로 묶어 받는 방식으로 짰다. 여기에 랜덤 조회용 `seed`를 별도 파라미터로 하나 더 선언했다. 서버는 정상적으로 떴다. Swagger를 열어 보니 모델의 필드(`offset`, `limit`)가 개별 쿼리 파라미터로 보이지 않았다.

원인을 끝까지 파고들지는 않았다. 증상은 분명했다. 모델 하나와 별도 파라미터를 함께 선언하면 FastAPI가 모델 필드를 개별 파라미터로 풀어 주지 않았다. `seed`를 모델 필드로 합치자 파라미터가 다시 나타났다. 내부 동작을 확인해서 얻은 결론이 아니다. 이 방식에서 그렇게 동작했다는 관찰이다.

그 `seed`는 결국 지웠다. 랜덤 조회에서 시드를 고정해 같은 순서를 재현하는 방법을 시도했다. 하지만 요구는 매 요청마다 랜덤으로 뽑는 것이었다. 응답 형식도 다른 API와 맞추기로 했다. 파라미터 문제를 풀려고 합친 필드가 이후에 통째로 사라진 셈이다.

## status 필드를 없애는 일

응답에서 `status` 필드를 빼고 HTTP 상태코드로 오류를 표현하도록 바꿨다. 코드로 보면 작은 변경이다. 그런데 공용 응답 모델이 이 필드를 갖고 있었고, 호출하는 쪽도 `status` 값을 보고 성공 여부를 판단하고 있었을 수 있다. 호출자 쪽 코드는 확인하지 못했다. 그래서 호출자에게 알려야 할 변경을 두 가지로 정리했다. 성공 판별이 HTTP 상태코드로 바뀐다는 것과, 기본 반환 개수가 달라진다는 것이다. 둘 다 조용히 바뀌면 문제가 되는 종류다.

## 검증한 것과 못 한 것

확인한 것은 이렇다.
- 스키마와 입력 경계값 검증
- 변경한 테이블 이름 기준으로 JOIN 참조를 고친 쿼리를 실제 DB에서 직접 실행

확인하지 못한 것도 있다. 앱의 SQLAlchemy 경로에서 `LIMIT :limit OFFSET :skip`이 제대로 바인딩되는지는 아직 보지 못했다. SQL을 직접 실행해서 통과한 것과, ORM을 거쳐 파라미터가 바인딩되는 것은 별개다. 이 변경은 로컬 커밋까지만 끝났고, 앱을 띄워서 실제 요청을 보내 보는 일과 원격 반영이 남아 있다.

외부망에서 만든 커밋을 패치로 내부망에 옮기는 과정에서도 로컬과 원격 브랜치 이력이 어긋나 push 오류가 났다. 이 부분은 이번 API 변경과 별개로 한 번 정리해야 한다.

`totalCount`를 구하는 `COUNT` 쿼리가 조회 쿼리와 같은 조건을 쓰는지도 앱을 띄운 뒤에 봐야 한다. 지금은 두 쿼리가 따로 있어서, 한쪽 조건만 고치면 `totalCount`와 `list`가 어긋날 수 있다.
