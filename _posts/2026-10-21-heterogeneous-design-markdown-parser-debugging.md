Markdown 하나에서 PPTX와 HTML 발표 자료를 뽑는 도구를 만들고 있었다. 원문 내용은 그대로 두고, 브랜드 디자인과 페이지 레이아웃만 바꿔 끼우는 구조다. 브랜드 디자인은 별도 Markdown 명세 파일로 받는다. 이 글은 그 명세 파일을 읽는 파서에서 겪은 문제 세 개를 적은 기록이다.

이 글에는 코드를 싣지 않았다. 이번 작업에서 가져온 저장소 코드는 파서와 관계가 없었다. 없는 코드를 지어 넣는 것보다 구조와 판단만 쓰는 편이 낫다고 봤다.

## 처음 가정: 명세는 다 같은 모양일 것

디자인 명세 파일이 모두 같은 스키마일 거라고 가정했다. frontmatter(문서 맨 위 `---` 사이의 메타데이터 블록)에 이름·설명·색상이 있고, 본문에 세부 규칙이 있는 구조다. 그 가정으로 정규식 하나에 모든 걸 맡겼다.

가정은 틀렸다. 명세는 여러 곳에서 모은 것이라 모양이 제각각이었다. 세 증상이 차례로 나왔다.

## 증상 1: 파서가 멈췄다

어떤 명세를 넣자 에러 없이 처리가 끝나지 않았다. 죽지도 않았다. CPU만 계속 쓰고 있었다.

Python 정규식이 catastrophic backtracking(매칭 실패 시 가능한 경로를 지수적으로 되짚느라 사실상 멈추는 현상)에 빠진 것이다. 중첩된 반복 패턴이 구조가 조금 다른 입력을 만나 걸렸다.

정규식을 고쳐 볼 수도 있었다. 하지만 구조가 제각각인 입력을 정규식 하나로 받는 설계 자체가 문제라고 판단했다. 그래서 정규식 전체를 라인 기반 파서로 교체했다. 한 줄씩 읽으면서 지금 어느 구간인지 상태만 들고 간다. 느리게 만들 경로가 없고 입력 길이에 비례해서만 돈다. 교체한 뒤에는 처리가 끝까지 진행됐다.

정규식 시절의 처리 시간과 교체 후 시간은 재지 않았다. "멈췄던 게 끝난다"만 확인했고, 성능 수치는 없다.

## 증상 2: 디자인 카드에 설명 대신 ‘|’

멈춤을 해결하자 다음 문제가 보였다. 디자인 선택 카드에서 어떤 브랜드의 설명 자리에 글자 `|` 하나만 떠 있었다.

원본 명세의 frontmatter는 이런 모양이었다.

```yaml
description: |
  여러 줄로 쓴 설명이 여기 들어간다
  둘째 줄
```

`|`는 YAML의 block scalar 표시다. "다음 줄부터 들여쓴 부분이 이 값의 본문"이라는 뜻이다. 내 파서는 `key: value`를 한 줄씩 읽었다. 그래서 `description`의 값을 `|`로 읽었고, 들여쓴 후속 행은 키가 없는 줄이라 버렸다. 설명 문자열이 `|`가 된 이유다.

frontmatter를 읽는 `_parseFrontmatterMeta`에 처리를 추가했다. 값이 `|`로 시작하면 이어지는 들여쓴 행을 모아 합친다. 들여쓰기가 끝나는 줄에서 멈춘다.

YAML 전체를 구현한 것은 아니다. 라이브러리를 쓰지 않고 필요한 부분만 손으로 처리했다. `|` 말고 다른 block scalar 표기나 중첩 구조는 아직 대응하지 않았다. 지금 명세에서 안 나왔을 뿐, 안 나온다는 보장은 없다.

## 증상 3: 색상이 아예 없다

카드에 색상 칩이 하나도 안 뜨는 명세가 있었다. 열어 보니 frontmatter 자체가 없는 문서였다. 파서는 frontmatter에서 색상 키를 찾고 있었으니 찾을 게 없었다.

대체 경로로 `_parseMarkdownFallback`을 만들었다. frontmatter가 없으면 다음 순서로 뽑는다.

- 이름: 첫 H1 제목
- 설명: 본문
- 색상: 본문 안에서 찾은 색상 코드

색상 쪽에는 설계 문제가 하나 더 있었다. 렌더링이 `primary`, `secondary` 같은 고정 키를 기대하고 있었다. 키 이름은 명세마다 달랐고, 대체 경로로 뽑은 색상에는 이름이 아예 없었다. 그래서 고정 키를 버렸다. 순서가 있는 `colorList`로 바꾸고, 렌더러는 있는 만큼 순서대로 칩을 그린다. 어떤 색이 어떤 역할인지는 이 방식으로는 알 수 없다. 이름 있는 키의 정보는 일부 잃는 셈이다.

## 확인한 범위

수정은 7개 브랜드 샘플로 검증했다. 설명이 `|`로 나오지 않고, 색상이 비지 않고, 멈추지 않는 것을 샘플 단위로 봤다. 샘플 외 명세에 대한 보장은 없다. 7개가 입력의 다양성을 충분히 덮는지도 따져 보지 않았다.

## 아직 남은 것

발표 자료 생성은 샘플 테스트를 통과했다. 그런데 마지막에 실제 UI에서 PPTX 생성에 문제가 있다는 제보가 들어왔다. 샘플로 돌리던 경로와 UI를 거치는 경로가 같은지부터 확인해야 한다. 원인이 파서인지, 파서 뒤쪽 렌더링인지, UI가 넘기는 입력인지는 아직 모른다. 지금 확인된 것은 샘플에서는 통과한다는 것뿐이다.
