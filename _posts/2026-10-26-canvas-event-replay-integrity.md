수학 교구를 조작한 기록으로 학생의 풀이 과정을 복원하는 분석기를 만들고 있다. 학생이 화면에서 블록을 옮기고 합치고 쪼갠 흔적을 이벤트 로그로 받아서, 그걸 다시 돌려 "이 학생은 3개짜리 묶음 두 개를 만들었다" 같은 문장으로 바꾸는 일이다.

처음 이상하다고 느낀 건 숫자가 아니라 **빈칸**이었다. 화면에서는 분명히 블록이 한 판에서 다른 판으로 넘어갔는데, 재생 결과에는 그 블록이 어디서도 나타나지 않았다. 사라진 것도, 옮겨진 것도 아니었다. 그냥 없었다.

## 식별자만으로는 값을 알 수 없다

버그에 닿기 전에 먼저 걸려 있던 문제가 있다. 로그에 남는 건 화면 요소의 식별자인데, 식별자만 봐서는 그 요소가 실제로 얼마를 뜻하는지 복원이 안 된다. 같은 모양의 조각이라도 교구마다 값의 의미가 다르다.

그래서 교구별 해석 규칙을 JSON 사전으로 빼고, 공통 코드가 그 사전을 읽어 값을 판독하도록 판독기를 고쳤다. 새 구조가 맞는지는 기존 사전을 그대로 넣었을 때 결과가 달라지지 않는지로 확인했다. 새 사전의 정확도가 아니라 **리팩터링 전후의 동일성**만 본 것이다. 이 구분은 뒤에서 다시 중요해진다.

## 로그가 들어오는 길

재생 버그를 의심하려면 입력이 어떻게 만들어지는지부터 알아야 했다. 조작 기록은 페이지마다 하나의 `recording` 문자열로 저장되어 있고, 압축된 경우 접두어가 붙는다.

```python
class AttemptIngest:
    @staticmethod
    def recording(text):
        if not text:
            return None
        if text.startswith("g:"):
            return json.loads(gzip.decompress(base64.b64decode(text[2:])).decode("utf-8"))
        return json.loads(text)
```

`g:` 가 붙으면 base64 → gzip 해제 → JSON 순서로 푼다. 이 단계는 문자열을 통째로 풀 뿐이라 이벤트를 하나도 건드리지 않는다. 로그가 사라지는 지점이 여기는 아니라는 걸 가장 먼저 확인한 셈이다.

그다음 활동 페이지만 골라 분석 단위로 나눈다.

## 판 사이를 이동할 때 사라진 것

재생기는 이벤트를 순서대로 읽으며 요소 상태를 갱신한다. 문제는 요소가 판 A에서 판 B로 넘어가는 경로였다. 이 경로에서는 이동, 삭제, 생성이 한꺼번에 일어난다. 원래 판에서 지우고 새 판에 만드는 식이다. 재생 과정에서 **요소 자체와 그 종류 정보가 떨어져 나갔다.** 삭제는 처리했는데 새 판에 만들 때 쓸 원본 정보가 이미 사라진 뒤였다고 이해하고 있다.

수정은 이동·삭제·생성을 같이 다루는 이 경로에서 정보가 끝까지 보존되게 하는 쪽이었다. 이 부분은 눈으로 한 번 보고 끝낼 수 없었다. 수정 뒤에는 "이동 전후로 같은 요소가 같은 종류로 남는가"를 따로 확인했다.

## `deleteAndCreate` 를 합치기로 읽어도 되나

로그를 훑다 보면 삭제 직후 생성이 이어지는 패턴(`deleteAndCreate`)이 자주 나온다. 처음엔 이걸 합치기나 쪼개기로 읽었다. 조각 둘이 사라지고 하나가 생기면 합친 것이고, 반대면 쪼갠 것이다.

프런트엔드 코드를 조사해 보니 이 가정은 틀렸다. 같은 패턴이 정렬에서도 나오고, 요소를 컨테이너에 넣을 때도 나올 수 있다. 사용자 눈에는 "정리했다"인 동작이 로그에서는 삭제 후 생성으로 찍힌다. 이벤트 이름이나 모양만으로 행동의 의미를 확정하면 안 된다. 앞뒤 요소의 값이 보존되는지까지 봐야 한다.

## 화면에 있는 것과 이력에 있는 것은 다른 증거다

더 근본적인 문제도 나왔다. 프런트엔드에는 현재 상태를 담은 `elements` 와 조작 이력을 담은 `historyStack` 이 따로 있다. 둘은 항상 같이 움직이지 않는다.

조사한 코드에서는 화면은 바뀌는데 이력에는 안 남는 경우가 있었다. 계산을 돌린 경우나, 연관된 다른 요소가 같이 바뀌는 경우가 그렇다. 이런 동작은 최종 상태를 읽으면 결과가 보이지만 중간 과정은 이력만으로 복원할 수 없다. 학생이 어떻게 그 답에 도달했는지를 보려는 시스템에서, 결과는 있는데 과정이 없는 구간이 생기는 셈이다.

그래서 분석기가 읽는 대상을 둘로 나눠서 생각하기로 했다. 최종 저장 상태는 "무엇이 남았나"의 증거이고, 이력은 "무슨 조작을 했나"의 증거다. 서로 다른 질문에 답한다.

## 빈 상태의 버튼 클릭은 검증이 아니었다

이 과정에서 내 시험이 얼마나 얕았는지도 드러났다. 기존 시험은 대부분 빈 캔버스에서 버튼을 누르는 정도였다. 요소가 없으면 이동도 계산도 일어나지 않으니 이벤트 누락이 있어도 통과한다.

시험 범위를 값 입력, 드래그, 계산, 저장 시점까지 넓혔다. 값을 넣고 끌어 놓고 계산한 뒤 저장했을 때, 화면의 상태와 로그에서 복원한 상태가 맞는지를 본다.

## 아직 남은 것

- 실제 화면과 재생 결과를 눈으로 대조하는 작업은 끝내지 못했다. 시험이 통과한다는 것과 화면과 같다는 것은 다른 이야기다.
- 화면과 이력이 어긋난다고 의심한 동작 중 일부는 아직 재현하지 못했다. 코드를 읽고 의심만 하는 상태라 확정해서 쓰지 않았다.
- 버그가 이번 수정 전에 얼마나 많은 기록에 영향을 줬는지는 세어 보지 않았다. 숫자가 없으니 쓰지 않는다.

이력에 빠지는 동작은 재생기를 아무리 고쳐도 복원되지 않는다. 그걸 분석 쪽에서 메울지, 수집 쪽에서 기록하게 할지는 아직 정하지 못했다.
