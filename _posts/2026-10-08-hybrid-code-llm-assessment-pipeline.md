학생이 화면 위에서 카드를 움직여 식을 만든다. 그 과정을 이미지와 활동 이력으로 남기고, 멀티모달 LLM이 판정과 서술형 평가를 낸다. 기존 평가 코드를 읽으면서 가장 먼저 걸린 질문은 모델 성능이 아니었다. 같은 기록을 두 번 돌리면 같은 말을 하느냐였다.

이 글은 그 코드를 읽고 정리한 학습 노트다. 새 시스템을 만들었다는 글이 아니다. 아래 코드는 저장소에서 읽은 것이다. 변동을 재는 쪽 코드이고, 재서 나온 수치는 내 손에 없다. 그래서 숫자는 쓰지 않는다.

## 실행 순서부터 다시 확인했다

처음엔 "이미지 분석 → 평가 → 리포트"로 알고 있었다. 호출 흐름을 따라가 보니 실제 순서는 이랬다.

```text
정규화 → 활동 이력 문장화 → 평가 입력 조립·코드 계산 → LLM 평가 → 코드 확정값 반영 → 리포트 서술 → 저장
```

오해한 부분은 "평가 입력 조립"이었다. 조작 횟수나 조건 충족 여부 같은 값은 별도의 계산 단계가 아니다. LLM에 넘길 입력을 조립하다가 같이 계산된다. 사전 비전 처리와 리포트 생성도 서로 다른 단계다. 이 둘을 한 덩어리로 보면 어느 값이 모델 호출 전에 확정되는지 흐려진다.

## 모델에게 맡기지 않을 것

설계의 뼈대는 이렇다. 코드로 셀 수 있는 것은 코드가 센다. 조작 수, 조건 충족 여부가 여기에 든다. 이 값은 LLM 평가 응답이 돌아온 뒤 후처리로 덮어쓴다. 마지막 서술 단계의 모델에게는 판정을 다시 내릴 권한을 주지 않는다. 서술은 확정된 값을 문장으로 풀어 쓰는 역할로 제한한다.

모델이 인용할 근거도 제한한다. 식별자가 붙은 관찰 목록만 인용하게 하고, 변하지 않는 지시문(정적 프롬프트)과 기록마다 달라지는 데이터를 입력에서 따로 구성한다. 이 부분은 구조를 분석한 수준이다. 구현해서 검증한 건 아니다.

## 근접도: "처음 화면 몫"을 빼는 정규화

코드가 확정하는 값의 예가 근접도 곡선이다. 시간에 따라 모범답안 카드와 겹치는 정도를 0~1로 정규화한다.

```python
class Normalized:
    @staticmethod
    def series(curve):
        if not curve:
            return None
        m0, tot = curve[0]["matched"], curve[0]["total"]
        if tot - m0 <= 0:
            return None
        return [{"t": c["t"], "v": max(0.0, min(1.0, (c["matched"] - m0) / (c["total"] - m0)))} for c in curve]

    @staticmethod
    def final(curve):
        s = Normalized.series(curve)
        return round(s[-1]["v"], 3) if s else None
```

첫 시점의 `matched`를 기준선(`m0`)으로 빼는 점이 중요하다. 문제가 처음부터 일부 카드를 맞춘 채로 시작할 수 있기 때문이다. 학생이 한 일만 점수에 남기려는 설계다. 분모가 0 이하이면 `None`을 돌려준다. 올릴 여지가 없는 문제에 0점이나 1점을 억지로 주지 않겠다는 뜻이다.

약점도 보인다. 이 기준선은 초기 화면 복원이 정확하다는 전제 위에 선다. 복원이 잘못되면 `m0`가 틀어진다. 그러면 같은 문제인데도 곡선이 다르게 정규화된다. 문제 정의 캐시와 판정 기준도 함께 갈라질 수 있다. 문제 정의와 답안 대조를 분리해 공통 기준을 재사용하는 구조의 이점이 이 지점에서 약점으로 바뀐다.

## 목표 단위로 짝짓기

구성 문제는 목표가 여러 개다. 가장 큰 식, 가장 작은 식 같은 것들이다. 학생 식을 어느 목표에 대응시킬지는 모범답안 식이 놓인 높이로 정한다.

```python
class GoalRows:
    """구성 문제의 목표(가장 큰/작은 식)마다 모범답안 식이 놓인 높이를 잡아, 학생 식을 목표에 짝짓는다."""

    # ... (모범답안 프레임에서 goal_y 계산)

    def assign(self, exprs):
        out = {}
        for e in exprs:
            cy = (e["box"][1] + e["box"][3]) / 2
            g = min(self.goal_y, key=lambda k: abs(self.goal_y[k] - cy))
            if abs(self.goal_y[g] - cy) < 140 and g not in out:
                out[g] = e
        return out
```

가장 가까운 목표 행에 붙이되, 140 픽셀 안에 들어오고 아직 비어 있는 목표일 때만 배정한다. 이 140이 어떻게 정해졌는지는 코드에서 근거를 찾지 못했다. 경험적으로 잡은 값으로 보이지만 확인이 필요하다. 또 `g not in out` 때문에 한 목표에는 식이 하나만 붙는다. 같은 줄에 식을 두 개 쓰면 먼저 순회된 쪽이 이긴다.

## 변동을 재는 코드

"LLM이 매번 다른 점수를 낸다"는 말을 코드로 검증해 보려는 곳이 안정성 측정이다. 웹 화면과 같은 입력, 같은 검사로 모델을 다시 부르되 저장본은 건드리지 않는다.

```python
class RepeatJob:
    """기록 하나에 웹과 같은 입력·같은 검사로 AI 를 다시 부르되 저장본은 건드리지 않는다."""

    def feedback_once(self):
        ev = self.pf.ev
        images = [ev.image()] + ([ev.model_image()] if self.pf.has_model else [])
        call = OpenaiChatCompletion(system=self.pf.system, user=self.pf.text, images=images, max_tokens=6000).run()
        if call.error:
            return {"error": call.error}
        result, _ = self.pf.check(call.parsed)
        return result
```

`self.pf.check(call.parsed)`가 이 글의 주제와 맞닿는다. 모델 응답이 그대로 결과가 되지 않고 코드의 검사를 한 번 거친다. 변동을 재는 대상도 모델 출력이 아니라 이 검사까지 통과한 최종 결과다. 코드가 확정한 값이 실제로 변동을 줄이는지 보려면 이 지점을 재야 한다.

비교할 항목은 값의 모양을 맞춰 뽑는다.

```python
    @staticmethod
    def values(fb, rv):
        out = {"판정": fb.get("판정"), "확인_필요": fb.get("확인_필요"), "모범답안과": fb.get("모범답안과")}
        for k in RUBRIC:
            out[f"루브릭:{k}"] = ((rv.get("루브릭") or {}).get(k) or {}).get("점수")
        out["전략"] = tuple(sorted({t["태그"] for t in rv.get("전략") or []}))
        out["오개념"] = tuple(sorted({m["id"] for m in rv.get("오개념") or []}))
        out["선개념"] = tuple(sorted((c["개념"], c["신호"]) for c in rv.get("선개념") or []))
        return out
```

리스트로 나오는 항목은 `sorted`와 `tuple`로 순서를 없앤다. 같은 오개념을 다른 순서로 말해도 같은 값으로 센다. 서술 표현은 비교하지 않고 태그, ID, 점수만 본다. 문장은 매번 달라지는 게 당연하기 때문이다. 일치율은 `repeats`만큼 반복한 뒤 항목별로 같은 값이 나온 비율로 센다. 기본값은 세 번이고 활동 전체 기록을 대상으로 돌린다.

## 아직 비어 있는 것

- 안정성 측정의 결과 수치는 이 글에 없다. 코드는 읽었지만 일치율 표를 내 눈으로 확인하지 못했다.
- 선개념·오개념이 검증된 지식 조회 결과인지 모델 추론인지는 구분해 두어야 한다. 전문가가 입력한 값과 학생의 이해도 판정도 별개다. 앞의 것이 뒤의 것을 보증하지 않는다.
- 다양한 활동 유형을 지원하는 신규 평가 시스템은 기획 초안까지만 정리했다. 영상 분석과 새로운 입력 경로는 검토 단계에서 멈췄다. 구현한 게 아니다.
- 타입 검사(`npx tsc --noEmit`)와 테스트(`npm test`)가 도는 쪽은 이번 읽기에서 확인하지 못했다.

초기 화면 복원이 틀어졌을 때 정규화 기준선이 얼마나 흔들리는지, 그리고 코드 확정값을 덮어쓴 뒤의 일치율이 덮어쓰기 전과 얼마나 다른지는 다음에 직접 재 볼 생각이다.
