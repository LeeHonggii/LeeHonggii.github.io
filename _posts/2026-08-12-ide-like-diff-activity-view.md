로그 뷰어를 열 때마다 같은 카드가 두 장씩 쌓여 있었다. 위 카드엔 "파일을 편집하려 함", 아래 카드엔 "파일을 편집했음". 툴 하나 호출에 카드가 두 장. 스크롤이 두 배가 됐고, 사용자는 두 카드를 번갈아 보다가 "이거 같은 거 아니에요?"라고 물었다.

같은 거 맞다. 에이전트가 도구를 부르기 직전에 한 번(`PreToolUse`), 결과를 받은 직후에 한 번(`PostToolUse`) — 이벤트가 두 번 발생한다. 별개의 이벤트로 흘려보내면 UI에도 두 번 찍힌다.

## 같은 호출이라는 걸 어떻게 아는가

처음엔 타임스탬프가 가까우면 같은 쌍으로 묶으려고 했다. 실패했다. 병렬로 도구를 두세 개 부르면 Pre 세 개가 먼저 몰려오고 Post 세 개가 뒤따라 오는데, 시간만 보면 누구랑 누구가 짝인지 알 수 없다.

Pre와 Post가 공유하는 값을 찾다가 fingerprint에 도착했다. 툴 이름·입력값 해시·요청 ID를 이어 붙인 문자열. Pre가 만들 때 넣고, Post도 같은 재료로 다시 계산해서 넣는다. 그러면 두 이벤트를 Map의 같은 키로 끌어와 하나로 합칠 수 있다.

로직 자체는 짧다. Pre가 먼저 오면 카드를 만들고 `post: null` 상태로 둔다. Post가 도착하면 같은 fingerprint의 카드에 `post`를 채워 넣는다. 카드 상태는 자연스럽게 "실행 중"에서 "완료"로 넘어가고, 카드 수는 절반이 된다.

한 가지 실수했던 건 Post가 먼저 도착하는 경우를 처음에 안 다뤘다는 것. 스트림이 살짝 순서가 뒤바뀔 때가 있는데, 그때 Post-only 카드가 화면에서 실종됐다. 지금은 fingerprint가 처음 보이는 이벤트를 그냥 카드로 만들고, 두 번째가 오면 그 위에 덮는 방식이다. 어느 쪽이 먼저 와도 결과는 같다.

## Edit 카드에서 파일 전체를 펼치지 않기

두 번째 문제는 카드가 너무 컸다는 것. `Edit` 툴이 200줄짜리 파일을 건드리면 카드에 old/new 전체가 붙어서, 실제 바뀐 다섯 줄을 찾으려고 스크롤을 한참 굴려야 했다. 정보는 다 있는데 읽을 수가 없다.

카드 상단에 3–5줄짜리 요약을 얹기로 했다. 완벽한 diff가 아니다 — 사용자가 "이 카드 열어볼 가치가 있는가"를 1초 안에 판단할 수 있게 하는 힌트다. 그래서 로직도 단순하게 두었다: new 쪽에만 있는 줄 몇 개를 `+`로, old 쪽에만 있는 줄 한두 개를 `-`로. 진짜 diff 알고리즘은 아니다. 줄 이동이 있으면 오탐한다.

그래도 이걸 붙이니 사용자가 카드 목록을 훑는 속도가 눈에 띄게 바뀌었다. 전체를 보고 싶으면 "전체 diff 보기" 토글을 누른다. 기본은 접혀 있다. 접기 기준은 카드마다 독립적으로 저장해서 하나를 펼쳐도 옆 카드가 튀지 않게 했다.

여기서 아직 애매하게 남긴 게 있다. 변경 줄이 정확히 10줄 근처면 접힘/펼침 임계가 어색하다. 지금은 그냥 10줄로 자르고 있는데, 파일 종류(md vs. 코드)에 따라 다르게 걸어야 하는지 아직 결정 못 했다.

## Prism 없이 색을 입히는 쪽으로 후퇴

원래는 코드 블록에 Prism.js를 쓰려고 했다. 문법 강조(syntax highlight) 라이브러리. 문제는 두 가지. 번들이 커진다. 그리고 로그 뷰어는 첫 렌더에 카드 수십 장이 한번에 쏟아지는 화면인데, Prism의 언어 정의를 동적으로 로드하는 순간엔 하이라이트가 빠진 채 렌더된 카드가 잠깐 보인다. 사용자 눈엔 "색이 왜 안 들어와 있지" → 스크롤 → "이제 들어왔네" 순으로 깜빡인다.

정공법은 Prism 언어를 미리 다 preload하는 것이고, 후퇴는 regex 몇 개로 직접 칠하는 것이다. 후퇴 쪽을 택했다. 이유는 이 화면이 IDE가 아니라 로그 뷰어이기 때문이다. 사용자가 여기서 코드를 편집하지 않는다. "주석은 초록, 문자열은 주황, 키워드는 파랑" 정도만 되면 목적을 다한다.

regex 규칙 몇 개 — 주석, 문자열, 키워드, 숫자 — 를 순서대로 돌리는 것으로 시작했다. Python, JS, TS, CSS, JSON, Bash에 동일한 규칙 테이블을 그대로 쓴다. 언어별로 키워드 목록이 미묘하게 다르지만 로그 뷰어 정확도로는 충분하다. AST를 만드는 것도 아니고 토큰 컨텍스트도 안 본다. 문자열 안의 `#`를 주석으로 오탐하는 상황이 있는데, 지금 우선순위에서는 그냥 감수한다.

이 결정은 나중에 뒤집힐 수도 있다. 사용자가 로그 뷰어에서 코드 블록을 그대로 복사해서 다른 곳에 붙여넣는 흐름이 관찰되면 정확한 하이라이트가 필요해진다. 아직은 그런 요청이 없다.

## 아직 안 고친 것

Bash 이벤트가 아직 별도 취급이다. `PreToolUse`에는 명령어가 들어오는데 `PostToolUse`에는 stdout/stderr가 붙는다. 지금은 fingerprint로 합쳐서 한 카드에 명령·출력을 같이 보여주는데, 출력이 수백 줄이면 카드가 다시 화면을 잡아먹는다. Edit에 준 요약 로직을 여기에도 넣어야 하는데, 출력의 "핵심 줄"이 뭔지 정의가 애매하다. 마지막 N줄? 에러 라인만? 아직 못 정했다.

그리고 fingerprint 자체도 완벽하지 않다. 같은 파일을 정확히 같은 내용으로 두 번 편집하는 (드문) 경우, 두 호출의 fingerprint가 겹칠 수 있다. 지금은 요청 ID를 재료에 넣어서 대부분 갈리지만, 요청 ID가 비는 스트림 경로가 하나 남아 있다. 그 경로를 언제 손볼지는 다음 주에 볼 예정.
