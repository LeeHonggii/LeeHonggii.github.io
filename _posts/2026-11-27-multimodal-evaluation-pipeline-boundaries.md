멀티모달 학습 평가 파이프라인을 처음부터 끝까지 읽고 순서를 문서로 정리했다. 학생이 화면(교구 조작 캔버스)에서 문제를 풀면 그 결과가 평가 리포트가 되기까지의 과정이다. 정리하면서 내가 잘못 알고 있던 게 두 군데 나왔다. 그 두 군데가 이 글의 출발점이다.

## 내가 틀리게 이해하고 있던 것

처음엔 이렇게 그렸다. 이미지를 비전 모델이 분석하고, 그 결과로 리포트를 만들고, 마지막에 코드가 수치를 계산해 붙인다.

실제 코드를 따라가 보니 둘 다 틀렸다.

- 비전 분석은 리포트 생성 흐름 안에 있지 않았다. **별도로 실행**되고, 그 결과가 저장돼 있다가 뒤에서 쓰인다.
- 코드 계산은 맨 끝이 아니라 **평가 프롬프트를 조립하는 도중**에 돈다. LLM이 평가하기 전에 이미 값이 정해진다.

그래서 실제 케이스 하나가 처리되는 순서는 이랬다.

정규화 → 활동 문장화 → 평가 입력 조립(여기서 코드 계산) → LLM 평가 → 코드가 확정한 값 반영 → 리포트 서술 → 저장

"개념적으로 어떤 단계가 있는가"와 "실제로 어떤 순서로 실행되는가"는 다른 질문이었다. 둘을 한 장에 그리면 이런 오해가 생긴다. 이번에는 시퀀스 다이어그램으로 실행 순서만 따로 그렸다.

## 문제 정의와 답안 판정을 왜 나누나

입력 쪽에서 제일 마음에 든 설계는 문제 화면과 모범답안 화면의 역할 분리였다.

- 문제 화면은 문제가 무엇인지 정의하는 데 쓴다.
- 모범답안 화면은 정답 상태가 어떤 모습인지 정의하는 데 쓴다.
- 화면 데이터에서 뽑은 텍스트를 이미지와 **함께** LLM에 준다. 이미지만 주면 글자를 잘못 읽을 수 있고, 텍스트만 주면 배치와 모양 정보가 사라진다.

이렇게 만든 문제 정의는 학생 답안과 별개로 한 번만 만든다. 학생별로는 최종 화면만 이 정의에 비춰 판정한다. 같은 문제를 푼 학생 전원이 공통 기준으로 비교된다.

약점도 확인했다. 이 구조는 **초기 화면 복원이 맞아야** 성립한다. 시작 화면이 잘못 복원되면 같은 문제인데도 서로 다른 문제로 식별될 수 있다. 공통 기준이라는 장점이 입력 한 곳에 기대고 있는 셈이다. 실제로 이런 일이 얼마나 자주 나는지는 아직 재보지 않았다.

문제 정의를 만드는 쪽 코드(활동 하나의 규칙을 만들어 저장하는 작업)를 보면 이 전제가 코드에도 드러난다. 식별자는 일반화해서 옮겼고, 이 글과 관련 없는 부분은 줄였다.

```python
def build_one(self, act):
    """활동 하나 — 오개념은 같은 단위개념 진단 문항에서, 캔버스 시작 화면으로 규칙을 만든다."""
    RuleRows.put(self.row_of(act, "running"))
    mis = self.info.mis_texts(self.info.unit_misconceptions(act.get("unit")))
    canvas = self.canvas_of(act)
    maker = RuleMaker(workspace, {**act, "canvas": canvas}, mis)
    try:
        if not canvas:
            raise ValueError("묶음 안 캔버스 파일이 필요합니다")
        made = maker.build()
        bundle = {"engineVersion": ENGINE_VERSION, "mapVersion": self.info.map_version(),
                  "activity": {k: act.get(k) for k in ("id", "no", "title", "unit", "goal", "question", "answer")},
                  "concept": self.info.concept(act.get("unit")),
                  "misconceptions": mis, "scale": made["scale"], "rule": made["rule"]}
        row = self.row_of(act, "done", bundle=bundle, error=None)
    except Exception as e:
        row = self.row_of(act, "failed", bundle=None,
                          error=f"{type(e).__name__}: {e}"[:500],
                          trace=traceback.format_exc()[-1500:])
    # ... 사용량 기록, 임시 작업 폴더 정리
    return row
```

세 가지가 눈에 들어왔다.

- 규칙은 **활동마다 따로** 만들고, `running → done / failed` 상태를 행 단위로 남긴다. 활동 하나가 실패해도 나머지는 계속 가고, 실패한 활동만 사유와 함께 남는다.
- 캔버스가 없으면 LLM을 부르기 전에 막는다. 시작 화면이 없는 입력으로 규칙을 만들지 않는다는 뜻이다. 위에서 말한 "초기 화면이 틀리면 전부 흔들린다"에 대한 최소한의 방어다. 다만 이건 **없는 것**만 막는다. 있는데 잘못 복원된 화면은 못 거른다.
- 산출물(`bundle`)에 엔진 버전과 매핑 버전을 같이 넣는다. 나중에 같은 문제의 정의가 왜 달라졌는지 추적하려는 장치로 읽었다.

선개념·오개념 목록의 출처도 여기서 갈렸다. 오개념은 같은 단위개념의 진단 문항에서 가져온다. 학생별 진단 근거는 이 목록이 아니라 그 학생의 실제 활동 기록에서 나온다. 목록은 "이런 오개념이 있을 수 있다"는 후보이고, 이 학생이 실제로 그랬는지는 별개의 근거로 판단한다. 처음에는 이 둘을 섞어서 이해하고 있었다.

## 코드가 문장까지 쥐고 있는 부분

"계산 가능한 값은 코드가, 근거 기반 평가와 서술은 LLM이"라고 경계를 말하기는 쉽다. 리포트 모델 쪽 코드를 읽어 보니 코드가 값뿐 아니라 **문장의 일부까지** 쥐고 있었다.

```python
LEVELS = {"approach": ["다가가는 중", "돌아서 다가감", "곧게 다가감"],
          "attempt":  ["바로 해결", "몇 가지 시도", "여러 갈래로 시도"],
          "engage":   ["가볍게 다룸", "보통으로 다룸", "많이 다룸"],
          "strategy": ["눈으로 맞춤", "바꿔 가며 세움", "관계를 세워 풂"]}
WEIGHT = {"place": 4, "off": 3, "fix": 3, "redo": 2, "try": 1, "put": 0}
MIS_WEIGHT, MARKS_MAX, MARK_NEAR = 4, 5, 0.08
```

수준 표현을 3단계 고정 어휘로 못 박았다. LLM이 "다소 아쉬운 편"이나 "꽤 훌륭한" 같은 말을 그때그때 만들어 내면 같은 행동이 학생마다 다른 표현으로 나갈 수 있다. 어휘를 코드에 두면 그 여지가 없다. 대신 표현의 폭도 같이 사라진다.

```python
FIXED = {"스스로바로": ("스스로 고침", "틀렸다는 표시 없이 바로 스스로 고쳤습니다."),
         "스스로나중": ("스스로 고침", "틀렸다는 표시 없이, 다른 곳을 다룬 뒤 돌아와 스스로 고쳤습니다."),
         "틀린표시뒤": ("표시 뒤 고침", "답이 틀렸다는 표시를 본 뒤 고쳤습니다."),
         "맞은표시뒤": ("표시 뒤 바꿈", "답이 맞았다는 표시를 본 뒤 바꿨습니다.")}
WHY = {"계산실수": "풀이 방법은 맞고 계산이나 옮기기 한 단계가 어긋난 것으로 보입니다.",
       "옮겨씀":   "문제나 화면에 있는 다른 수 · 기호를 그대로 가져온 것으로 보입니다."}
TOOL_SAID = {"answer_right_tool_wrong": "답은 맞았지만 교구에는 정답과 다른 것이 남아 있습니다.",
             "answer_wrong_tool_right": "답은 틀렸지만 교구는 정답대로 놓여 있습니다.",
             "both_right": "교구도 정답대로 놓여 있습니다."}
```

여기서 문장 톤이 갈린다. `FIXED`는 관찰된 **사실**이라 "~했습니다"로 단정한다. `WHY`는 **추정**이라 "~것으로 보입니다"로 쓴다. 이 구분이 코드 상수 단계에서 이미 고정돼 있다. LLM에게 "사실은 단정하고 추정은 유보하라"고 프롬프트로 부탁하는 것과 다르다. 부탁은 어길 수 있지만 상수는 어길 수 없다.

`TOOL_SAID`의 키(`answer_right_tool_wrong` 등)는 답과 교구 상태가 어긋나는 경우를 코드가 먼저 분류한다는 뜻이다. 이 분류가 맞는지는 별개 문제다. 아래에서 다시 다룬다.

한국어 처리도 코드가 맡는다. 조사 선택이 한 예다.

```python
def josa(word, with_final, without):
    """받침에 맞는 조사 — 「으로」는 ㄹ 받침 뒤에서도 「로」."""
    c = re.sub(r"[^가-힣0-9A-Za-z]+$", "", str(word or ""))[-1:]
    if "가" <= c <= "힣":
        final = (ord(c) - 0xAC00) % 28
        return with_final if final and not (with_final == "으로" and final == 8) else without
    if c.isdigit():
        return with_final if c in "136780" and not (with_final == "으로" and c in "178") else without
    return without

def mis_verb(name):
    """오개념 이름(「~함 · ~봄 · ~씀 · ~둠 · ~음」)을 「~는」 꼴로."""
    if name.endswith("음"):
        return name[:-1] + "는"
    end = {"봄": "보는", "함": "하는", "씀": "쓰는", "둠": "두는"}.get(name[-1:])
    return name[:-1] + end if end else name
```

`josa`는 받침 유무로 조사를 고른다. `final == 8`은 ㄹ 받침이고, 이 경우 "으로"가 아니라 "로"가 붙는다("연필로"). 숫자 뒤도 읽는 소리 기준으로 처리한다. "1"은 "일"이라 받침이 있고 "2"는 "이"라 받침이 없다. 이런 규칙은 코드가 틀릴 때 어떻게 틀리는지 예측할 수 있고, LLM은 대체로 맞히지만 가끔 틀린다. 리포트 문장 한 줄에 조사가 틀리면 신뢰가 확 깨져서 이 부분은 코드 쪽에 두는 게 낫다고 봤다.

## 코드값으로 덮어쓴다는 것의 한계

설계 의도는 이렇다. LLM이 평가하면서 어떤 수치나 판정을 내더라도, 코드가 확정한 값이 있으면 그것으로 덮어쓴다. 출력의 일관성은 확실히 올라간다. 평가 본문에서는 3단계라고 해 놓고 리포트에서는 다르게 쓰는 모순이 없어진다.

하지만 이게 **정확성**을 주지는 않는다. 코드값은 일관되게 틀릴 수도 있다. 덮어쓰기는 "LLM이 코드와 다른 말을 못 하게" 하는 장치일 뿐, 코드의 계산 로직이 맞다는 증거가 아니다. 위에서 본 `TOOL_SAID` 분류나 `WEIGHT` 값이 실제 학생 데이터에서 의도대로 동작하는지는 이 코드만 읽어서는 알 수 없다. `WEIGHT`가 어디서 어떻게 쓰이는지도 이번에는 끝까지 따라가지 못했다. 파일 일부만 읽었다.

반대쪽 한계도 있다. LLM이 맞게 평가했는데 코드값이 틀려서 맞는 평가가 덮어씌워지는 경우다. 이때는 오히려 코드가 품질을 깎는다. 덮어쓰기가 어느 방향으로 더 자주 작용하는지 측정한 적은 없다.

## 아직 안 한 것

풀이 **영상**으로 같은 분석을 해 보는 실험을 논의했다. 영상 한 편을 통째로 넣을지, 프레임을 뽑아서 정지 화면 여러 장으로 넣을지를 놓고 데이터 구성과 프레임 추출 방식을 이야기했다. 거기까지다. 영상 처리 코드는 짜지 않았고 결과도 없다. 그러니 "영상이 정지 화면보다 낫다/아니다"라고 쓸 근거가 지금은 없다.

지금 마음에 걸리는 건 프레임을 어떤 기준으로 뽑느냐다. 일정 간격이면 간단하지만, 학생이 교구를 한 번 옮기고 한참 생각하는 구간에는 같은 프레임이 반복되고 정작 중요한 순간은 놓칠 수 있다. 정지 화면 파이프라인이 "최종 화면"이라는 하나의 순간만 보던 것과 비교하면, 중간 과정을 보겠다는 건 판정 기준 자체를 다시 정해야 한다는 뜻이다. 이 부분을 어디서부터 건드릴지는 아직 못 정했다.
