목록 API에 페이지네이션을 붙이는 작업이었다. 코드는 금방 써졌고 문법 검사도 통과했다. 그런데 API가 실제로 받는 파라미터를 확인해 보니 `offset`, `limit`이 없었다. 이 글은 그 뒤에 한 확인 과정을 적은 기록이다.

## 선언은 했는데

요청 쪽 구조는 단순했다.

- `offset`, `limit`을 Pydantic 모델(데이터 검증용 클래스) 하나로 묶었다. 엔드포인트마다 파라미터를 따로 쓰지 않으려는 의도였다.
- 랜덤 정렬 목록에는 페이지 사이에 같은 항목이 겹치지 않게 하려고 `seed`를 별도 쿼리 파라미터로 추가했다.

문법 검사는 아무 말도 하지 않았다. 타입도 맞았다. 그래서 끝났다고 생각했다.

이상한 점은 생성된 API 스키마를 열어 보고서야 눈에 들어왔다. 모델에 선언한 필드들이 개별 쿼리 파라미터로 펼쳐져 있지 않았다. 호출자가 `?offset=2&limit=30`을 보내도 서버 입장에서는 선언된 계약이 아니었다.

## 원인은 아직 모른다

솔직히 말하면 원인을 끝까지 파지 못했다. 확인한 것은 이 정도다.

- 내가 쓰던 FastAPI 환경에서, 쿼리 모델과 별도의 `seed` 쿼리 파라미터를 함께 선언하면 모델 필드가 펼쳐지지 않았다.
- 프레임워크 버전별 동작 차이인지, 선언 방식 때문인지는 가려내지 않았다. 다른 버전에서 같은지도 재 보지 않았다.

그래서 이 글에서 "FastAPI는 이렇게 동작한다"고 일반화하지 않는다. 내 환경에서 이 조합이 깨졌다는 것까지만 말할 수 있다.

## 고친 방법

`seed`를 모델 밖에서 모델 안으로 옮겼다. 쿼리 파라미터를 모델 하나로 통일한 것이다. 다시 스키마를 생성해 보니 `offset`, `limit`, `seed`가 각각 개별 파라미터로 잡혔다.

이번에는 스키마만 믿지 않고 잘못된 입력에 대한 응답도 같이 봤다. 스키마에 이름이 보이는 것과 검증이 실제로 걸리는 것은 다른 문제이기 때문이다.

| 입력 | 결과 |
|---|---|
| `offset=0` | 422 |
| `limit=301` | 422 |
| `seed=-1` | 422 |

이 API에서 `offset`은 DB의 행 오프셋이 아니라 1부터 시작하는 페이지 번호처럼 쓰인다. 그래서 0은 거부된다. `limit`은 301이 거부되는 것으로 보아 상한이 300이다. 페이지 번호가 1, 2, 3일 때 내부 오프셋은 0, 30, 60으로 변환되는 것도 확인했다.

세 가지 422가 모두 나오자 비로소 계약이 구현됐다고 볼 수 있었다. 모델을 선언하는 것과 그 모델이 요청 바인딩에 반영되는 것은 서로 다른 일이었다.

## 그 seed는 지금 없다

이 수정은 기록으로만 남았다. 이후 요구사항이 바뀌어 랜덤 조회는 기존 무작위 정렬을 그대로 유지하기로 했다. `seed`는 제거됐다.

seed를 넣은 이유는 랜덤 정렬이 요청마다 순서를 새로 섞어서 페이지 사이에 중복이 생기기 때문이었다. 이 중복은 seed 없이 유지하기로 했으므로, 지금도 남아 있는 알려진 한계다. 얼마나 자주 겹치는지는 측정하지 않았다.

## 남은 것

- 변경은 로컬 커밋까지만 됐고 원격에는 올리지 않았다.
- 스키마와 422 응답은 확인했지만, 실제 앱을 띄워 DB까지 바인딩이 이어지는지는 아직 확인하지 않았다. 이걸 보기 전에는 끝났다고 말하기 어렵다.
- seed를 빼고 나서, 모델 하나로 통일한 쿼리 구조가 계속 정상적으로 펼쳐지는지도 다시 봐야 한다. 문제를 일으킨 조합이 사라졌으니 괜찮을 거라고 짐작할 뿐이다.
