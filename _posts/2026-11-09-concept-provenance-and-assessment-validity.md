멀티모달 평가 코드를 처음부터 읽다가 설명을 한 번 틀렸다. 이미지와 활동 로그가 평가와 리포트가 되기까지의 실행 순서를 내가 거꾸로 짚었다. 코드가 계산하는 부분과 LLM이 서술하는 부분이 섞여 있어서, 눈으로 훑을 때 둘을 구분하지 못했다. 순서를 바로잡고 문서와 시각화로 다시 정리한 뒤에야, 원래 궁금했던 질문이 보였다.

**이 시스템이 말하는 "선개념·오개념"은 어디서 오는가.**

## 목록이 어디서 오는지부터 확인했다

선개념(이 문제를 풀기 전에 이미 알고 있어야 하는 개념)과 오개념(학생이 흔히 잘못 이해하는 방식)을 보고 처음엔 교육과정 데이터베이스를 조회한 결과라고 생각했다. 그런데 프롬프트 쪽을 따라가 보니 아니었다. 문제를 입력하면 모델이 이런 모양으로 채워 넣을 수 있는 구조였다.

```json
"pre": ["이 문제를 풀기 전에 이미 알고 있어야 하는 개념"]
```

외부 지식베이스 조회가 아니다. 모델이 문제 텍스트에서 **추론한** 목록이다. 그럴듯하게 나올 수는 있어도, 검증된 교육과정 자료와 같은 자리에 놓으면 안 된다.

시험 코드를 다시 읽어 보니 같은 사정이 코드 주석에도 남아 있었다. 활동별 오개념 매핑을 시험용으로 손으로 넣어 둔 부분이다. (식별자는 일반화했다.)

```python
# 실증 문제집에는 활동별 오개념 칸이 없다 — 시험용 가정값, 실제 메타데이터가 오면 바꾼다
SETS = {
    "unit_A": (
        [f"session62-student{s}-p11" for s in ("01", "02", "03", "04", "11")]
        + [f"session62-student{s}-p12" for s in ("01", "02", "03", "11")],
        {11: ["A-M05"], 12: ["A-M04", "A-M06"]},   # 활동 번호 → 오개념 ID
    ),
    # ...
}
```

이 매핑은 내가 가정한 값이다. 활동 11번에서 일어날 오개념이 `A-M05`라는 근거는 문제집에 없다. 교사가 오개념 이름을 직접 입력하는 구조가 되더라도 결론은 같다. 목록의 출처는 사람일 수 있지만, 학생이 그 오개념을 갖고 있다는 판정은 여전히 별개 문제다.

## 기준이 생성되면, 판정은 무엇에 기대는가

이 파이프라인은 오개념을 곧바로 학생에게 붙이지 않는다. 먼저 활동을 단계로 나눈다. 그다음 "이 오개념의 혼동이 이 단계 조작에서 드러날 수 있는가"를 묻는다. 이 질문의 프롬프트가 설계에서 가장 마음에 든 부분이다.

```python
A4_SYS = """활동의 단계 하나와 오개념 하나를 본다. 이 오개념 설명에 나오는 혼동이 **이 단계의 조작**에서 드러날 수 있나만 판단한다.
- 있다: 설명 가운데 이 단계 조작과 겹치는 말을 원문 그대로 인용한다(설명에 없는 말 금지).
- 없다: 이 단계 조작으로는 그 혼동이 화면에 나타날 수 없다.
- 이 단계 자리에 [활동 조각]의 다른 조각을 넣거나 넣어야 할 조각을 빼는 것도 이 단계 조작이다.
JSON 으로만: {"답": "있다" 또는 "없다", "인용": "설명 원문 일부 또는 빈 글", "이유": "한 줄"}"""
```

"있다"고 답하려면 오개념 설명에서 **원문을 그대로 인용**해야 한다. 설명에 없는 말은 금지다. 모델이 그럴듯한 이유를 지어내는 길을 좁히는 장치다.

여기에 모델을 못 믿는 코드 쪽 안전장치가 하나 더 있다.

```python
# 정답 조각 ↔ 오개념 설명 낱말 짝 — 짝이 있는데 A4 가 「없다」면 놓친 것으로 보고 다시 묻는다
PAIRS = [("≤", "이하"), ("≥", "이상"), ("<", "미만"), (">", "초과"),
         ("●", "색칠한 점"), ("○", "빈 점"), ("닫힌", "색칠한 점"), ("-", "음수")]
```

정답 조각에 `≤`가 있고 오개념 설명에 "이하"가 있는데 모델이 "없다"고 하면, 놓친 것으로 보고 다시 묻는다. 모델의 부정 답변을 단순한 낱말 짝으로 검산하는 셈이다. 정교하진 않다. 낱말 짝이 이 여덟 개뿐이라는 것도 약점이다.

오개념이 일어났을 때 화면에 보일 조작을 쓰게 하는 쪽도 같은 방식으로 좁혀 놓았다.

```python
A5_SYS = """활동 단계 하나에서 오개념 하나가 일어나면 화면에 보일 조작을 쓴다.
- 정답 조작의 그 부분만 바꾼다(가장 작은 변형). ...
- 「넣는 조각」 = 정답 대신 들어갈 조각, 「빼는 조각」 = 그때 빠질 정답 조각. 조각은 화면 글 그대로 낱개로.
- 「핵심」 = 이 오개념을 가르는 조작 한 가지를 학생이 하는 쪽 말로(예: 「≤ 자리에 < 를 놓음」).
- 조각 이름은 [판독 예]가 쓰는 낱말 그대로 쓴다(코드가 이 낱말로 기록과 맞댄다).
JSON 으로만: {"보일 조작": "…", "넣는 조각": ["…"], "빼는 조각": ["…"], "핵심": "…"}"""
```

모델이 만든 "핵심"은 나중에 코드가 학생 기록과 맞대는 기준이 된다. 그래서 조각 이름을 판독 쪽 낱말에 맞추라고 강제했다. 코드가 문자열로 대조하려면 표현이 일치해야 하기 때문이다.

## 학생 쪽 판정에서는 "없음"을 근거로 쓰지 못하게 했다

학생이 실제로 한 조작을 기준과 맞대는 단계(Q2)에서는 이런 제약을 걸었다.

```python
Q2_SYS = """코드가 이 교구의 정답 조건을 맞대지 못했다. 학생 기록의 판독 줄만 보고 마지막 상태가 정답 조건과 같은지 고른다.
- 판독 줄에 그 조건을 가를 사실(그 위치·그 값)이 없으면 「판단 불가」. 조작했다는 것만으로 같음·다름을 정하지 않는다.
- 판독에 안 보인다는 것(없음)을 다름의 근거로 쓰지 않는다. 다름은 그 자리에 정답과 다른 것이 있다는 판독 사실이 있을 때만 고른다.
JSON 으로만: {"답": "같음 또는 다름 또는 판단 불가", ...}"""
```

관찰하지 못한 것을 "틀렸다"로 읽지 말라는 규칙이다. 로그와 이미지로 볼 수 있는 범위는 활동 유형마다 다르다. 로그에 값이 남는 활동은 비교적 믿을 수 있다. 마음속에서 일어난 추론은 어떤 로그에도 남지 않는다. 그 경우 "판단 불가"가 정직한 답이다.

이런 프롬프트는 로그에서 보인 사실에 판정을 묶는다. 그리고 판정에 쓸 오개념 후보는 한 번 더 좁힌다. 마지막 단계(Q4)에는 "다른 오개념을 새로 만들지 않는다"는 조항이 있어서, 목록에 없는 차이는 "목록에 없는 차이"로 남는다. 모델이 새 오개념을 발명해 학생에게 붙이는 길은 막았다.

## 그래도 타당도는 보장되지 않는다

여기서 한 번 착각했다. 출처를 표시하고, 인용을 강제하고, 관찰 근거와 대조하면 진단이 타당해진다고 생각했다. 아니다. 이 장치들은 **근거 없는 말을 줄이는 것**이지 **판정이 교사의 판단과 같다는 것**을 보여 주지는 않는다. 인용이 정확해도 그 오개념 설명 자체가 모델이 만든 것이면, 정확한 인용이 틀린 기준을 정확히 따라갈 뿐이다.

그러면 무엇이 필요한가. 교사가 같은 학생 기록을 보고 내린 판정 골드셋과, 사람 대비 일치도 평가다. 판정이 "있음/없음" 같은 명목 값이면 카파 계열을, 정도를 나타내는 서열 점수라면 가중 카파 같은 것을 검토할 수 있다. 어떤 지표가 맞는지는 판정 척도를 확정한 뒤에 정할 일이다.

현재 상태를 있는 그대로 적는다.

- 골드셋은 아직 없다. 일치도는 재보지 않았다.
- 위 시험 코드는 구조가 돌아가는지 보는 용도다. 정확도 수치는 이 글에 없다. 측정하지 않았기 때문이다.
- 영상 분석은 "로그로 안 보이는 활동을 영상으로 볼 수 있을까"라는 실험 구상 단계에 머물러 있다. 구현은 하지 않았다.

다음에 볼 것은 두 가지다. 하나는 오개념 목록을 교사가 검수하는 단계를 파이프라인 앞에 넣었을 때, 같은 학생 기록에서 판정이 얼마나 달라지는지다. 다른 하나는 PAIRS 같은 낱말 짝 검산이 실제로 놓침을 얼마나 잡는지다. 후자는 아직 감으로만 쓰고 있어서, 잡은 건수와 헛다시 물은 건수를 세어 보기 전에는 이 장치가 필요한지조차 모른다.
