문서 자동 생성기를 처음 붙여놓고, 결과물을 팀장에게 보여줬다. 첫 마디는 "이거 개발자가 읽는 거야?" 였다.

맞는 지적이었다. 첫 문단부터 파일 경로가 나오고, 배치 사이즈가 나오고, CronJob 이야기가 나오고 있었다. 자동화는 됐다. 다만 **잘못된 독자를 겨냥한 문서를 아주 빠르게 뽑아내고 있었을 뿐**이다.

---

## "문서 하나" 라는 착각

처음엔 프로젝트당 문서 한 벌을 만들려고 했다. LLM 한 번 태우고, 코드 파싱 결과 붙이고, 예쁘게 렌더링. 그런데 이게 작동하지 않는 이유가 있었다.

읽는 사람이 다르면 필요한 정보의 층위가 다르다. 기획자가 궁금한 건 "이게 뭘 하는 건가" 이고, 아키텍트가 궁금한 건 "어디에 얹혀 있고 뭘 부수면 뭐가 터지나" 다. 이걸 한 문서에 다 담으면 두 독자 모두에게 실패한 문서가 나온다.

그래서 타입부터 갈랐다.

| 타입 | 주 독자 | 초점 |
|---|---|---|
| `overview` | 기획자·경영진·PM | 무엇을·왜 |
| `sdd` | 팀 내부 개발자 | 설계 결정, 컴포넌트 역할 |
| `architecture` | 시니어·아키텍트 | 스택, 의존성, 인프라 |
| `api` | 연동 개발자 | 입출력 스펙 |

CLI 인자로만 나눈 게 아니라, **타입마다 LLM 프롬프트가 다르고, 파서가 코드에서 뽑아 주입하는 컨텍스트의 종류도 다르다.** 같은 저장소를 읽어도 `overview` 로 갈 땐 클래스명이 걸러지고, `api` 로 갈 땐 Pydantic 스키마가 우선순위 최상단으로 올라간다.

예를 들어 `api` 타입은 이런 스키마를 그대로 인용할 수 있어야 한다. 이건 실제로 우리 추천 API 요청 스키마의 일부다.

```python
class ContentHistoryItem(BaseModel):
    content_uuid: str | None = Field(None, description="이력 콘텐츠 UUID = content.content_uuid (권장). 회사 풀에서 매칭")
    content_id: str | None = Field(None, description="(하위호환) content.contents_agent_pk 또는 content_pk. content_uuid 우선")
    progress_rate: float | None = None
    pass_flag: int | None = None
    total_score: float | None = None
    learning_seconds: float | None = Field(None, description="실제 학습시간(초). 원천 TRNG_TCT 등에서 매핑")
    learned_at: str | None = Field(None, description="학습 시각(정렬용). 누락 시 가장 오래된 것으로 간주")

    @property
    def cid(self) -> str | None:
        return self.content_uuid or self.content_id
```

`api` 문서에서는 이 필드의 `description` 이 문서 본문이 된다. Pydantic 의 `Field(description=...)` 를 이미 열심히 써놨다면, LLM 은 이걸 재해석하려 들 게 아니라 그대로 인용해야 한다. **하위호환 필드에 왜 `content_id` 가 남아있는지, 어느 쪽이 우선인지** 같은 판단은 이미 필드 설명에 들어가 있다. 이걸 LLM 이 "예쁘게 다시" 쓰는 순간 사실이 흔들린다.

반대로 `overview` 타입에서는 이 스키마가 통째로 사라진다. `content_uuid` 라는 단어를 기획자가 볼 이유가 없다.

## 비개발자용 문서에서 진짜로 걷어내야 하는 것

`overview` 를 쓸 때 힘든 건 뭘 넣을지가 아니라 **뭘 안 넣을지** 였다. 코드에서 뽑을 수 있는 게 너무 많아서, 그중 대부분을 걷어내는 게 일이었다.

걷어내야 하는 것들:

- 파일 경로 (`recommend_engine/service.py` 같은 것)
- 함수·클래스명 (`ContentSimilarity`, `RelationMatrix`)
- 인프라 용어 (Pod, CronJob, replica 수)
- 파라미터 값 (`POOL_CACHE_SIZE`, `_TRANSITION_WINDOW = 10`)

`_TRANSITION_WINDOW = 10` 같은 상수는 개발자에겐 중요한 튜닝 포인트지만, 기획자에게는 "이 시스템은 사용자가 본 콘텐츠 뒤에 이어서 볼 만한 것을 찾아준다" 정도로 추상화되어야 한다.

```python
_TRANSITION_WINDOW = 10
_PEER_MIN_SUPPORT = 5
```

이 두 줄은 `sdd` 문서에서는 "왜 10 인가, 왜 5 인가" 를 설명하는 각주가 되고, `overview` 문서에서는 아예 존재하지 않는 것이 된다. 같은 코드가 문서 타입에 따라 다르게 보여야 한다는 얘기다.

## LLM 이 지어내면 안 되는 영역

가장 위험한 순간은, LLM 이 코드를 읽고 **비즈니스 목적을 스스로 추론해서 쓸 때** 였다.

한번은 어떤 프로젝트의 `overview` 초안에 이런 문장이 들어와 있었다. "본 시스템은 사용자 이탈률을 낮추기 위해 도입되었습니다." 나는 이 시스템을 이탈률 때문에 만든 적이 없다. 코드 어디에도 그런 힌트는 없다. 그냥 LLM 이 추천 시스템이라는 도메인을 보고 그럴듯한 목적을 지어낸 것이다.

문서 자동화에서 이런 문장이 하나 섞이면, 그 문서 전체를 못 믿게 된다. 특히 임원이 그걸 읽고 회의에서 인용하기 시작하면 되돌리기 어렵다.

그래서 방향을 뒤집었다. **컨텍스트를 코드에서 추론하지 않고, 외부 파일로 명시 주입한다.** 이 파일이 없으면 `overview` 빌드를 실패시킨다.

```yaml
project: content-reco
purpose: "학습 이력 기반으로 다음에 볼 만한 콘텐츠를 추천한다"
stakeholders: ["추천팀", "콘텐츠팀"]
scope: "추천 API 및 그에 필요한 콘텐츠 풀 캐싱까지. 모델 학습·평가는 범위 밖."
non_goals: ["실시간 A/B 테스트", "개인정보 기반 프로파일링"]
```

이걸 강제하는 이유는 단순하다. **"모르는 건 쓰지 않는다" 를 사람 의지가 아니라 시스템으로 강제**해야 지속된다. 나도 급할 땐 대충 넘기게 된다. 빌드가 아예 실패하면 넘길 수가 없다.

여기서 재밌는 부작용이 하나 있었다. `purpose` 를 한 문장으로 못 쓰는 프로젝트가 꽤 있었다. 그 순간 문서화 이전에 **그 프로젝트의 정체성이 흔들리고 있다는 신호**로 읽혔다. 문서 자동화가 프로젝트 리뷰 도구가 된 셈이다.

## DOCX 로 나가는 순간

또 하나 현실적인 문제. 기획자에게 `.md` 파일을 보내면 안 열어본다. `.docx` 로 나가야 한다.

`--docx` 플래그를 붙이면 `python-docx` 로 스타일을 잡고, Mermaid 다이어그램은 `mmdc` 를 subprocess 로 호출해 PNG 로 렌더링한 뒤 삽입한다. Mermaid 를 Word 에 직접 임베드할 방법이 없어서 이 우회가 필요했다.

이 지점에서 예전에 한번 크게 데인 적이 있어서, subprocess 호출부에는 `stdin=subprocess.DEVNULL` 을 명시하고 인터랙티브 옵션을 다 껐다. CLI 렌더러가 파이프에서 뭘 기다리다가 무한 hang 걸리는 걸 실제로 보고 나서 생긴 습관이다.

## 아직 안 풀린 것

`overview` 는 이제 팀장이 "이건 배포용으로 써도 되겠다" 고 하는 수준까지는 왔다. 그런데 `sdd` 는 아직도 애매하다. 이유는 `sdd` 가 요구하는 정보 — 왜 이렇게 짰는가, 왜 다른 방식은 버렸는가 — 는 **코드에도 없고 `project_meta.yaml` 에도 안 넣게 되는** 층위의 정보라서다.

지금은 커밋 메시지와 PR 본문을 같이 파싱해서 결정 이력으로 재구성해보고 있는데, 커밋 메시지 품질이 곧 문서 품질이라는 뻔한 결론에서 아직 못 벗어났다. 커밋 메시지를 다시 잘 쓰자는 얘기를 문서 자동화 프로젝트가 하고 있다는 게 조금 우습기도 하다.
