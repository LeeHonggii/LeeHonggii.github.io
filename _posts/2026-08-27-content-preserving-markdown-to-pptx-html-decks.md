AI한테 슬라이드를 만들어달라고 하면, 결과물은 대부분 예쁘다. 그리고 내용이 빠져 있다.

처음엔 내가 프롬프트를 잘못 쓴 줄 알았다. 원본 문서를 더 잘 요약해서 넣거나, "빠뜨리지 말고 전부 넣어라"는 지시를 추가하면 나아질 거라 생각했다. 그렇게 몇 번 시도해보니 패턴이 보였다. 슬라이드 개수 제약과 내용 완전성은 근본적으로 충돌한다. AI는 슬라이드 12장을 만들라고 하면 12장 안에 들어갈 수 있는 것만 고른다. 그 판단은 모델이 한다. 내가 중요하다고 생각한 부분이 조용히 잘려나간다.

## 문제의 구조

원인은 생성 방식 자체에 있다. AI가 슬라이드를 처음부터 "작성"하면, 출력 길이에 대한 암묵적 제약이 생긴다. 토큰 제한이든, 훈련 데이터의 분포든, 결과적으로 모델은 내용을 선택한다. 발표자료를 만드는 작업이 아니라 요약 작업이 된다.

방향을 바꿨다. **생성이 아니라 변환**으로.

원본 Markdown 문서의 구조를 그대로 읽어서 슬라이드 단위로 쪼개는 방식이다. AI가 무엇을 넣을지 판단하지 않는다. H1, H2, H3 헤딩 구조가 슬라이드 경계를 결정한다. 내용이 헤딩 아래에 있으면 그 슬라이드에 들어간다. 너무 길면 1:N으로 분할하지만, 내용을 버리지는 않는다.

"AI가 레이아웃 판단을 하지, 내용 선택은 하지 않는다"는 원칙이다.

## Marp를 고른 이유

변환 대상 포맷이 PPTX와 HTML 두 가지였다. PPTX는 오프라인 발표 때 필요하고, HTML은 공유 링크나 빌드 산출물로 쓴다. 두 포맷을 따로 만들면 내용이 어느 쪽에서 달라졌는지 추적하기 어렵다.

Marp(Markdown Presentation Ecosystem)는 슬라이드 Markdown 하나에서 두 포맷을 동시에 뽑는다.

```bash
marp deck.md --pptx -o deck.pptx
marp deck.md --html -o index.html
```

소스가 하나다. 싱크를 맞출 필요가 없다. HTML과 PPTX가 내용상 다르다면, 그건 변환 버그다.

테마는 별도 CSS 파일로 분리했다. `deck.md` 상단 frontmatter에서 참조하면 Marp가 읽는다. 이렇게 하면 내용과 스타일이 섞이지 않아서, 나중에 테마를 바꿀 때 슬라이드 파일을 건드릴 필요가 없다.

산출물 구조는 이렇게 정했다.

```
_decks/<slug>/
  deck.md        ← 슬라이드 Markdown (변환 결과)
  deck.pptx      ← Marp 출력
  index.html     ← Marp 출력
  theme.css      ← 브랜드 스타일
  source.md      ← 원본 (손대지 않음)
```

`source.md`를 별도로 보존한 이유가 있다. 변환이 잘못됐을 때 다시 돌릴 수 있어야 하고, 원본과 산출물을 diff할 수 있어야 한다. 덮어쓰면 두 번째 실행에서 원본을 잃는다.

## 유실 검증

구조 기반 변환을 해도 검증 단계가 없으면 믿기 어렵다. Marp는 CSS 레이아웃 문제로 내용이 잘릴 수 있다. 슬라이드 영역을 넘치는 텍스트는 시각적으로 보이지 않을 수 있다.

그래서 변환 직후에 확인해야 할 것들을 정리했다.

**코드블록**: `source.md`에 있는 펜스드 코드블록(fenced code block, 백틱 세 개로 감싼 코드)이 `deck.md`에도 같은 개수 있는지. 코드는 AI가 슬라이드를 쓸 때 가장 자주 날리는 요소다.

**표(table)**: Marp에서 표는 슬라이드 너비를 초과할 수 있다. PPTX 렌더링과 HTML 렌더링에서 다르게 보이는 경우가 있다. 원본 표 개수를 세어두고 산출물과 대조한다.

**헤딩 수**: 원본 H2 개수와 슬라이드 개수가 맞는지. 1:1 분할을 기본으로 할 경우, 헤딩이 슬라이드 경계가 되므로 숫자가 어긋나면 어딘가 합쳐지거나 사라진 것이다.

이 검증 단계를 자동화하지 않으면, 만들 때마다 직접 눈으로 봐야 한다. 작은 문서면 괜찮지만, 페이지가 늘어나면 빠뜨린다.

자동 검증은 아직 충분히 만들지 않았다. Playwright로 HTML을 렌더링해서 overflow된 요소를 감지하는 방향을 보고 있는데, CSS 계산이 headless 브라우저와 실제 브라우저에서 다르게 나오는 케이스가 있어서 완전히 믿을 수 없다.

## 아직 해결 안 된 것

슬라이드 하나에 내용이 너무 많을 때의 처리가 여전히 어렵다. 지금은 긴 슬라이드를 그냥 길게 두거나, 수동으로 분할한다. 자동으로 쪼개면 맥락이 끊기는 경우가 생긴다. "이 슬라이드는 여기서 끊기는 게 자연스럽다"는 판단은 아직 사람이 해야 하는 것 같다.

그리고 폰트와 아이콘 같은 리소스를 HTML 빌드에 번들링하는 문제가 남아 있다. 로컬에서 보면 멀쩡한데 공유 링크로 열면 폰트가 깨지는 경우가 있다. Marp의 HTML 출력이 외부 리소스를 참조하는 방식 때문인데, `--allow-local-files` 옵션과 함께 CDN 대신 인라인 폰트를 쓰는 방향을 봐야 한다.
