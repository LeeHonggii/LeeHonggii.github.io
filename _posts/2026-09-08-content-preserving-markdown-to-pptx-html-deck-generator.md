AI한테 발표자료 만들어달라고 하면, 완성본이 아니라 요약본이 나온다.

원문에 세 문장짜리 설명이 있으면 AI는 그걸 "핵심 단어 하나"로 줄인다. 표가 있으면 "참고: 데이터 있음" 정도로 치환한다. 긴 코드 블록은 아예 사라진다. 결과물이 깔끔해 보이는 이유가 있다. 내용이 없으니까.

이 문제가 반복되면서 방향을 바꿨다. AI가 슬라이드의 **내용을 판단하게 두지 않는 것.**

---

핵심 판단은 하나였다. 슬라이드 분할을 "요약"이 아닌 "구조 파싱"으로 처리한다.

Markdown 원본에는 이미 구조가 있다. `# 제목`, `## 소제목`, `---` 구분선. 이 신호들을 기준으로 문서를 잘라 슬라이드 하나씩에 매핑하면, AI가 어떤 내용을 살릴지 결정할 여지가 없어진다. 1:1 또는 1:N 분할이지, 요약이 아니다.

원문에 긴 문장이 있으면 긴 문장 그대로 슬라이드에 들어간다. 코드 블록도 그대로. 표도 그대로. 슬라이드가 답답해 보이면 원문이 그만큼 많다는 뜻이고, 그건 발표자가 편집할 문제다. 도구가 대신 판단할 문제가 아니다.

---

렌더링 엔진은 [Marp](https://marp.app/)를 골랐다. Marp가 하는 일이 정확히 이것이다. Markdown을 PPTX로, 또는 HTML로 렌더링한다. 단일 `.md` 파일이 두 산출물의 소스가 된다는 뜻이기도 하다.

```
marp deck.md --pptx
marp deck.md --html
```

두 명령이 같은 파일을 보고 있으니 PPTX와 HTML 사이에 내용 불일치가 생기기 어렵다. 종전에는 PPTX 따로, HTML 따로 생성 흐름이 있었고, 어느 한쪽에서 "정리"가 일어나면 둘이 달라졌다.

---

디자인 선택 부분이 예상보다 복잡했다.

발표 목적마다 어울리는 레이아웃이 다르다. 기술 공유 세션과 경영진 보고는 다른 슬라이드를 써야 한다. 이걸 코드 분기로 박아두면 디자인을 추가할 때마다 코드를 건드려야 한다.

그래서 디자인별로 `DESIGN.md` 파일을 뒀다. 파일 안에 Marp frontmatter 설정과 CSS 오버라이드, 그리고 "이 디자인이 어떤 상황에 맞는지"를 사람이 읽을 수 있는 설명으로 담았다. 생성 시점에 어떤 DESIGN.md를 쓸지 선택하면, 나머지는 make_deck.py가 Markdown과 합쳐서 Marp에 넘긴다.

```
make_deck.py input.md --mode both
```

`--mode both`는 PPTX와 HTML을 한 번에 뽑는다. 디자인을 명시하지 않으면 기본 DESIGN.md를 쓴다.

---

검증 단계를 따로 뒀다.

생성 직후에 원문에 있던 긴 문장, 코드 블록, 표가 산출물에 살아있는지 확인한다. 자동화된 검사라기보다는 체크리스트에 가깝다. "원문의 어떤 요소가 슬라이드에서 사라졌는가"를 명시적으로 보는 것이다.

이게 없으면 결과물이 그럴듯해 보일 때 실제로 유실이 있었는지 알 방법이 없다. 슬라이드가 깔끔하면 자동으로 좋은 거라는 착각이 생긴다.

---

아직 해결 못 한 부분이 있다. 원문이 길면 슬라이드 하나에 텍스트가 너무 많이 들어간다. 지금은 발표자가 직접 원문을 다듬어야 한다. 이 편집 부담을 도구가 어느 정도 덜어줄 수 있는지, 그런데 덜어주다가 다시 요약 문제로 돌아가지 않을지 — 아직 답을 못 냈다.
