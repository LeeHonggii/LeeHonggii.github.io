처음엔 한 줄이었다. 사용자 입력 → LLM 키워드 추출 → 템플릿 필터링 → 추천. 대부분의 케이스는 이걸로 커버될 거라고 생각했다.

## 로그를 열고 나서

오추천이 자꾸 나왔다. 원인을 뜯어보려고 실제 질의 로그를 훑는데, 입력이 세 종류로 갈리고 있었다.

- "3학년 2학기 4단원" — 학년·차시만
- "방정식 풀이 시각화" — 키워드만
- "중2 일차방정식 시각화" — 둘 다

세 종류가 전부 같은 경로를 탔다. 그리고 세 종류가 각각 다른 방식으로 망가지고 있었다.

학년·차시만 넘어오면 LLM이 키워드 자리를 비워둘 수 없어서 단원 이름을 지어냈다. 존재하지 않는 개념으로 매칭이 시도됐다. 키워드만 오면 학교급 정보가 없으니 초등용 도구가 중등 질의에 잡혔다. 둘 다 오면 학년 컨텍스트를 프롬프트에 실었는데도 LLM이 키워드 쪽에 끌려가서, 결국 중등 단원 대신 이름이 비슷한 초등 단원으로 매칭됐다.

원인은 하나로 수렴했다. 입력 유형에 따라 후보를 만드는 전략이 달라야 하는데, 파이프라인이 그 차이를 인식하지 않고 있었다. LLM 한 명한테 판별과 추출과 매칭을 다 시키고 있었다.

## `resolve_input_type` — LLM을 쓰지 않는 노드

리팩터링의 시작은 노드 하나를 추가하는 것이었다. `resolve_input_type`. 이 노드에서는 LLM을 쓰지 않기로 했다. 입력 필드가 있냐 없냐만 보면 되는 일이었다.

```python
if grade and semester and unit:
    input_type = "A"   # 학년·차시만
elif keywords and not (grade and semester):
    input_type = "B"   # 키워드만
else:
    input_type = "C"   # 둘 다
```

여기에 LLM을 붙였다면 "이 입력은 A/B/C 중 뭐야?"라는 질문을 매번 던져야 했을 것이다. 필드 유무 확인에 자연어 모델을 부르는 건 명백히 과잉이었다. 그리고 필드 확인은 확률이 필요한 작업이 아니다. 있으면 있는 거고 없으면 없는 거다.

전체 흐름은 이렇게 됐다.

```
validate → extract_keywords → resolve_input_type
                                  ├─ A → 교육과정 단원 조회 → 단원 기반 후보
                                  ├─ B → 키워드 매칭 + 단원 확장 보조
                                  └─ C → 학년차시로 후보 축소 → 키워드 정밀 매칭
                             → parallel_recommend → merge
```

각 경로의 후보 생성 방식이 다르다.

| 유형 | 입력 | 후보 생성 |
|------|------|----------|
| A | 학년·차시만 | 교육과정 DB 단원 조회 후 템플릿 필터 |
| B | 키워드만 | 활동 유형·설명·학습목표 텍스트 매칭 + 단원 확장 |
| C | 둘 다 | 학년차시로 후보 좁힘 → 키워드 정밀 매칭 |

## LLM한테 뭘 시키고 뭘 시키지 말 것인가

이번 작업으로 남은 건 분기 구조 자체보다도, LLM의 역할을 좁혔다는 것이었다.

LLM이 잘하는 건 자연어에서 의미 있는 키워드를 뽑는 일, 그리고 여러 후보 중 최종 하나를 고르며 설명을 붙이는 일이다. 그 반대편에 두면 안 되는 일들이 있었다. 학년·단원이 실제로 존재하는지 판별하는 건 DB 조회의 일이다. 입력 유형 분류는 필드 체크의 일이다. 교육과정 단원 매핑은 school_level이 누락되면 학교급이 뒤섞이는 문제가 있어서, 이것도 LLM에 맡기면 불안정해졌다.

역할을 나누고 나니 프롬프트가 저절로 짧아졌다. "어떤 유형인지 판단해서 그에 맞게 추천해"라는 뭉뚱그린 지시가 사라졌다. 대신 "이 키워드로 이 단원 목록 안에서 최적 도구를 골라"만 남았다. 프롬프트가 짧아진 것 자체보다도, 프롬프트에 넣는 컨텍스트가 무엇인지 내가 통제할 수 있게 된 게 컸다.

## A 경로의 함정 — 컨텍스트를 통째로 넘겨야 했다

A 경로(학년차시만)에서는 별도 문제가 남아 있었다. 후보 도구 리스트만 넘기면 추천 LLM이 왜 이걸 골라야 하는지 판단할 근거가 없었다. 단원 이름이 없고 학습 개념이 없으니, LLM은 도구 이름의 문자열 유사도 같은 걸로 순위를 매겼다. 결과가 그때그때 달랐다.

그래서 추천 노드에 넘기는 컨텍스트를 구조화된 형태로 조립했다.

```python
context = {
    "unit_name": "일차방정식",
    "learning_goals": ["미지수 개념 이해", "등식의 성질"],
    "school_level": "middle",
    "grade": 2,
    "candidates": [...]
}
```

이걸 넘기고 나서는 "방정식 관련 학습 개념이고 중등 대상이니, 시각화 도구보다 풀이 단계 템플릿이 더 적합하다"는 판단이 가능해졌다. 학습목표라는 텍스트를 LLM이 읽을 수 있게 됐다는 게 큰 차이였다. 초기에 잡힌 오추천의 상당수가 여기서 걸러졌다.

## 남은 것

이 구조에서도 아직 애매한 부분이 있다. B 경로에서 "단원 확장 보조"라고 이름 붙인 단계 — 키워드로부터 관련 단원을 역추적하는 로직 — 는 아직 규칙과 LLM 사이에서 왔다갔다 하고 있다. 지금은 임베딩 유사도로 상위 단원 몇 개를 뽑아 프롬프트에 힌트로 넣는데, 이걸 결정론적으로 좁힐 수 있는지 아직 확신이 없다. 키워드 자체가 여러 학년에 걸치는 경우(예: "함수")가 문제다.

C 경로에서도 학년차시로 좁힌 뒤 키워드 매칭이 실패하면 뭘 반환할지가 남았다. 지금은 학년차시만 남기고 매칭 실패를 그대로 로그에 남기는데, fallback을 넣어야 할지 그대로 두는 게 나은지는 다음 배치의 로그를 더 보고 결정할 생각이다.
