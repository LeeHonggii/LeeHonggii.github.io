## 통계로 뭉개면 될 줄 알았다

추천 엔진에 붙일 콘텐츠 묶음의 메타가 부실했다. 제목은 있고, 설명은 비어 있고, 태그는 아예 없다. 게다가 기존 CMS의 PK 체계와 맞지 않아서 그 쪽 메타 테이블을 그대로 쓸 수도 없었다.

처음엔 통계로 대충 뭉갤 수 있을 줄 알았다. 제목 토큰으로 클러스터링하고, 클러스터별 대표 키워드를 뽑아 붙이면 되지 않겠나. 실제로 해보니 마이너 클러스터가 다 죽었다. 30개짜리 그룹의 대표 키워드가 3개짜리 이웃 그룹까지 덮어썼다. 롱테일 콘텐츠에 붙는 태그는 사실상 이웃 소음이었다.

문제는 분포가 아니라 의미였다. "비즈매너"인지 "커뮤니케이션"인지는 제목 한 줄만 읽어도 사람은 안다. 통계는 그걸 못 본다.

그래서 결정했다. 1만6천 건, LLM이 하나씩 읽는다.

## 왜 임시 테이블을 따로 팠나

이 콘텐츠 묶음의 식별자는 CMS PK와 1:1이 아니었다. 시스템 경계가 다르고, 일부는 매핑 자체가 없다. 그런데 추천 엔진 안에서는 이걸로 조인해야 한다.

메인 메타 테이블을 건드리면 두 가지가 꼬인다. 하나, CMS 쪽 워크플로우가 우리 실험용 컬럼을 자기 스키마로 착각한다. 둘, 이 실험이 실패했을 때 롤백이 지저분해진다.

그래서 완전히 분리된 임시 테이블을 팠다. 컬럼은 최소한만.

```sql
CREATE TABLE content_meta_llm (
  content_pk    VARCHAR(20) PRIMARY KEY,
  keyword_tags  JSON,
  strand        VARCHAR(100),
  audience_tags JSON,
  generated_at  DATETIME DEFAULT NOW()
);
```

`content_pk`는 추천 엔진 내부 식별자다. 나중에 검증이 끝나고 메인 쪽에 병합할 때는 이 키로 `ON DUPLICATE KEY UPDATE` upsert만 하면 된다. 실패 시엔 이 테이블 하나만 drop하면 된다는 게 심리적으로 컸다.

여기서 붙일 `strand`와 `keyword_tags`가 추천 엔진 어디에 쓰이는지 감을 잡으려면, 사전 평가 단계에 들어가 있는 직무·키워드 매핑을 보면 된다. 대략 이런 구조로 상수화되어 있다.

```python
JOBS_16 = [
    '기획·전략', '경영·사무', '마케팅·홍보·광고', '영업·판매',
    '무역·물류·유통', '회계·세무·재무', '금융·보험', '인사·HRD',
    'IT·개발·데이터', '디자인·미디어', '고객상담·서비스',
    '생산·제조·품질', '연구·R&D·설계', '의료·보건·복지',
    '건설·건축·시설', '교육·강사',
]

SUB_TO_KEYWORDS = {
    'AI·머신러닝 엔지니어': ['AI', '데이터', '알고리즘'],
    '데이터 분석가·엔지니어': ['데이터', '통계'],
    '노무사': ['노동법', '근로계약', '취업규칙'],
    'F&B·외식 서비스직': ['고객', '비즈매너'],
    # ...
}
```

사용자 쪽에서 이런 키워드 세트가 뽑히는데, 콘텐츠 쪽에 붙은 태그가 비어 있으면 매칭이 안 된다. 즉 콘텐츠 태그가 비면 그 콘텐츠는 사실상 추천 후보에서 빠진다. 이 대칭 관계가 이 프로젝트의 성패 기준이었다.

## 결과를 잃지 않는다 — 배치 파일이 먼저다

1만6천 번의 LLM 호출을 돌린다는 건, 그 중 몇 %는 반드시 터진다는 뜻이다. 네트워크 타임아웃, rate limit, JSON 파싱 실패. 이걸 DB에 바로 쓰다가 중간에 죽으면 어디서부터 다시 돌려야 할지 알 방법이 없다. "지금 몇 번까지 됐지?"를 매번 SQL로 물어보는 것도 지친다.

그래서 원칙을 하나 세웠다. **결과는 무조건 파일에 먼저 떨어뜨린다. DB 적재는 맨 마지막.**

```
data/content_meta/
  batch_0000.json
  batch_0001.json
  ...
  batch_0159.json
```

배치 하나가 100건. 한 배치가 다 끝나면 그 배치 파일을 쓴다. 중간에 죽으면 존재하는 batch 파일 인덱스를 세서 그 다음부터 재개한다. 파일이 곧 체크포인트다.

레코드 한 개는 이런 모양.

```json
{
  "content_pk": "10000",
  "keyword_tags": ["비즈매너"],
  "strand": "자기관리",
  "audience_tags": ["공통"]
}
```

전체 러닝이 끝난 뒤엔 `partial.json`에 실패 건만 따로 모았다. 이 파일이 비어야 "완료"다. 이 규칙 하나 덕분에 재시도가 idempotent해졌다. 같은 배치를 두 번 돌려도 파일 덮어쓰기만 일어난다.

## 빈 태그는 침묵이 아니라 손실이다

첫 러닝 결과에서 `keyword_tags: []` 가 예상보다 많이 나왔다. LLM이 "제목만 봐선 확신 못하겠다"고 판단해서 빈 배열을 반환한 것이다. 성실한 반응이긴 한데, 추천 시스템 입장에서는 재앙이다.

앞에서 본 `SUB_TO_KEYWORDS` 매칭을 다시 보자. 사용자 쪽에서 `['AI', '데이터', '알고리즘']` 이 나왔는데 콘텐츠 쪽 태그가 `[]`면, 이 콘텐츠는 그 어떤 사용자와도 안 만난다. 침묵이 아니라 소실이다.

그래서 프롬프트를 뒤집었다. "확신 없으면 비워도 된다" → "**확신 없어도 가장 가능성 높은 것 하나는 반드시 낸다. 정 안 되면 `기타`라도 붙인다.**" 빈 태그보다 약한 태그가 낫다는 게 이 도메인의 결론이었다.

그리고 재처리 기준을 명문화했다.

- `keyword_tags`가 빈 배열
- `strand`가 null
- JSON 파싱 실패

이 셋 중 하나라도 걸리면 `partial.json`으로 간다. 프롬프트를 강화한 버전으로 이 파일만 다시 돌린다.

## 아직 안 해본 것

지금 이 파이프라인은 "빠뜨리지 않는 것"까지는 됐다. 하지만 붙인 태그가 얼마나 맞는지는 **표본 검수 말고는 재본 적이 없다.** 사람이 100건 훑어봤을 때 대략 감이 왔다는 수준이지, 정밀도·재현율 같은 숫자로 말할 수 있는 상태가 아니다.

원래 계획은 이 태그로 추천 A/B를 붙여서 CTR 차이로 역으로 태그 품질을 재는 것이었는데, 아직 그 단계 전이다. 다음 스프린트에서 이 부분을 잡아야 이 실험이 진짜로 끝난다.

한 가지 더 걸리는 건, LLM이 붙인 `strand` 값의 분포가 살짝 쏠려 있다는 점이다. "자기관리"와 "커뮤니케이션"이 지나치게 많다. 이게 실제 콘텐츠 분포를 반영하는 건지, LLM이 애매할 때 안전한 라벨로 회귀하는 편향인지 아직 못 갈랐다. 이 두 라벨만 뽑아서 사람 검수를 한 번 더 돌려봐야 안다.
