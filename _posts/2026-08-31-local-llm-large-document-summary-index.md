발단은 단순했다. 어느 날 Obsidian 그래프 뷰가 이상하게 느려졌고, 추적해보니 16MB짜리 Markdown 파일 하나가 인덱서를 마비시키고 있었다. 내보낸 회의록이나 분석 리포트를 그냥 vault에 던져넣다 보니 생긴 일이다.

처음엔 그냥 숨기면 된다고 생각했다. `.obsidian/app.json`에서 특정 폴더를 색인 제외하면 끝이라고. 근데 그건 문제를 없애는 게 아니라 못 보게 하는 것이다. 그 파일 안에 있는 내용은 여전히 검색하고 싶다.

그래서 구조를 바꿨다. 원본은 `.txt`로 변환해서 인덱서가 손대지 못하는 폴더에 보관하고, 로컬 LLM으로 요약한 `.md` 파일만 vault 안에 두는 방식이다. 검색엔 요약본만 걸리고, 원본은 필요할 때 직접 꺼내 보는 것.

---

## 큰 문서를 통째로 넣으면 안 되는 이유

16MB를 LLM 컨텍스트에 통째로 집어넣는 건 이론적으로 가능할 수도 있지만, 로컬에서 돌리는 Gemma 수준에서는 현실적이지 않다. 컨텍스트 길이 제한도 있고, 설령 들어간다 해도 긴 문서 중간의 내용은 attention이 약해져서 요약 품질이 떨어진다는 게 알려진 문제다.

그래서 선택한 건 Map-Reduce 방식이다. 문서를 Markdown 헤더(`#`, `##`) 기준으로 청크로 쪼개고, 각 청크를 개별 요약하고(Map), 그 부분 요약들을 모아 다시 최종 요약을 만드는(Reduce) 구조다.

헤더 기준으로 자르는 이유가 있다. 임의 토큰 수 기준으로 자르면 문단 중간에서 잘려 맥락이 끊긴다. 헤더는 문서 저자가 이미 의미 단위로 구획을 나눠놓은 것이기 때문에, 그걸 따라가는 게 맥락 보존에 유리하다. 물론 헤더 없이 길게 이어지는 구간이 있으면 추가로 분할해야 하지만, 그건 예외 처리로 두었다.

---

## mtime을 믿으면 안 된다

초기 구현에서 한 번 실수했다. 파일 수정 시간(`mtime`)으로 변경 여부를 판단하려 했다.

`mtime`은 파일 내용이 안 바뀌어도 바뀐다. 파일을 복사하거나 백업 도구가 타임스탬프를 건드리면 재요약이 트리거된다. Gemma로 16MB 요약 한 번 돌리면 몇 분 걸리는데, 이게 괜히 반복 실행되면 말이 안 된다.

그래서 SHA-256 해시로 바꿨다. 원본 파일의 해시를 계산해서, 생성된 요약 `.md` 파일의 frontmatter에 같이 기록해두는 방식이다. 다음 실행 때 이 값을 비교해서 같으면 건너뛴다.

```
original_hash: "a1b2c3..."
```

frontmatter 한 줄이지만, 이게 없으면 멱등성이 없다. 파이프라인을 반복 실행해도 안전하다는 보장이 이 줄에서 나온다.

---

## 파일 구조

변환 전후 구조를 말로 설명하면 이렇다.

- `data_parsed/*.md` → (`.txt`로 확장자 변경) → `data_archive/*.txt`
- `data_archive/*.txt` → (Gemma 요약) → `data_parsed/*.md`

원본 Markdown은 `.txt`로 바꿔서 Obsidian이 색인하지 않는 폴더로 옮긴다. Obsidian은 `.txt` 파일을 그래프 뷰에 포함하지 않기 때문에 이것만으로도 인덱서 부하 문제는 해결된다.

그리고 같은 이름으로 `.md` 요약본이 생성된다. 사람이 검색할 때 걸리는 건 이 파일이다. 원본을 보고 싶으면 frontmatter의 `source_path`를 따라가면 된다.

CLI에서는 이렇게 호출한다.

```bash
python3 gemma_processor.py summarize_large <file>
```

내부적으로 헤더 파싱 → 청크 요약 → 병합 요약 → frontmatter 기록의 순서로 처리된다. 실제 프롬프트 내용이나 청크 크기 튜닝은 글 한 편으로 다룰 분량이 따로 있어서 여기선 구조만 언급한다.

## 아직 해결 못 한 것

헤더 없이 산문으로만 이루어진 긴 문서는 청크 분할이 여전히 어렵다. 지금은 일정 토큰 수 초과 시 강제로 자르는 fallback이 있는데, 그 경계에서 요약 품질이 눈에 띄게 떨어진다.

더 신경 쓰이는 건 Reduce 단계다. 부분 요약을 다시 요약할 때 반복되는 정보가 많이 남는다. 각 청크 요약이 비슷한 배경 설명을 포함하면, 최종 요약도 그걸 그대로 다 담으려 한다. 이걸 얼마나 걷어낼 수 있는지는 아직 프롬프트 실험 중이다.
