시크릿 스캔이 실패했다. 리포트에는 코드에 박힌 키 하나와 서버 주소 하나가 찍혀 있었다.

처음엔 오탐인 줄 알았다. 배포 설정은 전부 환경변수로 돌리고 있었고, 그건 이미 오래전에 정리한 일이었다. 그런데 스캐너는 배포 설정 파일을 보지 않는다. 저장소의 소스 파일을 본다. 그리고 거기엔 정말로 값이 있었다.

## 환경변수 "로도" 읽는 코드

문제의 모양은 이랬다. 이름은 일반화했지만 구조는 그대로다. 환경변수를 읽되, 없으면 기본값을 쓴다.

```python
API_KEY = os.getenv("SERVICE_API_KEY", "<실제 키 문자열>")
BASE_URL = os.getenv("SERVICE_BASE_URL", "<실제 내부 주소>")
```

개발할 때는 편한 패턴이다. 변수를 안 세팅해도 로컬에서 바로 돈다. 그래서 누가 편의로 넣었고, 나중에 환경변수 방식으로 바꿀 때도 "읽는 코드가 있으니 끝났다"고 넘어갔을 것이다.

그런데 이 패턴은 환경변수를 쓰는 것과 시크릿이 저장소에 없는 것을 별개로 만든다. 배포 환경에서는 환경변수가 덮어쓰니 동작은 맞다. 하지만 git 히스토리에는 기본값 문자열이 그대로 남는다. gitleaks는 이 문자열을 본다. 런타임에 뭐가 쓰이는지는 관심이 없다.

(이 글에는 원본 코드와 스캔 로그를 싣지 않는다. 위 코드는 구조를 보여주려고 일반화해 다시 쓴 것이다.)

## 고친 방향

기본값을 지웠다. 키와 주소 모두 환경변수로만 읽는다.

```python
API_KEY = os.environ["SERVICE_API_KEY"]
BASE_URL = os.environ["SERVICE_BASE_URL"]
```

이 형태의 부작용은 분명하다. 변수가 없으면 로컬에서 시작이 안 된다. 나는 그쪽이 맞다고 봤다. 조용히 엉뚱한 값으로 도는 것보다 시작 단계에서 죽는 게 낫다. 다만 로컬 개발 편의는 확실히 줄었고, 예시 환경 파일을 어떻게 둘지는 따로 정해야 한다.

위 수정 코드도 방향을 보여주는 재구성이다. 실제 최종 형태가 정확히 이랬는지, 필수 변수 누락 시 어떤 에러 메시지를 내는지까지는 기록에 없다.

## 이름이 안 맞았다

기본값을 지우고 나니 두 번째 문제가 드러났다. 배포 환경에 등록된 변수 이름과 코드가 읽는 이름이 서로 달랐다. 기본값이 있을 때는 이 불일치가 가려져 있었다. 변수가 안 읽혀도 하드코딩 값이 대신 받아줬으니까.

기본값이 시크릿을 숨긴 게 아니라 설정 오류를 숨기고 있었던 셈이다. 환경별 설정 이름을 코드 쪽에 맞춰 정리했다. 기본값 제거는 보안 수정이기도 했지만 설정 검증 장치이기도 했다.

## 같이 섞인 구조 변경

이 작업 중에 폴더 구조도 정리했다. 그리고 이 부분은 잘못했다. 파일 이동과 동작 변경이 한 변경에 섞이니, 어디서 뭐가 달라졌는지 추적하기 어려웠다. 이름이 안 맞는 문제를 찾을 때도 이동된 파일 속에서 diff를 읽어야 했다.

다음부터는 구조 변경과 기능 변경을 커밋 단위로 갈라 두려고 한다. 이동만 있는 커밋은 리뷰도 빠르고 되돌리기도 쉽다.

## 아직 남은 것

- 최종 스캔이 통과했는지는 이 기록만으로 확인하지 못했다. 재실행 결과를 다시 봐야 한다.
- 이미 커밋된 기본값은 히스토리에 남아 있다. 코드에서 지운 것과 키가 안전해진 것은 다른 이야기다. 해당 키의 폐기·재발급 여부는 별도로 확인이 필요하다.
- 스캔을 PR 단계에서 막을지, 배포 직전에만 돌릴지 아직 정하지 않았다.

기본값을 지운 뒤에야 설정 이름 문제가 나온 걸 보면, 다른 곳에도 기본값이 가리고 있는 불일치가 더 있을 수 있다.
