## 로그가 없다

추천 엔진을 붙여달라는 요청을 받았을 때 가장 먼저 확인한 건 로그였다. 클릭 로그, 완료율, 평점. 셋 다 사실상 비어 있었다. 서비스가 초기였고 사용자 행동이 쌓이기 전이었다.

협업 필터링(collaborative filtering, 사용자 행동 기반 유사도)은 애초에 선택지가 아니었다. 그렇다고 "데이터가 없어서 못 만든다"고 넘길 수 있는 상황도 아니었다. 결국 남은 축은 하나였다. **콘텐츠 자체.** 콘텐츠 메타데이터만으로 두 항목이 얼마나 가까운지 계산하는 것.

이 글은 그때 잡은 6개 신호와, 같은 신호를 세 관점으로 다르게 쓰는 가중치 구조를 정리한 것이다.

## 공식 하나부터

두 콘텐츠 A, B의 관련도는 이렇게 정의했다.

```
base(A, B) = Σ(w_i · S_i(A, B)) / Σw_i
```

`S_i`는 신호 i에서의 유사도(0~1), `w_i`는 그 신호의 가중치. 분모를 활성화된 신호의 가중치 합으로 정규화한다.

단순 평균이 아닌 이유가 있다. 신호는 자주 빠진다. 어떤 콘텐츠는 자막(sub)이 통째로 없다. 어떤 콘텐츠는 태그가 부실하다. 이때 결측된 신호를 그대로 0으로 넣으면 그 콘텐츠의 전체 점수가 부당하게 낮아진다. 그렇다고 결측 처리를 안 하면 신호 개수가 다른 두 콘텐츠의 점수를 비교할 수 없다.

가중합을 살아 있는 신호의 가중치 합으로만 나누면, 어떤 콘텐츠든 최종 점수는 0~1 범위로 떨어진다. 비교 가능한 스케일이 유지된다. 별거 아닌 트릭이지만 이 한 줄이 없으면 뒤에 오는 랭킹이 전부 흔들린다.

## 신호 6개

집합은 이렇게 잡았다.

```
F = { kw, ncs, strand, dur, title, sub }
```

- **kw** (keyword) — 태그·키워드 겹침. 자카드(Jaccard) 계열
- **ncs** — NCS(국가직무능력표준, 직업훈련 콘텐츠를 직무로 계층 분류하는 체계) 코드 일치도
- **strand** — 학습 계열. 입문→심화 같은 흐름 축
- **dur** (duration) — 콘텐츠 길이. 비슷한 길이끼리 묶이는 성향
- **title** — 제목 텍스트 유사도
- **sub** (subtitle/script) — 자막·스크립트 의미 유사도

여기서 NCS를 굳이 별도 신호로 뽑은 이유가 있다. 이 도메인에서 NCS는 단순 카테고리가 아니라 **"이 콘텐츠가 어떤 직무를 위한 것인가"** 를 규정하는 1차 축이다. 키워드가 겹쳐도 직무 분류가 다르면 대개는 무관하다. 반대로 NCS가 같으면 키워드가 좀 어긋나도 실무적으로는 가까운 콘텐츠일 때가 많다. 이 비대칭을 하나의 신호 안에 뭉치면 놓친다.

`sub`은 처음엔 강한 신호일 거라 기대했다. 자막 텍스트의 의미 임베딩(embedding)을 잡으면 콘텐츠 내용을 가장 정확히 대변할 것 같았다. 실제로 넣어보니 자막이 존재하는 콘텐츠 비율이 생각보다 낮았다. 강한 신호가 아니라 **가끔 있을 때만 도와주는 보조 신호**로 자리를 옮겼다. 데이터 현실이 설계를 눌렀다.

## 하나의 공식, 세 개의 얼굴

같은 공식이지만 `w_i`를 다르게 잡으면 다른 추천기가 된다. 관점을 분리한 배경은 튜닝 중반쯤 나온 관찰이었다.

하나의 가중치 세트로 top-5를 만들면, 어떤 유저에게는 "직무는 맞는데 재미없는" 결과가, 어떤 유저에게는 "관심사는 맞는데 실무와 상관없는" 결과가 섞였다. 평균적으로 무난한 랭킹이 나왔지만, 어느 쪽에서 봐도 특별히 좋진 않았다. 하나로 다 잡으려다가 아무것도 못 잡는 상태.

그래서 세 관점으로 갈랐다.

**직무(Job) 관점** — "이 직무에 맞는 콘텐츠"

```
w = 0.20·kw + 0.45·ncs + 0.20·strand + 0.05·dur + 0.05·title + 0.05·sub
```

NCS가 축이다. 직무 경계를 넘어가는 순간 아무리 다른 신호가 겹쳐도 이 관점에선 관련도가 낮게 나와야 한다.

**관심(Interest) 관점** — "탐색 중인 주제와 비슷한 콘텐츠"

```
w = 0.45·kw + 0.20·ncs + 0.15·strand + 0.05·dur + 0.10·title + 0.05·sub
```

이번엔 kw가 주다. 직무 라인을 일부러 넘도록 놔둔다. 이 관점의 존재 이유가 그거다.

**선호(Preference) 관점** — "이 사람이 좋아할 스타일"

```
w = 0.20·kw + 0.15·ncs + 0.15·strand + 0.10·dur + 0.30·title + 0.10·sub
```

title이 이례적으로 높다. 이 결정은 지금도 애매하게 남아 있다. 제목이 콘텐츠의 톤, 난이도 감각, 포맷을 드러낸다는 가정에서 출발했는데, 사실 이건 검증이 부족하다. 자막 임베딩이 더 맞는 신호일 수도 있다. 그런데 앞서 말했듯 `sub`이 커버되는 비율이 낮았다. 있는 것 중 가장 스타일을 반영할 만한 텍스트가 title이었다.

세 관점 이전의 공통 초기값은 이거였다.

```
공통 초기값: 0.45·kw + 0.35·ncs + 0.15·strand + 0.05·dur
```

여기서 시작해 관점을 갈랐다.

## 가중치를 정당화하는 법

"왜 0.45인가"라는 질문에 답하지 못하면 6개월 뒤에 나 자신조차 튜닝 근거를 잃는다. 세 가지를 기준으로 잡았다.

**축 역할.** 이 관점에서 필터 역할을 하는 신호가 뭔가. 직무 관점에서 NCS가 그렇다. 다른 신호는 랭킹을 흔들지만 NCS는 후보 자체를 갈라낸다.

**신호의 희소성.** 결측이 잦은 신호는 아무리 이론적으로 중요해도 주신호로 못 쓴다. `sub`이 대표적. 있으면 좋지만 없다고 랭킹이 무너지면 안 된다.

**시나리오 리뷰.** 고정된 쿼리 셋을 놓고 top-5 결과를 눈으로 봤다. "이건 이상하다"는 케이스에 표시하고, 어떤 신호를 올렸을 때 그 케이스가 정리되는지 한 칸씩 움직였다. 정량 지표가 아니라 정성 검토였다. 로그가 없으니 A/B도 없었고, 결국 사람이 랭킹을 읽는 수밖에 없었다.

이 방식의 한계는 명확하다. 내가 놓친 케이스는 그대로 남는다. 오프라인 평가 셋을 만들어야 하는데 아직 못 만들었다.

## 아직 안 끝난 것

RRF(Reciprocal Rank Fusion, 역순위 융합)로 세 관점의 결과를 최종 병합하는 층이 위에 하나 더 있다. 그 층에서 세 관점의 무게를 어떻게 잡느냐가 사실 이 시스템의 진짜 튜닝 지점인데, 이건 다음에 따로 정리하려고 한다.

지금 걸려 있는 건 두 가지다. 하나는 `sub` 커버리지가 낮아 선호 관점이 title에 과하게 의존하는 문제. 자막 없는 콘텐츠에 대한 fallback으로 title을 어디까지 믿을 수 있는지 아직 못 재봤다. 다른 하나는 관점별 가중치가 시나리오 리뷰 기반이라는 것. 사용자 행동이 조금이라도 쌓이면 오프라인 평가 셋을 만들어 관점별로 hit rate를 따로 재보는 게 다음 순서다.

로그가 없다는 조건은 언젠가는 풀린다. 그때 이 구조가 얼마나 버티는지는 아직 모른다.
