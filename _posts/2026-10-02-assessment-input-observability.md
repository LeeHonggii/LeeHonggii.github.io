피드백 품질을 올리려고 프롬프트부터 만지다가, 모델이 애초에 볼 수 없는 것을 채점하라고 시키고 있는 건 아닌지 의심이 들었다. 평가 모델을 고치기 전에 입력에 뭐가 들어가는지부터 확인하기로 했다. 이 글은 그 점검 기록이다.

## 시작은 재생 코드의 버그였다

학생이 수학 캔버스에서 푼 과정을 시간순으로 재생하는 코드가 있다. 이 재생 결과를 AI 피드백의 근거로 넘기려고 다시 읽다가 문제를 두 개 찾았다.

- 지우기(erase) 이벤트가 처리되지 않았다. 학생이 쓴 필기를 지워도 재생 장면에는 그대로 남았다.
- 객체를 비교할 때 객체 자체의 ID(파이썬의 `id()` 같은 것)에 기대고 있었다. 이력에서 복원한 객체는 같은 도형이어도 다른 객체가 된다.

고친 뒤의 코드가 아래다. 이전 코드는 이 글에 싣지 않는다. 지금 구조만 설명한다.

```python
@staticmethod
def apply(scene, pens, kind, before, after):
    bl = before if isinstance(before, list) else []
    al = after if isinstance(after, list) else []
    if kind == "pen":
        pens.extend(al)
        return "필기"
    if kind == "erase":
        gone = {p.get("id") for p in al + bl}
        pens[:] = [p for p in pens if p.get("id") not in gone]
        return "지움"
    if kind == "delete":
        for e in bl:
            scene.pop(e.get("id"), None)
        return "삭제"
    for e in al:
        scene[e.get("id")] = e
    return "꺼냄" if kind == "create" else "이동"
```

비교 기준은 데이터가 가진 `id` 필드다. 장면은 `id → 요소` 딕셔너리로 들고 있어서 이동은 같은 키를 덮어쓰고 삭제는 키를 빼면 된다. 지우기는 `before`와 `after` 양쪽에서 ID를 모은다. 이력 기록 방식에 따라 지워진 획이 어느 쪽에 들어 있을지 확신하지 못했다. 그래서 둘 다 보는 쪽을 택했다. 어느 쪽에 실제로 들어오는지는 표본을 더 봐야 안다.

되돌리기는 이벤트를 하나씩 역산하지 않는다. 이벤트를 적용하기 직전의 장면을 매번 스냅샷으로 저장해 두고 그걸 복원한다.

```python
snapshots.append((dict(scene), list(pens)))
if kind == "init":
    sc = after if isinstance(after, dict) else {}
    scene = {e.get("id"): e for e in (sc.get("elements") or [])}
    pens = list(sc.get("penElements") or [])
    label = "시작"
elif x.get("subType") == "undo":
    scene, pens = snapshots[-2] if len(snapshots) >= 2 else (scene, pens)
    scene, pens = dict(scene), list(pens)
    if self.frames:
        self.frames[-1]["valid"] = False
        self.undone += 1
    label = "되돌리기"
else:
    label = self.apply(scene, pens, kind, before, after)
```

되돌린 프레임은 지우지 않고 `valid=False`로 표시하고, 되돌린 횟수(`undone`)를 센다. 평가 입장에서는 한 번 시도했다가 취소한 것도 풀이 과정의 일부라서, 프레임을 없애면 그 정보가 사라진다.

이 코드에는 아직 확인하지 못한 구석이 있다. `snapshots[-2]`는 직전 이벤트를 적용하기 전의 장면이다. 되돌리기가 연달아 두 번 나오면 두 번째는 첫 번째 되돌리기 직전 장면, 즉 취소했던 상태로 돌아갈 것 같다. 아직 그 이력으로 돌려 보지 않았다.

그리고 모든 이력이 이렇게 재생되는 것도 아니다. 이력 형식이 legacy가 아닌 hv3는 최종 장면 1장만 만든다.

```python
if not self.legacy or not self.items:
    self.frames = [{"step": 0, "t": 0, "label": "최종 장면", "valid": True,
                    "elements": self.state.get("elements") or [],
                    "pens": self.state.get("penElements") or []}]
    self.replayable = False
    return self.frames
```

`replayable=False`가 이 글의 주제로 이어졌다. 어떤 학생의 풀이는 과정이 입력에 아예 없다. 그 학생에 대해 "풀이 과정이 좋았다"고 쓰는 것은 근거가 없는 말이다.

## 흐름을 그려 봤다

실제 실행 순서를 처음부터 따라가 봤다. 문항 이미지와 정답 이미지, 학생 풀이 영상이 들어가면 LLM이 문제를 정의하고 답안을 판정한다. 그 뒤 루브릭 평가를 거쳐 리포트가 나온다. 이 중 코드가 계산하는 부분(재생, 프레임 구성, 되돌린 횟수)과 LLM이 추론하는 부분(문제 이해, 판정, 루브릭 적용)을 나눠서 적어 봤다. 나눠 보니 리포트의 문장 중 어느 것이 계산이고 어느 것이 추론인지 구분되지 않는 곳이 있었다.

선개념·오개념의 출처도 확인했다. 교육과정 조회 결과에서 나오는 줄 알았는데 아니었다. 교사가 입력하거나 모델이 추론한 값이었다. 그렇다면 설명을 둘로 나눠야 한다. 기준이 어디서 왔는지(교사 입력인지, 모델 추론인지)가 하나이고, 이 학생이 그 기준에 걸린다고 판정한 근거가 다른 하나다. 둘이 섞이면 모델이 만든 오개념 목록에 모델이 학생을 끼워 맞춘 꼴이 되어도 겉으로는 구분되지 않는다.

## 활동 유형마다 보이는 것이 다르다

활동 유형별로 지금 입력이 무엇을 관찰할 수 있는지 훑었다.

배치, 분류, 수식 구성은 상태 변화로 드러나는 행동이다. 무엇을 꺼냈고 어디로 옮겼고 무엇을 되돌렸는지가 조작 이력에 남는다. 위 재생 코드가 이 유형에 맞다.

그림이나 언어로 표현하는 활동은 다르다. 필기 이미지가 있어도 획 수나 지운 횟수는 내용을 이해했다는 근거가 못 된다. 많이 지웠다는 사실은 망설였다는 신호일 수도 있고 글씨를 고쳤다는 뜻일 수도 있다. 설명을 말하거나 쓰게 하는 활동인데 설명 입력이 없다면 설명 능력은 판단할 수 없다.

그러니 리포트에서 두 경우를 구분해야 한다. "낮은 수준으로 수행했다"와 "판단할 근거가 입력에 없다"는 다른 말이다. 지금은 루브릭 항목마다 점수를 채우는 구조여서, 근거가 없는 항목도 낮은 점수로 나올 위험이 있다. 이 부분은 아직 출력 스키마에 반영하지 않았다.

## 영상은 아직 구상이다

풀이 영상에서 프레임을 뽑아 이미지 시퀀스로 넘기는 방식이 제안됐다. 초당 간격으로 뽑거나 장면이 바뀔 때 뽑는 방식이다. 활동 유형별 표본을 모아 이 입력이 각 유형에 맞는지 보는 테스트도 구상했다. 구현은 하지 않았고 효과도 검증하지 않았다. 프레임 몇 장이면 충분한지, 지우기 같은 짧은 동작이 프레임 사이에서 빠지지는 않는지도 아직 재보지 않았다.

다음에 할 일은 두 가지다. 연속 되돌리기 이력으로 위 복원 동작을 돌려 보는 것과, 활동 유형별 표본을 모으는 것이다.
