API 응답 계약을 바꾸는 작업은 생각보다 한 군데만 건드리는 게 아니다. 응답 모델, 쿼리 로직, 에러 처리, Swagger 문서, 그리고 프론트엔드와 맞춰온 암묵적 약속까지. 이번에 템플릿 목록 API를 손보면서 그걸 다시 확인했다.

---

발단은 단순했다. 프론트엔드가 응답의 `status` 필드를 보고 성공/실패를 판단하고 있었다. 그런데 HTTP 상태코드가 이미 있다. 200이면 성공, 4xx/5xx면 실패. 같은 정보를 body에 또 담는 건 계약을 이중으로 만드는 것이고, 어느 쪽이 정본인지 모호해진다.

없애기로 했다. 실패 시엔 FastAPI의 `HTTPException`으로 처리하고, 성공 응답에는 `status` 키 자체를 포함하지 않는다.

---

페이지네이션은 처음엔 쿼리 파라미터 이름을 `page`로 할지 `offset`으로 할지부터 결정이 필요했다. 프론트가 이미 다른 엔드포인트에서 쓰는 방식이 있었고, 거기에 맞추는 게 나았다. `offset`으로 통일했다. 단, 이 `offset`은 행 단위 오프셋이 아니라 **1-based 페이지 번호**로 정의했다.

DB 쿼리에서 실제로 건너뛸 행 수는 이렇게 계산한다:

```
skip = (offset - 1) * limit
```

offset=1이면 skip=0, offset=2면 skip=30 (limit=30 기준). 이름은 offset이지만 동작은 page와 같다. 처음에 이 부분에서 한 번 헷갈렸다. 변수 이름이 의미를 배신하는 경우인데, 인터페이스 이름은 프론트 컨벤션을 따르고 내부 계산만 명확히 해두는 식으로 마무리했다.

`limit` 기본값은 30, 허용 범위는 1~300으로 잡았다. 상한을 안 두면 누군가는 limit=10000을 보낸다.

---

응답 구조도 바꿨다. 기존은 `count`와 `templates` 두 키였는데, 다른 API들이 쓰는 `PaginationDto` 스타일인 `totalCount`/`list`로 맞췄다. 이름을 통일하는 게 프론트에서 제네릭 처리를 할 때 훨씬 편하다는 피드백이 있었다.

`totalCount`의 정의도 명확히 해야 했다. 페이지네이션 이후 현재 페이지의 개수가 아니라, **필터 조건을 만족하는 전체 행 수**다. 클라이언트가 총 몇 페이지인지 계산할 수 있어야 하니까.

---

랜덤 추천 엔드포인트가 문제였다. `ORDER BY RAND()`로 매 요청마다 다른 결과를 돌려주고 있었는데, 거기에 페이지네이션을 붙이면 논리적으로 충돌한다. offset=1에서 본 목록과 offset=2에서 본 목록이 서로 독립적으로 셔플되니까, 중복이 생기거나 빠지는 항목이 생긴다.

해결 방향을 두 가지로 봤다. 세션 기반으로 셔플 결과를 캐싱하거나, 아예 랜덤성을 포기하고 결정론적 정렬로 바꾸거나. 지금은 세 번째 길을 택했다. 랜덤성은 유지하되 페이지네이션은 폼만 맞추는 것. 어차피 랜덤 추천에서 "다음 페이지"를 누르는 사용자 패턴이 거의 없다고 봤고, 응답 구조의 일관성이 더 중요했다. 완벽한 해답은 아니고, 나중에 이 엔드포인트의 실제 사용 패턴을 보고 다시 결정할 생각이다.

---

Swagger 문서도 같이 정리했다. FastAPI는 응답 모델을 명시하면 자동으로 스키마를 만들어주는데, `status` 필드가 응답 모델에 남아 있으면 문서에도 그게 나온다. 실제 응답과 문서가 달라지는 상황이 생기면 클라이언트 개발자 입장에서는 뭘 믿어야 할지 모른다. 모델을 수정하면 문서도 따라간다는 점이 FastAPI의 장점인데, 모델이 잘못 정의되어 있으면 그게 오히려 독이 된다.

지금 이 상태에서 `totalCount`가 페이지네이션 이전 총 개수라는 의미가 엔드포인트마다 일관되게 지켜지는지는 아직 전부 확인하지 않았다. 조인이 복잡한 쿼리에서 COUNT 시점이 WHERE 조건 적용 전인지 후인지 실수할 여지가 있다. 다음에 손댈 엔드포인트가 생기면 거기서부터 확인하려고 한다.
