페이지네이션(pagination — 데이터를 일정 단위로 나눠 순차적으로 내려주는 방식)을 붙이면서 처음엔 단순하다고 생각했다. `LIMIT`과 `OFFSET`만 넣으면 끝 아닌가. 그런데 정렬이 `ORDER BY RAND()`라는 걸 확인하고 멈췄다.

---

`ORDER BY RAND()`는 요청마다 새로 평가된다. DB가 쿼리를 받을 때마다 전체 행에 난수를 할당하고 다시 정렬한다. 그러면 page 1을 받을 때와 page 2를 받을 때, 배경에 깔린 순서가 달라진다.

```sql
-- page 1
SELECT * FROM content_meta
ORDER BY RAND()
LIMIT 10 OFFSET 0;

-- page 2 (다른 요청)
SELECT * FROM content_meta
ORDER BY RAND()
LIMIT 10 OFFSET 10;
```

두 쿼리는 독립적으로 실행된다. `OFFSET 10`은 "page 1에서 건너뛴 그 10개"가 아니라 "지금 이 순간 무작위로 섞인 결과의 11번째부터"다. page 1에 나왔던 항목이 page 2에서 다시 나올 수 있고, 반대로 영원히 안 나오는 항목도 생긴다.

offset이 작을수록 문제가 덜 보인다. page 1만 쓰는 클라이언트는 절대 눈치 못 챈다. `OFFSET 20` 이상부터 체감 중복률이 올라간다는 게 구조적으로 맞다 — 확률적으로 앞 페이지와 겹치는 행이 뒤로 갈수록 누적되기 때문이다. 수치로 측정한 건 없지만, 원리상 그렇다.

---

대안으로 검토한 게 seed 고정이었다.

```sql
-- seed를 받아 한 번 섞은 순서를 재현
SELECT * FROM content_meta
ORDER BY RAND(:seed)
LIMIT 10 OFFSET 10;
```

같은 seed를 쓰면 정렬 결과가 재현된다. 세션마다 seed를 발급하고 클라이언트가 페이지 탐색 동안 그걸 유지하면, "한 번 섞어놓은 덱을 한 장씩 넘기는" 동작을 흉내 낼 수 있다.

근데 DB 엔진마다 `RAND(seed)` 구현이 다르다. MySQL은 seed를 지원하고 같은 세션 내에서 재현성이 보장되지만, 버전에 따라 동작이 미묘하게 달라진다는 문서를 봤다. PostgreSQL은 `RANDOM()`에 seed 인자가 없고 `setseed()`를 세션에 먼저 걸어야 한다 — API 서버가 stateless하면 매 요청마다 세션을 세팅해야 하니 비용이 생긴다. 실제로 이 동작을 프로덕션에서 검증하진 않았다.

시간 버킷(time bucket) 방식도 있다. "오늘의 추천"처럼 하루 단위로 고정된 순서를 제공하는 경우, seed를 날짜 기반으로 파생시키면 된다. 추천이 자주 바뀌지 않아도 되는 도메인이라면 깔끔한 해결이다.

---

결국 이번 작업에서 내린 결론은 "페이지네이션을 붙이되 다중 페이지 탐색은 막는다"였다.

API 스펙상 랜덤성을 유지해야 했다. seed 방식은 검증 비용이 있고, 그 시점에서 우선순위가 아니었다. 그래서 응답 구조에는 `total`, `page`, `size` 필드를 채워서 페이지네이션 모양을 갖추되, 실질적으로 클라이언트가 page 1만 쓰도록 가이드했다. page 2 이상을 요청하면 에러를 내진 않지만, 중복이 발생할 수 있다는 걸 명세에 남겼다.

이게 만족스러운 해결은 아니다. 추천 목록을 스크롤하거나 "다음 페이지"를 누르는 UX가 생기면 다시 봐야 한다. 그때는 seed 방식이나, 아예 추천 결과를 한 번 계산해서 캐시에 저장하고 offset으로 슬라이스하는 구조를 선택해야 할 것 같다. 후자가 더 직관적이고 DB 부하도 낮지만, 캐시 무효화 타이밍이 새 문제가 된다.

아직 그 UX 요구사항이 안 왔다.
