원격 저장소에 직접 닿지 않는 환경에서 만든 커밋을, 닿는 환경으로 옮겨 개발 브랜치에 올려야 했다. 방법은 패치 파일이었다. 패치는 한 번에 적용됐다. 그런데 push가 두 번 막혔다.

## 중간 원격에 올려야 하나 하는 착각

처음에는 이렇게 생각했다. 커밋을 다른 환경으로 보내려면 어딘가 중간 원격에 push해서 거기서 받아야 하지 않나. 그런데 그 원격에 쓸 수가 없다.

아니었다. `git format-patch`는 로컬 커밋만 있으면 만들 수 있다. 원격은 필요 없다.

```bash
git format-patch <base>..<end>
```

`<base>`는 상대 환경에도 이미 있는 커밋으로 잡는다. 거기서부터 `<end>`까지의 커밋이 하나씩 `.patch` 파일이 된다. 파일을 메신저든 공유 폴더든 옮기기만 하면 된다. 받는 쪽은 이렇게 적용한다.

```bash
git am test.patch
```

`git am`은 diff만 붙이지 않는다. 작성자와 커밋 메시지까지 살려서 커밋으로 만든다. 그래서 "전달"이라는 말이 맞는다.

## 적용된 곳이 내가 생각한 브랜치가 아니었다

`git am`은 현재 체크아웃된 브랜치에 커밋을 쌓는다. 당연한 말인데, 수신 환경에서 지금 어느 브랜치에 있는지 확인하지 않고 적용했다. 개발 브랜치에 올릴 생각이었지만, 커밋은 `main`에 들어가 있었다.

push를 시도하자 이런 오류가 나왔다.

```
error: src refspec develop does not match any
```

처음엔 원격 쪽 문제인 줄 알았다. 문구를 다시 읽어 보니 `src`, 즉 보내는 쪽 refspec이 없다는 말이었다. 원격이 아니라 내 로컬에 `develop`이라는 브랜치가 없다는 뜻이다. 상태를 먼저 봤다.

```bash
git status -sb
git branch -a
git log --oneline -5
```

`git branch -a`에는 `remotes/origin/develop`만 있고 로컬 `develop`은 없었다. 이 수신 환경은 `main`만 체크아웃해 둔 상태였다. `git log`로는 방금 적용한 커밋이 `main`의 맨 위에 있는지 확인했다.

## 브랜치를 새로 만든 게 아니다

여기서 헷갈리기 쉬운 지점이 있다. "develop이 없다"를 "develop을 만들어야 한다"로 읽으면, 서버에 새 브랜치를 파는 것처럼 느껴진다. 실제로 필요한 건 이미 있는 `origin/develop`을 추적하는 로컬 브랜치를 만드는 일이다.

```bash
git checkout -b develop origin/develop
```

서버에는 아무것도 생기지 않는다. 로컬에 서버 브랜치를 따라가는 이름이 하나 생길 뿐이다. 원격에 같은 이름의 브랜치를 새로 만드는 `push`와는 성격이 다르다.

## main에 들어간 커밋 옮기기

이제 `develop` 위로 올라왔으니, `main`에 잘못 들어간 수정만 가져오면 된다.

```bash
git cherry-pick main
```

`main`이라는 브랜치 이름을 그대로 넘기면 그 브랜치의 맨 위 커밋 하나를 집는다. 이번에는 직전에 `git log --oneline -5`로 확인한 대로 옮길 커밋이 하나였기 때문에 이렇게 넘겼다. 패치가 여러 커밋이었다면 이 한 줄로는 부족하다. 커밋 해시를 직접 나열하거나 범위로 집어야 한다. 대상 커밋을 눈으로 확인하고 나서 cherry-pick 하는 순서는 지켰다.

`main`에 남아 있는 같은 커밋은 정리해야 한다. 이번 글에서는 이 정리를 다루지 않았고, 이 부분은 아직 내가 확인하지 못한 채 남아 있다.

## pre-receive hook declined

push를 다시 했다.

```bash
git push origin develop
```

이번에는 원격이 거절했다. 요약 한 줄은 `pre-receive hook declined`였다. 이 문구만 보면 서버 정책이 막은 것처럼 읽힌다. 커밋 메시지 규칙이나 브랜치 보호 같은 것을 떠올리게 된다. 그쪽을 뒤지기 전에 출력 전체를 위로 올려 읽었다.

hook이 내부적으로 호출하는 API에서 500이 나 있었다. 내 커밋이 규칙에 걸린 것이 아니라 hook이 의존하는 서비스 쪽이 실패한 것이다. 같은 명령을 그대로 재시도했더니 push가 성공했다.

## 남은 것

성공은 했지만 원인을 풀지는 못했다. 그 500이 일시적이었는지, 특정 시간대나 커밋 크기와 관련이 있는지 알아내지 못했다. 같은 일이 반복되면 hook이 호출하는 API 쪽 기록을 확인해야 한다. 지금은 재시도로 넘어갔다는 사실만 확실하다.

`main`에 남은 중복 커밋도 정리 대상으로 남아 있다.
