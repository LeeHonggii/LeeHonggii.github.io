"5학년 2학기"만 친 사람과 "비례식 풀이"만 친 사람에게 같은 필터를 태우고 있었다. 결과가 이상하다는 걸 알아채는 데 며칠, 원인을 인정하는 데 더 오래 걸렸다.

## 증상부터

학습 템플릿을 추천해주는 서비스였다. 사용자가 자유 텍스트로 요청하면 LLM이 템플릿 후보 중에서 골라주는 구조. 그런데 QA 시트에 이상한 케이스가 쌓이기 시작했다.

- "5학년 2학기" → 3학년 도형 템플릿이 상위에 뜸
- "비례식 풀이 알려줘" → 특정 학년 콘텐츠만 나옴, 다른 학년의 더 좋은 매칭은 밀림
- "5학년 2학기 비례식" → 그나마 얼추 맞음

세 케이스가 서로 다른 방향으로 틀어졌다는 게 이상했다. 보통 버그는 한 방향으로 편향되는데, 이건 입력마다 다른 방향으로 새고 있었다.

## 처음 의심한 곳 (틀렸다)

당연히 필터 점수 가중치를 의심했다. 학년 매칭 가중치를 올렸다 내렸다 하면서 두 케이스를 동시에 잡으려 했다. 5학년 케이스를 잡으면 비례식 케이스가 무너지고, 비례식을 잡으면 학년이 무너졌다. 시소였다.

가중치로 못 잡는다는 걸 인정하고 나서야 원인이 보였다. 필터에 들어오는 **입력의 의도가 다른데**, 파이프라인은 그걸 모르고 하나의 스칼라 점수로 합치고 있었다. 학년만 준 사람에게 키워드 점수 0점이 곱해지면서 후보군을 오염시켰고, 키워드만 준 사람에게 기본 학년 필터가 붙으면서 좋은 후보가 잘려나갔다.

의도가 다른 신호를 곱하고 있었다.

## 입력 타입을 먼저 갈라라

파이프라인 맨 앞에 판별 단계를 붙였다.

| 타입 | 조건 | 처리 |
|------|------|------|
| A | 학년·차시만 | 교육과정 역인덱스로 후보 좁힘 |
| B | 키워드만 | 텍스트 매칭 우선, 단원 확장은 보조 |
| C | 둘 다 | A로 좁힌 뒤 그 안에서 B |

기존:
```
validate → extract_keywords → filter_templates → LLM_recommend
```

변경 후:
```
validate
  → extract_keywords
  → resolve_input_type       # A/B/C
  → filter_templates (분기)
  → LLM_recommend
```

여기서 중요한 건 C가 A와 B의 산술 평균이 아니라는 점이다. C는 A를 먼저 돌려 후보군을 **줄인 다음**, 그 좁혀진 후보 안에서만 B를 돌린다. 두 신호가 순서대로 작동하지 서로 섞이지 않는다. 이 순서를 지키지 않으면 C는 결국 예전의 단일 파이프라인으로 회귀한다.

## LLM에게 뭘 넘길지가 다음 문제였다

분기까지 다 만들었는데 여전히 추천이 얕게 느껴지는 케이스가 있었다. 로그를 까보니 LLM 호출부에 사용자 원문만 그대로 넘기고 있었다. 필터 앞단에서 애써 구조화한 정보를 LLM에게는 안 주고 있던 것.

"비례식 풀이 알려줘" 원문만 받은 LLM은 이게 어떤 학년 흐름에서 나온 요청인지 모른다. C 경로였다면 이미 학년·단원이 결정된 상태였는데도 그걸 안 넘기고 있었다.

넘기는 컨텍스트를 이렇게 바꿨다.

```json
{
  "user_query": "비례식 풀이 알려줘",
  "school_level": "초등",
  "grade": 5,
  "semester": 2,
  "unit_name": "비와 비율",
  "learning_concepts": ["비례식", "비례배분", "내항·외항"],
  "input_type": "C"
}
```

`input_type`을 함께 넘기는 게 의외로 컸다. LLM이 "이 요청은 학년이 확정된 상태에서 온 것"인지 "키워드만으로 탐색 중인 것"인지 알면, 후보 중에서 고르는 방식이 달라진다. A 타입이면 단원 흐름에 충실한 걸 고르고, B 타입이면 개념 자체를 잘 설명하는 걸 고르는 식으로.

## 아직 남은 것

세 갈래로 나눈 건 잘한 판단인데, **판별 자체가 틀리는 케이스**를 아직 다 잡지 못했다. "5학년 방정식"처럼 학년 정보와 키워드가 섞여 있지만 실제로는 그 학년 교육과정에 없는 개념일 때 어떻게 처리할지가 애매하다. C로 태우면 후보가 0개가 되고, B로 태우면 학년 정보를 버리는 셈이다.

지금은 후보 개수를 보고 사후에 폴백하는 임시 코드로 막아놨는데, 이건 판별기가 확률적으로 두 개 이상의 타입을 반환하도록 바꾸는 쪽이 맞는 방향인 것 같다. 아직 못 재봤다.
