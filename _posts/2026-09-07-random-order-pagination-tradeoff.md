---

API 응답 계약을 정리하면서 템플릿 목록 API에 페이지네이션을 추가하는 작업을 맡았다. 대부분은 별 문제가 없었는데, 랜덤 추천 엔드포인트에서 막혔다.

요구사항은 단순해 보였다. 기존 응답에 `totalCount`와 `list`를 씌워서 다른 목록 API와 형태를 맞춰달라는 것. 그런데 이 엔드포인트는 `ORDER BY RAND()`로 결과를 뽑아왔다.

---

`ORDER BY RAND()`는 쿼리가 실행될 때마다 행마다 난수를 부여해서 정렬한다. 실행할 때마다 순서가 달라진다. 이게 문제의 근원이다.

offset 기반 페이지네이션은 "전체 결과를 고정된 순서로 쭉 늘어놓고, 거기서 몇 번째부터 몇 개를 잘라라"는 계약이다. 1페이지 요청과 2페이지 요청이 **같은 순서**를 전제로 한다. 그런데 `ORDER BY RAND()`는 매 요청마다 순서가 바뀐다.

```sql
-- 1페이지 요청
SELECT * FROM templates ORDER BY RAND() LIMIT 30 OFFSET 0;

-- 2페이지 요청 (다른 HTTP 요청)
SELECT * FROM templates ORDER BY RAND() LIMIT 30 OFFSET 30;
```

두 쿼리가 실행되는 시점이 다르다. RAND()가 만들어내는 순서도 다르다. 결과적으로 같은 row가 두 페이지에 모두 나타날 수도 있고, 아예 한 번도 안 나타나는 row가 생길 수도 있다. 수학적으로 피할 방법이 없다.

---

이걸 제대로 해결하려면 선택지가 몇 가지 있다.

**Seed 고정.** MySQL/MariaDB에서는 `RAND(seed)` 형태로 시드를 고정하면 같은 시드로 같은 순서가 나온다.

```sql
ORDER BY RAND(1234)
```

클라이언트가 첫 요청에서 seed를 받아서 이후 페이지 요청마다 그 seed를 같이 보내면 된다. 순서가 일관된다. 단점은 클라이언트가 상태를 들고 다녀야 하고, seed가 노출되면 결과를 예측할 수 있다는 점이다. 추천 특성상 예측 가능성은 크게 문제가 안 되지만, stateless를 기대하는 API 구조에서 seed 파라미터가 어색하게 들어가는 건 맞다.

**시간 버킷.** 하루 단위, 혹은 몇 시간 단위로 셔플을 고정하는 방식이다. 그 버킷 내에서는 순서가 바뀌지 않으니 페이지네이션이 가능하다. 구현이 복잡해지고, "언제 바뀌냐"를 클라이언트에 어떻게 알려주느냐는 별도 문제가 생긴다.

**고정 정렬 + 애플리케이션 레이어 셔플.** DB에서는 `ORDER BY id`처럼 결정론적으로 뽑아놓고, 애플리케이션에서 Fisher-Yates로 섞는다. 매 요청마다 섞는다면 여전히 같은 문제. 세션이나 캐시에 순서를 고정하면 다른 문제가 생긴다.

---

실제로 어떻게 했냐면, 랜덤 로직을 건드리지 않고 응답 형태만 맞췄다.

엔드포인트는 원래 의도가 "매 호출마다 다른 추천 결과를 보여주는 것"이었다. 사용자가 새로고침하면 다른 템플릿이 보여야 한다. 이게 기획 의도였다. 그러면 페이지네이션 자체가 이 API에 어울리는 개념인지가 먼저 의심스러운 거다.

확인해보니 클라이언트가 실제로 2페이지 이상을 요청하는 시나리오가 없었다. offset=0으로만 쓴다. 페이지네이션 구조를 응답에 얹으라는 요구는 "다른 목록 API들과 응답 포맷을 통일하라"는 계약 정리의 일환이었지, "페이지를 넘기는 UX를 만들라"는 게 아니었다.

그래서 응답을 `{ totalCount, list }` 형태로 감쌌다. `totalCount`는 DB 전체 count를 반환한다. 랜덤 정렬은 그대로 둔다. offset이 0 이상일 때 결과의 일관성을 보장하지 않는다는 것을 API 문서에 명시했다.

```
GET /api/random-templates?offset=0&limit=30
→ { totalCount: 120, list: [...30개, 매 요청마다 순서 다름] }

GET /api/random-templates?offset=1&limit=30
→ { totalCount: 120, list: [...30개, 1페이지와 독립적으로 랜덤] }
```

---

이 결정이 완전히 깔끔하냐고 하면 그렇진 않다. offset 기반 페이지네이션이라는 형태를 쓰면서 그 의미를 일부 위반하고 있는 건 사실이다. API를 쓰는 클라이언트 개발자가 나중에 2페이지를 쓰려고 시도했다가 이상한 결과를 보고 당황할 수 있다.

문서화가 그걸 막아주기를 바라는 건데, 실제로 문서를 읽는지는 별개 문제다.

seed 방식이 더 정직한 해결책이긴 하다. 언젠가 클라이언트가 "다음 페이지로 더 보기" 기능을 요구하면 그때 다시 봐야 할 것 같다.
