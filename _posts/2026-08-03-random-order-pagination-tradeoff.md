추천 API에 페이지네이션을 얹는 작업을 하다가 QA 로그에서 이상한 걸 봤다. 무한 스크롤로 목록을 내리다 보면 방금 지나간 카드가 다시 튀어나온다는 거였다. 처음에는 프론트 렌더 캐시를 의심했다. 그다음엔 offset 계산 실수를 의심했다. 둘 다 아니었다.

원인은 훨씬 시시했고, 그래서 더 오래 걸렸다. `ORDER BY RAND()` 로 뽑은 결과에 offset 을 붙이고 있었다.

## 눈으로는 잘 안 보이는 충돌

문제를 코드 두 줄로 줄이면 이렇다.

```sql
-- 1페이지
SELECT * FROM content ORDER BY RAND() LIMIT 30 OFFSET 0;

-- 2페이지
SELECT * FROM content ORDER BY RAND() LIMIT 30 OFFSET 30;
```

문법적으로는 아무 문제 없다. 두 쿼리 다 정상적으로 30개씩 돌려준다. 그런데 두 쿼리 사이에는 **공유되는 순서가 없다**. 첫 번째 쿼리가 만든 랜덤 순열은 그 쿼리 실행이 끝나는 순간 사라진다. 두 번째 쿼리가 실행될 때 DB 는 처음부터 다시 섞는다. 그러니 offset 30 이라는 값이 가리키는 "그 다음 30개" 라는 개념 자체가 성립하지 않는다.

무한 스크롤 UX 는 그 개념이 성립한다는 전제 위에서 만들어져 있었다. 프론트는 "이전에 본 것 다음을 달라" 고 요청하고 있는데, 서버는 매번 "지금 이 순간의 랜덤 30개" 를 주고 있었다. 겹치는 게 정상이고, 안 겹치면 그건 운이 좋았던 거다.

## "그럼 seed 를 박으면 되지 않나" 라는 흔한 답

가장 먼저 떠오르는 답이 있다. seed 를 고정해서 순열을 공유하는 방법이다. 세션 시작 때 seed 하나 발급해서 클라이언트가 들고 다니게 하면 된다.

```sql
SELECT * FROM content ORDER BY RAND(:seed) LIMIT 30 OFFSET 0;
SELECT * FROM content ORDER BY RAND(:seed) LIMIT 30 OFFSET 30;
```

이론상 깔끔하다. 실제로 넣어보려다가 접었다. 이유는 두 가지였다.

첫째, 우리 추천은 그냥 `SELECT * ... RAND()` 가 아니다. 사용자 프로파일(직무 16개 축, 커리어 단계, 캐릭터 유형)에 따라 축별 가중치가 붙고, 그 위에서 후보 풀을 만든 뒤 다양성 재정렬(MMR)까지 통과한다. 랜덤은 그 흐름의 마지막 tie-break 이지, 정렬의 본체가 아니다. 예를 들어 축 가중치는 이렇게 잡혀 있다.

```python
MATRIX = {
    'job':     {'level': 0.6, 'self': 0.2, 'trend': 0.2},
    'career':  {'level': 0.4, 'self': 0.2, 'trend': 0.4},
    'company': {'level': 0.4, 'self': 0.4, 'trend': 0.2},
}
```

여기에 캐릭터에 따른 델타가 더 얹힌다.

```python
CHARACTER_AXIS_DELTA = {
    '트렌드 적응가': {
        'job':     {'trend':  0.04, 'level': -0.04},
        'career':  {'trend':  0.06, 'level': -0.04, 'self': -0.02},
        'company': {'trend':  0.05, 'level': -0.02, 'self': -0.03},
    },
    '실무 적용가': {
        'job':     {'self':   0.04, 'trend': -0.04},
        'career':  {'level':  0.03, 'trend': -0.03},
        'company': {'self':   0.03, 'trend': -0.03},
    },
    # ...
}
```

seed 하나로 순열을 고정한다는 건 이 파이프라인 전체의 출력이 세션 내내 얼어붙는다는 뜻이다. 사용자가 스크롤하는 동안 프로파일 신호가 갱신돼도 반영되지 않고, 신규 콘텐츠가 들어와도 다음 세션이 되기 전에는 후보에 낄 수 없다. 추천 시스템에서 "결정론적 순열" 은 생각보다 큰 대가를 요구한다.

둘째, seed 를 어디에 보관할지가 애매했다. 쿠키에 박자니 로그인 없이 쓰는 경로가 있고, 서버 세션에 박자니 스테이트리스로 유지하고 싶은 엔드포인트였다. seed 를 클라이언트가 들고 다니게 하면 "10페이지쯤 봤을 때 seed 잃어버리면 어떻게 되지" 같은 케이스가 계속 튀어나온다. 잃어버리면 다시 처음부터 중복이 시작된다. 결국 원래 문제로 돌아온다.

## 결정론 컬럼으로 정렬하는 안

두 번째로 검토한 건 그냥 `created_at DESC, id DESC` 같은 결정론적 정렬로 바꾸는 거였다. 페이지네이션은 정확해진다. 대신 "랜덤 추천" 이라는 컨셉이 사라진다.

이 API 는 사용자가 새로고침할 때마다 "오, 이번엔 이런 게 뜨네" 하는 감각이 있어야 하는 자리였다. 매번 같은 순서로 최신순 상위 30개를 보여주면 그건 랜덤 추천이 아니라 그냥 최신순 리스트다. 다른 페이지에 이미 최신순 리스트가 있었기 때문에, 이 자리까지 최신순으로 바꾸면 두 API 가 사실상 같은 걸 하게 된다.

기술적으로는 이게 제일 쉬웠는데, 제품 관점에서 이 옵션은 애초에 선택지가 아니었다. "쉽다" 는 이유로 이걸 골랐다면 나중에 기획자한테 다시 갈아엎으라고 요청받았을 거다.

## 실제로 고른 답 — 페이지네이션의 의미를 바꿨다

결국 고른 방법은 세 번째였다. **API 응답의 껍데기만 페이지네이션 모양을 유지하고, 매 요청을 독립된 랜덤 뽑기로 만드는 것**.

```
GET /recommend/random?offset=1&limit=30
→ 매 요청마다 새로 뽑은 랜덤 30개
  응답 포맷은 { total, page, has_next, items } 로 유지
```

여기서 `offset` 은 클라이언트가 몇 페이지째를 보고 있는지 표시하는 용도로만 남기고, 서버 내부 쿼리에는 반영하지 않는다. `has_next` 는 후보 풀이 요청 크기보다 큰지만 본다. 사실상 클라이언트가 "다음" 버튼을 눌러도 서버가 하는 일은 첫 요청과 같다.

이렇게 정하고 나면 중복은 사라지지 않는다. 오히려 발생 가능성으로 남는다. 대신 그 중복은 **버그가 아니라 명세** 가 된다. 프론트에는 "이 엔드포인트는 요청마다 독립적으로 신선한 추천을 준다. 중복 제거가 필요하면 클라이언트에서 이미 본 id 를 필터링해라" 라고 문서에 못을 박았다. 실제로 프론트는 최근 본 id 50개 정도를 링 버퍼로 들고 다니면서 응답에서 걷어내는 식으로 처리했다.

## 이게 정답이라기보다는

돌아보면 이 판단은 "무한 스크롤에서 한 콘텐츠를 절대 두 번 봐서는 안 되는가?" 라는 질문에 얼마나 강경한 답을 갖고 있느냐로 갈렸다. 우리는 그렇게 강경하지 않았다. 사용자가 스크롤을 아주 오래 내리는 사용 패턴도 아니었고, 겹치더라도 그게 흐름을 끊는 종류의 콘텐츠가 아니었다.

만약 이게 학습 이력처럼 "이미 수료한 걸 또 추천받으면 짜증나는" 도메인이었다면 답이 달랐을 거다. 그때는 seed 를 물고 가는 비용을 감수하거나, 아예 랜덤을 버리고 완결성 있는 커서 페이지네이션으로 갔을 것 같다.

아직 안 해본 것도 남아 있다. 후보 풀 자체를 세션 단위로 캐시하고 그 안에서만 offset 을 굴리는 방식 — seed 고정의 사촌 격인데 프로파일 갱신을 일정 주기로 반영할 수 있는 형태 — 는 다음에 트래픽이 커지면 다시 검토해봐야 할 것 같다. 지금은 그럴 만한 요청 볼륨이 아니라서 미뤄뒀다.
