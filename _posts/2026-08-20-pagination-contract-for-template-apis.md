프론트엔드에서 페이지네이션 요청을 어떻게 보낼지 논의하다가, 우리가 `offset`이라는 단어를 서로 다르게 쓰고 있다는 걸 뒤늦게 알았다.

프론트 쪽은 Nest에서 쓰던 `PaginationDto` 습관 그대로였다. `offset=1`이면 1페이지, `offset=2`면 2페이지. 즉 **1-based 페이지 번호**다. 반면 내가 처음 작성한 FastAPI 엔드포인트는 SQL 관례를 따라 `offset`을 **행 오프셋(row offset)**으로 받고 있었다. `offset=1`이면 첫 번째 행을 건너뛴다는 뜻.

같은 파라미터 이름인데 해석이 정반대였다. 프론트가 `offset=1&limit=30`을 보내면 나는 1행부터가 아니라 2행부터 결과를 돌려주고 있었던 것이다.

---

맞추는 방법은 간단했다. API 계약 자체를 프론트 기대에 맞게 바꾸는 것.

```
skip = (offset - 1) * limit
```

`offset`은 1-based 페이지 번호로 공식 해석한다. 백엔드 내부에서 SQL `OFFSET`으로 변환할 때만 이 식을 쓰면 된다. 이렇게 하면 `offset=1`은 건너뛸 행이 없고, `offset=2`는 첫 `limit`개를 건너뛰는 식으로 자연스럽게 작동한다.

엔드포인트 모양은 이렇게 됐다.

```
GET /templates-by-tool/{main_tool}?offset=1&limit=30
GET /random-templates?offset=1&limit=30
```

---

같은 시점에 응답 구조도 손봤다.

기존 응답은 `count`와 `templates`라는 키를 쓰고 있었다. 문제는 `count`가 "지금 페이지에 담긴 개수"인지 "전체 레코드 수"인지 이름만으론 알 수 없다는 점이었다. 실제로는 전체 개수를 내려주면서 이름이 모호했다.

바꾼 뒤 응답은 이렇다.

```json
{
  "totalCount": 7,
  "list": [ ... ],
  "main_tool": "SM02PB"
}
```

`totalCount`는 전체 레코드 수, `list`는 현재 페이지 아이템 배열. 이름에서 의미가 바로 읽힌다. `templates`라는 키가 도메인 특화 이름이었던 것도 `list`로 일반화하면 다른 목록 API와 패턴을 통일하기 쉬워진다.

---

`status` 필드도 이번에 제거했다.

응답 body 안에 `status: "success"` 같은 값을 넣는 패턴은 HTTP 상태코드가 이미 하는 일을 다시 표현한다. 실패할 때도 body에 상태를 담으면 클라이언트가 두 군데를 동시에 봐야 한다. 어느 쪽이 진실인지도 모호해진다.

정리 방향은 이쪽이다. 성공이면 `200`에 데이터만, 실패하면 `4xx`/`5xx`에 에러 메시지. body 안에 성공/실패 플래그를 두지 않는다.

입력 검증 실패를 확인할 때도 이 기준을 썼다.

```bash
curl.exe -i "http://localhost/random-templates?limit=301"
```

`limit`이 허용 범위를 넘으면 `422 Unprocessable Entity`를 돌려주는지 직접 때려봤다. body 안에 `status: "error"`를 보는 게 아니라 HTTP 상태코드 자체가 응답이어야 하니까.

---

랜덤 정렬 엔드포인트는 다른 문제를 건드렸다.

랜덤 순서로 결과를 뽑으면 페이지마다 순서가 달라진다. `offset=1`과 `offset=2`를 연속으로 요청했을 때 같은 항목이 두 번 나올 수도 있고 빠질 수도 있다. 페이지네이션의 기본 전제인 "같은 결과셋을 페이지 단위로 슬라이싱한다"가 깨진다.

seed를 고정하는 방안도 검토했다. 클라이언트가 첫 요청 때 받은 seed를 이후 요청에 계속 넘기면 같은 랜덤 순서가 유지된다. 구현은 가능하지만 seed를 어떻게 전달하고 보관할지, 만료는 어떻게 처리할지, 같은 seed가 서버 재시작 뒤에도 같은 순서를 보장하는지까지 고려하면 범위가 커진다.

지금 단계에서는 랜덤 자체는 그대로 두고, 응답 형태만 페이지네이션 규격에 맞추기로 했다. `totalCount`와 `list`를 내려주되 랜덤 특성으로 인한 중복·누락 가능성은 API 문서에 명시하는 방향이다.

```json
{
  "totalCount": 276,
  "list": [ ... ]
}
```

이게 완전한 해결인지는 솔직히 잘 모르겠다. 프론트에서 무한스크롤로 붙이거나 "더 보기"를 누를 때 중복 항목이 실제로 얼마나 문제가 되는지는 써봐야 안다.
