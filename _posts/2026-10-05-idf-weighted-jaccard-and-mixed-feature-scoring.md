추천 시스템의 점수 계산 코드를 다시 읽다가 막힌 지점이 있었다. 키워드 비교 부분에 IDF가 들어가 있는데, 발표 도식에는 "TF-IDF 벡터 비교"라고 적혀 있었다. 둘이 같은 건가? 같다면 TF는 어디 갔나?

이 글은 그걸 코드와 도식에 대조하면서 정리한 학습 노트다. 코드 원문은 싣지 않는다. 확인한 구조만 적는다.

## 코드를 열어보니 TF-IDF가 아니었다

콘텐츠마다 키워드 태그 집합이 붙어 있고, 두 콘텐츠의 키워드 점수는 **IDF 가중 자카드**(Jaccard, 두 집합의 교집합 크기를 합집합 크기로 나눈 유사도)였다. 제목 비교도 같은 방식이다. 벡터 내적이나 코사인이 아니다.

일반 자카드는 이렇게 생겼다.

```
J(A, B) = |A ∩ B| / |A ∪ B|
```

IDF 가중 버전은 원소를 세는 대신 원소의 IDF를 더한다. 분자는 겹치는 태그들의 IDF 합, 분모는 합집합 태그들의 IDF 합이다. IDF(Inverse Document Frequency, 역문서빈도)는 이렇게 정의된다.

```
IDF(t) = log(N / df(t))
```

N은 전체 콘텐츠 수, df(t)는 태그 t가 붙은 콘텐츠 수다. 어디에나 붙는 태그는 0에 가깝고, 드문 태그는 크다.

## TF는 왜 필요 없나

처음엔 "TF-IDF에서 IDF만 쓰는 건 반쪽 아닌가" 싶었다. 그런데 TF(Term Frequency, 문서 안 단어 출현 횟수)는 한 문서에서 같은 단어가 여러 번 나올 때 의미가 있다. 태그 집합은 중복이 없다. 한 콘텐츠에 같은 태그가 두 번 붙을 수 없으니 TF는 항상 0 아니면 1이고, 구별해 줄 정보가 없다.

남는 문제는 "흔한 태그의 겹침과 드문 태그의 겹침을 같게 볼 것인가"다. 이건 IDF가 푼다. '입문' 태그가 겹치는 것과 아주 구체적인 주제 태그가 겹치는 것은 다른 신호다.

여기서 내가 한 번 헷갈렸다. df는 "태그 종류가 몇 개인가"가 아니라 "그 태그가 몇 개 콘텐츠에 붙었는가"다. 키워드 종류 수와 부착 횟수를 섞어 생각하고 있었다. 설명을 정리하다가 바로잡았다.

## 속성마다 비교 규칙이 다르다

키워드만 있는 게 아니다. 콘텐츠에는 성격이 다른 속성이 섞여 있어서 한 가지 거리로 못 잰다.

- 텍스트성 태그(키워드, 제목): IDF 가중 자카드
- 계층 코드(분류 체계): 공통 상위 단계가 얼마나 깊은지로 비교
- 시간 구간(학습시간): 구간 간 근접도
- 범주(유형 등): 같으면 1, 다르면 0

각 속성을 0~1 점수 s_i로 만든 뒤 가중 평균을 낸다.

```
기본 관련도 = Σ(w_i × s_i) / Σw_i
```

분모를 Σw로 나누는 건 가중치 총합이 바뀌어도 점수 범위가 0~1로 유지되게 하려는 것이다. 추천 목적(같은 주제를 더 볼 것인가, 다음 단계로 갈 것인가)에 따라 w를 다르게 준다. 같은 s_i로도 관점이 다른 점수를 얻는다.

다음 단계 추천은 여기에 조건부 부스팅을 얹고, 여러 관점의 순위는 RRF(Reciprocal Rank Fusion, 순위의 역수를 합산해 순위 리스트를 합치는 방식)로 합친다. 이 부분은 계산 과정을 손으로 따라가 본 수준이고, 가중치 값 자체를 검증한 건 아니다.

## 경계 조건 두 가지

**스무딩 상수.** 분자와 분모에 같은 상수를 더하는 스무딩을 쓰면, 겹치는 태그가 하나도 없어도 점수가 양수가 된다. 분자 0에 상수 ε, 분모 D에 ε을 더하면 ε/(D+ε)다. 태그가 극단적으로 적은 콘텐츠끼리는 이 값이 무시할 수 없게 커질 수 있다. "겹침 없음 = 0"을 전제로 하는 하류 로직이 있으면 어긋난다. 이 경계를 실제 데이터에서 재보지 않았다.

**"벡터화하면 계층 정보를 잃는다"는 설명.** 도식을 보며 이런 설명이 붙어 있었는데, 과하다. 계층 코드를 원-핫으로 펴면 잃지만, 상위 단계별 접두 피처를 따로 만들면 계층이 보존된다. 잃느냐는 벡터화 자체가 아니라 피처 설계의 문제다. 이 코드가 규칙 기반 비교를 택한 이유는 "벡터화가 불가능해서"가 아니라 해석 가능성과 단순함에 가깝다고 본다. 이 역시 코드 주석이 아니라 내 추정이다.

## 아직 남은 것

학습시간을 난이도의 대리 지표(proxy)로 쓰는 가정이 있다. 시간이 길면 어렵다는 전제인데, 긴 입문 과정이 있을 수 있다. 다음 단계 추천의 부스팅이 이 가정에 기대고 있어서, 시간 구간과 실제 난이도 라벨이 있는 샘플로 상관을 먼저 봐야 한다. 아직 보지 않았다.
