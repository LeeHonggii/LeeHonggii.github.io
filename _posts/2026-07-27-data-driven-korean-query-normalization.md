임베딩부터 붙이고 싶었다. 그게 요즘 방식이니까.

그런데 alias map(별칭 사전 — 동의어·약어를 표준 표현에 매핑하는 딕셔너리) 초안을 짜다가 손이 멈췄다. 내가 지금 넣고 있는 이 "초6 → 6학년" 같은 규칙은, 사용자가 실제로 그렇게 친다는 근거가 있나. 아니면 내 머릿속에서 그럴 것 같다고 만들어낸 규칙인가.

## 로그를 먼저 꺼냈다

분석 스크립트를 돌려 실제 입력을 전부 뽑았다. 총 2104건. `strip()` 과 공백 기준 중복 제거 후 1849건. 약 12%가 공백·대소문자만 다른 중복이었다. 이 12%가 첫 번째 힌트였다 — 사용자는 우리가 예상하는 것보다 더 지저분하게 친다.

분포를 훑어봤다. 임베딩이 필요한 "의미가 다른데 비슷한 질문"은 예상보다 훨씬 적었다. 대신 이런 게 대부분이었다.

| 유형 | 예시 |
|---|---|
| 학년·차시 표현 다양성 | "6-1 분수", "6학년 1학기 분수", "초6 분수" |
| 어미·조사 변형 | "나눗셈 하는법", "나눗셈 방법", "나눗셈이란" |
| 띄어쓰기 | "분수의나눗셈", "분수 의 나눗셈" |
| 명백한 오타 | "곱세기" → "곱셈" |

이걸 임베딩으로 풀 수도 있다. 그런데 표층 정규화(surface normalization — 문자열 수준의 정규화)로 잡을 수 있는 걸 굳이 모델 추론으로 돌리는 건 낭비다. 캐시도 안 되고, 왜 매칭됐는지 설명도 안 된다.

## 파이프라인은 단계로 쪼갰다

한 함수에 다 몰아넣지 않았다. 검색 인덱스 생성 시점과 사용자 입력 시점에 **완전히 같은 함수**가 호출되어야 하기 때문이다. 인덱스는 A로 정규화됐는데 질의는 B로 정규화되면, 아무리 로직이 정교해도 매칭이 깨진다. 이 대칭성이 흔들리는 걸 막으려면 함수를 얇게 자르는 게 낫다.

기본 정규화는 눈에 안 보이는 차이만 털어낸다.

```python
def normalize_text(s: str) -> str:
    s = s.strip()
    s = re.sub(r"\s+", " ", s)
    s = unicodedata.normalize("NFC", s)
    return s.lower()
```

NFC(유니코드 정규화 형식 C — 결합 자모를 합성 형태로 통일)를 여기서 처리하는 이유는 한국어 텍스트가 입력 경로에 따라 자모 분리형으로 들어올 때가 있어서다. 이게 다르면 겉보기 같은 "분수"가 다른 키가 된다.

그 위에 매칭용 정규화가 얹힌다.

```python
def normalize_for_match(s: str) -> str:
    s = normalize_text(s)
    s = re.sub(r"[의\s]+", "", s)
    return s
```

"분수의나눗셈"과 "분수 나눗셈"이 같은 키가 되도록. 조사 "의"를 지우는 결정은 도메인 특수해서 일반화 못 한다. 하지만 수학 개념명에서 "의"는 소유·연결 조사로만 쓰이지 개념 그 자체가 아니라는 관찰이 로그에서 확인됐다.

alias map은 코드에 박지 않고 YAML로 뺐다. 학년·학기 표현이 가장 많았는데, 이건 교육과정 개편에 따라 계속 바뀐다. 리뷰하기 쉬워야 했다.

## 오타는 건드리지 않기로 했다

가장 오래 고민한 부분이다. "곱세기" → "곱셈" 같은 건 명백해 보이지만, 일반 맞춤법 교정기를 그대로 붙이면 "sin코사인" 같은 표현을 망친다. 수학 도메인 단어는 사전에 없을 확률이 높고, 사전에 없으면 교정기가 가장 가까운 일반 단어로 끌고 가버린다.

원칙을 하나로 좁혔다: **사전에 명시된 오타 → 정답 매핑에 있는 것만 고친다.** 자동 교정은 없다. 이 원칙 하나로 위험한 케이스는 다 빠졌지만, 대신 alias map이 계속 자라야 한다. 이건 감수하기로 했다.

## 회귀 테스트가 잡은 것

각 단계마다 테스트를 누적했다. 이게 왜 중요한지는 "1학기"를 canonical 형태로 통일하는 규칙을 추가하다가 알았다. 이 규칙 하나가 curriculum index(교육과정 단원 인덱스 — 학년·학기·단원을 역조회하는 구조)의 키 조립 방식과 충돌했다. 인덱스 쪽은 "1학기"를 별도 필드로 보관하는데, 정규화가 그걸 제목 안에 끼워 넣으니까 키가 두 번 겹쳐 들어갔다.

```
PASS  normalize_for_match("분수의나눗셈") == normalize_for_match("분수 나눗셈")
PASS  apply_alias_map("초6 분수") == "6학년 분수"
FAIL  apply_alias_map("1학기") → curriculum index key 충돌
```

테스트가 없었으면 프로덕션 로그에서 잡았을 거다. alias map을 사람이 계속 만지는 구조를 택한 이상, 이 안전망은 꼭 필요했다.

## 아직 안 한 것

임베딩은 결국 붙일 거다. 다만 순서가 바뀌었다. 표층 정규화로 걸러진 뒤 남는 "정말 의미로만 다른" 질의가 얼마나 되는지, 그걸 봐야 임베딩 모델 선택 기준이 잡힌다. 지금 붙였으면 정규화가 해줬을 일까지 모델이 뒤집어썼을 거고, 왜 이 결과가 나왔는지 설명을 못 했을 거다.

alias map은 지금 손으로 채우고 있다. 로그가 계속 쌓이니까, 신규 표현이 얼마 이상 빈도로 등장하면 후보로 뽑아주는 반자동 파이프라인이 다음 순서다. 아직은 눈으로 본다. 눈으로 보는 게 지겨워질 시점이 언제인지도 재보고 있다.
