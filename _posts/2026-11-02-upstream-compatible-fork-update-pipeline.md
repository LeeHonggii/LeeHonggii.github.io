오픈소스 에디터를 포크해서 쓰고 있다. 어느 날 앱을 열었더니 직접 고친 부분이 사라져 있었다.

원인은 단순했다. 공식 자동 업데이트가 내 빌드를 새 공식 바이너리로 통째로 갈아엎은 것이다. 한글 번역도, 직접 넣은 기능도 같이 날아갔다.

## 무엇을 잃었나

그 포크에는 이번 주에 작업한 것이 몇 개 있었다.

- 긴 셸 명령이 코드 블록 밖으로 새어 나오는 렌더링 문제 수정
- PPTX 문서를 여는 기능
- 캔버스 배치를 PPTX·HTML로 바꾸는 변환 코드 확장

이걸 하루 이틀 만에 다시 만들 수는 있다. 하지만 업스트림은 계속 새 버전을 낸다. 업데이트 때마다 같은 일이 반복된다면 포크를 유지하는 의미가 없다.

## 먼저 한 일: 자동 업데이트 끄기

급한 불부터 껐다. 설정에서 `"auto_update": false`로 바꿨다. 이건 임시방편이다. 새 버전의 수정과 보안 패치를 받는 길까지 같이 막기 때문이다. 업데이트를 받되 내 변경을 잃지 않는 별도 경로가 필요했다.

## 변경을 둘로 쪼갠다

가장 먼저 한 판단은 내 변경을 성격별로 나누는 것이었다.

- **번역 변경**: 문구를 바꾸는 작업이다. 양이 많고 기계적이다.
- **기능 변경**: 렌더링 수정, PPTX 열기처럼 로직을 건드린다.

한 덩어리 diff로 들고 있으면 업스트림이 바뀔 때 어디서 충돌했는지 구분이 안 된다. 번역은 도구로 다시 돌리면 되고, 기능은 패치를 재적용해야 한다. 다루는 방식이 달라서 따로 관리하기로 했다.

두 번째로, 지금 내 소스를 "깨끗한 원본 + 패치"로 재현할 수 있어야 했다. 깨끗한 원본을 받아 놓고 현재 소스와의 차이를 패치로 뽑았다. 이때 쓴 것이 `make_patch.py`다. 새 버전이 나오면 `update_upstream.sh`가 새 소스를 받아 이 패치들을 다시 얹는다.

## 설치하기 전에 확인한다

패치가 적용됐다고 곧바로 설치하면 위험하다. 파이프라인은 이렇게 짰다.

1. 별도 작업 공간에 새 소스를 받는다.
2. 번역과 기능 패치를 적용한다.
3. 빌드한다.
4. 만들어진 바이너리 안에 내가 넣은 문구가 실제로 들어 있는지 확인한다.
5. 통과하면, 앱이 종료될 때 설치한다.

4번을 넣은 이유가 있다. 패치는 에러 없이 적용되는데 번역이 조용히 빠지는 경우를 겪었기 때문이다. 빌드가 성공했다는 사실로는 내 변경이 살아 있다는 것을 알 수 없다. 결과물을 직접 열어 문구를 찾아보는 수밖에 없었다.

5번의 "앱 종료 시 설치"는 실행 중인 앱을 덮어쓰다가 깨지는 일을 피하려는 선택이다.

## 막혔던 곳들

처음부터 매끄럽게 돈 건 아니다. 부딪힌 문제를 기억나는 대로 적는다.

**번역 도구가 작업 디렉터리에 의존했다.** 어디서 실행하느냐에 따라 결과가 달라졌다. 파이프라인은 별도 작업 공간에서 돌기 때문에 이 의존성이 바로 문제가 됐다. 실행 위치를 고정해서 풀었다.

**Git 색인이 어긋났다.** 작업 트리와 색인 상태가 맞지 않아서 diff가 실제 변경과 다르게 나왔다. 패치가 이상하면 패치 로직보다 색인부터 의심하게 됐다.

**업스트림이 파일을 쪼갰다.** 내가 패치하던 파일이 새 버전에서 여러 파일로 나뉘었다. 기존 패치는 대상이 없어서 적용에 실패한다. 이건 자동으로 해결되지 않았고, 새 구조에 맞춰 패치를 다시 만들어야 했다. 포크 유지에서 가장 비용이 큰 지점이 이쪽이라고 느꼈다.

**새 파일 패치의 경로가 틀렸다.** 기존 파일을 고친 패치는 잘 붙는데, 새로 추가한 파일은 경로 처리에서 계속 어긋났다. 패치 생성 쪽 문제였다.

## 외부 에이전트 어댑터

같은 시기에 외부 코딩 에이전트와 연결하는 어댑터도 손봤다. 엔진 버전을 맞추고, 연결이 됐는지 응답을 시험했다. 여기서 확인한 것은 연결 응답까지다. 에이전트와 실제로 대화를 주고받는 전체 기능이 동작하는지는 이 시험으로 확인하지 못했다. 둘을 같은 것으로 쓰면 안 된다고 생각해서 구분해 둔다.

## 아직 남은 것

- 전체 파이프라인이 새 업스트림 버전에서 처음부터 끝까지 도는지는 지켜봐야 한다. 지금까지는 실패 사례를 하나씩 막아 온 단계다.
- 업스트림이 또 파일 구조를 바꾸면 패치 재작성은 여전히 수작업이다. 이걸 줄일 방법은 아직 못 찾았다.
- 여러 에이전트의 대화와 진행 상태를 보여 주는 보드는 만들었지만, 최종 화면 검증은 끝나지 않았다. 에이전트 간 작업 전달 기능도 아직 없다.
- 업데이트에 걸리는 시간과 패치 충돌 빈도는 재 보지 않았다.

자동 업데이트는 지금도 꺼져 있다. 파이프라인이 다음 버전에서 한 번 더 버텨 주면 그때 켜는 것도 생각해 보려 한다.
