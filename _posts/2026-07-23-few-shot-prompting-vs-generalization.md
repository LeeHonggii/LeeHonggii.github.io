"이 질의에서 키워드가 틀렸어요."

이 문장 하나면 그날 오후는 다 갔다. 재현하면 정말로 틀린 결과가 나온다. 그러면 나는 무엇을 했나. 프롬프트 아래쪽에 예시를 하나 더 붙였다. "이런 입력엔 이렇게 뽑아야 한다"고. 테스트를 다시 돌려 그 케이스가 통과하면 **고쳤다**고 적었다. 지금 돌아보면 그건 고친 게 아니었다. 다음 버그를 예약해 둔 거였다.

## 퓨샷은 망치가 아니라 테이프다

퓨샷(few-shot, 프롬프트에 예시 몇 개를 박아 넣어 모델 행동을 유도하는 방식)은 즉효약처럼 느껴진다. 한 케이스가 틀리면 그 케이스와 정답을 나란히 붙여 넣으면 되니까. 문제는 이게 **한 케이스를 고치면서 다른 케이스를 부수는 방향으로 작동한다**는 데 있다.

이런 게 있었다.

```
입력:  "수 모으기 활동"
기대:  ["모으기"]
출력:  ["수", "수 모으기"]
```

예시로 박으면 이 줄은 통과한다. 그런데 모델은 이제 "활동"이 붙은 다른 질의에서도 맥락을 좁히려는 흉내를 낸다. 내가 원한 건 원리의 일반화였는데, 모델이 학습한 건 표면 패턴의 모사였다.

더 곤란한 건 이런 쪽이다.

```
입력:  "전체와 부분의 관계 이해"
박은 예시: → keywords=["분수"]
```

초등 수학이라면 그럴싸하다. 하지만 이 문장은 문맥이 없다. 비율일 수도, 도형 넓이일 수도, 집합일 수도 있다. 퓨샷으로 "분수"라고 못을 박으면 커리큘럼이 조금만 달라져도 오답이 나온다. 그리고 그 오답은, 누군가가 다시 회의에서 지적해 주기 전까지는 조용히 지나간다.

## 회의 케이스는 프롬프트가 아니라 테스트셋으로 간다

퓨샷 예시와 회귀 테스트(regression test, 이전에 통과하던 케이스가 변경 후에도 통과하는지 검증)는 겉보기엔 비슷하지만 사는 곳이 다르다.

| | 퓨샷 예시 | 회귀 테스트셋 |
|---|---|---|
| 사는 곳 | 프롬프트 안 | 테스트 파일 |
| 목적 | 모델 행동 유도 | 변경 후 안전 확인 |
| 다른 케이스에 미치는 영향 | 있음 | 없음 |
| 누적 | 프롬프트 길이 한계 | 사실상 무제한 |

회의에서 지적된 케이스가 나오면 내가 지금 하는 순서는 이렇다. 먼저 원인을 본다. 프롬프트 지시가 모호했나, 후보 생성 쪽이 이상한 후보를 넣어 준 건가, 모델이 맥락을 못 읽은 건가. 그다음 그 케이스를 테스트셋에 등록한다. 프롬프트를 고쳤을 때 이 줄이 통과하는지, 그리고 **기존 케이스가 안 깨지는지**를 확인하는 용도로만.

이렇게 하면 케이스가 쌓일수록 안전망이 두꺼워진다. 퓨샷을 늘리는 방식은 정확히 반대다. 케이스가 쌓일수록 프롬프트가 길어지고, 모델의 행동은 예측하기 어려워진다.

## LLM의 결정 공간을 좁힌다

이 이야기의 진짜 교훈은 프롬프트 기교가 아니라 **LLM에게 얼마나 큰 결정권을 주느냐**였다. 처음에 나는 이렇게 짰다.

```
프롬프트: "이 질의에서 교육과정 키워드를 뽑아라"
LLM:      keywords=["분수", "분모", "분자"]
```

한 방에 확정한다. 시원해 보이지만, 모델이 헛발질하면 그게 곧 시스템의 답이 된다.

지금은 이렇게 나눈다.

```
1) 규칙 기반으로 후보 목록 생성
   → ["분수", "비율", "도형의 넓이"]

2) LLM은 후보 중에서 고르거나, 모호하면 플래그를 든다
   → keywords=["분수"]
     또는
   → needs_clarification=true,
     reason="전체-부분 관계는 단원 맥락 필요"
```

이 구조가 왜 실제로 먹히는지는 우리 쪽 추천 엔진의 사전 매핑을 보면 알기 쉽다. 직무·세부직무·키워드가 데이터로 딱딱하게 박혀 있다.

```python
JOBS_16 = [
    '기획·전략', '경영·사무', '마케팅·홍보·광고', '영업·판매',
    '무역·물류·유통', '회계·세무·재무', '금융·보험', '인사·HRD',
    'IT·개발·데이터', '디자인·미디어', '고객상담·서비스',
    '생산·제조·품질', '연구·R&D·설계', '의료·보건·복지',
    '건설·건축·시설', '교육·강사',
]

SUB_BY_JOB = {
    'IT·개발·데이터': [
        '백엔드·웹 개발자',
        '프론트엔드·모바일 개발자',
        'AI·머신러닝 엔지니어',
        '데이터 분석가·엔지니어',
    ],
    # ...
}

SUB_TO_KEYWORDS = {
    'AI·머신러닝 엔지니어': ['AI', '데이터', '알고리즘'],
    '데이터 분석가·엔지니어': ['데이터', '통계'],
    '백엔드·웹 개발자':     ['웹개발', '프로그래밍'],
    '노무사':               ['노동법', '근로계약', '취업규칙'],
    # ...
}
```

이 테이블이 왜 중요한가. 사용자의 직무가 정해지는 순간 후보 키워드 집합이 **자동으로 좁혀진다**. "AI·머신러닝 엔지니어"라면 `['AI', '데이터', '알고리즘']`이 1차 후보다. LLM은 이 좁혀진 세계 안에서 골라내거나, "이 질의는 이 후보로 해석할 근거가 부족하다"고 신호만 올리면 된다. 자유 서술로 아무 단어나 뱉을 공간을 처음부터 주지 않는 것이다.

NCS 코드 매핑도 같은 취지다.

```python
JOB_TO_NCS = {
    '기획·전략':       ['02', '01'],
    'IT·개발·데이터':   ['20'],
    '금융·보험':       ['03'],
    '생산·제조·품질':  ['15', '16', '17', '19'],
    # ...
}
```

직무 하나에 붙는 NCS 대분류가 정해져 있으니, 추천 후보를 만들 때 애초에 다른 대분류의 콘텐츠는 후보 풀에서 빠진다. 그럼 회의에서 "이건 왜 뜬 거죠?" 하는 질문이 나올 확률도 같이 줄어든다.

## 결정권을 좁힌 다음에 오는 것

결정권을 줄이면 다음이 편해진다. 실제 서비스 코드 쪽은 캐시된 풀을 기반으로 후보를 만든다.

```python
@lru_cache(maxsize=config.POOL_CACHE_SIZE)
def _company_pool(tenant_id: str) -> dict:
    return load_company_pool(tenant_id)


@lru_cache(maxsize=config.POOL_CACHE_SIZE)
def _inst_pool(tenant_id: str) -> dict:
    return {
        cid: c
        for cid, c in _company_pool(tenant_id).items()
        if c.get('content_type') == 'INSTITUTION' and c.get('has_meta')
    }


def _info_score(c: dict) -> int:
    return (
        (2 if c.get('keyword_tags') else 0)
        + (1 if c.get('ncs_code') else 0)
        + (1 if c.get('title') else 0)
    )
```

`_info_score`는 별거 아닌 것 같지만, "메타가 얼마나 채워졌는가"를 숫자로 만든 함수다. 같은 UUID를 가진 콘텐츠가 여러 벌 있을 때 **가장 정보가 잘 채워진 놈**을 대표로 골라 준다.

```python
@lru_cache(maxsize=config.POOL_CACHE_SIZE)
def _uuid_map(tenant_id: str) -> dict:
    pool = _company_pool(tenant_id)
    m: dict[str, str] = {}
    for cid, c in pool.items():
        u = c.get('content_uuid')
        if not u:
            continue
        if u not in m or _info_score(c) > _info_score(pool[m[u]]):
            m[u] = cid
    return m
```

여기서 하고 싶었던 얘기는, LLM에 넘기는 후보의 품질을 **결정론적 코드가 먼저 손질**해 준다는 것이다. LLM이 뒤에서 "분수인지 비율인지 모르겠으면 needs_clarification 올려"라고 판단할 때, 그 판단이 향하는 후보는 이미 규칙으로 정돈된 상태다. 프롬프트에 예시를 하나 더 박아서 뭘 유도하는 것과는 결이 완전히 다르다.

## 아직 남아 있는 것

이렇게 정리해 놓고 나서도 회의는 계속 열린다. 지난주에는 `needs_clarification=true`가 너무 자주 뜨는 카테고리가 있었다. 규칙 기반 후보가 너무 좁게 잡혀서 LLM이 고를 게 없는 케이스였는지, 아니면 원래 그 카테고리 질의가 정말 모호한 건지 아직 안 갈라 봤다. 후자라면 UI에서 사용자에게 되묻는 흐름을 붙여야 하는데, 그건 프롬프트 문제가 아니라 제품 결정이라 다음 주로 미뤄 뒀다.

한 가지는 확실해졌다. 회의에서 케이스가 나오면 이제 프롬프트를 먼저 열지 않는다. 테스트 파일을 먼저 연다.
