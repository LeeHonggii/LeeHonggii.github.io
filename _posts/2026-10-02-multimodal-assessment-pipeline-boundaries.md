학습 활동 기록을 AI 피드백으로 바꾸는 파이프라인을 뜯어보다가, 처음엔 사소해 보이던 버그 하나에서 이야기가 시작됐다. 학생이 쓴 필기를 지웠는데 재생된 장면에는 그대로 남아 있었다.

이 글은 그 버그에서 출발해 "이 시스템에서 어디까지가 코드의 일이고, 어디부터가 LLM의 일인가"를 정리한 학습 노트다. 영상 기반 분석 얘기는 맨 끝에 나온다. 거기는 아직 구상 단계다.

## 지운 필기가 안 지워져 있었다

학생의 풀이 과정은 이벤트 이력(historyStack)으로 저장된다. 필기, 지우기, 도형 꺼내기, 이동, 삭제, 되돌리기가 순서대로 쌓인다. 피드백의 근거로 "최종 답"만 넘기면 중간 풀이와 지운 필기가 사라진다. 그래서 이력을 장면(frame) 단위로 재생해서 넘기는 코드가 있다. 아래가 이벤트 하나를 장면 상태에 적용하는 함수다. 식별자는 일반화했고 로직은 그대로다.

```python
@staticmethod
def apply(scene, pens, kind, before, after):
    bl = before if isinstance(before, list) else []
    al = after if isinstance(after, list) else []
    if kind == "pen":
        pens.extend(al)
        return "필기"
    if kind == "erase":
        gone = {p.get("id") for p in al + bl}
        pens[:] = [p for p in pens if p.get("id") not in gone]
        return "지움"
    if kind == "delete":
        for e in bl:
            scene.pop(e.get("id"), None)
        return "삭제"
    for e in al:
        scene[e.get("id")] = e
    return "꺼냄" if kind == "create" else "이동"
```

수정 전 코드와의 diff는 이 글에 싣지 않는다. 지금 저장소에 있는 상태만 근거로 쓴다. 현재 `erase` 분기는 `before`와 `after` 양쪽 목록에서 id를 모아 한 번에 제거한다. `pen`에서 "지움"으로 가는 경로가 빠져 있던 것이 하나, 객체 비교를 id가 아닌 다른 기준으로 하던 것이 다른 하나였다. 이 두 가지가 내가 찾아 고친 문제다.

`scene`을 `{id: element}` 딕셔너리로 둔 것도 같은 맥락이다. 객체 자체를 비교하면 이동 후의 같은 도형이 다른 객체가 된다. 그래서 "무엇이 같은 도형인가"의 기준을 id 하나로 고정했다. 이동은 같은 id를 덮어쓰고, 삭제는 그 id를 뺀다.

## 되돌리기는 "직전 장면 복원"으로 읽는다

이력 형식이 두 가지다. 오래된 legacy 형식은 이벤트가 전부 남아 있고, hv3 형식은 최종 장면만 믿을 수 있다. 재생 클래스는 이 둘을 갈라서 처리한다.

```python
def build_frames(self):
    self.frames, self.undone = [], 0
    if not self.legacy or not self.items:
        self.frames = [{"step": 0, "t": 0, "label": "최종 장면", "valid": True,
                        "elements": self.state.get("elements") or [],
                        "pens": self.state.get("penElements") or []}]
        self.replayable = False
        return self.frames
    self.replayable = True
    # ...
```

재생할 수 없는 형식이면 거짓으로 재생하지 않고 `replayable = False`와 최종 장면 1장으로 내려간다. 다운스트림이 "과정이 있다"고 오해하면 안 되기 때문이다. 과정이 없는 데이터로 과정을 서술하는 쪽이 LLM에게는 더 위험하다.

legacy 쪽에서 되돌리기는 이렇게 처리한다.

```python
elif x.get("subType") == "undo":
    scene, pens = snapshots[-2] if len(snapshots) >= 2 else (scene, pens)
    scene, pens = dict(scene), list(pens)
    if self.frames:
        self.frames[-1]["valid"] = False
        self.undone += 1
    label = "되돌리기"
```

되돌려진 장면을 지우지 않고 `valid=False`로 표시해 둔다. 학생이 무언가를 그렸다가 취소했다는 사실 자체가 풀이의 일부이기 때문이다. `undone` 횟수가 따로 쌓이는 것도 같은 이유다.

여기에 아직 확인하지 못한 게 있다. 코드를 읽은 내 해석으로는 `snapshots`가 이벤트를 처리하기 직전에 쌓인다. 되돌리기가 두 번 연속으로 오면 두 번째 되돌리기는 첫 번째 되돌리기 직전 상태를 복원한다. 한 단계 더 거슬러 올라가지 않는다. 실행해서 확인한 것이 아니고, 연속 되돌리기가 실제 이력에 얼마나 나오는지도 재보지 않았다. 이건 아래 "남은 것"에 적어 둔다.

## 이 재생 결과가 어디로 들어가나

장면 재생은 파이프라인 전체의 한 칸일 뿐이다. 전체를 단계로 나누면 이렇다. 특히 비전 전처리와 리포트 생성은 서로 다른 실행이다.

```text
[비전 전처리]
  문제 정의: 초기 화면 + 모범답안 화면 + 추출한 화면 텍스트
  학생 판정: 마지막 화면을 이미 정의된 정답과 대조

[리포트 생성]
  케이스 정규화 → 활동 문장화 → 프롬프트 조립(promptPiece)
  → 평가(assess) → 코드값 반영(applyCodeFacts) → 독자별 서술(render-both) → 저장
```

문제 정의와 학생 판정에서 가장 신경 쓴 건 입력 이미지의 역할 표기다. 문제 이미지와 정답 이미지를 한 프롬프트에 넣으면 모델이 둘을 섞는다. 그래서 "이 이미지는 문제 정의용 초기 화면, 이 이미지는 정답 화면"이라고 역할을 명시한다. 학생 판정은 새로 정답을 추론하지 않는다. 마지막 화면을 이미 정의된 정답과 대조만 한다.

문제 유형은 네 가지(value / placement / rule / action)로 나눠 둔다. 정답이 어디서 나오는지는 우선순위가 있다.

```text
코드 계산 → 정답 화면 → 모델 추론
```

계산할 수 있으면 코드가 계산하고, 안 되면 정답 화면에서 읽는다. 모델 추론은 마지막 수단이다. 이 순서가 틀리면 LLM이 계산 가능한 값까지 "그럴듯하게" 만들어 낸다.

## 선개념·오개념은 어디서 오나

한동안 착각하고 있었다. 평가에 쓰는 선개념(미리 알아야 할 개념)과 오개념(흔한 잘못된 이해)이 교육과정 조회 결과에서 올 거라고 생각했다. 실제로 따라가 보니 아니었다. 교사가 입력한 값이거나 모델이 추론한 값이다.

그러면 기준의 출처와 학생에 대한 판정 근거를 따로 설명해야 한다. 리포트에 "이 학생은 이 오개념이 있다"고 쓸 때, 그 오개념 목록이 어디서 왔는지(교사 입력인지 모델 추론인지)와 이 학생이 그걸 보였다는 근거(어떤 장면, 어떤 지운 필기)는 서로 다른 증거다. 지금은 이 둘을 한 문장으로 뭉뚱그리지 않으려고 한다.

## 코드가 정하는 것, LLM이 읽는 것

리포트 단계에서 정한 선은 단순하다. 코드가 계산한 필드는 코드값이 이긴다(`applyCodeFacts`). LLM이 해석하는 필드는 평가 단계에서만 정한다. 마지막 서술 단계(`render-both`, 독자별 문장 생성)에는 재판정을 맡기지 않는다.

서술 단계가 판정을 바꾸면 같은 학생의 평가가 독자 버전마다 달라진다. 그래서 서술은 이미 정해진 판정을 문장으로 옮기기만 한다.

별개의 수정 과정에서 캐시 문제도 하나 잡았다. 캐시 키가 기록만 반영하고 프롬프트는 반영하지 않았다. 지시문을 고쳐도 같은 기록이면 옛 판정이 그대로 재사용됐다. 그래서 캐시 키에 프롬프트를 포함했다. 이제 지시문이 바뀌면 재판정으로 이어진다. 재판정이 비용이라는 건 알지만, 바뀐 지시문이 결과에 반영되지 않는 쪽이 더 나쁘다고 판단했다. 비용 차이는 재보지 않았다.

## 활동 유형별로 뭘 볼 수 있나

현재 입력 데이터가 활동 유형마다 무엇을 관찰할 수 있는지도 검토했다. 이력이 이벤트로 남는 활동은 위의 재생으로 과정을 볼 수 있다. 최종 장면만 남는 활동은 과정을 볼 수 없다. 이걸 숨기지 않고 `replayable`로 드러내는 것이 앞으로의 방침이다.

## 남은 것

- 연속 되돌리기 처리. 위에서 읽은 대로라면 두 번째 되돌리기가 한 단계 덜 되돌릴 수 있다. 연속 되돌리기가 들어 있는 실제 이력으로 재생해서 확인해야 한다. 아직 안 했다.
- 영상 기반 분석. 필기 순서와 멈춤 같은 신호는 영상에서 더 풍부하게 나올 수 있지만, 지금은 테스트 구상 단계다. 구현도 측정도 없다. 이게 이력 이벤트보다 얼마나 더 알려 주는지는 해 보기 전에는 모른다.
