작업 디렉터리에 Markdown 파일이 하나 있었다. 16MB. `wc -l` 로 보니 10만 줄이 넘었다. 회의록, 스펙, 의사결정 로그가 수개월치 쌓인 것이었다.

이 파일을 검색 가능하게 만들고 싶었다. 문제는 컨텍스트 윈도우다. 어떤 로컬 모델이든 이 파일을 통째로 받아먹을 수 없다. 클라우드 API에 올리는 것도 아니었다 — 내부 문서니까.

그래서 방향을 바꿨다. 먹이는 대신, 쪼개고 합치기로.

---

## 어디서 자를 것인가

Markdown 파일을 청크로 나눌 때 가장 쉬운 선택은 고정 토큰 수다. 1,000토큰마다 자르면 된다. 근데 이게 문제다. 문맥의 경계를 무시하고 자르면 요약 결과가 이상해진다. "이 섹션은 이전 섹션의 결정을 반박합니다"라는 문장이 앞 청크에도 뒤 청크에도 온전히 속하지 않는 상태가 된다.

헤더 기준으로 자르기로 했다. `## `, `### ` 가 나오는 줄에서 경계를 만든다. Markdown이 원래 의미 단위를 헤더로 표시하게 되어 있으니, 문서 작성자가 이미 경계를 그어둔 셈이다.

헤더 단위 청크가 너무 길면? 재귀적으로 더 쪼갠다. 너무 짧으면? 다음 청크와 합친다. 이 두 조건을 반복하면 대부분의 경우 모델이 한 번에 읽기 적당한 크기로 수렴했다.

---

## Map → Reduce

각 청크를 로컬 모델(Ollama + Gemma)에게 넘겨서 요약을 받는다. 이 단계가 Map이다. 청크마다 모델을 한 번씩 호출한다.

Map 결과물을 이어 붙이면 원본보다 훨씬 짧은 텍스트가 된다. 이걸 다시 모델에 넘겨서 최종 요약 하나를 만든다. 이 단계가 Reduce다.

```
원본 16MB
  └── 헤더 기준 청크 분할
        ├── 청크 1 → 요약 1
        ├── 청크 2 → 요약 2
        ├── ...
        └── 청크 N → 요약 N
              └── 요약 1~N 합산 → 마스터 요약
```

Map-Reduce (분산 처리 패러다임)라는 이름이 붙은 건 원래 대규모 분산 시스템에서 쓰는 말인데, 여기서는 단일 머신에서 순차 처리지만 구조는 동일하다. 큰 문제를 병렬 가능한 작은 문제들로 쪼갠 뒤 결과를 합친다.

마스터 요약은 원본 파일과 같은 이름의 `.md`로 저장한다. 크기는 원본의 1~2% 수준. 이게 인덱싱에 걸리고 검색에 노출된다. 원본 파일은 `.txt`로 확장자를 바꿔서 검색 인덱서가 건너뛰게 한다.

## mtime 을 믿지 마라

처음에는 파일 수정 시각(mtime)으로 재처리 여부를 판단했다. 파일이 새로 수정된 경우에만 요약을 다시 만드는 방식이다.

이게 두 가지 이유로 깨진다. 첫째, `rsync` 나 백업 도구가 파일을 건드리면 mtime이 바뀐다. 내용은 동일한데 요약을 다시 돌린다. 둘째, mtime이 바뀌지 않아도 내용이 바뀌는 경우가 있다 — 사실 드물지만 발생한다.

SHA-256 해시로 바꿨다. 파일 전체를 읽어서 해시값을 구하고, 이전 실행 때의 해시와 비교한다. 값이 같으면 건너뛴다. 내용이 단 한 바이트라도 달라지면 다시 처리한다.

```python
original_hash = sha256(file_contents).hexdigest()
```

해시값은 요약 파일의 frontmatter에 같이 저장한다. 다음 실행 때 그걸 읽어서 현재 파일 해시와 비교하면 된다. 별도 DB 없이 멱등성(idempotency — 같은 입력에 같은 출력, 중복 실행해도 결과가 달라지지 않는 성질)을 유지할 수 있다.

CLI 인터페이스는 단순하게:

```bash
python3 gemma_processor.py summarize_large <file>
```

파일 하나를 받아서 청크 분할 → Map → Reduce → 저장까지 한 번에 처리한다. 디렉터리 전체를 순회하는 배치 모드도 있는데, 각 파일에 대해 이 파이프라인을 그냥 반복 호출한다.

## 로컬 모델이 만들어낸 요약의 품질

좋다고는 못 하겠다.

의사결정의 맥락을 날린다. "A안 대신 B안을 선택했다"는 요약에 들어오는데 왜 B를 골랐는지는 종종 빠진다. 맥락 보존보다 압축에 치우친 결과다.

그리고 긴 회의록을 청크로 자르면 같은 주제가 여러 청크에 걸쳐 반복해서 나오는 경우가 있다. 이걸 요약하면 "A에 대해 논의했다"가 마스터 요약에 여러 번 등장한다. Reduce 단계에서 중복을 걸러내는 프롬프트를 넣어도 완전하진 않다.

목적을 좁게 잡으면 쓸 만하다. "이 파일에 뭐가 들어있었는지"를 빠르게 파악하거나 전문 검색이 걸릴 키워드를 남기는 용도라면 충분하다. 의사결정의 전말을 재구성하려면 원본을 봐야 한다 — 그건 당연한 일이기도 하다.

---

Reduce 단계에서 여러 청크 요약을 합산할 때 순서를 섞으면 마스터 요약이 달라진다는 걸 우연히 발견했다. 프롬프트에 시간 순서 힌트를 주면 나아지는 것 같은데, 아직 체계적으로 재보지 않았다.
