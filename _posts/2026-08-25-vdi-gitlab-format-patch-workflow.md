망 분리 환경에서 개발하면 커밋을 직접 push할 수 없다. 외부망에서 작성한 코드를 VDI(Virtual Desktop Infrastructure — 내부망 전용 가상 데스크탑) 안의 GitLab으로 옮기려면 파일을 어떤 방식으로든 건네야 한다.

처음엔 단순하게 생각했다. 파일 복사해서 붙여넣으면 되는 거 아닌가. 그러다가 커밋 히스토리가 사라지는 문제를 마주쳤고, `git format-patch`를 알게 됐다.

---

## format-patch가 하는 일

`git format-patch`는 커밋을 이메일 형식의 `.patch` 파일로 만든다. 커밋 메시지, 작성자, 타임스탬프, diff가 전부 담긴다. 받는 쪽에서 `git am`으로 적용하면 원래 커밋 단위와 메타데이터가 그대로 재현된다.

```bash
git format-patch <base>..<end> --stdout > changes.patch
```

`<base>`는 옮기고 싶은 커밋 직전, `<end>`는 마지막 커밋. `--stdout`으로 하나의 파일에 몰아넣는 게 편하다. 커밋이 여러 개면 순서대로 이어진다.

이 파일을 VDI 안으로 옮기는 방법은 환경마다 다르다. 공유 폴더, 웹 업로드, USB 정책 등. 그건 각자 상황에 따라. 중요한 건 **파일이 텍스트**라는 것 — 바이너리가 아니라 사람이 읽을 수 있고, 필요하면 손으로 고칠 수도 있다.

---

## VDI에서 잘못된 브랜치에 적용했을 때

패치를 받아서 VDI 쪽 저장소에서 이렇게 적용했다.

```bash
git am changes.patch
```

적용은 됐다. 그런데 브랜치를 확인하니 `main`에 적용돼 있었다. `develop`에 넣어야 했는데.

`git am`은 현재 체크아웃된 브랜치에 그냥 커밋을 만든다. 브랜치 확인을 안 한 게 실수였다.

```bash
git cherry-pick main
```

`develop`으로 이동한 뒤 방금 `main`에 생긴 커밋을 cherry-pick(특정 커밋만 다른 브랜치로 가져오는 명령)으로 옮겼다. `main`에 생긴 커밋은 이후 reset으로 제거했다.

교훈이라기보다는 그냥 절차 문제다. `git am` 전에 브랜치를 먼저 확인하면 된다. 아니면 명시적으로 먼저 `git checkout develop`을 치고 적용하거나.

---

## push할 때 500이 떴다

`develop`으로 push를 날렸다.

```bash
git push origin develop
```

pre-receive hook이 500을 반환했다. pre-receive hook은 GitLab 서버가 push를 받을 때 실행하는 서버사이드 스크립트다. 여기서 실패하면 push가 거절된다.

처음엔 패치 적용 과정에서 커밋이 잘못됐나 싶었다. 커밋 로그를 다시 보고, 파일 상태도 확인하고. 이상 없었다.

결국 재시도했더니 됐다.

이게 가장 모호하게 남은 부분이다. 내 커밋 문제가 아니라 GitLab 서버 내부 오류였을 가능성이 높다. 500은 서버 에러 코드다. 재현하기도 어렵고, GitLab 서버 로그를 직접 볼 수 있는 권한도 없었다. 비슷한 상황이 또 생기면 그때는 인프라 담당자에게 서버 로그를 요청해볼 생각이다.

---

이 워크플로 자체가 근본 해결책은 아니다. 망 분리가 완화되거나 내부망에서 바로 개발할 수 있으면 필요 없어지는 과정이다. 지금은 그게 안 되니까 하는 것이고, 당분간은 이 방식을 쓸 것 같다.
