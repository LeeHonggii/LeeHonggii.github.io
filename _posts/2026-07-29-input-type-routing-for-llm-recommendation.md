## 프롬프트를 계속 고치고 있었다

추천 결과가 이상하면 프롬프트를 열어봤다. 예시를 하나 더 붙이고, few-shot을 늘리고, temperature를 낮추고. 그래도 어떤 입력에서는 계속 엉뚱한 걸 물어왔다. "3학년 곱셈"으로 넣으면 잘 되는데 "분수 이해가 어려운 아이"라고 넣으면 갑자기 6학년 자료를 추천한다든가.

한참 뒤에야 알아차렸다. 이건 프롬프트 문제가 아니었다. 두 입력은 **아예 종류가 다른 입력**이었고, 나는 그걸 같은 노드에 밀어 넣고 있었다.

## 입력이 하나로 안 보인다

들어오는 걸 며칠 로그로 뜯어보니 세 덩어리로 갈렸다.

- **A**: 학년·차시 같은 구조 정보만 있음 — "5학년 2학기 3단원"
- **B**: 키워드만 있음 — "이차방정식 풀이 연습"
- **C**: 둘 다 섞임 — "중2 일차함수 그래프 그리기"

세 유형에서 가장 정확한 처리 방식이 서로 다르다. A는 단원 코드로 역인덱스(inverted index, 키로 항목을 바로 꺼내는 자료구조)를 치는 게 가장 정확하다 — LLM한테 굳이 "키워드를 뽑아줘"라고 시킬 필요가 없다. 오히려 시키면 LLM이 없는 키워드를 만들어낸다. B는 반대다. 자유 텍스트를 정규화한 뒤 유사도 검색이 낫다. C는 A로 후보를 좁히고 B로 재정렬한다.

같은 파이프라인에 다 태우니까, A 입력에서 LLM이 억지로 키워드를 짜내다가 필터 조건을 오염시켰다. 프롬프트가 아무리 좋아도 이건 안 풀리는 문제다.

## 노드 하나만 끼워 넣었다

LangGraph(LLM 워크플로를 노드·엣지로 짜는 오케스트레이터)로 돌리고 있어서 파이프라인 중간에 판별기 하나만 넣으면 됐다.

전:

```
validate → extract_keywords → filter → parallel_recommend → merge
```

후:

```
validate → extract_keywords → resolve_input_type → filter → parallel_recommend → merge
```

`resolve_input_type` 은 LLM을 안 쓴다. 이전 노드가 남긴 state를 보고 룰로 판정만 한다.

```python
def resolve_input_type(state: RecommendState) -> RecommendState:
    has_grade = state.get("grade") is not None
    has_keywords = bool(state.get("keywords"))

    if has_grade and not has_keywords:
        input_type = "A"
    elif has_keywords and not has_grade:
        input_type = "B"
    else:
        input_type = "C"

    return {**state, "input_type": input_type}
```

여기서 LLM으로 "이게 A야 B야?"를 물어보고 싶은 유혹이 있었는데, 참았다. 같은 입력을 두 번 넣으면 다른 답이 나올 수 있는 판정을 파이프라인 앞단에 두고 싶지 않았다. 재현이 안 되면 회귀 테스트도 못 짠다. 이건 룰이 할 일이다.

`filter` 노드는 `input_type` 값을 보고 조회 경로를 갈랐다. 뒤에 붙는 두 개의 추천 모델(템플릿·도구)에도 같은 값이 그대로 넘어가서, 두 모델이 **같은 컨텍스트로 판단**하게 됐다. 이게 생각보다 크게 작용했다 — 이전에는 두 모델이 다른 힌트를 보고 서로 다른 답을 내는 경우가 있었다.

## 진짜 문제는 책임이 섞여 있었던 것

되짚어보니 원래 구조의 문제는 이거였다. `extract_keywords` 가 자기 일(자유 텍스트에서 키워드 뽑기)만 하지 않고, 학년·차시 같은 구조 정보까지 추출하려고 했다. LLM이 잘하는 일과 룰이 잘하는 일이 한 노드에 뭉쳐 있으니, LLM이 확실하지 않을 때 다음 노드가 흔들렸다.

책임을 쪼개 다시 정리했다.

- `extract_keywords` — LLM이 잘함: 자유 텍스트에서 의미 키워드
- `resolve_input_type` — 룰이 잘함: 구조 정보 유무 판별
- `filter` — 둘 결과를 받아 경로 선택

노드 이름만 바뀐 게 아니라, "이건 누구 일인가"를 명시적으로 갈랐다.

## 아직 안 풀린 것

정확도가 눈에 띄게 좋아졌다고 쓰고 싶은데, 정량 지표를 아직 안 붙였다. 오프라인 골든셋을 만들어 A/B/C 각각의 top-k 히트율을 재봐야 하는데, 골든셋 라벨링이 남아 있다. 감으로는 A 유형에서 오답이 확 줄었고 B는 비슷하다.

그리고 C 유형이 애매하다. 지금은 A→B 순서로 후보를 좁히는데, 사용자가 학년을 잘못 적었을 때 B의 신호를 무시하는 실패 케이스가 있다. 학년이 "약한 힌트"인지 "강한 제약"인지를 상황에 따라 다르게 봐야 할 것 같은데, 여기까지 오면 다시 LLM한테 판단을 넘겨야 할지도 모르겠다. 그러면 처음에 피하려던 재현성 문제가 다시 돌아온다. 아직 답을 못 냈다.
