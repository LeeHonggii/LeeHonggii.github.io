기존 멀티모달 평가 코드를 읽으면서 정리한 학습 노트다. 새로 만든 건 아니다. 이미지와 활동 이력이 들어와서 평가와 리포트가 나가기까지 실제로 어떤 순서로 도는지 따라가 봤다. 가장 먼저 눈에 들어온 건 **입력 이미지마다 역할이 다르다**는 점이었다.

## 같은 "화면"이 세 종류다

처음엔 "화면 이미지를 모델에 주고 채점시킨다" 정도로 이해했다. 코드를 따라가 보니 화면은 세 가지였다.

- **초기 문제 화면**: 학생이 손대기 전 상태. 문제가 무엇인지 정의하는 데 쓴다.
- **정답 화면**: 교사가 만들어 둔 예시 화면. 문제를 정의하는 자료가 아니고, 정답을 읽어내는 자료다.
- **학생 최종 화면**: 학생이 끝낸 상태. 이미 정의된 정답과 대조하는 대상이다.

이 셋을 한 프롬프트에 같이 넣으면 모델은 어느 이미지가 "문제"이고 어느 쪽이 "답"인지 스스로 추측해야 한다. 학생 화면에 답이 이미 올라가 있으면 그걸 문제의 일부로 읽을 수도 있다. 그래서 단계를 둘로 나눈다.

**1단계**는 초기 문제 화면과 그 화면에서 추출한 텍스트로 문제를 정의한다. 결과는 개념을 선행(pre)·핵심(core)·후행(post)으로 나눈 구조와 정답이다. 정답을 읽을 때만 별도 정답 화면을 보조 자료로 쓴다.

**2단계**는 학생 최종 화면을 1단계가 만든 정답과 대조한다. 출력은 이 정도 모양이다.

```text
concepts: { pre: [...], core: [...], post: [...] }
answerSource: "code:optimum" | "vision:truth" | ...
{ verdict: 정답|부분|오답, basis, confidence }
```

2단계에서 놓치기 쉬운 한계가 하나 있다. **최종 화면은 결과일 뿐이라 풀이 과정을 관찰할 수 없다.** 어떻게 풀었는지는 이 화면에서 나오지 않는다. 과정은 활동 이력 같은 다른 입력이 있어야 보인다. 그래서 2단계의 `basis`는 "최종 답이 조건에 맞는가"까지만 주장해야 한다.

## 정답의 출처에 우선순위를 둔다

정답을 누가 정하느냐가 이 구조의 중심이었다. 순서는 이랬다.

1. 계산할 수 있는 문제면 **코드 계산값**(`code:optimum`)
2. 안 되면 **정답 화면에서 읽은 값**(`vision:truth`)
3. 그것도 없으면 모델 추론

정답 화면이 비어 있는 경우도 처리해야 했다. 교사가 화면을 만들어 두지 않았거나 아무것도 배치하지 않은 경우다. 이때 빈 화면을 "정답이 없다"로 읽지 않고 다음 순위로 넘기는 분기가 필요했다. `answerSource`를 결과에 남기는 이유도 여기에 있다. 나중에 오채점이 나오면 정답이 코드에서 왔는지 이미지에서 왔는지부터 갈라서 볼 수 있다.

같은 저장소의 실험용 코드에 "코드가 정답 집합을 전수 계산"하는 부분이 있어서 옮겨 둔다. 앞의 2단계 파이프라인 코드가 아니라 별도 검증 실험의 코드다. 정답을 코드가 우선한다는 생각이 어떻게 생기는지 보여 주는 예로 읽었다. 식별자는 일반화했다.

```python
class ProblemInput:
    """문제(페이지)마다 AI 에 넣을 지시문·모범답안 식과, 코드가 전수 계산한 정답 집합을 만든다."""

    def __init__(self, page):
        self.page = page
        self.spec = PAGE_SPEC[page]
        self.get_instruction()
        self.get_model_expr()
        self.build_truth()

    def build_truth(self):
        self.truth = {}
        if self.spec["kind"] != "구성":
            op = self.spec["op"]
            self.truth["계산"] = {f"{a}{op}{b}={a + b if op == '+' else a - b}" for a, b in self.spec["items"]}
            return self.truth
        prob = PlaceValueProblem(self.spec["digits"], self.spec["shape"])
        for goal in self.spec["goals"]:
            value, best = prob.best(goal)
            self.truth[goal] = {f"{s['a']}{prob.op}{s['b']}" for s in best}
        return self.truth
```

`build_truth`는 정답을 하나가 아니라 **집합**으로 만든다. "가장 큰 합을 만들어라" 같은 구성형 문제는 최적해가 여러 개일 수 있다. 예컨대 숫자 5, 6, 7, 8로 만드는 두 자리 수 합은 `86+75`와 `85+76`이 둘 다 최댓값이다. 모범답안 화면의 식은 그중 하나의 예시일 뿐이다. 모범답안과 식이 다르다는 이유로 학생을 틀렸다고 하면 안 된다. 이 코드는 모든 배치를 코드로 세어서 그 위험을 막는다.

LLM에게 "더 큰 배치가 없는지 따져 봐라"고 시키는 방법도 같은 저장소에서 여러 조건으로 시험하고 있었다. 다른 배치를 직접 만들어 비교하게 하는 규칙, 정답을 먼저 구하는 2단계 호출, 풀이 예시 하나 추가 같은 것들이다. 각 조건의 결과는 내가 갖고 있지 않아서 어느 쪽이 나았는지는 말할 수 없다. 다만 "비교가 필요한 정답은 모델에게 맡기지 않고 코드로 계산하는 쪽이 낫다"는 방향은 코드 구조에서 읽힌다.

## 판정 프롬프트가 막으려는 것

판정 쪽 시스템 프롬프트에서 눈에 띈 규칙은 두 개다.

```python
JUDGE_SYSTEM = """너는 초등 수학 활동의 학생 기록을 읽고 판정하는 교사 보조다.
- 판정은 **최종 답**을 지시문의 조건으로 본다. 모범답안과 식이 달라도 조건을 만족하면 정답이다.
- 정답 = 최종 답이 조건을 모두 만족 / 부분 정답 = 답이 여러 개인 문제에서 최종 답 일부만 맞음 / 오답 = 최종 답이 틀림.
- 확인_필요 = 최종 답이 틀린 부분이 있는데, 과정 기록에 그 부분의 정답을 만든 적이 있으면 true. 이때 과정 칸에 정답을 찾았다가 수정했다고 쓴다. 과정 중 정답은 판정을 올리지 않는다.
- 모범답안과 다르지만 정답이면 「틀렸다」고 쓰지 말고 「모범답안과 풀이(식)가 다르다」고만 쓴다.
JSON 하나로만 답한다:
{"판정":"정답|부분 정답|오답","확인_필요":false,"모범답안과":"같음|정답이지만 다름|틀림","과정":"...","근거":"...","선생님께":"..."}"""
```

두 번째 항목이 특히 좋았다. 과정 중에 정답을 만들었다가 지운 학생을 어떻게 할 것인가. 판정을 올려 주면 최종 결과를 채점한다는 원칙이 깨진다. 그렇다고 아무 표시도 안 하면 교사가 중요한 신호를 놓친다. 이 프롬프트는 **판정은 그대로 두고 `확인_필요` 플래그만 켜는** 방식으로 둘을 분리했다. 채점과 관찰을 한 필드에 섞지 않는다는 점이 1·2단계 분리와 같은 생각이라고 느꼈다.

판정 근거를 제한하는 장치이기도 하다. 모델이 쓸 수 있는 근거는 코드가 만든 사실(식, 펜 기록 등)로 한정되고, 나머지는 서술로만 나간다.

## 캐시 단위: 문제를 어디에 묶을 것인가

1단계 결과인 문제 정의는 학생이 바뀌어도 같다. 그러면 학생마다 1단계를 다시 부를 이유가 없다. 초기 장면의 fingerprint(장면 내용을 요약한 식별값)를 키로 문제 정의를 공유하면 호출이 줄어든다.

여기에 함정이 있다. fingerprint는 "초기 장면"을 대표해야 하는데, 복원된 초기 장면에 학생 조작이 남아 있을 수 있다. 그러면 같은 문제인데도 학생 조작 때문에 fingerprint가 달라져 캐시가 갈라지거나, 반대로 한 학생의 조작이 섞인 정의가 다른 학생의 기준으로 재사용될 수 있다. 앞의 경우는 호출이 늘 뿐이지만 뒤의 경우는 채점 기준이 오염된다. 이 코드를 읽는 동안 내가 가장 오래 붙잡고 있던 부분이다. 초기 장면 복원 로직이 학생 조작을 어디까지 되돌리는지는 확인하지 못했다.

## 단계도와 실제 호출 순서는 다르다

개념도로 그리면 "1단계 → 2단계 → 리포트"가 한 줄로 이어진다. 실제로는 비전 분석과 리포트 생성이 별도 실행 경로다. 리포트 서술은 평가 결과를 받아 따로 돌린다. 코드로 계산한 사실과 LLM 추론을 분리하고, 결과 서술을 별도 단계로 두는 설계라서 그렇다. 호출 횟수나 지연을 따질 때는 단계도가 아니라 실행 순서를 기준으로 세야 한다. 나는 이 둘을 한 번 섞어 생각했다가 코드를 다시 읽고 고쳤다.

## 모델이 만든 선개념은 검증된 지식이 아니다

`concepts: { pre, core, post }`에는 한계가 있다. 선행·후행 개념은 검증된 지식 조회가 아니라 모델 추론으로 생성될 수 있다. 오개념도 마찬가지다. 그럴듯하게 쓰여 있어도 교육과정에서 확인한 것은 아니다. 그래서 전문가가 입력한 항목과 학생 관찰에서 나온 근거를 구분해서 다뤄야 한다. 같은 저장소에는 풀이 방식 기준을 모델이 쓰게 하는 프롬프트도 있었는데, 그 프롬프트에도 연구·평가 자료 발췌를 참고 자료로 따로 넣는 구조가 있었다. 모델 생성물에 외부 근거를 붙이려는 시도로 읽었다.

## 아직 남은 것

이후에 이 구조를 바탕으로 새 평가 시스템의 기획 초안을 썼다. 활동 유형별로 관찰할 수 있는 것과 없는 것을 나누고, 전문가 자문이 필요한 항목과 평가 기준 중 미확정인 부분을 정리하는 데까지만 갔다. 구현은 하지 않았고, 영상 입력 실험도 끝내지 않았다.

그래서 이 글에서 정량적으로 말할 수 있는 것은 없다. 호출이 얼마나 줄었는지, 채점 정확도가 어땠는지는 재 보지 않았다. 확인해야 할 것은 둘이다. 복원된 초기 장면에서 학생 조작이 fingerprint에 영향을 주는지, 그리고 정답 화면이 빈 경우 코드 계산값으로 내려가는 분기가 실제로 얼마나 자주 타는지.
