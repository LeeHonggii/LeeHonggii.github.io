기존 멀티모달 평가 코드를 읽다가 "이걸 풀이 영상으로 확장하면 되나?"라는 생각이 들었다. 바로 프롬프트부터 쓰고 싶었다. 그런데 코드를 다 읽고 나니 먼저 정할 것이 있었다. 모델에 뭘 넣고 뭘 한 묶음으로 볼지, 즉 실험 단위다. 이 글은 그 정리 노트다. 영상 경로는 아직 구현도 검증도 하지 않았다. 그래서 결과 대신 정해야 할 것들만 적는다.

## 기존 경로가 실제로 받는 입력

기존 코드의 실행 순서는 문제 정의, 학생 답안 판정, 루브릭 평가, 리포트 생성이다. 비전 분석과 리포트 생성은 별도 실행이라는 점도 이번에 확인했다. 그래서 단계별로 입력과 출력, 코드가 계산한 값과 LLM이 추론한 값을 나눠 시퀀스 문서로 그렸다.

이 과정에서 놓치기 쉬운 사실이 하나 나왔다. 이 경로의 입력은 화면이 아니라 **조작 이력**이다. 프레임마다 화면에 놓인 요소의 구조화된 목록이 있다. 그 위에서 코드가 사실을 먼저 계산하고, LLM은 그 사실을 해석한다. 수 모형 활동 분석 모듈이 그 예다. 먼저 프레임별로 자리×종류 개수를 센다.

```python
# 판에 담긴 모형은 판의 격자가 정본이다 — 판 사이를 옮길 때 재생된 모형 요소는 갱신되지 않는 경우가 있다
@staticmethod
def kind_counts(elements):
    n = [0] * len(PLACE)
    for e in elements:
        if is_board(e):
            for row in BaseTenTrace.grid(e):
                for k, c in enumerate(row[:len(PLACE)]):
                    n[k] += c
        elif is_block_tool(e) and not e.get("connectedBoardId") and isinstance(e.get("shapeType"), int) and 0 <= e["shapeType"] < len(PLACE):
            n[e["shapeType"]] += 1
    return n
```

판에 놓인 모형은 판의 격자 값을 믿고, 판에 붙지 않은 낱개 모형만 요소 단위로 센다. 주석에 이유가 적혀 있다. 이력을 그대로 재생하면 틀린 값이 나오는 경우가 있어서 정본을 따로 정해 둔 것이다. 입력이 구조화되어 있어도 어느 필드를 믿을지는 사람이 정해야 한다.

이렇게 센 값을 프레임끼리 빼서 학생이 한 일을 사건으로 만든다.

```python
@staticmethod
def change(d):
    for k in range(len(PLACE) - 1):
        lo, hi = d[k], d[k + 1]
        rest = [x for j, x in enumerate(d) if j not in (k, k + 1)]
        if any(rest):
            continue
        if hi > 0 and lo == -10 * hi:
            return {"kind": "합치기", "label": f"{PLACE[k]} 모형 {-lo}개 → {PLACE[k + 1]} 모형 {hi}개"}
        if hi < 0 and lo == -10 * hi:
            return {"kind": "쪼개기", "label": f"{PLACE[k + 1]} 모형 {-hi}개 → {PLACE[k]} 모형 {lo}개"}
    # ... 덜어 냄 / 더 놓음
```

한 자리에서 10개가 줄고 바로 윗자리에서 1개가 늘면 "합치기"다. 이 판정에는 LLM이 필요 없다. 다른 자리의 개수가 변했다면 합치기로 보지 않고 넘어간다. 되돌리기 프레임이나 유효하지 않은 프레임도 이벤트 계산에서 뺀다.

영상에서는 이 계산을 코드로 대신할 수 없다. 영상의 픽셀에는 "십 모형 10개가 사라졌다"는 값이 없다. 프레임을 보고 모델이 세어야 한다. 그러니 조작 이력 경로와 화면 녹화 경로는 같은 분석의 두 입력이 아니다. 얻을 수 있는 정보도, 틀릴 수 있는 지점도 다르다. 별도 실험으로 다루기로 했다.

## 개념 목록은 어디서 오는가

시퀀스 문서를 만들다가 또 하나 확인한 것이 있다. 평가에 쓰는 선개념·오개념 목록이 교육과정 데이터를 조회한 결과가 아니었다. 교사가 입력하거나 모델이 추론한 값이었다.

이 차이는 크다. 목록이 어디서 왔는지와 그 목록으로 학생을 판정한 근거는 서로 다른 문제다. 영상 실험에서도 둘을 구분해서 적어야 한다. 모델이 "이 학생은 이 오개념이 있다"고 했을 때, 그 오개념 후보가 입력으로 주어진 것인지 모델이 만들어 낸 것인지 모르면 결과를 해석할 수 없다.

## 실험 한 세트에 넣을 것

논의한 구성은 이렇다. 문항 이미지 한 장, 정답 이미지 한 장, 학생 한 명이 그 한 문항을 푼 영상 하나를 한 세트로 묶는다. 영상에서 얻은 장면은 일정 시간 간격으로 뽑거나 장면이 바뀔 때 뽑아 이미지 시퀀스로 준다.

시간 간격으로 뽑으면 구현이 단순하지만 짧은 조작이 프레임 사이로 빠질 수 있다. 장면 변화로 뽑으면 의미 있는 순간은 잡히지만, 화면 전체가 조금씩만 바뀌는 풀이에서는 기준이 흔들릴 것 같다. 전부 추측이다. 추출 전략별로 정보가 얼마나 손실되는지, 분석 품질이 어떻게 달라지는지는 아직 재보지 않았다. 수치도 없다.

## 표본 구성은 목적별로 따로 정한다

표본을 어떻게 고를지가 가장 헷갈렸다. 목적이 두 가지로 갈린다.

- 활동 유형을 고르게 포함하려는 구성. 영상 입력이 유형마다 잘 다뤄지는지 보는 용도다.
- 같은 문항에 대해 학생끼리 비교하려는 구성. 풀이 방식의 차이가 분석에 드러나는지 보는 용도다.

앞쪽은 문항이 다양해야 하고, 뒤쪽은 문항을 고정하고 학생을 늘려야 한다. 한 표본으로 둘을 다 만족시킬 수는 없다.

기존 기능에는 최소 표본 조건이 있었다. 그 조건을 이번 실험의 통계적 충분성 기준으로 가져오면 안 된다. 기존 기능의 조건은 그 기능이 돌아가기 위한 하한이지, 영상 분석 결과를 일반화할 근거가 아니다.

## 분류 이름을 다루는 법

대화에서 문제 수행 방식을 비교·분류·구성·조작·표현·설명으로 나눠 정리했다. 실험 설계에는 유용한 구분이다. 하지만 이것을 교육과정의 공식 영역 분류라고 적지는 않기로 했다. 공식 분류인지는 확인하지 않았다. 확인 없이 공식 용어처럼 쓰면 면접에서 출처를 물었을 때 답할 수 없다. 이 글에서는 "대화에서 정리한 구분"으로만 쓴다.

## 아직 정하지 못한 것

프레임 추출 기준은 시간 간격과 장면 변화 중 어느 쪽으로 먼저 돌려볼지 정하지 못했다. 한 세트를 모델에 넣었을 때 문항 이미지와 정답 이미지가 프레임 시퀀스와 함께 어떻게 쓰이는지도 모른다. 조작 이력 경로의 결과를 정답처럼 비교 기준으로 삼아도 되는지도 아직 판단하지 못했다. 이력이 있는 활동에서는 코드 계산값이 있으니 같은 학생의 영상과 이력을 짝지어 비교할 수 있겠지만, 그러려면 같은 풀이 과정에서 둘을 함께 수집해야 한다. 지금 가진 자료로 그게 가능한지부터 확인해야 한다.
