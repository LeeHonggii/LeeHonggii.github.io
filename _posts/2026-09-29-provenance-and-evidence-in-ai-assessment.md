기존 AI 평가 파이프라인의 코드를 읽다가 한 가지가 계속 걸렸다. 문제 이미지를 해석하고, 답안을 판정하고, 활동 이력을 분석해서 리포트를 만드는 흐름이다. 리포트에는 "이 학생은 이 선개념이 부족하다", "이런 오개념이 보인다"는 문장이 들어간다. 그 선개념 목록과 오개념 목록은 어디서 왔을까.

코드를 따라가 보니 교육과정 자료를 조회하는 단계는 없었다. 목록은 모델이 문제를 보고 만들어낸 것이었다. 사전학습 지식에 기대 추론한 기준이다. 검증된 교육과정 지식이 아니다.

이걸 알고 나니 리포트의 문장이 다르게 읽혔다.

## 두 번의 추론이 붙어 있다

이 파이프라인에는 서로 다른 추론이 두 번 들어간다.

1. 문제를 보고 선개념 목록과 오개념 규칙을 **만든다.** 규칙은 대략 이런 모양이다.

```json
"misconceptionRules": [
  { "observation": "학생이 이렇게 하면", "gap": "이것이 부족한 것으로 본다" }
]
```

2. 학생의 관찰된 행동을 1번에서 만든 규칙에 **대조한다.**

둘 다 모델이 한다. 둘 다 틀릴 수 있다. 그런데 최종 리포트에는 이 구분이 사라진 채 "부족한 개념" 하나로 나온다. 1번이 틀렸다면 2번이 아무리 정확해도 결론은 틀린다. 반대로 1번이 그럴듯해도 2번에서 관찰과 규칙을 잘못 이으면 역시 틀린다.

교사가 개념 이름을 직접 넣어 주는 경우도 생각해 봤다. 기준의 출처는 확실해진다. 하지만 학생이 그 개념을 익혔는지는 여전히 확정되지 않는다. 기준의 출처와 판정의 근거는 따로 기록해야 하는 별개의 축이다.

## 코드가 이미 이 문제를 알고 있었다

읽은 코드에는 이 불안을 다루는 장치가 몇 개 있었다. 코드로 계산할 수 있는 사실과 LLM이 추론하는 부분을 나눈 구조가 그 하나다. 모델이 근거를 인용할 때 증거 묶음(evidence bundle)에 있는 것만 가리키게 하고, 인용에 실패하면 그 실패를 코드로 세는 것도 있다. 응답에는 `uncertainNotes`와 `confidence` 필드가 있어서 모델이 "확신하지 못하는 부분"을 따로 적게 한다.

가장 눈에 들어온 건 반복 호출 프로브 스크립트다. 같은 입력으로 여러 번 돌려서 결과가 얼마나 흔들리는지 재는 도구다. 개념 파악 단계용은 정답셋(gold set)을 코드에 박아 둔다.

```python
TASK = "task-A"
GOLD = {
    "core": "S_ADD2",
    "pv_pre_measurable": "S_PV",
    "add1_not_measurable": "S_ADD1",
    "must": {"MG081", "MG083"},
    "nobs_must": {"MG003", "MG004", "MG005"},
}
```

(문제·개념 ID는 일반화했다.) 정답셋은 본개념이 무엇인지, 어떤 선행 개념이 **관측 가능**한지, 어떤 오개념은 반드시 나와야 하는지, 어떤 것은 "볼 수 없음"으로 분류돼야 하는지를 적은 것이다. 이 표는 사람이 정했다. 모델이 만든 기준을 사람이 만든 기준에 대조하는 구조다.

채점 함수는 그 대조를 그대로 코드로 옮긴다.

```python
def score(d):
    sk = {s["id"]: s for s in d.get("skills") or []}
    core = [s["id"] for s in d.get("skills") or [] if s.get("role") == "본개념"]
    obs = {m["id"] for m in d.get("misconceptions") or []}
    nobs = {m["id"] for m in d.get("not_observable") or []}
    return {
        "본개념OK": core == [GOLD["core"]],
        "자릿값 선행·관측": sk.get("S_PV", {}).get("role") == "선행"
                          and sk.get("S_PV", {}).get("measurable") is True,
        "의미 선행·관측불가": sk.get("S_ADD1", {}).get("measurable") is False,
        "필수 오개념": GOLD["must"] <= obs,
        "필수 중 빠짐": ",".join(sorted(GOLD["must"] - obs)),
        "볼수없음 3종": GOLD["nobs_must"] <= nobs,
        "후보 수": len(obs),
        "볼수없음 수": len(nobs),
    }
```

`measurable`이라는 플래그가 있다는 점이 설계의 핵심이다. 선행 개념 중에는 이 활동에서 **관찰할 수 있는 것**이 있고, 관찰할 수 없는 것이 있다. 덧셈의 의미 같은 개념은 계산 조작을 보는 활동으로는 볼 수 없다. 그런 개념을 오개념 후보로 올려 놓고 "이 학생은 부족하다"고 쓰는 순간, 근거 없는 판정이 된다. 그래서 "볼 수 없음" 목록을 오개념 목록과 따로 두고, 정답셋에서도 반드시 거기 들어가야 할 항목을 지정했다.

`필수 중 빠짐` 열도 있다. 스크립트 안의 해설에는 특정 오개념(자릿값 개념 미형성)이 자주 빠지면, 모델이 그것을 "볼 수 없음"으로 보내는 경향으로 읽으라고 적혀 있다. 이전에 그런 실패를 실제로 겪었다는 뜻이다.

실행은 모델 여러 종을 각각 여러 번 돌리는 이중 루프다.

```python
for model in MODELS:
    for i in range(1, REPEAT + 1):
        t0 = time.time()
        d = DraftTaskModel(TASK, grade="auto", model=model, save=False)
        r = d.result
        row = {"모델": model, "회": i, "초": round(time.time() - t0, 1),
               "형식 오류": len(r.get("validation_errors") or [])}
        if r.get("draft"):
            row.update(score(r["draft"]))
```

요약 표 아래에는 읽는 법이 한 줄 붙는다. "같은 모델 3회가 다르면 그만큼 흔들리는 것이다. 한 번 결과로 모델을 고르지 않는다." 이 문장이 이 글의 질문과 이어진다. 기준을 만드는 단계가 매번 다르게 나온다면, 그 기준은 "이 문제의 선개념"이 아니라 "이번 호출의 선개념"이다.

## 판정 단계도 같은 방식으로 흔들어 본다

두 번째 추론, 즉 관찰을 규칙에 대조해 정오를 가르는 단계를 재는 스크립트는 더 단순하다. 케이스마다 기대값을 붙이고 같은 증거로 반복 호출한다.

```python
EXPECT = {"정답을바로맞춰버림": "정답", "정답을바로틀림": "오답",
          "활동을잘하고정답도맞춤": "정답", "활동을잘했지만틀림": "오답"}

for c in CaseStore.list(TASK):
    cid = c["case_id"]
    ev = EvidenceBundle(cid, CaseStore.get(TASK, cid), model_answer)
    for i in range(1, REPEAT + 1):
        j, call, err = ask_verdict(ev, pdef, None, MODEL, TASK, cid)
        rows.append({
            "케이스": cid, "회": i, "기대": EXPECT.get(cid, "?"),
            "판정": j["verdict"],
            "일치": j["verdict"] == EXPECT.get(cid),
            "근거 수": len(j.get("based_on") or []),
            "실패": (err or {}).get("code", ""),
            "자신감": j.get("confidence"),
        })
```

케이스 이름이 곧 시나리오다. 정답을 바로 맞힌 학생, 활동을 잘했지만 틀린 학생 같은 것이다. 특히 마지막 케이스가 중요하다. 과정은 좋은데 답이 틀린 경우에 모델이 답만 보고 "오답"으로 끝내는지, 과정을 근거로 인용하는지를 볼 수 있다. `based_on`의 길이와 인용 실패 코드를 함께 남기는 이유는 판정이 맞았는지 못지않게 **무엇을 근거로 댔는지**를 보고 싶어서다. 정답 판정이 일치해도 근거 수가 0이면 찍은 것과 다르지 않다.

여기서 `confidence`는 조심해서 읽는다. 모델이 스스로 매긴 자신감이다. 표에 열로 넣어 두었지만 정오 일치율과 어떻게 엮이는지는 따로 봐야 한다. 자신감이 높다고 맞는 게 아니다.

## 이것이 해 주는 것과 해 주지 않는 것

솔직히 정리하면 이렇다. 관찰 가능한 기준을 코드에 연결하고, 인용할 수 있는 근거를 제한하고, 출처를 표시하면 판정을 **추적**할 수 있다. 같은 입력이면 비슷하게 나오는지도 잴 수 있다. 재현성은 이런 장치로 높일 수 있다.

하지만 재현성이 높다고 정답인 것은 아니다. 항상 같은 오개념을 뽑는 모델은 일관되게 틀리고 있을 수도 있다. 정답셋 역시 누군가 정한 것이라서, 그 사람의 판단이 옳은지는 이 스크립트가 알려 주지 않는다. 점수가 잘 나오면 "정답셋과 일치한다"까지만 말할 수 있다. 그 관찰 가능한 기준이 학생의 실제 이해도를 대변하는지는 교육 전문가의 검증이나, 사람 판정과 AI 판정의 일치도 평가로 따로 확인해야 한다.

## 아직 못 한 것

솔직하게 적어 둔다. 위 스크립트로 돌린 결과 표를 이 글에 싣지 않았다. 모델별로 몇 번 중 몇 번 맞았는지 수치를 여기서 말할 근거가 내 손에 없다. 스크립트는 읽었고 구조는 이해했다. 그 결과를 이 글의 주장으로 쓰려면 직접 돌려서 확인해야 한다.

여러 활동 유형을 지원하는 새 평가 시스템을 구상하고 있지만, 지금 가진 것은 구조 설명과 설계 초안이다. 새 평가 엔진이나 영상 분석 프로토타입을 만들어 검증한 기록은 없다. 영상처럼 입력이 풍부해지면 "관찰 가능한 것"의 범위가 넓어질 것 같지만, 넓어지는 만큼 모델이 관찰했다고 주장하는 것과 실제로 관찰된 것의 간격도 벌어질 것이다. 그 간격을 어떻게 기록할지는 아직 정하지 못했다.

또 하나 남은 게 있다. 규칙을 만드는 단계의 출처 표시다. 지금은 "모델이 생성함"이라는 사실을 리포트를 읽는 교사에게 어떻게 보여 줄지 정하지 못했다. 표시를 붙이면 신뢰가 떨어져 보이고, 안 붙이면 검증된 것처럼 읽힌다.
