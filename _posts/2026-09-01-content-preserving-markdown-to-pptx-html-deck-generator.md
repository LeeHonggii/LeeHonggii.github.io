AI한테 발표자료 만들어달라고 하면 생기는 일이 있다. 내가 쓴 3문단짜리 설명이 "핵심 포인트 3개"로 압축된다. 표가 사라지고 불릿 하나로 대체된다. 코드 블록은 "코드 예시 참고" 한 줄이 된다.

틀린 말은 아닌데, 내 글이 아니다.

## 문제는 재작성 허용이다

AI가 발표자료를 망치는 근본 원인은 요약·재작성을 기본 허용했기 때문이다. "슬라이드에 맞게 정리해줘"라는 말 자체가 함정이다. 모델 입장에서는 슬라이드 한 장에 텍스트가 많으면 줄이는 게 합리적이다. 그래서 줄인다. 내용이 사라진다.

해결 방향은 단순하다. 재작성을 막고, 분할만 허용한다.

입력 Markdown 한 섹션이 슬라이드 한 장이 되거나, 너무 길면 여러 장으로 쪼개진다. 섹션 안의 텍스트·표·코드블록은 그대로 들어간다. 모델이 할 수 있는 건 "이 섹션은 두 장으로 나눈다" 판단뿐이다. 요약하거나 다른 말로 바꾸는 건 허용하지 않는다.

## 단일 Markdown 소스 → PPTX + HTML

PPTX와 HTML을 각각 다른 경로로 만들면 둘 사이에 괴리가 생긴다. 텍스트가 조금씩 달라진다. 어떤 게 맞는 버전인지 알 수 없게 된다.

Marp(Markdown Presentation Ecosystem)를 쓰면 이 문제를 피할 수 있다. Marp는 Markdown 파일 하나를 받아서 PPTX나 HTML로 변환한다. 소스가 하나니까 결과도 동일하다.

```bash
marp deck.md --pptx -o out/deck.pptx
marp deck.md --html -o out/index.html
```

두 명령이 같은 `deck.md`를 읽는다. HTML 버전과 PPTX 버전이 내용상 달라질 수 없다.

실제로 쓸 때는 디자인 스펙과 레이아웃을 함께 넘긴다.

```bash
python make_deck.py input.md --mode both --design brand_a --layout split
```

`--design`은 브랜드별 CSS 테마를, `--layout`은 슬라이드 레이아웃 패턴을 고른다. 어떤 팀은 글/이미지가 좌우로 나뉘는 split을 쓰고, 어떤 팀은 텍스트만 full을 쓴다. 레이아웃을 선택 가능하게 분리한 건 Marp의 CSS 변수 구조 덕분이다. 테마 파일에 레이아웃 로직을 넣지 않고, 레이아웃을 별도 클래스로 오버라이드하는 방식이다.

산출물 디렉토리 구조는 고정했다.

```
_decks/<slug>/
  source.md      # 원본 입력
  deck.md        # Marp 변환용 (슬라이드 구분자, front matter 포함)
  theme.css      # 적용된 테마
  deck.pptx
  index.html
```

`source.md`와 `deck.md`를 따로 두는 이유가 있다. Marp 변환에 필요한 `<!-- --- -->` 슬라이드 구분자와 front matter(`marp: true`, 테마 경로 등)가 원본에 섞이면 나중에 원본을 읽기 불편해진다. 변환 전 중간 산출물이 따로 있으면 어디서 문제가 생겼는지 추적하기도 쉽다.

## 콘텐츠 유실 검증

분할만 허용해도 누락은 생긴다. 섹션이 잘못 나뉘거나, Marp가 너무 긴 텍스트를 잘라버리거나, 코드블록의 언어 태그가 떨어지는 경우가 있다.

그래서 변환 후 검증 단계가 필요하다.

검증 로직의 아이디어는 단순하다. 입력 Markdown에서 추출 가능한 구조물(코드블록 개수, 표 개수, 특정 길이 이상 문장들)을 산출물 텍스트와 대조한다. 코드블록이 입력에 3개 있었으면 PPTX 텍스트를 파싱했을 때 3개 분량의 코드가 보여야 한다. 표의 헤더 셀이 산출물에 전부 남아있어야 한다.

이 검증을 완전하게 구현하지는 않았다. 현재는 코드블록 개수 대조와 표 헤더 텍스트 존재 여부만 체크한다. 긴 문장 단위 검증은 아직 없다. PPTX를 파싱해서 텍스트를 뽑아내는 부분이 생각보다 까다롭기 때문이다—`python-pptx`로 텍스트를 가져오면 도형 순서가 슬라이드 논리 순서와 다르게 나오는 경우가 있다. HTML 버전은 BeautifulSoup으로 비교적 깔끔하게 뽑히는데 PPTX는 아직 불안정하다.

## 아직 불편한 것

Marp HTML 출력은 기본적으로 단일 `index.html` 파일이다. 슬라이드 이미지가 Base64로 인라인 임베드되는데, 이미지가 많으면 파일 하나가 수십 MB가 된다. GitHub Pages에 올리거나 이메일로 공유하기 불편하다. 슬라이드별로 쪼개는 방법이 없지는 않은데, Marp CLI가 기본 지원하지 않아서 후처리가 필요하다.

그리고 "1:N 분할만 허용"이라는 원칙이 모든 입력에 잘 맞지는 않는다. 입력 Markdown이 이미 슬라이드 의식 없이 흘러가는 산문체로 쓰여 있을 때—예를 들어 회의 노트나 이슈 정리—는 어디서 자르는지가 전혀 자명하지 않다. 섹션 헤딩이 없으면 분할 기준이 없다. 그때는 결국 모델한테 "여기서 자르세요"를 판단시킬 수밖에 없고, 그 판단 자체가 맥락을 잘라버리는 위험을 다시 도입한다.

입력 형식에 전제가 많은 도구다.
