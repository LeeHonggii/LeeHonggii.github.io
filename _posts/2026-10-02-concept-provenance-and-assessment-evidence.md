학생 풀이를 보고 피드백을 만드는 파이프라인의 실행 순서를 처음부터 끝까지 따라가 봤다. 문제 이미지에서 문제를 정의하고, 학생 답안을 판정하고, 루브릭으로 평가한 뒤 리포트를 만든다. 단계마다 "이건 코드가 계산한 값인가, 모델이 추론한 값인가"를 표시하다가 한 군데에서 손이 멈췄다.

프롬프트가 요구하는 출력 중에 이런 게 있었다.

```json
{"concepts":{"pre":["이 문제를 풀기 전에 이미 알고 있어야 하는 개념"],"core":["이 문제로 익히게 하려는 개념"],"post":["이걸 익히면 다음에 배우게 되는 개념"]}}
```

선개념(문제를 풀기 전에 있어야 하는 개념), 본개념, 후개념이다. 리포트에는 이 목록이 아주 그럴듯하게 들어간다. 그런데 이 값은 어디서 왔나.

## 조회한 게 아니었다

처음엔 교육과정 데이터를 어딘가에서 조회해 온다고 막연히 생각했다. 코드를 따라가 보니 아니었다. 교사가 개념을 입력해 둔 경우가 아니면 이 목록은 모델이 문제 이미지를 보고 사전학습 지식으로 만든 추론이다. 교육과정 DB 조회는 없었다.

이걸 알고 나니 JSON이라는 형태가 오히려 거슬렸다. 스키마에 맞춰 키가 `pre`, `core`, `post`로 나뉘어 나오면 검증된 분류표처럼 읽힌다. 하지만 형식이 맞다는 것과 내용이 타당하다는 것은 별개다. 스키마 검증은 키가 있는지만 본다. "대응 관계"가 이 문제의 선개념으로 맞는지는 아무도 확인하지 않았다.

그럴듯하다는 것 자체가 위험했다. 틀린 개념이 나오면 바로 눈에 띄지만, 그럴듯한 개념은 그냥 통과한다.

## 규칙을 만드는 일과 학생을 보는 일

오개념 쪽은 한 단계 더 얽혀 있었다. 오개념 규칙은 이런 모양이다.

```json
{"observation":"합계 칸에 그루 수를 그대로 쓴다","gap":"대응 관계 이해 부족"}
```

`observation`은 관찰 가능한 행동이고 `gap`은 그 행동에서 추정한 이해의 빈틈이다. 이 규칙을 만드는 단계와, 만든 규칙에 학생의 실제 행동을 대조하는 단계는 다른 일이다.

규칙 생성은 모델이 문제를 보고 "학생들이 이렇게 틀릴 것이다"라고 가설을 세우는 일이다. 대조는 이 학생이 실제로 합계 칸에 그루 수를 썼는지 보는 일이다. 대조는 꽤 단단해질 수 있다. 하지만 대조가 아무리 정확해도 대조 대상인 규칙이 모델이 만든 가설이라는 사실은 사라지지 않는다. 학생이 규칙에 걸렸다는 것은 "모델이 예상한 오류 패턴과 일치했다"이지, "이 학생에게 이 오개념이 있다"가 아니다.

문제는 리포트에서 둘이 구분되지 않는다는 점이었다. 교사가 넣은 기준이든 모델이 만든 기준이든 같은 문장, 같은 자리에 같은 어조로 나온다. 그래서 출처를 따로 들고 다니게 하는 쪽으로 생각을 잡았다.

```text
출처 표기: 교사기준 / 비전기준 / 추정
```

교사가 입력한 것은 `교사기준`, 이미지를 보고 읽어 낸 것은 `비전기준`, 모델이 지식으로 채운 것은 `추정`이다. 아직 이 표기가 전 단계에 전달되도록 구현을 끝낸 건 아니다. 지금은 출처를 보존해야 한다는 판단까지다.

## 교사가 이름을 넣어도 끝이 아니다

그러면 교사가 개념 이름을 직접 입력하면 해결되나. 반쯤만 해결된다.

교사가 "대응 관계"라고 입력하면 `추정`이 `교사기준`으로 바뀐다. 그런데 "대응 관계를 이해했는가"를 학생의 어떤 행동으로 판정할지는 여전히 비어 있다. 개념 이름과 관찰 가능한 판정 기준 사이에는 간격이 있다. 이름만 주면 모델이 그 간격을 다시 자기 추론으로 메운다. 출처 표기는 `교사기준`인데 실제 판정 로직은 모델 몫이 되는, 가장 오해하기 쉬운 상태가 된다.

판정을 코드로 고정하면 일관성은 생긴다. 같은 입력에 같은 결과가 나오니 재현도 된다. 다만 코드로 박아 둔 기준이 교육적으로 맞는지는 코드가 보장해 주지 않는다. 합계 칸에 그루 수를 쓰면 오개념이라는 규칙이 결정적으로 돌아가도, 그 규칙이 틀렸을 수 있다. 일관성과 타당성은 다른 축이었다.

## 관찰이 실제로 무엇을 볼 수 있는가

기준의 출처와 별개로, 학생에 대한 판정은 입력이 실제로 담고 있는 것만큼만 단단하다. 이쪽은 코드로 확인할 수 있어서 먼저 손을 댔다.

학습 활동 기록을 재생하는 코드에서 지우기 이벤트가 빠지고, 객체 비교를 ID에 의존하다 틀리는 문제를 찾아 고쳤다. 지금 재생기는 이벤트 종류별로 장면을 갱신한다.

```python
@staticmethod
def apply(scene, pens, kind, before, after):
    bl = before if isinstance(before, list) else []
    al = after if isinstance(after, list) else []
    if kind == "pen":
        pens.extend(al)
        return "필기"
    if kind == "erase":
        gone = {p.get("id") for p in al + bl}
        pens[:] = [p for p in pens if p.get("id") not in gone]
        return "지움"
    if kind == "delete":
        for e in bl:
            scene.pop(e.get("id"), None)
        return "삭제"
    for e in al:
        scene[e.get("id")] = e
    return "꺼냄" if kind == "create" else "이동"
```

`erase`는 `before`와 `after` 양쪽의 ID를 모아 한꺼번에 제거한다. 지우기 이벤트가 어느 쪽에 지운 획을 담아 오는지 확신할 수 없어서 합집합으로 받았다. `isinstance` 검사는 `before`/`after`가 리스트가 아닌 이벤트(시작 이벤트처럼 dict가 들어오는 경우)에서 깨지지 않게 하려는 방어다.

이 수정이 피드백 품질에 의미 있는 이유는 따로 있다. 학생이 썼다가 지운 것은 최종 화면에 남지 않는다. 최종 장면만 보는 판정은 학생이 처음에 뭘 썼고 왜 고쳤는지 알 수 없다. 지운 필기는 학생이 어디서 망설였는지를 보여 주는 가장 직접적인 단서일 수 있다.

되돌리기는 다르게 다룬다.

```python
elif x.get("subType") == "undo":
    scene, pens = snapshots[-2] if len(snapshots) >= 2 else (scene, pens)
    scene, pens = dict(scene), list(pens)
    if self.frames:
        self.frames[-1]["valid"] = False
        self.undone += 1
    label = "되돌리기"
```

매 이벤트를 적용하기 전에 장면 스냅샷을 쌓아 두고, 되돌리기가 오면 직전 이벤트 이전의 스냅샷으로 복원한다. 되돌려진 프레임은 지우지 않고 `valid=False`로 표시해서 남긴다. 되돌려진 시도도 학생이 해 본 행동이기 때문이다. 이 값을 AI 피드백 쪽으로 중간 풀이와 지운 필기와 함께 넘기게 했다.

그리고 이 재생이 모든 기록에 가능한 건 아니다.

```python
if not self.legacy or not self.items:
    self.frames = [{"step": 0, "t": 0, "label": "최종 장면", "valid": True,
                    "elements": self.state.get("elements") or [],
                    "pens": self.state.get("penElements") or []}]
    self.replayable = False
    return self.frames
```

이력 형식이 legacy가 아니면 최종 장면 1장뿐이고 `replayable`이 `False`가 된다. 이 경우 과정은 관찰할 수 없다. 코드가 이걸 숨기지 않고 플래그로 남기는 건 맞는 방향이라고 생각한다. 다만 그 플래그가 리포트 문장까지 내려가서 "과정은 보지 못했다"로 표현되는지는 아직 확인하지 못했다.

활동 유형별로 지금 입력이 무엇을 볼 수 있는지도 훑어봤다. 필기 중심 활동은 위처럼 획 단위 과정이 남는다. 말로 설명하거나 손으로 조작하는 활동은 현재 입력에 근거가 거의 없다. 이런 활동에서 나온 오개념 판정은 관찰이 아니라 추정으로 표기하는 게 맞다. 영상으로 보면 달라질 수 있겠다는 구상은 있다. 테스트 구상 단계이고, 돌려 본 결과는 없다.

## 아직 남은 것

정리하고 보니 "AI가 선개념과 오개념을 아는가"라는 질문 자체가 두 개로 갈라져 있었다. 기준을 만드는 쪽은 모델이 가설을 생성한 것이고, 학생을 판정하는 쪽은 입력이 허락하는 만큼만 관찰한 것이다. 둘을 같은 문장으로 쓰면 앞의 불확실성이 뒤의 확신으로 둔갑한다.

아직 안 정한 게 있다. 출처 표기를 학생용 리포트에까지 드러낼지, 교사용 화면에만 둘지다. 학생에게 "추정"이라는 말이 어떻게 읽힐지 모르겠다. 교사 기준이 들어온 경우에도 개념 이름과 판정 기준 사이의 간격을 누가 채울지는 설계가 없다. 이 부분은 지금도 모델이 채우고 있을 가능성이 크고, 그걸 확인하는 일이 다음 순서다.
