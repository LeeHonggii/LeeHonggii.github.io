페이지네이션을 추가하는 일인 줄 알았다.

막상 해보니 그게 아니었다. LIMIT과 OFFSET 두 줄 넣는 게 전부가 아니라, 응답 계약 전체를 고쳐야 했다. 오류를 어떻게 표현하는지, 총 개수를 어디서 어떻게 가져오는지, 클라이언트가 "다음 페이지가 있는지"를 어떻게 아는지 — 이것들이 전부 바뀐다.

---

기존 응답은 대충 이렇게 생겼다.

```json
{
  "status": "success",
  "count": 30,
  "templates": [...]
}
```

`status` 필드로 성공/실패를 구분하고, HTTP 상태 코드는 사실상 200으로 고정. 오류도 `status: "error"` 로 표현하고 200을 반환하는 구조였다.

이 방식이 나쁘다고 생각하지 않았다. 간단하고, 어떤 상황에서도 응답 파싱이 예측 가능하다. 하지만 페이지네이션을 붙이면서 `totalCount` 가 필요해졌고, 그러면서 `count` 와 `templates` 를 `totalCount` 와 `list` 로 바꾸는 게 자연스러웠다. 한번 손대기 시작하면 "그러면 오류 표현도 HTTP 표준으로 맞추자"로 이어지는 건 시간문제다.

바뀐 응답은 이렇다.

```json
{
  "totalCount": 276,
  "list": [...]
}
```

오류는 HTTP 상태 코드로 분리했다. 파라미터 검증 실패는 422, 사용량 초과는 429, 처리 실패는 500. 그리고 오류일 때 바디에는 `error_code` 와 `error_detail` 을 담아서 클라이언트가 원인을 구분할 수 있게 했다.

---

`offset` 정의를 어떻게 잡느냐가 생각보다 중요했다.

행 번호(0-based)로 쓸 수도 있다. SQL에 직접 꽂아 넣기 편하다. 그런데 API 소비자 입장에서 "2페이지"를 요청하려면 `offset=30` 같은 값을 직접 계산해서 넘겨야 한다. 이건 UI 쪽에서 실수를 유발한다.

그래서 1-based 페이지 번호로 정의했다. 1페이지는 `offset=1`, 2페이지는 `offset=2`. SQL로 변환할 때는 서버에서 계산한다.

```
skip = (offset - 1) * limit
```

이 계산 한 줄이 어디 있느냐가 계약의 핵심이다. 서버 안에 있으면 클라이언트는 페이지 번호만 알면 된다. 바깥에 있으면 클라이언트가 limit 값을 알고 있어야 한다. 작은 차이처럼 보이지만 limit 기본값을 나중에 바꾸면 영향을 받는 쪽이 달라진다.

---

FastAPI 에서 Pydantic 쿼리 모델(query model — 쿼리 파라미터를 클래스로 묶어 받는 방식)을 쓰면서 별도 파라미터를 함께 선언했더니 문제가 생겼다.

```python
async def get_templates(
    main_tool: str,          # path parameter
    pagination: PaginationParams = Depends(),  # Pydantic query model
    limit: int = 30          # 이 파라미터가 조용히 무시됨
):
```

`limit` 이 쿼리 파라미터로 잡히지 않았다. 에러도 없었다. 그냥 값이 안 들어왔다. `Depends()` 로 주입된 Pydantic 모델과 같은 레벨에 별도 파라미터를 두면 FastAPI 가 라우터 시그니처를 파싱하는 과정에서 충돌이 생기는 것 같았다.

해결은 단순했다 — 모든 쿼리 파라미터를 모델 안으로 넣거나, 아니면 `Depends()` 를 쓰지 않거나. 둘 중 하나로 통일해야 한다. 이건 FastAPI 문서에 명시적으로 적혀 있지 않아서 실제로 안 되는 걸 보기 전까지는 알기 어렵다.

---

랜덤 정렬 엔드포인트에 페이지네이션을 붙이는 건 구조적으로 모순이다.

`ORDER BY RANDOM()` 을 쓰면 같은 쿼리를 두 번 실행해도 순서가 달라진다. 그러면 2페이지를 요청했을 때 1페이지에서 봤던 항목이 다시 나오거나, 어떤 항목은 아예 안 나올 수 있다. 페이지네이션이 보장해야 하는 "각 항목은 정확히 한 번 등장한다"는 속성이 깨진다.

선택지는 세 가지였다.

첫 번째는 랜덤성을 포기하고 고정 정렬로 바꾸는 것. 두 번째는 전체 결과를 한 번 가져와 메모리에서 섞고 캐시해두는 것. 세 번째는 랜덤성을 유지하되 다중 페이지 정합성은 보장하지 않는다고 문서에 명시하는 것.

첫 번째는 이 엔드포인트의 존재 이유를 없앤다. 두 번째는 데이터가 많아지면 캐시 관리가 복잡해진다. 세 번째는 정직하게 한계를 드러낸다.

세 번째로 결정했다. 각 페이지가 독립적으로 랜덤하게 정렬된다. 1페이지를 다시 요청하면 다른 결과가 나온다. 이 엔드포인트는 "전체 카탈로그를 순회"하는 용도가 아니라 "그때그때 다양하게 보여주는" 용도이기 때문에 이 제약이 실제 사용 패턴과 충돌하지 않는다고 판단했다.

---

`totalCount` 를 반환하려면 목록 조회 쿼리와 별도로 COUNT 쿼리가 필요하다. 같은 WHERE 조건을 두 번 쓴다는 게 찜찜하고, 조건이 복잡해지면 두 쿼리 사이에 불일치가 생길 위험도 있다. 한 쿼리로 데이터와 전체 개수를 동시에 가져오는 방법도 있지만 — 윈도우 함수(window function) 를 쓰면 된다 — 대신 쿼리가 복잡해지고 설명하기 어려워진다. 현재는 두 쿼리를 따로 유지하는 방식을 택했는데, 이게 더 나은 선택인지는 아직 확신이 없다. 데이터 규모가 커지면 다시 봐야 할 것 같다.
