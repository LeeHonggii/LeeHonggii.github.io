date: 2026-09-11 17:00:00 +0900
categories: [Backend]

---

템플릿 목록 API에 페이지네이션을 붙이는 작업이었다. 어렵지 않아 보였다. `offset`과 `limit`을 받아서 쿼리에 넘기면 끝이라고 생각했다.

---

작업 전 API는 status 필터 하나만 쿼리 파라미터로 받고 있었다. 여기에 `offset`과 `limit`을 추가하고, 응답도 `totalCount`와 `list`를 가진 구조로 바꾸는 게 목표였다.

처음에는 라우터 함수 시그니처에 파라미터를 그냥 쭉 늘어놓는 방식을 택했다. 기존에 Pydantic 모델로 묶어둔 파라미터가 있었고, 새로 추가하는 `offset`/`limit`은 `Query()`를 이용해 개별로 선언했다.

에러는 없었다. 서버도 뜬다. 쿼리도 일단 동작하는 것처럼 보였다.

그런데 `/docs`를 열어봤더니 뭔가 이상했다.

---

FastAPI의 Swagger UI(`/docs`)는 실제 라우팅 스키마를 그대로 반영한다. OpenAPI 스펙 — 어떤 파라미터가 어떤 이름으로 어떤 타입으로 노출되는지 — 을 가장 빠르게 육안으로 확인할 수 있는 곳이다.

거기서 `offset`과 `limit`이 보이지 않았다. 아니, 정확히는 파라미터 목록에는 있는데 쿼리 파라미터로 개별 입력 필드가 뜨지 않았다. 선언은 했는데 스키마에 반영이 안 된 상태였다.

코드를 다시 들여다봤다. Pydantic 모델과 개별 `Query()` 파라미터를 함께 선언하면 FastAPI가 둘을 어떻게 해석하는지가 문제였다.

FastAPI는 라우터 시그니처에서 파라미터를 해석할 때 Pydantic 모델을 만나면 그 모델 전체를 하나의 덩어리로 처리한다. 그 옆에 개별 `Query()` 파라미터를 따로 두면, FastAPI 버전이나 조합 방식에 따라 의도대로 펼쳐지지 않는 경우가 생긴다. 문법 오류가 아니라 스키마 해석의 문제다. 에러 없이 조용히 동작이 달라진다는 게 이 함정의 본질이다.

---

수정 방향은 단순했다. `offset`과 `limit`을 별도 파라미터로 두지 말고, 관련 쿼리 파라미터를 하나의 Pydantic 모델 안에 전부 넣는 것이다.

```python
class TemplatePaginationQuery(BaseModel):
    offset: int = Field(default=1, ge=1)
    limit: int = Field(default=30, ge=1, le=300)
```

이렇게 묶고 라우터에 모델 하나만 받으면, FastAPI가 모델 필드를 쿼리 파라미터로 하나씩 펼쳐서 스키마에 노출한다. `/docs`에서 `offset`, `limit` 입력 필드가 각각 제대로 보이기 시작했다.

응답 구조는 `totalCount`와 `list`를 담은 딕셔너리로 맞췄다. 랜덤 추천 API도 같은 응답 포맷을 써야 했는데, 거기서는 페이지네이션 자체가 의미가 없다는 게 문제였다. 랜덤으로 뽑은 결과를 `offset`/`limit`으로 자르면 중복이 생기고, 매 요청마다 순서가 달라지기 때문에 `totalCount`도 의미가 애매해진다. 결국 랜덤 로직은 그대로 두되 응답 포맷만 페이지네이션 형태로 맞추는 쪽으로 결론냈다. 클라이언트가 포맷 통일을 원했으니까.

---

이 케이스가 걸리는 게 어려운 이유는 아무것도 깨지지 않기 때문이다. 서버는 뜨고, 호출은 되고, 어느 상황에서는 값도 들어온다. 잘못됐다는 신호가 없다. OpenAPI 스펙을 직접 눈으로 확인하지 않으면 놓치고 넘어가기 쉬운 종류의 버그다.

FastAPI 버전에 따라 Pydantic 모델과 개별 `Query()` 파라미터를 혼용했을 때 동작이 어떻게 달라지는지는 아직 정확히 재현해보지 않았다. 버전별로 동작이 다르게 보이는 이슈 리포트가 있긴 한데, 내 환경에서 체계적으로 확인한 건 아니다.
