문서가 너무 컸다.

어떤 도메인의 누적 데이터를 Markdown으로 정리해두면 편할 것 같아서 그렇게 했는데, 쌓이다 보니 단일 파일이 16MB를 넘었다. 로컬 LLM에 요약을 시키려고 파일을 그냥 넘겼더니 당연히 컨텍스트를 초과했다. 클라우드 API로 보내는 건 선택지 밖이었다 — 내용 자체가 외부로 나가면 안 됐다.

그래서 파이프라인을 직접 만들었다.

---

## 통째로 넣지 않는다는 것의 의미

Markdown 문서는 헤더(`#`, `##`, `###`) 구조를 따른다. 이걸 청크(chunk) 단위로 쪼개면 각 조각은 수백~수천 토큰 수준이 된다. 로컬 LLM이 충분히 소화할 수 있는 크기다.

전략은 간단하다. Map-Reduce — 분산 처리에서 쓰는 그 패턴이다. 각 청크를 개별 요약하고(map), 그 부분 요약들을 다시 LLM에 넣어 최종 문서 하나로 합친다(reduce). 원본 전체를 컨텍스트에 올리지 않아도 전체를 한 번 훑은 것과 비슷한 결과를 얻는다.

실제 실행은 이렇게 생겼다:

```bash
python3 gemma_processor.py summarize_large <file>
```

Gemma를 로컬에서 돌리고, 대상 파일 하나를 넘기면 파이프라인이 알아서 청킹 → 부분 요약 → 병합 순서로 처리한다. 모델 호출이 순차적이라 빠르지는 않다. 대신 인터넷 연결 없이, 로그 한 줄 밖으로 안 나간다.

---

## mtime을 믿지 않는다

처음엔 파일 수정 시각(mtime)으로 재처리 여부를 판단했다. `git pull`이나 파일 복사가 일어나면 내용이 안 바뀌어도 mtime이 갱신된다. 결과적으로 변하지 않은 파일을 계속 다시 요약하게 됐다.

SHA-256 해시로 바꿨다. 파일 내용의 해시를 처음 처리할 때 저장해두고, 다음 실행 때 비교한다:

```
sha256(original_file) == stored_hash  →  skip
```

내용이 같으면 요약을 건너뛴다. 이 단순한 변경으로 증분 실행이 실제로 증분이 됐다. 이전 요약 결과를 덮어쓰지 않으니 멱등성(idempotency)도 자연스럽게 확보된다.

---

## 원본과 산출물을 섞지 않는다

처리 전략과 별개로, 파일 배치를 바꿨다.

원본 Markdown 파일은 크다. 검색 인덱스에 올라가면 노이즈다. 그래서 원본을 `.txt`로 확장자를 바꿔 검색 대상에서 제외했다:

```
data_parsed/*.md  →  data_parsed/*.txt
```

요약 결과는 별도 디렉터리로 뽑아냈다:

```
_summaries/docs/.../<name>.md
```

이렇게 하면 무거운 원본은 보존되면서, 검색과 그래프 뷰에는 경량 요약만 노출된다. 원본을 지우지 않아도 되고, 요약이 잘못됐을 때 원본에서 다시 생성하면 된다.

---

## 아직 손대지 않은 것들

청킹 기준이 헤더뿐이라 헤더 없이 쭉 이어진 긴 섹션은 한 덩어리로 들어간다. 이 덩어리가 모델 컨텍스트를 다시 초과하는 케이스가 드물게 있다. 지금은 그냥 통으로 보내는데, 토큰 수를 미리 재고 초과 시 추가 분할하는 로직이 필요하다.

Reduce 단계도 단순하다. 부분 요약을 그냥 이어붙여 다시 넣는다. 문서가 많아질수록 Reduce 입력 자체가 커지는 문제가 있다. 계층적 Reduce — 부분 요약의 요약을 한 단계 더 두는 방식 — 를 써야 할 시점이 올 것 같은데 아직 재보지 않았다.
