테이블 이름을 바꿨다. 마이그레이션도 돌렸다. 그런데 특정 조회 경로에서만 오류가 났다.

처음엔 마이그레이션이 안 적용된 줄 알았다. `information_schema.tables` 로 확인했더니 새 이름의 테이블은 제대로 있었다. 그럼 뭐가 문제인가.

---

쿼리를 다시 들여다봤다. 목록 조회용 쿼리 하나가 이전 테이블 이름을 LEFT JOIN 에서 그대로 참조하고 있었다. LEFT JOIN(왼쪽 테이블 기준으로 오른쪽 테이블을 붙이되, 매칭이 없어도 왼쪽 행을 유지하는 조인)이라 빈 행이 나와도 쿼리 자체는 에러 없이 실행되는 경우가 있었고, 그게 진단을 늦췄다.

실제로 `LEFT JOIN`은 오른쪽 테이블이 없는 행에 NULL을 채워 반환하는 특성 때문에, 이름이 바뀐 테이블을 참조하는 조인이 있더라도 쿼리가 결과를 돌려주는 것처럼 보일 수 있다. 정확히는 테이블 자체가 없어서 에러가 나야 정상인데, 환경에 따라 캐싱이나 뷰가 끼어 있으면 증상이 더 늦게 나타나기도 한다.

---

이 상황에서 검증을 두 단계로 나눴다.

**1단계 — 테이블 존재 확인**

`information_schema.tables` 로 신규 이름의 테이블이 있는지 먼저 확인했다. 이건 통과.

**2단계 — 실제 조회 성공 확인**

해당 조인을 포함한 쿼리를 DB에서 직접 실행해 결과를 봤다. 이 단계에서야 이전 이름을 참조하는 구문이 에러를 뱉었다. 테이블 존재 확인으로 검증을 끝냈으면 이걸 놓쳤을 것이다.

LEFT JOIN 결과를 보면서 한 가지 더 확인했다. 연관 데이터가 없는 행이 NULL 로 유지되는지였다. 이건 확인됐다. 하지만 NULL 이 출력됐다는 것 자체가 조인 조건 전체의 정확성을 증명하지는 않는다. ON 절의 컬럼 참조가 올바른지는 별도로 봐야 한다.

---

수정은 간단했다. JOIN 절의 테이블 이름 한 줄을 바꾸는 것이었다. 그런데 이걸 서버에 반영하는 게 조금 달랐다.

작업 환경이 망 분리되어 있어서 직접 push 를 할 수 없었다. git patch 로 커밋을 만들어 전달하는 방식이었다. 이 과정에서 로컬 브랜치가 없는 상태의 오류와 서버 쪽 push 권한 오류를 구분해야 했다. 증상이 비슷해 보여도 원인이 달랐고, 둘을 섞어 대응하면 시간을 두 배로 쓴다.

---

지금 남은 것은 앱 수준 검증과 원격 반영이다. DB 직접 실행으로는 통과했지만, API 레이어를 거쳐 앱에서 조회했을 때 형식이 기대한 것과 같은지는 아직 안 봤다. 이걸 확인해야 이 작업이 끝났다고 할 수 있다.
