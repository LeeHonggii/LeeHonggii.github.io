학생 활동 기록이 어디에 저장되는지 찾아야 했다. 분석 코드에 넣을 입력 데이터가 필요했는데, 누구도 저장 위치를 정확히 말해 주지 못했다.

처음엔 이름과 날짜로 짐작했다. 서비스 이름과 비슷한 DB가 있었고, 과거 데이터는 특정 시기 것이니 그 무렵 만들어진 DB겠거니 했다. 이 짐작이 틀렸다는 걸 확인하는 데 시간이 꽤 걸렸다.

## 이름을 믿지 않기로 했다

`SHOW DATABASES` 로 목록을 뽑으니 이름만으로는 용도를 알 수 없는 것이 여럿 있었다. 이름이 그럴듯한 DB가 실제로는 다른 용도일 수도 있었다. 그래서 DB 이름 추측을 그만두고, 여러 DB를 돌면서 테이블과 컬럼 구조를 한꺼번에 훑는 조회 스크립트를 만들었다. 컬럼명에 식별자 성격의 단어가 들어간 곳, 텍스트·JSON 타입 컬럼이 있는 곳부터 후보로 좁혔다.

DB 이름이나 데이터의 날짜로 위치를 단정하지 말고 실제 테이블·컬럼 구조를 봐야 한다는 건 당연한 말이다. 그런데 막상 급하면 이름부터 믿게 된다.

## 0건이 나왔다

후보 테이블에서 찾는 학생의 ID로 검색했더니 결과가 0건이었다. 여기서 "이 DB에는 없다"로 결론 내릴 뻔했다.

멈춘 이유는 단순했다. 내가 검색한 건 ID 성격의 짧은 컬럼들뿐이었다. 활동 기록처럼 구조가 복잡한 데이터라면 식별자가 별도 컬럼이 아니라 JSON 본문이나 URL 안에 들어 있을 수 있다. 그렇다면 컬럼 검색의 0건은 "내가 본 곳에 없다"일 뿐 "데이터가 없다"가 아니다. 검색 범위를 JSON 컬럼과 URL이 든 문자열 컬럼까지 넓히자 같은 ID가 나왔다.

## 전체를 열지 않고 구조만 보기

JSON 안에서 찾았으니 이제 그 JSON이 어떻게 생겼는지 알아야 했다. 다만 활동 기록에는 학생 정보가 있을 수 있어서 내용을 통째로 출력하고 싶지 않았다. 그래서 두 가지만 뽑았다.

- 중첩 JSON의 키 경로 목록
- 유형별로 값 예시 한두 개

이렇게 하면 내용을 노출하지 않고도 구조를 파악할 수 있다. 개인정보가 일반 컬럼에만 있다고 가정해선 안 된다는 점도 이때 확인했다. 중첩된 JSON 안쪽에도 있을 수 있어서, 예시를 뽑는 단계에서도 값을 그대로 찍지 않도록 주의했다.

## 복호화 오류

활동 기록 본체는 압축된 문자열로 저장되어 있었다. 풀어 보니 오류가 났다. 원인은 문자열 앞에 붙은 형식 접두어(어떤 방식으로 인코딩했는지 알리는 표식)였다. 압축 데이터 자체가 아니라 이 접두어를 포함한 채로 풀려고 해서 실패한 것이다. 접두어를 분리하고 나머지를 풀자 복원이 됐다.

복원한 데이터가 기존 분석 코드의 입력 구조와 호환되는지도 확인했고, 호환됐다. 새로 변환 코드를 짤 필요는 없었다.

## 아직 안 끝난 것

같은 작업의 다음 단계로 AI 문항 생성용 메타데이터를 설계했다. 기준 예시를 어떤 역할로 둘지, 생성 지침과 출력 스키마가 어디까지 제약할지, 전문가 검수를 어디까지 받을지를 정했다. 생성 실험 코드와 입력 조건도 준비했다.

하지만 첫 실행은 크레딧 부족으로 실패했다. 충전한 뒤에는 API 연결이 되는지만 확인했다. 그래서 **이 메타데이터가 생성 품질을 높이는지는 아직 모른다.** 비교 실험을 돌려 보지 않았으니, 지금 말할 수 있는 건 설계 의도까지다.

다음에 할 일은 메타데이터를 넣은 경우와 뺀 경우를 같은 입력으로 돌려 전문가 검수 결과를 비교하는 것이다. 그 전에 평가 기준부터 정해야 하는데, 그 부분이 아직 애매하다.
