학습 활동 기록을 해석해서 리포트를 만드는 기능을 다루고 있었다. 학생이 화면 위에서 도형과 막대를 움직여 문제를 푸는 기록이다. 풀이 구간을 나누는 건 코드가 하고, 구간이 무슨 의미인지 분류하는 건 AI가 한다. 분류 정확도에 한계가 있다는 것도 확인했다. 여기까지는 어느 정도 정리가 됐다.

문제는 그 다음이었다. 평가 방식을 "모범답안과 얼마나 비슷한가"에서 "정답 조건을 얼마나 충족했는가"로 바꾸기로 했고, 그러려면 모범답안 없이도 AI가 평가 기준을 만들 수 있는지 봐야 했다. 이 실험 과정에서 내가 설계를 두 번 잘못 짰다. 그 기록이다.

## 이미지를 빼면 틀린다, 라는 결론

서비스는 모델에 글과 시작 화면 그림을 같이 넣는다. 이미지가 토큰도 먹고 호출 비용도 올리니, 빼도 되는지 궁금했다. 이미지를 빼고 돌려보니 모델이 틀렸다.

처음엔 "이미지가 필요하다"로 읽을 뻔했다. 그런데 틀린 내용을 들여다보니 계산이 틀린 게 아니었다. **무엇을 해야 하는지**를 잘못 읽고 있었다. 문제 문장만으로는 화면에 뭐가 몇 개 놓여 있는지 알 수 없고, 그래서 과제 자체를 오독했다. 계산 능력 문제와 과제 이해 문제는 다른 문제다. 별도로 한 평가에서는 이미지를 줬는데도 화면의 개수를 잘못 읽는 실패가 나왔다. 판독 실패와 과제 이해 실패가 섞여서 "틀렸다" 하나로 보이고 있었던 것이다.

## 판독을 코드로 대신 주면 어떻게 되나

개수 판독이 약하다면 그 부분만 코드로 해주면 된다. 시작 화면의 원소를 종류별로 세고, 가까이 붙은 것끼리 묶어서 글로 적어주는 클래스를 만들었다.

```python
class StartCount:
    """시작 화면 원소를 종류별로 세고, 붙은 것끼리 묶어 무리마다 개수·겹침·그림 속 위치(%)를 글로 적는다."""

    def __init__(self, ev):
        self.ev = ev
        f0 = ev.replay.frames[0]
        self.camera = camera_for(ev.replay.view_box, f0["elements"])
        self.items = []
        for e in f0["elements"]:
            box = extent_of(e)
            d = ev.describe(e) if box else None
            if d and d.get("on_screen") and d["kind"] not in SKIP_KIND and d.get("name"):
                self.items.append({"what": d["name"] + (f" {d['shape']}" if d.get("shape") else ""), "box": box,
                                   "at": (round(e["x"]), round(e["y"]))})
```

화면 밖에 있거나 글자·배경·슬롯·카드인 요소는 건너뛴다. 세려는 건 학생이 움직이는 조작 대상뿐이다.

무리를 어떻게 묶을지가 까다로웠다.

```python
    # 상자 사이 틈이 작은 변 절반 이하면 같은 무리 — 한 줄로 늘어놓은 막대는 떨어진 채로 남는다
    @staticmethod
    def near(a, b):
        gx = max(a["box"][0], b["box"][0]) - min(a["box"][2], b["box"][2])
        gy = max(a["box"][1], b["box"][1]) - min(a["box"][3], b["box"][3])
        side = min(min(i["box"][2] - i["box"][0], i["box"][3] - i["box"][1]) for i in (a, b))
        return max(gx, gy) <= side / 2
```

기준은 상자 사이 틈이 두 원소 중 짧은 변의 절반 이하인가다. 절대 거리를 쓰면 화면 크기나 원소 크기에 따라 기준이 흔들린다. 짧은 변 대비 비율로 잡으면 크기가 달라도 "붙어 있다"의 느낌이 유지된다. 주석에 적은 것처럼 한 줄로 쭉 늘어놓은 막대는 일부러 떨어진 채로 남긴다. 이걸 한 덩어리로 묶으면 개수 정보가 뭉개진다.

묶기 자체는 같은 종류 안에서 이웃을 따라가는 탐색이다.

```python
    def groups(self):
        by_kind = defaultdict(list)
        for it in self.items:
            by_kind[it["what"]].append(it)
        out = []
        for what, left in by_kind.items():
            while left:
                g, q = [], [left.pop()]
                while q:
                    cur = q.pop()
                    g.append(cur)
                    nb = [o for o in left if StartCount.near(cur, o)]
                    left = [o for o in left if o not in nb]
                    q += nb
                out.append((what, g))
        return out
```

그리고 같은 좌표에 겹쳐 있는 것도 따로 센다. 겹친 도형은 그림으로 보면 하나로 보이기 때문이다.

```python
    def text(self):
        rows = []
        for what, g in self.groups():
            stacks = defaultdict(int)
            for i in g:
                stacks[i["at"]] += 1
            piled = [n for n in stacks.values() if n > 1]
            note = ", 모두 한 자리에 겹쳐 있음" if piled == [len(g)] else (f", 그중 한 자리에 겹친 것 {'·'.join(f'{n}개' for n in piled)}" if piled else "")
            rows.append((sum(i["box"][1] for i in g) / len(g), sum(i["box"][0] for i in g) / len(g), f"- {what} {len(g)}개{note} ({self.where(g)})"))
        # 재생이 안 되는 기록은 첫 프레임이 최종 장면이라 「시작 화면」으로 적으면 틀린 말이 된다
        if not rows or not self.ev.replay.replayable:
            return ""
        return "\n".join(["<시작 화면 개수 — 코드 판독>"] + [r[2] for r in sorted(rows)])
```

마지막 분기는 실험 중에 발견해서 서비스 쪽 코드에 넣은 것이다. 재생이 안 되는 기록은 첫 프레임이 이미 최종 장면이라서, 그걸 "시작 화면 개수"라고 적으면 거짓 정보를 모델에 먹이게 된다. 그런 경우엔 빈 문자열을 돌려준다. 실험용 코드에는 이 분기가 없었다. 서비스 코드로 옮기면서 생긴 차이다.

## 내가 놓친 변수

여기서 실험 설계를 잘못 짰다. 비교 조건을 이렇게 구성했다.

```python
class CountDraft:
    """서비스 풀이 기준 입력 그대로(글+시작 화면 그림). count=True 면 시작 화면 개수 판독 글만 덧붙인다."""

    def build_input(self):
        self.sw.build_input()
        self.text = self.sw.text + ("\n" + StartCount(self.sw.ev).text() if self.count else "")
        return self.text
```

독스트링이 말하는 원칙은 맞다. 서비스와 같은 입력과 프롬프트를 기준으로 두고, 바꾸는 변수는 하나만 둔다. 그런데 초기에 돌린 비교는 이미지를 뺀 조건에 판독 글을 같이 넣은 조건이 섞여 있었다. 그러면 "이미지 없이도 된다"는 결과가 나와도 그게 이미지가 필요 없어서인지, 새로 추가한 판독 정보가 이미지를 대신해서인지 구분할 수 없다. 판독 글은 서비스에 원래 없던 정보다. 새 정보를 추가한 조건을 이미지 유무만의 효과로 읽으면 안 된다.

정리하면 비교해야 할 칸이 이렇게 갈린다. 기준(글+이미지), 이미지만 제거, 판독 글만 추가(이미지는 유지), 이미지 제거+판독 글 추가. 하나씩만 바꿔야 각 변경의 효과가 분리된다. 지금 코드의 `count` 플래그는 판독 글 추가 한 축만 담당하고, 이미지 유무는 `sw` 쪽 입력에서 따로 다룬다.

## 정답이 이름에 새고 있었다

평가 기준 생성 실험에서 또 하나 걸렸다. 모범답안 없이 AI가 정답 조건을 만들 수 있는지 보려면, 모델이 정답을 힌트로 볼 수 있는 경로가 없어야 한다. 그런데 비교용 데이터에서 파일·활동 이름에 정오답 표시가 붙어 있었다. 모델이 그 이름을 읽으면 풀지 않고도 답을 안다.

고친 방향은 이름을 중립 식별자로 바꾸고, 어느 것이 정답인지 적힌 대응표는 평가 쪽에만 두는 것이다. 모델 입력 경로에는 대응표가 아예 닿지 않게 했다. 이미지도 확인 대상이다. 화면 위에 정답 단서가 그대로 남아 있을 수 있어서, 이미지 안에 남은 표시도 점검 목록에 넣었다. 이 이미지 점검은 아직 전수로 끝내지 못했다.

## 평가와 서술을 한 프롬프트에 두지 않기

프롬프트 구조도 바꿨다. 한 번의 호출에서 "이 풀이가 맞는가"를 판정하게 하고 동시에 "학생이 어떻게 풀었는지"를 서술하게 하면, 판정 결과가 서술을 끌고 간다. 맞다고 판정하면 서술이 맞는 쪽으로 미화되고, 틀렸다고 판정하면 틀린 지점을 찾아 서술한다. 평가와 서술을 호출 단위로 나눴다. 서술은 판정 결과를 모르는 상태에서 쓰고, 평가는 그 서술과 정답 조건을 받아서 한다.

## 아직 남은 것

각 조건의 실제 정확도 수치는 이 글에 쓰지 않았다. 재정리가 끝나지 않았고, 조건 분리 전에 나온 숫자는 위에서 말한 이유로 해석할 수 없다. 변수를 분리한 4칸 비교를 다시 돌려야 한다. 이미지에 남은 정답 단서 점검도 마저 해야 한다.

그리고 하나 더 있다. 개수 판독 실패가 모델의 시각 능력 때문인지, 겹쳐 있는 도형처럼 그림 자체가 애매한 탓인지는 아직 못 갈랐다. 겹침 정보를 코드로 주는 방식이 이 부분을 가려버릴 수도 있어서, 그 점은 다음 실험에서 따로 봐야 한다.
