NestJS 쪽 코드를 처음 봤을 때 `PaginationDto`는 꽤 직관적으로 생겼다. `offset`, `limit` 두 필드, 응답엔 `count`와 `templates`. 그리고 모든 응답에 `status: "success"` 또는 `status: "fail"` 이 붙어 있었다.

FastAPI로 같은 엔드포인트를 새로 만들어야 했는데, 그대로 옮기는 게 맞는지 잘 모르겠었다.

## status 필드부터 정리했다

`status: "success"` 를 응답 바디에 넣는 패턴은 흔하다. HTTP가 이미 200을 줬는데 바디에 또 성공을 선언하는 건 중복이긴 하지만, 레거시 클라이언트들이 이걸 파싱하는 경우도 있어서 함부로 빼기 어렵다.

이번 케이스에서는 프론트와 BFF(Backend for Frontend) 모두 새로 작성 중이었다. `status` 필드를 받아 처리하는 기존 코드가 없는 상황. 그래서 빼기로 했다. 성공/실패는 HTTP 상태코드로, 실패 시에는 아래 구조로 내려보낸다.

```json
{
  "error_code": "TEMPLATE_QUERY_ERROR",
  "error_detail": "..."
}
```

`error_code`는 프론트에서 다국어 메시지로 매핑하거나 로깅 키로 쓸 수 있게 상수로 관리한다. `error_detail`은 개발 환경에서만 채우고 프로덕션에서는 비워두는 게 원래 의도였는데, 지금은 그냥 다 채우고 있다. 나중에 정리해야 할 부분.

## 응답 envelope 이름을 바꿨다

`count`와 `templates`를 `totalCount`와 `list`로 바꿨다. 이유는 단순하다. `count`가 뭘 세는 건지 애매했다. 현재 페이지에 있는 항목 수인지, 전체 개수인지. `totalCount`로 바꾸면 의미가 명확해진다.

`templates` → `list`는 도구 기준 조회 API에도, 랜덤 추천 API에도 같은 구조를 쓰게 하려는 의도였다. 엔드포인트마다 응답 키 이름이 달라지면 프론트 코드에 분기가 생긴다. `list`로 통일하면 응답 파싱 로직을 공유할 수 있다.

`totalCount`는 페이지네이션 이전 전체 개수로 정의했다. 즉 `limit`을 100으로 줘도 전체 템플릿이 276개면 `totalCount: 276`이 내려간다. 프론트에서 총 페이지 수를 계산하려면 이 값이 필요하다.

## offset 해석 방식

이게 약간 헷갈렸다. `offset`이라는 이름은 보통 SQL의 `OFFSET`처럼 행 번호 기반 오프셋을 뜻한다. 0을 주면 첫 번째 행부터, 10을 주면 11번째 행부터.

그런데 기존 NestJS 코드에서 `offset`의 기본값이 `1`이었다. 이건 페이지 번호다. 1-based 페이지 번호.

그래서 FastAPI 쪽에서도 같은 해석을 유지했다. 내부적으로는 `skip = (offset - 1) * limit`로 변환해서 쿼리에 넘긴다. 파라미터 이름은 `offset`으로 유지했는데, 이게 맞는 선택인지는 솔직히 확신이 없다. `page`라고 명명하는 게 더 직관적이었을 것 같기도 하다. 하지만 프론트가 이미 `offset`이라는 이름으로 요청을 만들고 있어서 바꾸지 않았다.

## 랜덤 정렬과 페이지네이션이 충돌한다

랜덤 템플릿 추천 API에 페이지네이션을 붙이면서 문제가 생겼다. 매 요청마다 랜덤으로 정렬하면 페이지 2를 요청했을 때 페이지 1과 겹치는 항목이 나올 수 있다. 사용자가 스크롤을 내리면서 같은 카드를 두 번 보게 된다.

seed 기반 랜덤 정렬을 쓰면 해결된다. 세션이나 요청마다 seed 값을 고정해두면, 같은 seed에서는 항상 같은 순서로 정렬되니 페이지 간 중복이 없다. 일부 DB에서는 `setseed()` 같은 함수로 이걸 지원한다.

다만 이번엔 seed 방식을 쓰지 않았다. 추천 특성상 매번 다른 결과를 보여주는 게 UX상 더 낫다는 판단이 있었고, 그보다는 한 번에 충분한 수를 내려보내는 방식으로 방향을 틀었다. `limit`을 크게 주면 클라이언트에서 페이지네이션을 흉내낼 수 있다.

이게 깔끔한 해결책은 아니다. 추후에 무한 스크롤 방식으로 UI가 바뀌거나, 추천 알고리즘이 복잡해지면 다시 설계해야 할 것 같다.
