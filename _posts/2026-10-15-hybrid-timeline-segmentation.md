학습 활동 로그로 AI 리포트를 만들다 보면 같은 질문이 계속 돌아온다. 이 줄은 코드가 읽어도 되는가, 아니면 AI가 읽어야 하는가.

처음엔 경계를 꽤 단순하게 그었다. 시간과 이벤트로 나눌 수 있는 건 전부 코드가 한다. 의미를 따져야 하는 것만 AI에게 준다.

## 구간 나누기는 코드가 한다

풀이 로그는 이벤트의 연속이다. 학생이 요소를 옮기고, 멈추고, 다시 옮기고, 답을 제출한다. 이걸 "구간"으로 자르는 데는 해석이 필요 없다. 이벤트 종류가 바뀌거나 일정 시간 공백이 생기면 자르면 된다. 같은 로그를 넣으면 같은 구간이 나온다. 면접에서 "이 구간은 왜 여기서 끊겼죠?"라는 질문을 받아도 규칙으로 답할 수 있다.

이 부분의 코드는 이 글에 싣지 않았다. 아래에서 인용하는 코드는 같은 원칙을 쓴 다른 모듈이라서, 분할 로직을 지어내서 보여 주고 싶지 않았다.

문제는 그다음이다. 구간이 나뉘었다고 그 구간이 무슨 시간이었는지 알 수 있는 건 아니다. 요소를 한참 만지작거린 구간이 "답을 향해 가는 중"인지 "이것저것 눌러 보는 중"인지는 이벤트 수만 봐서는 모른다. 이 지점부터 AI가 필요했다.

## 이름을 붙이지 않으려 했다

처음 설계에서는 구간 이름 생성을 아예 뺐다. 이름을 붙이는 순간 AI가 지어낸 말이 리포트에 사실처럼 들어가기 때문이다. 구간은 "3번 구간, 40초, 이동 12회" 같은 숫자로만 보여 주고, 해석은 읽는 사람 몫으로 두려 했다.

써 보니 그게 더 불친절했다. 리포트를 읽는 쪽은 숫자 나열에서 풀이 흐름을 복원하고 싶어 하지 않는다. 그래서 방향을 바꿨다. 의미 해석이 필요한 일부 구간에만 쉬운 표현의 이름을 자동으로 붙이고, 그 결과를 저장해 두고 재사용한다. 저장하는 이유는 같은 구간이 리포트를 열 때마다 다른 이름으로 나오면 안 되기 때문이다.

범위를 "일부 구간"으로 좁힌 것도 같은 이유다. 코드로 설명되는 구간까지 AI가 이름을 붙이면 판독 가능한 정보를 일부러 흐리는 셈이 된다.

## 시도와 진행은 여전히 헷갈린다

분류가 잘 되지 않는 쌍이 있다. "시도"(이것저것 해 보는 중)와 "진행"(풀이를 밀고 가는 중)이다. 정확도를 수치로 정리한 건 아직 없어서 여기에 숫자는 적지 않는다. 다만 구간 안의 이벤트만으로는 둘의 경계가 흐리다는 것은 확인했다.

그래서 두 가지를 하기로 했다.

- 이 분류 결과에는 AI 추정이라는 표시를 붙인다. 틀릴 수 있는 값을 확정처럼 보여 주지 않기 위해서다.
- 구간이 끝나는 시점의 장면 이미지를 AI 입력에 추가해 본다. 이벤트 숫자로는 안 보이는 "지금 화면이 어디까지 만들어졌나"를 이미지가 보충해 줄 수 있는지 보려는 실험이다. 이건 아직 돌려 보지 않았다.

## 같은 원칙을 다른 곳에서도 썼다

이 경계는 구간 분할에만 있는 게 아니다. 비슷한 일이 정답 평가 쪽에도 있었다.

모범답안과의 유사도로 채점하면, 모범답안과 모양이 다른 정당한 풀이가 감점된다. 그래서 유사도 대신 정답 조건을 충족했는지로 평가하는 방향을 잡았다. 그러면 평가 기준을 누가 만드느냐는 문제가 생긴다. 모범답안 없이 AI가 기준을 생성할 수 있는지를 실험하게 됐고, 이때 AI에게 줄 입력에서 코드가 먼저 읽을 수 있는 것이 시작 화면의 원소 개수였다.

화면에 막대가 몇 개 있는지 세는 일은 이미지 모델에게 맡기면 틀리기 쉽다. 반면 좌표와 크기로는 정확히 센다. 그래서 개수는 코드가 세서 글로 적어 주고, AI는 그 글을 읽고 정답 조건을 만들게 했다. 이 실험의 결과 수치는 이 글에 가져오지 않았다.

붙어 있는 원소를 한 무리로 묶는 판정부터 보자.

```python
# 상자 사이 틈이 작은 변 절반 이하면 같은 무리 — 한 줄로 늘어놓은 막대는 떨어진 채로 남는다
@staticmethod
def near(a, b):
    gx = max(a["box"][0], b["box"][0]) - min(a["box"][2], b["box"][2])
    gy = max(a["box"][1], b["box"][1]) - min(a["box"][3], b["box"][3])
    side = min(min(i["box"][2] - i["box"][0], i["box"][3] - i["box"][1]) for i in (a, b))
    return max(gx, gy) <= side / 2
```

임계값을 고정 픽셀로 두지 않고 두 상자 중 작은 변의 절반으로 잡았다. 화면 배율이 달라져도 기준이 따라가고, 일렬로 늘어놓은 막대는 서로 떨어진 개체로 남는다. 이 값 자체가 최적인지는 따로 검증하지 않았다. 지금은 "의도한 모양의 배치에서 의도대로 묶이는가"만 눈으로 확인한 상태다.

이 판정으로 묶은 무리를 `groups()`가 종류별 탐색(BFS)으로 모은 뒤, `text()`가 개수·겹침·위치(%)를 글로 적는다. 마지막 줄에 이 코드가 가장 많이 신경 쓴 부분이 있다.

```python
# 재생이 안 되는 기록은 첫 프레임이 최종 장면이라 「시작 화면」으로 적으면 틀린 말이 된다
if not rows or not self.ev.replay.replayable:
    return ""
return "\n".join(["<시작 화면 개수 — 코드 판독>"] + [r[2] for r in sorted(rows)])
```

코드가 읽은 결과를 AI에게 넘기면, AI는 그것을 사실로 믿는다. 그래서 코드가 틀린 말을 하는 쪽이 더 위험하다. 재생이 불가능한 기록은 첫 프레임이 이미 최종 장면이다. 그걸 "시작 화면 개수"라고 적어서 넘기면 AI는 풀이가 끝난 뒤의 화면을 출발점으로 오해한다. 그래서 확신이 없으면 아무것도 적지 않는다. 빈 문자열을 돌려주는 쪽을 택했다.

비교 실험의 변수 통제도 같은 모듈에 들어 있다.

```python
class CountDraft:
    """서비스 풀이 기준 입력 그대로(글+시작 화면 그림). count=True 면 시작 화면 개수 판독 글만 덧붙인다."""

    def build_input(self):
        self.sw.build_input()
        self.text = self.sw.text + ("\n" + StartCount(self.sw.ev).text() if self.count else "")
        return self.text
```

두 조건이 다른 건 개수 판독 글 한 덩어리뿐이다. 프롬프트, 모델, 이미지, 서비스에서 쓰는 입력 구성은 그대로 둔다. 개수 글을 넣었을 때 정답 조건이 달라졌다면 원인은 그 글 말고는 없다. 이미지를 빼고 비교하는 실험도 같은 식으로 짜야 하는데, 이미지만 빼고 다른 입력은 그대로 둬야 차이를 이미지 탓으로 돌릴 수 있다.

## 아직 정해지지 않은 것

평가와 서술을 한 프롬프트에 섞으면 AI가 서술을 매끄럽게 쓰려고 평가를 깎거나 부풀린다. 그래서 평가를 먼저 하고, 서술은 평가 결과를 받아서 쓰는 구조로 나눴다. 모범답안 없이 정답 기준을 만들게 할 때는 정답 라벨이 입력에 새어 들어가지 않는지도 신경 썼다. 라벨이 보이면 AI가 기준을 만든 게 아니라 베낀 게 되기 때문이다.

그런데 이 글의 처음 질문에는 아직 답이 없다. "시도"와 "진행"을 가르는 일을 끝까지 AI에게 맡길지, 구간 끝 장면 이미지를 넣어서 정확도가 얼마나 오르는지 본 뒤에 결정할지. 이미지를 넣는 실험을 먼저 돌려 보고, 그 결과로 AI 추정 표시를 계속 붙일지 판단하려 한다.
