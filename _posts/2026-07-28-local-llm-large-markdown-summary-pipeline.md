노트 앱에서 검색을 쳤는데 결과 목록이 이상하게 지저분해졌다. 클릭해보면 죄다 한 파일에서 뽑혀 나온 조각들이었다. 그 파일 하나가 16MB를 넘겨 있었다.

지우기는 아까웠다. 몇 달치 기록이 시간순으로 붙어 있는 원본이었으니까. 그렇다고 두면 그래프 뷰가 그 노드 하나 때문에 계속 무거워지고, 전문 검색은 노이즈로 도배됐다.

## 확장자 하나만 바꾸면 인덱스에서 빠진다

한참 헤맸다. 플러그인 설정에서 특정 파일 제외하기, 검색 필터 커스터마이즈, 별도 vault로 분리하기까지 봤는데 다 뭔가 어긋났다.

결론은 허무했다. 검색 대상은 `.md` 확장자로만 걸리게 되어 있었다. 파일을 `.txt` 로 이름만 바꾸면 그 순간 인덱스에서 사라진다. 원본은 그대로 남기고, 검색에서만 뺀다. 이거면 됐다.

문제는 그 다음이었다. `.txt` 로 밀어 넣으면 파일 자체를 이 앱에서 찾을 수가 없다. 나는 원본은 감추고 싶었지, 존재를 지우고 싶었던 게 아니었다.

## 요약본을 원본 자리에 세워둔다

그래서 방향을 뒤집었다. 원본은 `.txt` 로 내려서 인덱스에서 빼고, 대신 **로컬 LLM이 만든 요약본 `.md` 를 원본 경로를 미러링한 자리에 걸어둔다.**

```
data_parsed/note.md         →  data_parsed/note.txt              (검색 제외)
                            →  _summaries/data_parsed/note.md    (검색·그래프 노출)
```

이러면 그래프 뷰에는 요약본이 노드로 뜨고, 검색은 요약본에서 걸린다. 원본 위치가 궁금하면 요약본 frontmatter에 경로를 박아뒀으니 따라가면 된다.

## 16MB를 한 방에 넣을 수는 없다

Gemma(구글이 공개한 로컬 실행 대형 언어 모델) 로 요약을 돌리려는데, 파일 크기가 컨텍스트 윈도우를 한참 넘겼다. 통으로 넣으면 당연히 못 받는다.

`#`, `##`, `###` 헤더로 자른다. 섹션마다 개별 요약을 돌리고(map), 그 요약들을 다시 한 번 합쳐서 최종본을 만든다(reduce). 새로울 것 없는 고전적인 map-reduce인데, LLM 앞단에 붙이면 갑자기 실용적이 된다.

```bash
python3 gemma_processor.py summarize_large <file>
```

호출은 한 줄이지만 안에서는 헤더 파싱 → 청크 리스트 → 각 청크 요약 요청 → 최종 합산이 순서대로 흐른다.

## mtime을 믿었다가 두 번 당했다

파이프라인을 매일 돌리기 시작하니 문제가 생겼다. 안 바뀐 파일도 재요약을 도는 경우가 있었고, 반대로 바뀐 파일이 스킵되기도 했다.

원인은 `mtime` (파일 수정 시각) 이었다. rsync로 다른 머신에서 당겨오면 mtime이 원본을 따라가지 않는다. 반대로 git checkout으로 다른 브랜치에 갔다 오면 내용은 그대로인데 mtime이 갱신된다. mtime은 "파일이 실제로 바뀌었는가"에 대한 답이 아니었다.

내용의 SHA-256 해시로 바꿨다. 요약본 frontmatter에 원본의 해시를 박아두고, 다음 실행에서 현재 파일의 해시와 비교한다.

```yaml
---
original_hash: "a1b2c3..."
source_path: "data_parsed/note.md"
---
```

```python
current_hash = sha256(file.read_bytes()).hexdigest()
if summary_exists and summary_meta["original_hash"] == current_hash:
    skip()
```

내용이 정말 바뀐 파일만 다시 돈다. 로컬 GPU가 새벽에 놀지 않아도 된다.

## 아직 애매하게 남은 것

요약본이 검색 결과로 뜬 다음, 거기서 원본으로 넘어가는 동선이 매끄럽지 않다. 지금은 frontmatter의 `source_path` 를 눈으로 읽고 파일 매니저에서 여는데, 그 파일이 `.txt` 라 앱 밖에서 열린다. 링크로 걸어두면 확장자 때문에 인덱스에 다시 딸려 들어올 것 같아 아직 손을 못 댔다.

map-reduce의 reduce 단계도 아직 못 미더운 지점이 있다. 섹션 요약을 다시 요약하면 원본에서 두 다리 건너온 내용이라, 세부 수치나 고유명사가 뭉개진다. 검색용으로는 충분한데, "이 요약만 보고 원본을 안 읽어도 되는" 수준까지 가려면 reduce 프롬프트를 손봐야 한다. 다음 주에 볼 것.
