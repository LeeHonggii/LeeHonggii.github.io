목록 API에 페이지네이션을 붙이는 일은 처음엔 SQL 한 줄 문제처럼 보였다. `LIMIT :limit OFFSET :skip`만 달면 끝날 줄 알았다. 막상 해보니 바뀐 건 쿼리가 아니라 호출자와 맺은 약속이었다.

## 규격은 이미 다른 쪽에 있었다

같은 서비스의 TypeScript 쪽에 페이지네이션 DTO가 있었다. 새로 설계하지 않고 그 규격을 Python 요청 모델로 옮기기로 했다. 같은 시스템의 API끼리 페이징 규칙이 다르면 프런트가 두 벌을 알아야 하기 때문이다.

옮기면서 가장 먼저 걸린 건 `offset`이다. 이름은 SQL의 OFFSET 같지만 **행 위치가 아니라 1부터 시작하는 페이지 번호**다. 그래서 쿼리로 내려갈 때 변환이 한 번 필요하다.

```
skip = (offset - 1) * limit
```

`offset=0`이 들어오면 `skip`이 음수가 된다. 이 값을 그대로 SQL에 넘기면 DB 오류가 난다. 그래서 `offset=0`은 경계값 테스트 항목으로 따로 잡았다. 이름 때문에 0부터 시작한다고 착각한 호출자가 실제로 보낼 만한 값이다. `limit=301`처럼 상한 바로 위의 값도 같은 이유로 확인 대상에 넣었다.

## count와 totalCount는 다른 숫자다

응답 필드도 바뀌었다. 기존 `count`는 **이번 응답에 담긴 항목 수**였다. 새 `totalCount`는 **페이지로 자르기 전의 전체 항목 수**다.

```json
{ "totalCount": 100, "list": [] }
```

이름만 바꾸는 변경이면 호출자가 컴파일 오류나 undefined로 바로 알아챈다. 이번엔 숫자 의미가 달라졌다. 전체가 한 페이지에 다 담기던 시절에는 두 값이 우연히 같았다. 그래서 `count`를 "전체 개수"로 쓰던 호출자가 있다면 값이 틀려도 눈에 띄지 않을 수 있다. 필드명 변경과 의미 변경을 문서에 같이 적어야 하는 이유다. 아직 호출자를 전수 조사하지는 못했다.

## 기본값도 계약이다

전체 목록을 주던 API에 기본 `limit`을 넣으면, 파라미터를 하나도 안 보내던 기존 호출자는 **조용히 일부만** 받는다. 오류도 없고 200이 온다. 데이터만 모자란다.

페이지네이션 도입을 SQL 변경으로만 보면 이 지점을 놓친다. 새 파라미터는 선택이어도 그 기본값은 기존 호출의 결과를 바꾼다. 이번에는 호출자 쪽 수정과 문서 갱신을 같은 변경에 묶었다.

## status 필드를 없애고 HTTP 상태코드로

같은 변경에서 업무 API의 응답 `status` 필드를 제거했다. 성공과 실패를 본문에 담던 방식을 버리고 실패는 HTTP 상태코드로 표현한다.

여기서 구분할 게 하나 있다. FastAPI는 요청 검증에 실패하면 기본으로 422와 자체 형식의 본문을 돌려준다. 우리가 정의한 오류 본문과는 모양이 다르다. 호출자 입장에서는 "잘못된 `offset`"이 우리 형식으로 올지 FastAPI 기본 형식으로 올지에 따라 파싱 코드가 달라진다. 검증을 모델에 맡길지 직접 처리해서 같은 형식으로 맞출지 정해야 했다.

쿼리 파라미터를 요청 모델로 묶는 과정에서도 FastAPI가 그 모델을 쿼리로 인식하지 못하는 문제가 있었다. 이 건은 처리했지만 근본 원인을 끝까지 파고들지는 않았다. 그래서 여기에 원인을 적지 않는다.

## 랜덤 조회는 건드리지 않기로 했다

무작위 정렬 조회에도 페이지네이션을 붙일지 검토했다. 문제는 요청마다 순서가 새로 섞인다는 점이다. 1페이지와 2페이지가 서로 다른 순서에서 잘려 나오면 같은 항목이 두 페이지에 나오거나 어떤 항목은 영영 안 나온다.

시드를 고정하거나 정렬 키를 따로 두는 방법도 있다. 하지만 랜덤 조회의 용도가 "아무거나 몇 개"라면 페이징 자체가 필요 없다. 그래서 기존 무작위 정렬을 그대로 두기로 했다. 필요가 생기면 그때 다시 본다.

## 검증한 것과 못 한 것

SQL은 직접 실행해서 확인했다. 변경은 로컬 커밋까지 끝냈다.

하지만 직접 실행한 SQL이 맞다는 것과 앱의 SQLAlchemy가 `:limit`, `:skip`을 제대로 바인딩한다는 것은 별개다. 앞의 것만 확인했다. 앱을 띄워 실제 요청으로 DB까지 가보는 검증은 아직 하지 않았다. 원격 브랜치 반영도 남아 있다.

다음에 할 일은 앱을 띄워서 `offset=0`, 상한 초과 `limit`, 파라미터 없는 호출 세 가지를 실제 요청으로 보내는 것이다. 응답의 `totalCount`가 페이지를 넘겨도 같은 값인지도 같이 본다. 그 전까지는 이 변경을 "됐다"고 말하지 않는다.
