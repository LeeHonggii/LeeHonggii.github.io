## 슬라이드가 절반으로 줄어 돌아왔다

15페이지짜리 원고를 넘겼는데 7장이 왔다. "요약했습니다." 나머지 절반은 어디로 갔냐는 물음에 돌아오는 표준 답변이다.

보고서라면 고마운 습관이다. 발표자료에서는 아니다. 발표자료는 근거 데이터와 예시가 살아 있어야 하고, 청중은 그 세부를 보러 온다. 요약된 슬라이드는 발표자를 벌거벗긴다.

이걸 프롬프트로 막으려 한동안 애를 썼다. "요약하지 말 것"이라고 굵게 써놓아도, 원문이 조금만 길어지면 모델은 다시 압축을 시작한다. 결국 규칙을 도구 쪽으로 끌고 내려왔다.

## 왜 Marp였나

Markdown 하나에서 PPTX와 HTML을 동시에 뽑을 수 있어서다. 회의실에서는 PPTX가 필요하고, 공유 링크로는 HTML이 필요하다. 두 번 만들지 않아도 된다는 게 결정적이었다.

```bash
marp deck.md --pptx
marp deck.md --html
```

이전에는 PPTX를 완성한 뒤 "웹 버전"을 손으로 다시 짰다. 그 이중 노동을 없애는 게 첫 번째 목표였다.

## 산출물을 두 파일로 쪼갠 이유

한동안 `.md` 한 개로 다 처리했다. 편집도 하고 렌더도 하고. 그러다 원문에 손을 대는 일과 슬라이드 마크업에 손을 대는 일이 자꾸 섞였다. 원문에 문장 하나 고쳤을 뿐인데 Marp 지시어가 어긋나서 레이아웃이 망가지는 식이다.

지금은 이렇게 나눠 둔다.

```
_decks/<slug>/
├── source.md      # 사람이 쓰는 원문
├── deck.md        # 생성된 Marp 마크업
├── deck.pptx
├── index.html
└── theme.css
```

`source.md`는 문장만 있다. Marp 지시어도, 슬라이드 구분도 없다. `deck.md`는 생성기가 만들어내는 결과물이라 손으로 편집할 대상이 아니다. 이 경계가 없으면 원문 수정 한 번이 슬라이드 구조를 흔든다.

## 요약을 못 하게 만드는 규칙

가장 오래 붙잡고 있던 문제다. AI가 발표자료를 만들 때 내용이 새어 나가는 경로는 뻔하다. 원문 여러 단락을 슬라이드 한 장으로 뭉치는 순간이다. N:1로 합치는 그 자리에서 근거가 사라진다.

그래서 생성 로직에 이 방향만 허용해 두었다.

- 원문 단락 1개 → 슬라이드 1장
- 원문 단락 1개 → 슬라이드 여러 장 (넘치면 나눈다)

역방향, 그러니까 원문 여러 단락을 한 장으로 합치는 조작은 도구가 거부한다. 요약이 필요하면 원문 쪽에서 하고 다시 넣으라는 뜻이다.

생성이 끝나면 원문 토큰과 슬라이드 토큰을 대조한다. 커버리지가 눈에 띄게 떨어지면 경고를 낸다. 정확히 몇 퍼센트를 임계로 삼을지는 아직 손보는 중이다. 처음엔 80%로 잡았는데, 표나 코드 블록이 많은 원문에서 오탐이 났다. 토큰 단위 비교가 아니라 키워드 커버리지로 바꿔야 할 것 같다.

## 브랜드는 공통, 레이아웃은 HTML에서만

PPTX와 HTML은 근본이 다르다. 하나는 고정 픽셀 좌표계이고, 하나는 뷰포트에 따라 흐른다. 이걸 하나의 CSS로 억지로 맞추면 어느 쪽이든 이상해진다. PPTX에 맞추면 HTML이 답답하고, HTML에 맞추면 PPTX에서 요소가 밀린다.

두 층으로 나눴다.

- `theme.css` — 색, 폰트, 로고. PPTX·HTML 어디서 봐도 같아야 하는 것
- Marp 슬라이드 지시어 — HTML에서만 동작하는 Grid/Flexbox 규칙

```css
:root {
  --brand-primary: #1A56DB;
  --font-heading: "Pretendard", sans-serif;
}
```

슬라이드마다 `<!-- _class: layout-split -->` 같은 지시어를 붙이면 HTML 렌더러는 2단 그리드로 풀어주고, PPTX 렌더러는 이 클래스를 사실상 무시한다. HTML 쪽에서만 레이아웃이 풍부해지는 걸 받아들이는 편이 낫다는 결론이다. PPTX에서 그리드 흉내를 내려다 좌표가 어긋난 적이 몇 번 있었다.

## 아직 못 푼 것

몇 가지 남아 있다.

토큰 커버리지 임계값은 아직 감으로 잡고 있다. 원문에 코드 블록이 크게 들어가면 실제로는 잘 옮겨왔는데도 수치가 낮게 나온다. 코드·표·본문을 분리해서 각각 재는 쪽으로 바꿔야 한다.

레이아웃 지시어가 늘어나면서 `deck.md` 안에 주석이 두꺼워지고 있다. 이걸 별도 프론트매터로 뽑아낼지, 아니면 지금처럼 인라인으로 두는 게 나은지는 아직 못 정했다. 인라인은 슬라이드와 지시어가 붙어 있어 읽기 쉽지만, 원문에서 자동 생성하는 쪽에는 방해가 된다.

프롬프트로 규칙을 강제하려던 시절과 지금을 비교해 보면 확실히 나아지긴 했다. 다만 "도구가 막아준다"고 방심하는 순간이 새 실수의 자리가 되는 것 같아서, 커버리지 리포트를 사람이 매번 눈으로 훑는 습관은 당분간 안 없앨 생각이다.
