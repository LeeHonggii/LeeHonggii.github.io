기존 백엔드를 FastAPI로 옮기자는 얘기가 나왔을 때 제일 먼저 든 생각은 "이참에 구조도 싹 정리하자"였다. 이 생각을 접는 데 회의 한 번이 걸렸다.

이 글은 포팅을 끝낸 기록이 아니다. **포팅 완료는 아직 확인되지 않았다.** 착수 전에 범위를 어떻게 잘랐고 검증을 어떻게 하기로 했는지에 대한 학습 노트다. 코드는 싣지 않는다. 이 시점에 보여줄 만한 포팅 결과물이 아직 없고, 없는 코드를 지어내고 싶지도 않다.

## 범위부터 잘랐다

결정은 단순했다. 프론트엔드는 그대로 두고 백엔드만 바꾼다. 그리고 신규 기능 설계보다 기존 기능의 1:1 포팅을 먼저 한다.

언어 전환에 기능 개편이 섞이면 나중에 출력이 달라졌을 때 원인을 가를 수 없다. 포팅 과정에서 생긴 버그인지, 일부러 바꾼 동작인지 알 수 없게 된다. 그래서 "동작이 달라지면 일단 버그"라는 기준을 세웠다. 개선하고 싶은 지점이 보여도 목록에만 적어두고 손대지 않는다. 솔직히 이게 제일 참기 힘들었다.

## 층을 나눠서 대응시킨다

기존 코드를 Python 구조로 옮기기 위해 네 층으로 나눠 보기로 했다.

- 라우팅
- 요청·응답 모델
- 도메인 처리
- 스토리지 접근

FastAPI 쪽에서는 앱 조립을 `create_app()` 같은 팩토리 함수로 모으는 안을 검토했다. 요청·응답 모델은 pydantic의 `Field`에 example과 description을 달아 두면 스키마 문서가 곧 계약서 역할을 한다. 프론트를 건드리지 않으니 이 계약이 기존 응답과 정확히 같아야 한다. 필드 이름, null 처리, 정렬 순서까지 같아야 한다.

다만 이 대응표는 아직 검토안이다. 실제로 옮겨 보면 도메인 처리와 스토리지 접근이 기존 코드에서 한 함수에 엉켜 있는 곳이 나올 것 같다. 그때 어디까지 쪼개고 어디서 멈출지는 미정이다.

## 검증: 같은 입력, 출력 비교

검증은 골든 마스터(golden master) 방식을 제안했다. 기존 구현의 출력을 기준값으로 삼고, 같은 입력을 새 구현에 넣어 결과를 비교한다. 테스트를 새로 설계하는 대신 기존 시스템을 명세로 쓰는 셈이다. 기존 동작이 틀렸더라도 일단 똑같이 재현한다는 점이 이 방식의 불편한 부분이자 장점이다.

입력 집합을 어떻게 고를지는 아직 정하지 않았다. 실제 요청 기록에서 뽑을지 직접 만들지, 몇 건이면 충분한지도 정하지 못했다. 재 본 적이 없으니 숫자는 쓰지 않는다.

## 비교가 안 되는 것

브라우저 화면 캡처처럼 실행 환경에 의존하는 기능은 이 방식으로 비교하기 어렵다. 폰트, 렌더링 엔진, 헤드리스 브라우저 버전에 따라 바이트 단위로 달라질 수 있다. 이건 골든 마스터 대상에서 빼고 별도로 검토할 항목으로 분류해 두었다. 픽셀 비교로 갈지, 구조적 비교로 갈지, 아니면 사람 눈으로 확인할지는 열려 있다. 지금은 답이 없다.

다음에 할 일은 기존 API 목록을 네 층에 맞춰 표로 채우는 것이다. 표를 채우다 보면 화면 캡처 말고도 비교하기 어려운 기능이 더 나올 것 같다.
