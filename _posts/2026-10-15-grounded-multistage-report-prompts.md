학습 활동 기록을 읽고 학생의 풀이를 해석해 주는 AI 리포트를 맡고 있다. 처음 만든 버전에서 걸린 문제는 이렇다. 같은 기록을 넣어도 리포트 문장에 따라 "이 학생은 맞혔다"와 "거의 맞혔다"가 오갔다. 서술을 잘 쓰라고 시킨 모델이 서술하는 김에 채점까지 다시 하고 있었다.

문장을 다듬는 일과 맞고 틀림을 정하는 일은 한 호출에 섞이면 안 된다. 이 글은 그 둘을 떼어낸 구조를 정리한 학습 노트다.

## 한 호출이 하던 일을 다섯 칸으로 나눴다

기존 구조에서 책임이 이렇게 갈린다는 것을 코드와 프롬프트를 읽으며 확인했다.

1. 문제 정의: 이 문제가 무엇을 요구하는지
2. 답안 판정: 학생 답이 정답 조건을 채웠는지
3. 로그 문장화: 풀이 기록을 사람이 읽는 문장으로
4. 평가: 판정과 문장화된 근거를 묶어 평가 항목으로
5. 최종 서술: 평가 결과를 학생·교사용 글로

규칙은 하나다. **5단계는 재판정하지 않는다.** 서술 단계 프롬프트에는 "평가 결과를 그대로 옮겨라"는 방향만 있고, 정답 여부를 다시 따질 여지를 주지 않는다. 앞 단계에서 정해진 결론이 뒤 단계에서 뒤집히려면 뒤 단계가 판단 권한을 가져야 하는데, 애초에 그 권한을 빼 버린 것이다.

평가 단계에는 규칙이 두 개 더 있다. 코드로 확정한 사실은 LLM 평가보다 우선 적용한다. 근거는 제공된 항목 중에서만 고르게 한다. 모델이 근거를 새로 지어내는 길을 막는 장치다.

## "코드로 확정한 사실"의 한 예: 시작 화면 개수

코드로 확정하는 쪽이 실제로 어떻게 생겼는지 보여 주는 부분이 있다. 학생이 처음 마주한 화면에 도형이 몇 개, 어디에, 겹쳐서 놓여 있었는지를 세는 모듈이다. 이미지를 모델에 주고 "몇 개로 보이냐"고 물으면 겹쳐 있는 것을 하나로 세거나 한 줄로 늘어놓은 막대를 뭉뚱그리는 일이 생긴다. 그래서 기록 데이터의 첫 프레임에서 원소를 직접 읽어 센다.

```python
class StartCount:
    """시작 화면 원소를 종류별로 세고, 붙은 것끼리 묶어 무리마다 개수·겹침·그림 속 위치(%)를 글로 적는다."""

    def __init__(self, ev):
        self.ev = ev
        f0 = ev.replay.frames[0]
        self.camera = camera_for(ev.replay.view_box, f0["elements"])
        self.items = []
        for e in f0["elements"]:
            box = extent_of(e)
            d = ev.describe(e) if box else None
            if d and d.get("on_screen") and d["kind"] not in SKIP_KIND and d.get("name"):
                self.items.append({"what": d["name"] + (f" {d['shape']}" if d.get("shape") else ""), "box": box,
                                   "at": (round(e["x"]), round(e["y"]))})
```

`SKIP_KIND`는 글자·배경·칸·카드를 제외한다. 이것들은 학생이 조작한 대상이 아니라 화면 장식이어서 세면 오히려 노이즈가 된다. `on_screen` 검사로 화면 밖에 나가 있는 원소도 뺀다. 이름이 없는 원소는 라벨을 붙일 수 없으니 버린다. 센다는 행위 이전에 무엇을 셀지를 정하는 코드가 의외로 많다.

다음은 "가까이 붙은 것끼리 묶기"다.

```python
    # 상자 사이 틈이 작은 변 절반 이하면 같은 무리 — 한 줄로 늘어놓은 막대는 떨어진 채로 남는다
    @staticmethod
    def near(a, b):
        gx = max(a["box"][0], b["box"][0]) - min(a["box"][2], b["box"][2])
        gy = max(a["box"][1], b["box"][1]) - min(a["box"][3], b["box"][3])
        side = min(min(i["box"][2] - i["box"][0], i["box"][3] - i["box"][1]) for i in (a, b))
        return max(gx, gy) <= side / 2

    def groups(self):
        by_kind = defaultdict(list)
        for it in self.items:
            by_kind[it["what"]].append(it)
        out = []
        for what, left in by_kind.items():
            while left:
                g, q = [], [left.pop()]
                while q:
                    cur = q.pop()
                    g.append(cur)
                    nb = [o for o in left if StartCount.near(cur, o)]
                    left = [o for o in left if o not in nb]
                    q += nb
                out.append((what, g))
        return out
```

상자 사이 틈이 둘 중 작은 변의 절반 이하면 같은 무리로 본다. 기준을 두 상자의 짧은 변으로 잡은 이유는 주석에 적어 둔 그대로다. 막대를 한 줄로 쭉 늘어놓았을 때 떨어진 채로 남아야 "막대 10개가 따로 놓여 있다"가 되고, 붙여 놓았을 때는 "한 무리"가 된다. 고정 픽셀 거리를 쓰면 확대·축소에 따라 이 구분이 깨진다. 묶기는 종류별로 따로 하고, 같은 무리 안에서는 BFS(너비 우선 탐색)로 이웃의 이웃까지 따라간다. A–B가 붙고 B–C가 붙으면 A와 C가 멀어도 한 무리다.

마지막은 이것을 모델이 읽을 글로 바꾸는 부분이다.

```python
    def text(self):
        rows = []
        for what, g in self.groups():
            stacks = defaultdict(int)
            for i in g:
                stacks[i["at"]] += 1
            piled = [n for n in stacks.values() if n > 1]
            note = ", 모두 한 자리에 겹쳐 있음" if piled == [len(g)] else (f", 그중 한 자리에 겹친 것 {'·'.join(f'{n}개' for n in piled)}" if piled else "")
            rows.append((sum(i["box"][1] for i in g) / len(g), sum(i["box"][0] for i in g) / len(g), f"- {what} {len(g)}개{note} ({self.where(g)})"))
        # 재생이 안 되는 기록은 첫 프레임이 최종 장면이라 「시작 화면」으로 적으면 틀린 말이 된다
        if not rows or not self.ev.replay.replayable:
            return ""
        return "\n".join(["<시작 화면 개수 — 코드 판독>"] + [r[2] for r in sorted(rows)])
```

겹침은 같은 좌표 `(x, y)`에 몇 개가 쌓여 있는지로 판정한다. 무리 전체가 한 자리면 "모두 한 자리에 겹쳐 있음", 일부만 쌓였으면 쌓인 개수를 따로 적는다. 그림으로만 보면 겹친 도형은 하나로 보이는데, 이 학습 활동에서는 몇 개가 숨어 있었는지가 핵심 정보일 때가 있다. 출력 줄은 위에서 아래, 왼쪽에서 오른쪽으로 정렬한다. 모델이 이미지의 배치와 글의 순서를 맞춰 읽게 하려는 의도다.

## 비어 있으면 아예 빼 버린다

이 모듈에서 가장 나중에 들어온 코드는 맨 아래 가드(guard) 두 줄이다. 처음 프로토타입 버전에는 없었다. 서비스 쪽으로 옮기면서 붙었다.

재생이 안 되는 기록은 첫 프레임이 곧 최종 장면이다. 그걸 `<시작 화면 개수>`라는 제목으로 모델에 주면 거짓 정보가 된다. 모델은 제목을 믿고 "처음에 이만큼 있었다"고 해석할 것이다. 그래서 이 경우 빈 문자열을 돌려주고, 호출하는 쪽에서는 빈 문자열이면 그 블록 자체를 프롬프트에 넣지 않는다.

같은 원리를 근거 목록에도 적용했다. "아래 근거 중에서 고르라"는 지시가 있는데 목록이 비어 있으면, 모델은 고를 것이 없다는 사실을 말하는 대신 뭔가를 만들어 낸다. 빈 근거 블록은 헤더째 생략한다. 지시문과 데이터가 함께 사라지니 모델 입장에서는 그런 선택지가 애초에 존재하지 않는다.

## 프롬프트 순서

정적인 자료, 즉 규칙·형식·평가 기준은 프롬프트 앞쪽에 둔다. 기록마다 달라지는 데이터는 뒤로 보낸다. 앞부분이 호출마다 같으면 프롬프트 캐시(앞부분 토큰을 재사용해 비용과 지연을 줄이는 기능)를 쓸 수 있기 때문이다. 다만 실제로 캐시 적중률이 얼마나 나오는지는 재 보지 않았다. 지금은 캐시를 "고려한 배치"까지만 말할 수 있다.

## 실험에서 부딪힌 것들

이 구조를 검토하면서 몇 가지 실험을 했다. 결과를 숫자로 적을 만큼 정리된 것은 없어서 확인한 방향만 적는다.

- **모범답안과의 유사도 대신 정답 조건 충족도로 평가한다.** 풀이 방식이 다양한 문제에서 모범답안과 문장이 비슷한지를 보면 다른 길로 맞힌 학생이 손해를 본다. 그래서 "정답이 되려면 무엇을 만족해야 하는가"를 조건으로 두고 충족 여부를 본다.
- **모범답안 없이 AI가 평가 기준을 만들 수 있는지** 실험했다. 이때 정답 라벨이 입력에 새어 들어가면 기준 생성이 사실상 답을 베끼는 일이 되므로, 라벨이 들어가지 않게 입력을 통제해야 했다.
- **이미지를 뺀 비교 실험**에서는 이미지만 변수여야 하는데, 이미지 유무에 따라 텍스트 입력까지 달라지면 비교가 성립하지 않는다. 변수 통제가 생각보다 어려웠다.
- **풀이 구간 중 일부는 AI가 의미를 분류하게 했는데 정확도에 한계가 있었다.** 구간을 나누는 일은 코드가 하고 의미를 붙이는 일만 모델이 한다. 그래도 분류가 틀리는 경우가 있었다. 정확도 수치는 이 글에 쓸 만큼 정리하지 못했다.

## 아직 남은 것

분류가 틀릴 때 그 오류가 평가 단계로 흘러가는 문제가 남아 있다. 서술 단계가 재판정하지 않는다는 규칙은 지켰지만, 앞 단계가 틀린 판정을 내놓으면 뒤 단계는 그것을 충실히 옮긴다. 일관성은 얻었으나 정확성은 앞 단계 몫이다. 분류 오류를 평가 단계에서 어떻게 걸러낼지는 아직 정하지 못했다.
