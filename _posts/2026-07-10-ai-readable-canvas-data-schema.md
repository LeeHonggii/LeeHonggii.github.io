교육용 캔버스 제품에 AI 피드백을 붙여달라는 요청을 받았을 때, 나는 그게 프롬프트 튜닝 문제라고 착각했다. 캔버스에는 이미 상호작용 로그가 쌓이고 있었으니까. 그걸 LLM(Large Language Model, 대규모 언어 모델)에 잘 넣기만 하면 되는 줄 알았다.

로그를 열어봤다.

```
오브젝트 734가 (120, 80) → (620, 80)으로 이동
오브젝트 891이 (200, 300) → (200, 300)으로 이동 (변화 없음)
```

이걸 그대로 프롬프트에 붙여봤다. 모델은 아무 말도 못 했다. 정확히는, 아무 말이나 했다. "학생이 오브젝트를 오른쪽으로 옮겼습니다"까지가 한계였다. 그게 맞았는지 틀렸는지, 왜 옮겼는지, 다음에 뭘 힌트로 줘야 하는지 — 하나도 안 나왔다.

## 로그가 아니라 언어를 넘겨야 한다

문제를 반대로 봐야 했다. LLM은 좌표를 못 읽는 게 아니다. **좌표에 의미가 없는 것이다.** 오브젝트 734가 500px 이동했다는 사실에서 사람도 아무 판단을 못 한다. 그 오브젝트가 삼각형인지 숫자 카드인지, 옮겨간 자리가 정답 자리인지, 교사가 원래 어떤 의도로 문제를 만들었는지 — 좌표 어디에도 안 들어 있다.

렌더러가 화면을 다시 그리는 데는 이 로그가 완벽하다. undo/redo 만드는 데도 충분하다. 그런데 그건 기계가 기계에게 하는 말이다. LLM한테는 **사람이 사람에게 설명할 때 쓰는 언어의 조각**이 필요했다.

그래서 접근을 뒤집었다. 캔버스 오브젝트가 만들어질 때부터 자기가 뭔지, 뭘 위해 존재하는지를 함께 들고 있게 했다.

```json
{
  "object_id": "734",
  "type": "shape",
  "class": "triangle",
  "label": "노란 삼각형",
  "intent": "학생이 정답 위치로 이동",
  "answerLayer": {
    "correct_zone": "drop-zone-B",
    "is_correct": true
  },
  "teacherGuide": "삼각형은 꼭짓점이 위를 향해야 정답"
}
```

`(120, 80)` 대신 `노란 삼각형`, `→ (620, 80)` 대신 `drop-zone-B`. AI에 넘기는 이벤트는 이렇게 바뀐다.

```
[이동] 노란 삼각형(class=triangle) → drop-zone-B
[판단] answerLayer.is_correct = true
[해설] teacherGuide: "삼각형은 꼭짓점이 위를 향해야 정답"
```

좌표가 통째로 사라졌는데 모델은 훨씬 많이 이해한다. 이 로그를 받은 LLM은 "학생이 삼각형을 올바른 자리에 놓았고, 교사 가이드 기준으로 방향까지 맞았다"까지 한 번에 짚는다. 프롬프트를 정교하게 다듬어서 얻은 게 아니라, 데이터 스키마가 이미 그 말을 하고 있어서 모델이 옮겨 적기만 하면 되는 상태다.

## 그럼 비전 모델은?

여기까지 오면 자연스럽게 나오는 반론이 있다. "화면을 그대로 캡처해서 비전 모델(Vision AI, 이미지·영상 멀티모달 모델)에 던지면 되지 않나?" 실제로 팀 내에서도 이 얘기가 먼저 나왔다.

시도는 해볼 만하다. 색이 이상하게 겹쳤다거나, 오브젝트가 캔버스 밖으로 튀어나갔다거나, 레이아웃이 어색한 것 — 이런 건 이미지가 제일 잘 잡는다. 그런데 채점과 피드백의 본체는 시각적으로 안 보이는 데 있다. **정답 조건**은 픽셀에 안 적혀 있다. **교사가 이 문제를 왜 냈는지**도 픽셀에 없다. 삼각형이 drop-zone-B 위에 있다는 걸 이미지에서 읽어내도, 그 zone이 정답 zone인지는 캔버스 데이터 없이는 알 수 없다.

내 결론은 이랬다. 비전은 시각 이상 감지 같은 보조 역할에 두고, 판정과 설명은 구조화된 캔버스 데이터가 담당한다. 둘 다 쓰되 각자 잘하는 것만 시킨다.

## 아직 안 정리된 것

지금 정리된 스키마는 도형·드롭존 같은 **판정 가능한 오브젝트** 기준으로 짜여 있다. 학생이 자유 낙서로 뭔가를 그리거나, 정답이 하나가 아닌 오픈형 문제 — 이런 경우엔 `answerLayer.is_correct` 자체가 성립하지 않는다. 이 부분은 아직 스키마가 없다. 아마 판정 대신 "관찰 요약"쯤 되는 다른 필드를 새로 파야 할 것 같은데, 어떤 모양이어야 할지는 아직 못 정했다.

프롬프트 엔지니어링으로 시작한 프로젝트가 결국 데이터 모델링 프로젝트가 됐다. 다음 오브젝트 타입을 붙일 때가 이 스키마의 진짜 시험대일 것 같다.
