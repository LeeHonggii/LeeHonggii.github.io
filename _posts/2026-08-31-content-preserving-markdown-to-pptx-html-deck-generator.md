발표자료를 자동으로 만들어달라고 AI에 맡긴 경험이 있다면 아마 한 번쯤 이런 일을 겪었을 거다. 원문엔 분명히 있던 내용이 슬라이드에서 사라진다. 요약하면서 "이 부분은 덜 중요하다"고 판단해서 쳐낸 거다. 그 판단이 틀렸는지 옳았는지는 발표하는 사람이 스스로 알 텐데, AI는 그냥 결정해버린다.

문제의 핵심은 *요약*이다. 프레젠테이션 생성을 요약 과제로 풀면 내용 누락이 구조적으로 발생한다. 내가 원한 건 달랐다. 원문의 내용을 하나도 버리지 않고 슬라이드라는 그릇에 *재배치*하는 것. 요약이 아니라 분할.

---

처음 설계를 잡을 때 원칙을 하나 먼저 정했다.

> 슬라이드 생성기는 Markdown 섹션을 병합하거나 삭제해서는 안 된다. 1:1 또는 1:N 분할만 허용한다.

`##` 제목 하나가 슬라이드 하나가 되거나, 내용이 길면 여러 슬라이드로 쪼개진다. 거꾸로 여러 섹션이 하나로 합쳐지는 건 금지다. 이 규칙 하나만으로 "내용이 어디 갔지?"를 거의 없앨 수 있었다.

실제로 동작하는 형태로 만들기까지 걸리는 시간보다, 이 규칙을 위반하는 엣지 케이스를 발견하고 막는 데 더 많은 시간이 들었다. 특히 중첩 목록이 깊을 때, 코드 블록 안에 `##`처럼 보이는 문자열이 있을 때. 파서가 구조를 잘못 인식하면 조용히 섹션 하나가 사라졌다.

---

두 번째 결정은 출력 형식이었다. PPTX와 HTML을 같은 소스에서 만든다.

PPTX는 공식 자리에서 열리는 파일이다. 회사 로고가 들어가고, 폰트가 브랜드 가이드를 따라야 한다. HTML은 공유 링크로 보내거나 모바일에서 보는 용도다. 반응형이어야 하고 빠르게 열려야 한다.

두 포맷의 요구사항이 다르다 보니, 처음엔 렌더러를 각각 따로 두려고 했다. 그런데 그러면 소스가 달라지는 시점이 반드시 온다. PPTX를 고쳤는데 HTML은 옛날 버전인 상황. 관리 포인트가 둘로 쪼개지는 건 싫었다.

대신 소스는 하나로 고정하고, 브랜드 디자인 시스템과 레이아웃 템플릿을 레이어로 분리했다.

- **디자인 시스템**: 색상, 폰트, 간격. 스타일 이름으로 전달한다. 예를 들어 `--style claude`를 주면 해당 팔레트가 두 포맷에 동시 적용된다.
- **레이아웃 템플릿**: 슬라이드별 레이아웃. `hero`, `code-focus`, `two-column` 같은 이름으로 지정한다.

레이아웃은 슬라이드 인덱스에 매핑한다.

```
--per-slide-layouts '{"0":"hero","1":"code-focus"}'
```

0번 슬라이드는 hero 레이아웃(제목만 크게), 1번은 코드가 강조되는 레이아웃. 명시하지 않은 슬라이드는 기본 레이아웃을 쓴다.

PPTX는 python-pptx가 이 레이아웃 정보를 받아서 슬라이드를 채운다. HTML은 Marp(Markdown 기반 슬라이드 프레임워크)를 쓰는데, 각 섹션 앞에 `<!-- _class: hero -->` 같은 지시자를 심어서 같은 레이아웃 이름이 CSS 클래스로 연결된다.

```
python3 make_deck.py --md notes/draft.md --style claude --mode both --vault /path/to/vault
```

`--mode both`를 주면 같은 실행에서 `.pptx`와 `.html` 둘 다 나온다. `--vault`는 Markdown 파일이 있는 루트 경로다. 파일 안에서 상대 경로로 이미지를 참조하면 여기서 찾는다.

---

실제로 써보니 예상과 다른 점이 있었다.

레이아웃을 미리 지정하지 않으면 내용의 성격을 파악해서 자동으로 고르는 기능을 붙이고 싶었다. 코드 블록이 많으면 `code-focus`, 이미지가 있으면 `image-right` 같은 식으로. 구현은 어렵지 않다. 그런데 막상 넣어보니 틀리는 경우가 생각보다 잦았다. 코드는 있는데 설명이 본체인 슬라이드에 `code-focus`를 붙이면 오히려 이상해진다.

지금은 자동 추론 기능을 비활성화 상태로 뒀다. 정확도를 더 올릴 방법을 아직 못 찾았다.

또 하나. HTML 쪽에서 모바일 폰트 크기가 문제다. Marp는 기본적으로 16:9 고정 비율로 렌더링하는데, 이걸 반응형으로 만들려면 CSS를 꽤 많이 덮어써야 한다. 지금 구현은 뷰포트 너비에 따라 `font-size`를 `vw` 단위로 바꾸는 방식인데, 기기마다 결과가 조금씩 다르다. 테스트를 충분히 못 했다.

PPTX와 HTML이 같은 소스에서 나오는 건 만족스럽다. 내용 불일치 문제는 실제로 없어졌다. 하지만 두 포맷이 *같아 보이는*지는 별개 문제다. 폰트 렌더링 방식이 달라서 같은 스타일 이름을 써도 시각적으로 완전히 동일하게 만드는 건 불가능에 가깝다. 어느 선까지 맞추는 게 적절한지는 아직 결론을 못 냈다.
