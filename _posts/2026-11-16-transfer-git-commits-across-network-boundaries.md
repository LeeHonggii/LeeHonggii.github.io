테이블 이름이 바뀐 뒤에도 JOIN 몇 군데가 옛 이름을 참조하고 있었다. 그걸 고치고 실제 DB에 쿼리를 날려 확인하는 데까지는 순조로웠다. 문제는 그 커밋을 개발 브랜치에 올리는 일이었다.

## 두 개의 망

작업 환경이 둘로 나뉘어 있다. 코드를 짜는 외부망에는 로컬 저장소가 있고, 원격 저장소는 내부망에만 있다. 외부망에서 내부망 원격으로 직접 push할 수 없으니 커밋을 파일로 만들어 옮긴 뒤 내부망에서 반영해야 한다.

처음엔 "외부 원격에 먼저 push하고 거기서 가져가야 하나" 싶었다. 그럴 필요가 없었다. `git format-patch`는 로컬 커밋만 있으면 만들어진다. 원격에 올라갔는지는 상관없다.

```bash
git format-patch <base>..<end>
```

범위의 앞이 기준점이고 뒤가 마지막 커밋이다. 커밋 하나당 `.patch` 파일이 하나 나온다. 작성자와 메시지가 파일에 들어 있어서 내부망에서 적용해도 이력이 그대로 남는다. 이 파일을 내부망으로 옮겼다.

## 어디에 붙었나

내부망에서는 이렇게 적용했다.

```bash
git am test.patch
```

오류 없이 붙었다. 그런데 이게 함정이었다. `git am`은 지금 체크아웃된 브랜치에 커밋을 쌓는다. 어느 브랜치인지 묻지도 않고 알려주지도 않는다. 그리고 내가 있던 브랜치는 `develop`이 아니라 `main`이었다. 패치는 정상적으로, 엉뚱한 곳에 붙었다.

패치를 적용하기 전에 `git branch`를 한 번 봤어야 했다. 이제는 그렇게 한다.

## develop이 없다

`main`에 붙은 커밋을 `develop`으로 보내려고 push했다.

```bash
git push origin develop
```

`src refspec develop does not match any` 계열의 오류가 났다. 이 메시지는 원격이 아니라 로컬 얘기다. "push할 `develop`이라는 로컬 브랜치가 없다"는 뜻이다. 내부망 저장소에는 `origin/develop`(원격 추적 브랜치)만 있고, 그걸 따라가는 로컬 `develop`은 한 번도 만든 적이 없었다.

로컬 브랜치부터 만들었다. 기존 `origin/develop`을 추적하도록 해서, 원격의 현재 상태에서 출발하게 했다.

```bash
git checkout -b develop origin/develop
git cherry-pick main
```

`cherry-pick main`은 `main`의 맨 끝 커밋 하나를 가져온다. 이번엔 패치가 커밋 하나였기 때문에 이 한 줄로 충분했다. 여러 개였다면 범위로 지정했어야 한다. 잘못 붙은 `main` 쪽 커밋은 원격에 올린 게 아니라서 건드리지 않았다. 다만 내부망 로컬 `main`이 원격보다 앞서 있는 상태로 남았으니 정리는 해야 한다.

## 브랜치와 상관없는 500

다시 `git push origin develop`을 했는데 이번엔 다른 오류가 나왔다. `pre-receive` 훅에서 내부 API가 500을 돌려줬다는 내용이었다. pre-receive는 서버가 push를 받기 직전에 도는 검사 단계다. 브랜치 문제는 이미 해결됐으니 이건 별개의 문제였다.

원인을 파헤칠 만한 단서가 없었다. 그냥 같은 push를 한 번 더 했고 이번엔 들어갔다. 서버 쪽 일시 장애로 보이지만 확인한 건 아니다. 훅이 호출하는 내부 API의 로그는 내가 볼 수 없는 위치에 있다. 같은 증상이 반복되면 서버 담당자에게 시각과 함께 물어볼 생각이다.

## 아직 남은 것

같은 날 Python API 쪽도 손댔다. 페이지네이션과 HTTP 상태코드 기반 오류 응답을 넣었고, FastAPI 쿼리 모델이 일부 파라미터를 인식하지 못하는 문제도 고쳤다. 랜덤 조회는 시드 고정을 시도했다가 매 요청 랜덤으로 동작하게 하고 응답 형식을 통일하는 쪽으로 정했다. 이 변경은 로컬 커밋까지만 했다. 앱을 띄워서 실제로 도는지 보지 못했고, 원격에도 올리지 않았다.

그러니 이 커밋은 다음 패치로 또 같은 길을 가야 한다. 이번엔 `git am` 전에 브랜치를 확인하고, `develop`을 먼저 만들어 둔 상태에서 시작할 것이다. 내부망의 `main`에 잘못 얹힌 커밋을 어떻게 정리할지는 아직 정하지 못했다.
