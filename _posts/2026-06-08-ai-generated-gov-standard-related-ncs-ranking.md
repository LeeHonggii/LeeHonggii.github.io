## 4자리 안에 너무 많이 몰려 있었다

직무 역량 콘텐츠를 추천할 때 처음 잡은 규칙은 단순했다. NCS(국가직무능력표준, 직무를 6자리 코드로 분류하는 체계) 코드가 같으면 유사, 앞 4자리(중분류)까지 같으면 같은 분야. 그 이하는 대분류로만 걸치면 약하게 연결.

```python
def sim_ncs_legacy(a: str, b: str) -> float:
    if a[:6] == b[:6]: return 1.0
    if a[:4] == b[:4]: return 0.7
    if a[:2] == b[:2]: return 0.4
    return 0.0
```

돌려보면 대부분의 후보가 0.7 구간에 뭉쳐 있었다. 같은 중분류라는 이유 하나로 서로 크게 상관없는 직무들이 동일한 점수를 받았다. 반대로 중분류가 다르지만 실무에서 함께 배우는 직무 — 데이터 분석과 머신러닝처럼 — 는 0.0으로 떨어졌다. 점수의 스케일은 있는데 의미의 스케일이 없었다.

prefix 매칭은 코드 표기법에 의존한 유사도지 실무 관계의 유사도가 아니었다. 여기까지가 출발점이다.

## "보완 직무"라는 신호를 어디서 얻을까

가장 먼저 든 생각은 사람이 만든 매핑 테이블을 하나 두는 거였는데, 소분류 단위로 수백 개를 손으로 이어붙일 자신이 없었다. 그래서 LLM(Large Language Model, 대규모 언어 모델)에게 각 소분류별로 "실무에서 함께 필요한 보완 직무"를 물어 초안을 뽑기로 했다.

여기서 한 가지 판단을 먼저 못박았다. **보완관계 후보를 전체 코드 공간에서 뽑을지, 같은 4자리 안에서만 뽑을지.**

전체 공간에서 뽑아본 결과는 지나치게 넓었다. IT 개발 직무의 보완으로 마케팅 분석이 들어오는 식이라, 개별 관계는 그럴듯한데 추천 신호로 쓰기엔 노이즈가 강했다. 반면 같은 4자리 안에서만 뽑으면 "이미 0.7점을 받고 있는 큰 덩어리 안에서, 그중 더 붙어 있는 것"을 골라내는 성격이 된다. 이쪽이 기존 규칙 체계와 위계가 맞았다.

관계 사전은 이렇게 저장했다. JSON 하나에 소분류 → 보완 소분류 리스트.

```json
{
  "020101": ["020102", "020103"],
  "020102": ["020101", "020104"]
}
```

## 원본은 건드리지 않는다

콘텐츠 테이블의 `ncs_code`는 원본 그대로 두고, LLM이 만든 결과는 `related_ncs`라는 별도 메타 필드로 분리했다.

```
content.ncs_code    = "020101"          # 원본
content.related_ncs = ["020102", ...]   # AI 생성, 별도 메타
```

이 분리를 고집한 이유는 두 가지였다. 하나는 원본 분류 체계에 AI 결과가 섞이면 나중에 어디까지가 사람이 정한 것이고 어디부터가 LLM이 만든 것인지 구분이 안 된다는 것. 다른 하나는 관계 사전 자체를 버전 교체하거나 특정 코드만 수기로 덮어쓸 여지를 남기고 싶었다는 것. 원본과 파생을 붙여놓으면 이 두 가지가 다 어려워진다.

## 위계는 숫자에도 반영되어야 한다

관계 사전이 준비되고 나서 유사도 함수를 다시 짰다. 여기서 핵심은 **보완관계에 매기는 점수를 4자리 일치보다 위에** 두는 것이었다.

```python
def sim_ncs(a: str, b: str, relations: dict) -> float:
    if a[:6] == b[:6]:
        return 1.0
    if b[:6] in relations.get(a[:6], []):
        return 0.8
    if a[:4] == b[:4]:
        return 0.7
    if a[:2] == b[:2]:
        return 0.4
    return 0.0
```

만약 보완관계와 4자리 일치를 같은 0.7로 두면, LLM이 만든 신호는 아무 일도 하지 않는다. 이미 4자리 일치로 잡히던 후보들 사이에서 순서를 흔들지 못하기 때문이다. 0.8로 올려야 "같은 중분류 안에서 특별히 더 붙어 있다고 판단된 것"이 상위로 올라온다. 보완관계 사전을 애초에 4자리 안에서만 뽑기로 정한 판단이 여기서 값어치를 한다 — 관계에 들어온 항목은 이미 4자리로도 걸리는 항목이니, 그 위에 얹는 게 자연스럽다.

| 조건 | 점수 |
|------|-----|
| 6자리 일치 | 1.0 |
| 보완관계 (AI) | 0.8 |
| 4자리 일치 | 0.7 |
| 2자리 일치 | 0.4 |
| 무관 | 0.0 |

## 그다음 층 — 직무명과 키워드

NCS 코드는 결국 코드일 뿐이고, 사용자가 화면에서 고르는 건 "IT·개발·데이터" 같은 상위 직무군이다. 그래서 코드 유사도 위에 사용자용 직무군 → NCS 대분류 매핑을 한 겹 더 두었다. 예를 들어 IT·개발·데이터를 고른 사용자는 대분류 `20`으로 넘어가고, 그 안의 소분류별로 다시 위 유사도 함수가 작동한다.

```python
JOB_TO_NCS = {
    'IT·개발·데이터': ['20'],
    '생산·제조·품질': ['15', '16', '17', '19'],
    '연구·R&D·설계': ['17', '19', '15'],
    # ...
}
```

같은 방식으로, 소분류별 대표 키워드도 별도 사전으로 뺐다. 코드로만 매칭하면 놓치는 미묘한 색깔 — 예를 들어 "AI·머신러닝 엔지니어"에 `AI`, `데이터`, `알고리즘`을 붙여두는 식 — 을 콘텐츠의 태그·제목과 부딪혀보게 하기 위해서다.

```python
SUB_TO_KEYWORDS = {
    'AI·머신러닝 엔지니어': ['AI', '데이터', '알고리즘'],
    '데이터 분석가·엔지니어': ['데이터', '통계'],
    '백엔드·웹 개발자': ['웹개발', '프로그래밍'],
    # ...
}
```

이 세 층 — 코드 prefix, LLM 보완관계, 키워드 — 을 별개의 점수로 두고 합치는 구조로 잡았다. 어느 한 층에서 신호가 약해도 다른 층에서 붙잡을 여지를 남기려는 의도였다.

## 남은 것

정량적으로 얼마나 나아졌는지는 아직 재보지 않았다. 오프라인 평가셋을 어떻게 구성할지가 남은 숙제고, 특히 "실무 보완 관계"라는 개념 자체가 정답이 명확하지 않아서 사람 평가자와의 합의부터 다시 잡아야 한다.

LLM이 만든 관계 사전을 주기적으로 재생성할 때 이전 버전과 얼마나 흔들리는지도 아직 안 봤다. 흔들림이 크면 추천 결과가 특별한 이유 없이 튀게 되니, 버전 간 diff를 뽑는 작은 도구부터 만드는 게 다음 순서일 것 같다.
