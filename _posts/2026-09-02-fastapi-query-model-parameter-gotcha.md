date: 2026-09-02 17:00:00 +0900

---

랜덤 추천 API에 페이지네이션을 붙이다가 이상한 걸 발견했다.

분명히 `PaginationQuery` 모델을 선언하고 라우터에 넣었는데, `/docs` 를 열어보니 `offset`과 `limit`이 쿼리 파라미터로 노출이 안 됐다. 에러는 없었다. 서버도 멀쩡히 떴다. 그냥 파라미터가 없는 것처럼 보였다.

처음엔 모델 클래스 자체를 의심했다. `BaseModel` 을 상속받았는지, `Field` 정의가 잘못됐는지. 근데 다른 엔드포인트에서는 똑같은 모델이 정상적으로 펼쳐지고 있었다.

차이점을 찾는 데 시간이 좀 걸렸다. 문제가 된 엔드포인트에는 `seed` 라는 파라미터가 따로 있었다. `Query(default=None)` 형태로 함수 시그니처에 직접 선언한 것. 랜덤 추천 특성상 클라이언트가 같은 시드값으로 다음 페이지를 요청할 수 있어야 해서, 페이지네이션 모델과는 별개로 처리하고 싶었다.

Pydantic 모델 파라미터와 개별 `Query` 파라미터를 같은 함수에 섞으면 FastAPI가 모델을 쿼리 파라미터로 "펼치는" 동작에 영향을 줄 수 있다. 정확히 왜 그런지는 FastAPI 내부의 의존성 해석 순서와 관련이 있는데, 아직 소스를 파고들지는 않았다. 에러 메시지도 없고 경고도 없어서 실제로 뭔가 잘못됐다는 신호를 받기 어렵다. `/docs` 를 열어보기 전까지는.

해결은 단순했다. `seed`를 별도 `Query`로 두지 않고 페이지네이션 모델 안으로 옮겼다. 모델 하나에 `offset`, `limit`, `seed`를 전부 넣으니 `/docs` 에서 세 파라미터가 모두 정상 노출됐다.

랜덤 추천의 정렬 안정성 문제는 따로 있다. 페이지네이션 형태를 갖췄다고 해서 2페이지에서 1페이지 항목이 다시 나오지 않는다는 보장이 생기진 않는다. 시드를 고정해도 DB 레벨에서 순서가 완전히 보장되지 않으면 페이지 경계에서 항목이 중복되거나 빠질 수 있다. 지금은 "응답 형태만 페이지네이션 규격에 맞추는" 선에서 일단 정리했는데, 이 부분은 실제로 어떻게 동작하는지 아직 재보지 않았다.
