목록 API 몇 개에 페이지네이션을 붙이는 작업이었다. 응답 필드를 공통 형태로 맞추고, 오류 처리를 HTTP 상태 코드 쪽으로 바꾸고, 문서를 고치는 평범한 일이었다. 그런데 "랜덤으로 N개 가져오는" 조회 하나가 걸렸다. 거기에 `offset`을 붙이면 무슨 뜻이 되는지 답이 바로 나오지 않았다.

## 2페이지는 무엇의 2페이지인가

기존 쿼리는 이런 모양이었다.

```sql
ORDER BY RAND()
```

여기에 페이지네이션을 맞추려고 나머지 목록 API와 같은 꼴로 붙이면 이렇게 된다.

```sql
ORDER BY RAND()
LIMIT :limit OFFSET :skip
```

문법은 맞고 돌아가기도 한다. 문제는 `ORDER BY RAND()`가 요청마다 전체를 새로 섞는다는 점이다. 1페이지를 받고 2페이지를 요청하면 서버는 다시 섞은 결과에서 `skip`만큼 건너뛴 구간을 준다. 1페이지에 나왔던 항목이 2페이지에 또 나올 수 있고, 어떤 항목은 어느 페이지에도 안 나올 수 있다. `OFFSET`은 "이미 정해진 순서에서 여기부터"를 뜻하는데, 순서가 매번 바뀌면 그 약속이 성립하지 않는다.

처음엔 이걸 버그로 봤다. 지금은 서로 다른 두 요구가 한 API에 겹쳐 있었던 것이라고 본다.

- 요청할 때마다 다른 무작위 결과를 받고 싶다.
- 페이지를 넘기는 동안은 순서가 유지되길 바란다.

앞쪽은 `RAND()`가 이미 해결하고 있었다. 뒤쪽은 `RAND()`로는 안 된다.

## seed를 고정하면

한 번 섞은 순서를 여러 요청에서 재사용하려면 `RAND()`에 seed를 주는 방법이 있다.

```sql
ORDER BY RAND(seed)
```

MySQL은 seed가 같으면 같은 난수 열을 만든다. 클라이언트가 seed를 들고 다니며 페이지마다 같은 값을 보내면 같은 순서에서 잘라 쓰는 셈이다. 시험 데이터로 두 가지를 확인했다.

```text
seed 고정 재현성 : 동일 ✓
페이지1 vs 2 중복 : 0건 ✓
```

같은 seed로 두 번 조회하면 같은 결과가 나왔고, 페이지 1과 2 사이에 겹치는 항목은 없었다. 시험 데이터의 규모와 반복 횟수는 따로 기록하지 않았다. 그래서 이 결과를 "seed 방식이 동작한다"는 확인 정도로만 읽는다.

그 이상은 말할 수 없다. 페이지를 넘기는 사이에 행이 추가되거나 삭제되면 같은 seed여도 순서가 달라질 수 있다. 실행 계획이 바뀌었을 때 같은 seed가 같은 순서를 내는지도 확인하지 않았다. 중복이 0건이라는 사실과 순서가 안정적이라는 보장은 다른 이야기다.

## 시간 단위 seed

seed를 클라이언트에 맡기기 싫어서 서버에서 시간으로 만드는 안도 나왔다. 예를 들어 시 단위 값을 seed로 쓰는 식이다. 같은 시간대에는 모두 같은 순서를 받고, 시간이 바뀌면 새로 섞인다.

구현은 간단하지만 시간 경계가 문제다. 사용자가 1페이지를 10시 59분에 받고 2페이지를 11시 정각에 요청하면 순서가 바뀐다. 중복 가능성이 완전히 없어지지 않고, 줄어들 뿐이다. 그래서 이 안은 채택하지 않았다.

## 결국 seed를 뺐다

최종 구현에서는 seed를 제거했다. 랜덤 조회는 기존 `ORDER BY RAND()`를 그대로 두고, 응답 형태만 다른 목록 API와 같은 공통 구조로 맞췄다.

이 조회가 쓰이는 목적을 따져보니 결론이 단순해졌다. 이 API는 "아무거나 몇 개 보여주기"에 쓴다. 호출하는 쪽도 여러 페이지를 넘겨가며 전수 탐색하지 않는다. 그런 용도에 seed 전달과 순서 보존 계약을 얹으면 클라이언트가 지켜야 할 규칙만 늘어난다. 쓰이지 않을 기능을 위해 계약을 복잡하게 만드는 셈이었다.

대신 제약을 문서에 적었다. `offset`을 받기는 하지만, 이 조회로 여러 페이지를 중복 없이 탐색하는 기능은 제공하지 않는다고 명시했다. 인자는 받는데 의미가 약한 상태이므로, 문서에서 그 사실을 감추지 않는 쪽이 낫다고 판단했다.

## 같이 부딪힌 것들

이 작업에는 곁가지가 몇 개 있었다.

- 페이지네이션 파라미터를 FastAPI 쿼리 모델로 묶으려는데 모델이 쿼리 파라미터로 인식되지 않는 문제가 있었다. 이 건은 따로 처리했다.
- 응답 필드를 바꾸면 기존 호출자가 영향을 받는다. 오류를 HTTP 상태 코드로 돌려주는 방식으로 바꾼 것도 마찬가지다. 호출자 쪽 영향 범위는 문서에 정리했다.

## 아직 안 한 것

변경은 로컬 커밋까지만 끝났다. 실제 앱을 띄워서 DB 바인딩이 의도대로 되는지는 아직 확인하지 못했다. 앞서 본 재현성과 중복 검증도 시험 데이터 위에서 한 것이지 실제 앱 경로를 거친 결과가 아니다. 원격 반영도 남아 있다.

그리고 `offset`을 받으면서 의미가 약하다는 점은 여전히 마음에 걸린다. 인자를 아예 받지 않는 편이 더 정직한 설계일 수도 있다. 다른 목록 API와 시그니처를 맞추는 편의가 그 어색함보다 큰지는 호출자들의 반응을 보고 다시 판단하려고 한다.
