## "AI가 그렇게 판단했어요" 라고 말할 수 없는 자리

추천 시스템 설계를 맡고 얼마 안 됐을 때, 회의에서 이런 질문을 받았다.

> "이 사람한테 왜 이게 추천됐는지, 담당자가 민원 오면 뭐라고 답해요?"

머릿속에서 원래 준비하던 답이 흐트러졌다. LLM(Large Language Model, 대형 언어 모델) 붙여서 응답 만들면 되죠, 라고 말하려던 참이었다. 그런데 그 문장이 감사 앞에서, 민원 대응 앞에서 어떻게 들릴지를 생각해보니 답이 안 됐다. "AI가 그렇게 판단했습니다"는 사유가 아니라 회피다.

이 글은 그 회의 이후에 내가 내린 결정 — LLM을 추천 서빙에서 완전히 걷어낸 결정 — 을 정리한 기록이다.

## 세 개의 제약이 동시에 걸려 있었다

내가 다루던 도메인은 공공 성격이 강했고, 실행 환경은 온프레미스(on-premise, 자체 서버 운영)였다. 정리하면 이런 조건이었다.

- 외부 API 실시간 호출은 못 한다. 네트워크와 계약 양쪽 다 걸린다.
- 응답은 초 단위 안에 끝나야 한다. 사용자 대기시간이 UX 지표에 직접 반영된다.
- 추천 사유는 신호 단위로 로그에 남아 있어야 한다. 사후 재현이 가능해야 한다.

이 세 개 중 하나라도 덜 빡빡했으면 나는 그냥 실시간 LLM 호출로 갔을 것이다. 그런데 셋을 한꺼번에 만족시킬 방법이 없었다. 응답 속도만 봐도, 온프레미스 GPU에서 프롬프트 조립부터 토큰 생성까지 다 태우면 예산이 남지 않는다. 무엇보다도 같은 사용자에게 같은 시점에 두 번 호출해도 결과가 다를 수 있다는 점 — 이게 감사 대응 관점에서 치명적이었다.

## 그래서 LLM을 뒤로 뺐다

방향을 뒤집었다. LLM은 **추천을 만들지 않는다.** LLM은 **추천이 쓸 재료를 만든다.**

재료는 오프라인 배치(batch, 일괄 처리) 단계에서 미리 뽑아 DB에 넣어둔다. 서빙은 그 테이블만 읽어서 결정론적(deterministic, 같은 입력이면 항상 같은 결과)으로 계산한다. 사용자 요청이 들어오는 순간에는 LLM이 어디에도 관여하지 않는다.

배치에서 LLM이 실제로 하는 일은 두 가지로 좁혔다.

하나는 **키워드 정규화**다. 원본 데이터에는 "머신러닝", "ML", "기계학습"이 뒤섞여 있고, 같은 의미인지 아닌지를 규칙으로만 판단하기가 애매하다. LLM에게 "이 표현들을 같은 개념 묶음으로 볼 수 있냐"를 물어보고, 그 결과를 표준 키워드 맵으로 저장한다. 서빙 시점에는 그냥 룩업 테이블일 뿐이다.

다른 하나는 **직무 간 보완관계 분석**이다. 어떤 두 개의 직무 코드가 함께 있을 때 시너지가 나는지, 아니면 서로 다른 방향이라 함께 추천하면 어색한지 — 이건 사람이 도메인 감으로 다 채우기 어렵다. LLM에게 페어 단위로 판단시켜 가중치 행렬로 만든다. 이것도 그냥 숫자 테이블로 앉는다.

두 산출물 모두 **한 번 만들면 서빙 요청 수천 건에 재사용된다.** 사용자마다 매번 LLM을 부르는 낭비가 사라진다.

## 신호 단위 로그 — 이게 진짜 목적이었다

추천 결과 옆에는 이런 형태의 근거가 항상 붙어 나간다.

```json
{
  "item_id": "ITEM_0042",
  "score": 0.87,
  "signals": [
    {"type": "code_match",       "weight": 0.40},
    {"type": "keyword_overlap",  "matched": ["Python", "데이터분석"], "weight": 0.30},
    {"type": "complement_bonus", "pair": ["ITEM_0039", "ITEM_0042"], "weight": 0.17}
  ]
}
```

민원이 들어오면 이걸 그대로 근거로 쓴다. "이 아이템은 코드 일치가 0.4, 키워드 두 개 겹침이 0.3, 그리고 앞에 본 항목과의 보완관계 보너스가 0.17이라서 상위에 왔습니다." 이건 답이 된다.

내부적으로도 이 로그는 유용하다. 어떤 신호가 결과를 지나치게 지배하고 있는지, 특정 사용자 층에서 왜 특정 카테고리만 뜨는지 — 가중치 조정 전에 로그부터 뒤진다. 예전에 나는 LLM 응답을 자연어로 받아서 파싱하려다 실패한 적이 있는데, 그때 배운 게 이거였다. **결과의 이유를 사후에 붙이려 하지 말고, 만드는 순간부터 구조화된 형태로 남겨야 한다.**

## 결과를 하나로 안 내고 네 개로 쪼갠 이유

처음에는 단일 리스트로 top 10을 뽑아 내보내려 했다. 그런데 튜닝을 하다 보니 문제가 생겼다. 사용자의 명시적 관심사와, 프로필에서 추론한 직무 신호가 서로 다른 방향을 가리키는 경우가 꽤 있었다. 하나의 리스트로 합치면 가중치 밸런스 논쟁이 끝나지 않는다.

그래서 관점을 나눴다. 직무 관점, 관심 관점, 선호 관점, 그리고 네 개를 다시 종합한 관점 — 각 10건씩. UI 쪽에서 어떻게 배치할지는 그쪽 판단에 맡기고, 서빙은 네 관점의 원본을 다 준다.

이 구조의 진짜 이점은 유지보수에서 나왔다. "종합 추천이 이상하다"는 피드백이 오면, 네 관점 각각의 결과를 나란히 놓고 어디서 왜곡이 들어왔는지 바로 본다. 종합 관점의 가중치를 만졌을 때 다른 세 관점은 건드리지 않아도 된다. 지금은 관점별 가중치가 룰 기반이지만, 실사용 로그가 충분히 쌓이면 이 자리를 학습 기반으로 갈아끼울 계획이다. 그때가 되면 관점 단위로 A/B를 붙일 수 있게 미리 잘라둔 셈이다.

## 아직 정리 못 한 것

이 구조로 몇 가지는 확실히 얻었다. 응답 시간에 대한 걱정이 사라졌고, 민원 대응 회의에서 방어할 문장이 생겼다.

그런데 대신 배치 쪽이 무거워졌다. LLM으로 뽑는 키워드 맵과 보완관계 테이블은 **얼마나 자주 갱신해야 하는가?** 이걸 아직 못 정했다. 매일 돌리자니 비용이 아깝고, 주간 단위로 두자니 신규 항목이 들어왔을 때 반영이 늦다. 지금은 수동으로 트리거하고 있는데, 이걸 언제 자동화할지, 자동화한다면 어떤 지표로 재실행을 결정할지가 다음 숙제다.

가중치 캘리브레이션도 남았다. 관점별로 뽑히는 상위 아이템의 겹침 정도를 실제로 재본 적이 없다. 네 관점이 사실상 같은 것을 조금씩만 흔들어서 내놓고 있는 건 아닌지 — 이건 로그부터 다시 봐야 할 것 같다.
