파일 하나가 16MB였다. 마크다운. 회의록, 스펙 조각, 코드 붙여둔 것, 나중에 볼 링크. 몇 년치가 한 파일 안에 쌓여 있었다. 이걸 로컬 LLM에 통째로 던지고 "요약해줘"라고 했다.

당연히 안 됐다. 컨텍스트 초과. 그다음엔 JSON 파싱 실패. 그다음엔 프로세스가 몇 분째 안 돌아왔다.

## 통째로가 왜 나쁜가

크기 문제부터 걸린다. 로컬로 돌리는 모델은 컨텍스트 윈도우(한 번에 볼 수 있는 토큰 상한)가 8K~32K 언저리다. 16MB 마크다운은 그걸 수십 배로 넘긴다.

그런데 사실 이건 두 번째 문제였다. 진짜 문제는 다른 데 있었다. 문서가 길어지면 **모델이 중간을 잊어버린다**. 앞머리에서 잡은 맥락이 뒤에 가면 사라진다. 논문에서 "lost in the middle"이라고 부르는 현상. 억지로 창을 늘려서 다 넣어봐도, 나오는 요약은 앞 5%와 뒤 5%만 기억하는 요약이었다.

그래서 "창을 늘리면 되지"가 아니라 "쪼개야 한다"로 방향을 틀었다.

## 헤더 경계로 쪼갠 이유

Map-Reduce 자체는 새로운 게 아니다. 큰 걸 잘게 나눠서 각자 처리(Map)하고 결과를 합친다(Reduce). 문제는 **어디서 자르느냐**.

토큰 수 기준으로 자르면 편하지만, 문장 중간·문단 중간에서 끊긴다. 부분 요약이 어색해진다. 시맨틱 임베딩 유사도로 자르는 방법도 있는데, 로컬 처리 파이프라인에 임베딩 모델을 하나 더 얹는 게 부담이었다.

마크다운이라는 점을 살리기로 했다. `##`, `###` 같은 헤더가 이미 작성자(과거의 나)가 정해둔 논리적 경계다. 이걸 그대로 쓴다.

```python
def split_by_headers(text: str) -> list[str]:
    sections = []
    current = []
    for line in text.splitlines(keepends=True):
        if line.startswith("#") and current:
            sections.append("".join(current))
            current = []
        current.append(line)
    if current:
        sections.append("".join(current))
    return sections
```

주의할 게 하나 있었다. 코드 블록 안의 `#`(파이썬 주석, 쉘 프롬프트)이 헤더로 잡히면 안 된다. 처음엔 이걸 놓쳐서 파이썬 예제 코드가 있는 섹션이 이상하게 갈라졌다. 코드 펜스(` ``` `) 안쪽을 무시하는 상태 플래그를 하나 얹어서 해결했다. 위 스니펫은 그 부분을 뺀 요지만 남긴 거다.

섹션 하나가 그래도 크면 어떻게 하나. 재귀로 다시 쪼갠다. 하위 헤더도 없이 한 섹션이 계속 크면 최후엔 문단 경계로 자른다. 재귀가 깊어질수록 요약 품질은 떨어진다. 하지만 파이프라인이 죽는 것보단 낫다.

## mtime을 믿었다가 데인 이야기

파이프라인이 실용적이려면 **같은 파일을 두 번째로 만났을 때 다시 안 해야** 한다. 처음엔 파일 수정 시각(`mtime`)으로 판단했다. 이전 실행 때보다 mtime이 나중이면 다시 요약, 아니면 skip.

한 사흘 만에 무너졌다. 

`git checkout`으로 브랜치를 바꿨더니 내용은 그대로인 파일도 mtime이 바뀌었다. 다른 편집기에서 저장 방식(안전 저장 - 임시파일 쓰고 rename)이 mtime을 예측 밖으로 튀게 만들었다. 파일 하나 만졌는데 옆의 백 개가 재요약 큐에 들어왔다.

SHA-256으로 갈아치웠다.

```
[읽음] file.md
[해시] a3f9…c211
[캐시] 마지막 해시 a3f9…c211 → 일치 → skip

[읽음] other.md
[해시] 4b7e…09aa
[캐시] 마지막 해시 없음 → summarize_large() 실행 → 새 해시 저장
```

이걸 붙이자 실제 바뀐 파일만 처리했다. LLM 호출 수가 극적으로 줄었다. 정확한 배수는 안 재봤다. 다만 파이프라인을 다시 돌릴 때 "얼마 걸리려나" 하고 눈치 보던 게, "금방 끝나겠지" 하고 다른 창으로 시선 옮기는 게 됐다.

## thinking을 껐더니 조용해졌다

어떤 로컬 모델은 답 내기 전에 내부 추론을 뱉는 모드가 있다. 흔히 `thinking`이라고 부른다. 어려운 태스크에선 이게 품질을 올려준다고 알려져 있다.

요약 파이프라인에선 두 방향으로 어긋났다.

첫째, 출력이 지저분해졌다. 나는 요약을 JSON으로 받아 다음 단계(인덱스 삽입)에 넘기고 있었는데, thinking 블록이 JSON 앞에 딸려 나오는 경우가 있었다. 파서가 `<think>` 태그를 만나면 그냥 실패했다. 정규식으로 걷어내볼까 하다가, 결국 그건 증상 대증치료다.

둘째, 시간이 크게 늘었다. 요약할 섹션은 짧은데 thinking이 몇 배로 길었다. 배치를 돌리면 그 지연이 곱해진다.

요약이라는 태스크의 성격을 다시 생각했다. 이건 **압축**이지 창의적 추론이 아니다. 이미 있는 문장에서 중복을 걷고 요지를 뽑는 일. thinking이 도와줄 여지가 별로 없다. 껐다. 파싱 실패가 거의 0으로 갔고, 배치 총 시간이 뚝 떨어졌다.

## 아직 안 푼 것

파이프라인이 실무엔 쓸 만해졌지만 남은 게 있다.

헤더 기준으로 자른 섹션들 사이의 **참조 관계**를 요약이 못 살린다. "위에서 말한 X"라고 쓴 부분이 다른 섹션에 있으면, 그 섹션만 따로 요약할 때 X가 무엇인지 모른다. 지금은 각 섹션 요약 앞에 이전 섹션의 최종 요약 한 줄을 살짝 얹는 식으로 눈속임 중이다. 제대로 하려면 문서 전체 목차·엔티티를 먼저 뽑아 각 Map 단계에 컨텍스트로 넣어야 할 것 같다. 아직 안 해봤다.

Reduce 단계에서 부분 요약 20~30개를 다시 한 번에 넣는 지금 방식도 곧 다시 컨텍스트에 부딪힐 거다. 계층적 Reduce(부분 요약들을 또 그룹으로 묶어 중간 요약을 만드는 방식)로 갈지, 아니면 아예 트리 구조를 유지한 채 인덱싱만 할지 아직 결정 못 했다. 다음에 볼 것.
