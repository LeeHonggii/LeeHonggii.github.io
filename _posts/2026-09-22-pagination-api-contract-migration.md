목록 API에 페이지네이션을 추가하는 일은 "SQL에 LIMIT, OFFSET 붙이기"가 아니었다.

기존 API는 조건에 맞는 모든 항목을 반환했다. 호출자는 그걸 당연하게 여겼고, 클라이언트 코드는 리스트를 통째로 받아 렌더링했다. 거기에 "기본 30개 반환"을 붙이는 순간, 호출자는 아무 에러 없이 데이터를 덜 받기 시작한다. 에러가 없어서 더 위험하다.

---

## SQL부터 짚어보자

페이지네이션 파라미터를 `offset`과 `limit`으로 받기로 했는데, `offset`의 정의를 먼저 확정해야 했다. 행 번호인지 페이지 번호인지. 프론트엔드와 협의해 1부터 시작하는 페이지 번호로 정의했다. 그러면 실제 SQL에 넘기는 행 오프셋은 `(offset - 1) * limit`이 된다.

```python
skip = (offset - 1) * limit
```

그리고 쿼리에서는

```sql
LIMIT :limit OFFSET :skip
```

단순해 보이지만 `offset=0`을 허용하면 음수 스킵이 나온다. 검증 레이어에서 `offset >= 1`을 강제하지 않으면 쿼리 자체는 조용히 이상한 결과를 낸다. 422 검증 오류를 기대하고 호출했는데, FastAPI 기본 검증 응답과 커스텀 에러 본문의 형식이 달라서 클라이언트가 두 가지 구조를 파싱해야 하는 상황도 생겼다. 별도 예외 핸들러를 두지 않으면 그냥 그렇게 나간다.

---

## 응답 계약이 더 문제였다

SQL은 고쳤다. 더 어려운 건 응답 구조였다.

호출자는 두 가지를 다르게 필요로 한다. 지금 페이지에 담긴 항목 수(`count`)와, 조건에 맞는 전체 항목 수(`totalCount`). 전자는 `list.length`로 알 수 있으니 사실 응답에 굳이 넣지 않아도 된다. 중요한 건 `totalCount`다. 이게 있어야 클라이언트가 "다음 페이지가 있는지"를 판단할 수 있다.

타입스크립트 쪽에서 응답 타입을 정리하면 이런 구조가 된다.

```typescript
interface PaginationResponse<T> {
  totalCount: number;
  list: T[];
}
```

`count`를 별도 필드로 유지할지 논의했지만 `list.length`와 중복이라 뺐다. 그 대신 `totalCount`는 필수로. 이 결정을 나중에 다시 바꾸면 호출자 전체를 또 수정해야 한다.

---

## 기존 호출자가 조용히 망가지는 지점

"기본 30개"로 바꾼 뒤 클라이언트가 보이는 증상:

1. 전체 리스트가 필요한 뷰에서 첫 30개만 표시됨
2. 에러는 없음
3. 데이터가 실제로 적은 건지, 잘리는 건지 알 방법이 응답만 봐서는 없음 — `totalCount`가 없으면

`totalCount`를 응답에 포함시키고, 클라이언트에서 `list.length < totalCount`이면 다음 페이지를 요청하도록 수정하는 게 올바른 흐름이다. 클라이언트 변경 없이 서버만 바꾸면 데이터 손실처럼 보이는 버그가 생긴다.

HTTP 상태코드로 실패를 전달하는 방식도 이번에 바꿨다. 기존에는 응답 본문에 `status` 필드가 있었다. 이걸 제거하고 HTTP 상태코드로 통일하면 클라이언트 코드가 단순해진다.

```javascript
if (!response.ok) {
  // HTTP 4xx/5xx → 여기서 처리
}
```

`status` 필드를 읽던 기존 코드는 이 변경 이후 조건이 항상 통과되거나 무시된다. 조용히 망가지는 패턴이 또 하나 생기는 것이다.

---

## 검증이 끝나지 않은 곳

직접 SQL을 실행해서 결과는 확인했다. 모델과 문법 수준의 검증도 통과했다.

남은 건 실제 앱을 올렸을 때 SQLAlchemy의 바인딩이 `:limit`, `:skip` 파라미터를 제대로 처리하는지였다. ORM을 통하지 않고 raw SQL을 넘기는 경로라면 파라미터 바인딩 방식이 드라이버마다 다를 수 있다. 이건 앱을 실제로 실행해봐야 알 수 있는 부분이었고, 대화가 끝날 시점에 아직 확인하지 못했다.
