API가 조용히 죽어있었다.

에러 로그도 없고, 서버도 살아있었다. 그냥 응답 데이터가 비어 있었다. 처음엔 프론트 쪽 필터 문제인 줄 알았다.

---

발단은 스키마 정리였다. 어느 시점에 테이블 이름이 바뀌었다. 이름이 너무 길고 일관성이 없어서 팀 내부에서 rename을 진행했고, 마이그레이션 파일도 배포됐다. 코드베이스 검색으로 구 이름을 찾아서 고쳤다고 생각했다.

그 생각이 틀렸다.

한 군데가 남아 있었다. 추천 API 내부 쿼리의 `LEFT JOIN` 절이었다. 존재하지 않는 테이블에 JOIN을 걸고 있었으니 결과가 비는 건 당연했다. DB 레벨에서는 에러가 아니라 그냥 빈 결과였다.

---

디버깅 순서를 적어두는 이유는 다음에도 같은 상황이 올 것 같아서다.

**1단계 — 실제로 DB에 무엇이 있는지 확인한다**

코드에서 테이블명을 고쳤다고 DB도 바뀐 건 아니다. 마이그레이션이 실제로 돌았는지, 이름이 진짜로 바뀌었는지 직접 확인해야 한다. `information_schema.tables` 를 조회하거나, 직접 `\dt` 를 치거나. 이 프로젝트엔 스키마 상태를 빠르게 확인하는 스크립트가 있었고, 그걸 먼저 돌렸다.

```
python scripts/check_schema.py
```

스크립트 출력에서 구 테이블명은 없었고, 신 테이블명만 존재했다. 즉 DB 쪽은 정상 — 코드가 문제였다.

**2단계 — 의심되는 쿼리를 손으로 실행해본다**

코드에서 ORM이나 쿼리 빌더를 쓰는 경우, 실제로 어떤 SQL이 나가는지 눈으로 보는 게 빠르다. raw query를 DB 클라이언트에 직접 붙여서 실행해봤다. `LEFT JOIN` 결과에 NULL 행이 몇 개나 나오는지도 같이 확인했다. NULL 행이 전부라면 JOIN 대상이 아예 없거나 조건이 잘못됐다는 뜻이다.

예상대로였다. 구 테이블명을 참조하는 JOIN이 매칭을 하나도 못 하고 있었다.

**3단계 — 한 줄 고친다**

수정 자체는 단순했다. JOIN 절의 테이블명 하나를 바꾸는 것. 설계를 다시 할 일도, 로직을 건드릴 일도 없었다.

**4단계 — 수정 후 같은 쿼리를 다시 실행한다**

고쳤다고 끝이 아니다. 같은 raw query를 다시 돌려서 이번엔 결과가 제대로 나오는지, NULL 행이 사라졌는지 확인했다. 이 단계를 생략하면 "아마 됐겠지"가 된다.

---

커밋 메시지는 짧게 적었다.

```
fix: 카테고리 공개캔버스 조회 JOIN 테이블명 수정
```

그리고 develop에 올렸다.

---

사후에 남은 질문이 있다.

왜 코드 검색에서 이 한 군데가 빠졌나. `grep` 으로 구 테이블명을 검색했을 텐데 — 문자열이 일부 다르게 분리돼 있었거나, 해당 파일이 검색 경로에서 빠져 있었거나. 확인은 못 했다. 다음에 스키마 rename을 할 때는 코드 검색 결과를 믿기 전에 DB에서 구 이름으로 직접 쿼리해보는 단계를 먼저 넣을 것 같다. `SELECT * FROM old_table_name LIMIT 1` — 존재하면 아직 마이그레이션이 안 된 거고, 없으면 코드에서 참조하는 게 문제라는 뜻이다.

그게 더 빠르다.
