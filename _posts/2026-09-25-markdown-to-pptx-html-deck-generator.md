발표자료를 만들 때마다 같은 삽질을 반복하고 있었다. Keynote에서 텍스트를 옮겨 붙이고, 폰트를 맞추고, 회사 로고 위치를 고정하고. 결국 내용보다 레이아웃 조정에 시간이 더 걸렸다.

그래서 Markdown을 입력으로 받아 PPTX와 HTML을 동시에 뽑아주는 도구를 직접 만들어봤다.

---

## 왜 두 가지 출력인가

PPTX는 공유용이다. 받는 사람이 PowerPoint를 열어 편집할 수 있어야 하는 상황이 실제로 많다. HTML은 내 발표용이다. 브라우저 전체화면으로 띄우면 따로 설치할 것도 없고, 키보드 화살표로 넘기면 된다.

둘 다 [Marp](https://marp.app/) — Markdown을 슬라이드로 변환하는 도구 — 를 거쳐서 생성한다.

```
marp deck.md --pptx -o output.pptx
marp deck.md --html -o output.html
```

명령어 자체는 단순하다. 문제는 그 사이에 있는 것들이었다.

---

## 설계에서 먼저 결정한 것

내용을 요약할지, 아니면 그대로 슬라이드로 나눌지.

처음에는 긴 문서를 받으면 LLM이 슬라이드 분량에 맞게 압축하는 방식을 생각했다. 그런데 이건 발표자가 한 말을 발표자 모르게 바꾸는 것과 다를 바 없었다. 수치나 근거가 요약 과정에서 사라지면 나중에 질문을 받았을 때 대답을 못 한다.

그래서 방향을 바꿨다. **요약하지 않고 분할한다.** 입력 Markdown을 `---`(슬라이드 구분자) 기준으로 끊거나, 헤딩 구조에 따라 자르는 방식으로. 내용 보존을 우선 원칙으로 삼았다.

---

## 브랜드와 레이아웃을 분리한 이유

디자인 파일을 단일 CSS로 만들면 곧 한계가 온다. 표지 슬라이드와 본문 슬라이드의 레이아웃 구조가 다르기 때문이다. 표지는 세로 중앙 정렬, 본문은 상단 제목 + 본문 영역, 인용 슬라이드는 또 다른 구조.

그래서 두 층으로 나눴다.

- **글로벌 브랜드**: 색상 팔레트, 타이포그래피, 로고 위치처럼 모든 슬라이드에 공통 적용되는 것
- **페이지 레이아웃**: 슬라이드별로 다른 클래스(예: `<!-- _class: layout-cover -->`)로 선택

레이아웃 선택은 와이어프레임 이미지를 보여주고 고르는 방식으로 구성했다. CLI에서는 `--layout` 플래그로, 슬라이드별로는 JSON으로 전달하도록 했다.

```
make_deck.py --layout centered-title --per-slide-layouts '{"2": "two-column", "5": "quote"}'
```

Marp 측에서는 해당 클래스를 CSS에서 받아서 처리한다.

```css
/* 각 레이아웃 클래스는 독립적으로 */
section.layout-cover { ... }
section.layout-two-column { ... }
section.layout-quote { ... }
```

---

## 파서가 멈췄다

디자인 파일을 읽는 파서에서 문제가 생겼다. 정규식으로 YAML frontmatter를 파싱하고 있었는데, 값이 멀티라인 블록 문자열(`description: |`)이거나 frontmatter 자체가 없는 Markdown 파일이 들어오면 파서가 멈췄다.

복잡한 정규식을 고치는 대신 라인 단위 파서로 통째로 교체했다. `---`를 만나면 상태를 전환하고, 그 사이를 YAML로 파싱하는 방식이다. YAML 블록이 없으면 전체를 Markdown 본문으로 취급한다.

더 단순하고, 실패 지점도 명확했다.

---

## 스모크 테스트와 실제 검증 사이

자동화 테스트를 돌렸을 때 확인한 것은 이렇다:

- 5개 슬라이드 파일이 생성됐는가
- PPTX와 HTML 두 파일이 모두 존재하는가
- 특정 텍스트가 출력 파일에 포함됐는가

이걸 다 통과했다. 그런데 이건 파일 생성을 확인한 것이지, 슬라이드가 실제로 잘 보이는지를 확인한 게 아니다. 텍스트가 박스 바깥으로 잘리거나, 표가 찌그러지거나, 모바일 해상도에서 레이아웃이 깨지는 건 이 테스트에 걸리지 않는다.

Playwright 같은 도구로 렌더링된 결과를 스크린샷 찍고 비교하지 않으면 시각적 회귀는 수동으로 직접 열어보는 수밖에 없다.

---

## 끝내지 못한 것

실제 UI에서 "PPTX 생성" 버튼을 눌렀을 때 파일이 나오지 않는다는 보고가 마지막에 들어왔다.

CLI에서는 됐다. 스모크 테스트도 통과했다. 그러면 UI와 CLI 사이 어딘가에서 실패하는 것인데, stderr 메시지가 UI로 전달되지 않아 무엇이 실패하는지 보이지 않는다는 가설까지만 나왔다.

stderr를 UI로 넘기거나 로그 창을 별도로 두는 방식으로 확인해볼 수 있는 문제다. 그런데 그 확인을 아직 못 했다.
