새 활동 유형을 기존 평가 시스템에 붙여 달라는 요청이 들어왔다. 처음 든 생각은 "루브릭에 연결만 하면 되겠네"였다. 그 생각이 틀렸다는 걸 확인하는 데 코드를 읽는 시간이 대부분 들었다.

## 먼저 기존 코드가 뭘 보고 있는지부터

기존 평가는 학생이 캔버스에서 한 조작 기록, 최종 화면 이미지, 정답 예시 이미지를 입력으로 받는다. 이걸 프롬프트에 넣어 LLM이 판정과 과정 점검(루브릭·전략·오개념·선개념)을 낸다. 코드로 계산할 수 있는 사실과 LLM이 추론하는 평가가 분리돼 있었다. 이 구조는 쓸 만하다고 봤다.

읽으면서 눈에 걸린 건 따로 있었다. 평가 항목 대부분이 **조작 로그에서 직접 관찰되는 것**에 기대고 있다는 점이다. 카드를 어디에 놓았는지, 식이 정답과 얼마나 겹치는지는 로그로 잴 수 있다. 그런데 새 활동에는 "비교한다", "배치한다", "설명한다"가 한 활동 안에 섞여 있다. 앞의 둘은 로그에 남는다. 마지막 하나는 클릭으로 남지 않는다.

그래서 활동 유형 이름("비교형", "설명형")만으로 평가 목표를 정할 수 없다. 한 활동 안에서 학생이 하는 행동이 겹치기 때문이다. 내 첫 제안은 활동 유형을 기존 루브릭에 매핑하는 것이었다. 검토해 보니 그 매핑을 뒷받침하는 근거가 없었다. 내가 그럴 거라고 가정했을 뿐이라서 보류했다.

## 기존 코드에서 "못 잰다"를 다루는 방식

이 문제와 맞닿은 부분이 기존 코드에 이미 하나 있었다. 학생의 식이 정답 식에 얼마나 가까워지는지를 시간순 곡선으로 만드는 부분이다.

```python
class Normalized:
    @staticmethod
    def series(curve):
        if not curve:
            return None
        m0, tot = curve[0]["matched"], curve[0]["total"]
        if tot - m0 <= 0:
            return None
        return [{"t": c["t"], "v": max(0.0, min(1.0, (c["matched"] - m0) / (c["total"] - m0)))} for c in curve]

    @staticmethod
    def final(curve):
        s = Normalized.series(curve)
        return round(s[-1]["v"], 3) if s else None
```

처음 화면에서 이미 일치한 몫(`m0`)을 빼고 0~1로 정규화한다. 첫 화면에서 이미 다 맞아 있으면 분모가 0이 된다. 이때 0점이나 1점을 주지 않고 `None`을 돌려준다. 학생이 아무것도 안 해서 변화가 0인 것과, 변화를 잴 여지 자체가 없는 것은 다른 상황이기 때문이다.

이걸 읽고 "평가 불가"와 "낮은 성취"를 구분하자는 생각이 분명해졌다. 관찰 근거가 없다는 이유로 낮은 점수를 매기면 입력이 부족한 것을 능력이 부족한 것으로 읽게 된다. 설명 능력이 그 전형이다. 로그만 보면 설명을 잘한 학생과 말없이 넘어간 학생이 똑같이 "근거 없음"으로 보인다.

이 `None`이 뒤에서 어떻게 소비되는지도 같은 파일에 있다.

```python
VERDICT = {"정답": "정답", "부분 정답": "부분", "오답": "오답", "판단 보류": "보류"}

# ...
self.rows.append({"활동": task_id, "문제": order, "학생": r["student"],
                  "판정": VERDICT.get(fb.get("판정"), "분석 전"),
                  "확인_필요": bool(fb.get("확인_필요")),
                  "곡선": cmp["has_curve"],
                  "근접(지금)": Normalized.final(curves.get(r["student"])) if cmp["has_curve"] else None})
```

판정에는 정답·부분·오답 말고도 "판단 보류"와 "분석 전"이 있고, 곡선이 없으면 근접도는 `None`으로 남는다. 상태 값이 "점수 없음"을 표현할 수 있게 설계돼 있다는 뜻이다. 다만 이 코드는 내가 읽은 것이고, 이 보류 값들이 실제 피드백 문구나 리포트에서 어떻게 보이는지는 이번에 끝까지 확인하지 못했다.

## 같은 입력으로 다시 돌렸을 때 같은 값이 나오나

저장소에는 측정용 코드가 하나 더 있다. 기록 하나를 같은 입력, 같은 검사로 n번 다시 돌려서 항목별로 값이 같게 나오는 비율을 재는 하네스다. 비교하는 항목은 아래와 같다.

```python
ITEMS = ["판정", "확인_필요", "모범답안과", *[f"루브릭:{k}" for k in RUBRIC], "전략", "오개념", "선개념"]
```

```python
@staticmethod
def values(fb, rv):
    out = {"판정": fb.get("판정"), "확인_필요": fb.get("확인_필요"), "모범답안과": fb.get("모범답안과")}
    for k in RUBRIC:
        out[f"루브릭:{k}"] = ((rv.get("루브릭") or {}).get(k) or {}).get("점수")
    out["전략"] = tuple(sorted({t["태그"] for t in rv.get("전략") or []}))
    out["오개념"] = tuple(sorted({m["id"] for m in rv.get("오개념") or []}))
    out["선개념"] = tuple(sorted((c["개념"], c["신호"]) for c in rv.get("선개념") or []))
    return out
```

전략·오개념·선개념은 집합으로 정규화해서 비교한다. 순서가 달라서 다르다고 세는 일을 막으려는 것이다.

이 하네스의 결과 수치는 이 글에 싣지 않는다. 지금 내가 쓸 수 있는 자료에는 일치율이 들어 있지 않고, 기억에 의존해 숫자를 쓰고 싶지도 않다. 이 하네스에서 내가 쓸 수 있는 건 구조뿐이다. 새 평가 항목을 설계할 때 처음부터 "반복해서 재볼 수 있는 값인가"를 기준에 넣어야 한다는 것.

## 선개념·오개념이라는 이름이 약속하는 것

기존 리포트의 선개념·오개념 항목은 읽다 보면 검증된 지식 조회 결과처럼 보인다. 그런데 어느 쪽인지 구분해서 읽어야 했다. 지식 베이스를 조회해서 나온 것인지, 모델이 추론해서 붙인 라벨인지에 따라 같은 필드라도 신뢰 수준이 다르다. 이 구분이 화면에서 보이지 않으면 읽는 사람은 둘을 같은 무게로 받아들인다.

전문가 입력에도 한계가 있다. 교사가 입력한 정보는 활동 맥락에 대한 정보다. 학생이 실제로 이해했는지에 대한 판정은 별개다. 이 둘을 한 필드에 넣으면 평가의 근거가 흐려진다.

## 신규 설계 초안에서 정한 순서

초안은 이렇게 잡았다. 활동 유형별로 루브릭을 먼저 고르지 않는다. 활동마다 이 순서로 확보한다.

- 평가하려는 능력의 조작적 정의
- 그 정의에 걸치는 경계 사례
- 로그·이미지·서술·음성 중 무엇으로 관찰할 수 있는지
- 전문가가 직접 판정한 기준 사례

관찰 수단이 없는 능력은 "평가 불가"로 두고, 낮은 점수와 섞지 않는다. 다음 입력이 필요하다면 그 입력을 요구하는 쪽이 맞다.

## 아직 안 한 것

문항 이미지와 정답 이미지, 풀이 영상을 활용하는 분석 경로는 실험안으로 논의했다. 영상에서 프레임을 어떻게 뽑을지, 활동 유형별로 영상에서 무엇이 관찰되는지는 구현도 검증도 하지 않았다. 새 입력 경로도 아직 검토 단계다.

지금 가장 애매한 건 "설명"이다. 음성이나 서술을 받으면 관찰 가능해지지만, 그러면 말을 잘하는 학생과 개념을 이해한 학생이 같은 점수를 받을 위험이 생긴다. 이걸 가를 기준 사례를 전문가에게 몇 개나 받아야 하는지는 아직 정하지 못했다.
