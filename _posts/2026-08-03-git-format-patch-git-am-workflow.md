작업 브랜치에 커밋을 다섯 개쯤 쌓아둔 상태였다. 마지막에 `git push` 를 쳤더니 원격이 응답을 안 한다. 사내망 정책, 방화벽, 저장소 접근 권한 — 원인은 그때그때 다르다. 그날은 그중 하나였고, 당장 풀 방법은 없었다.

머릿속에 제일 먼저 스친 건 "그냥 파일만 복사해서 다른 데서 커밋하면 되잖아" 였다. 실제로 그렇게 하는 사람도 봤다. 다만 그러면 커밋 메시지, 작성자, 시간이 통째로 날아간다. 나중에 `git blame`(깃 블레임 — 특정 줄을 누가 언제 왜 바꿨는지 추적) 을 걸어도 죄다 오늘 날짜의 나로 찍힌다. 이력이 하루로 압축된다는 뜻이다. 그건 이력이 아니다.

## 커밋을 파일로 뽑는다 — format-patch

`git format-patch`(포맷 패치) 는 커밋 범위를 이메일 패치 형식의 텍스트 파일로 직렬화한다. 원래 리눅스 커널 개발자들이 메일링 리스트로 패치를 주고받던 시절의 유물인데, 그래서 파일을 열어보면 `From:`, `Date:`, `Subject:` 헤더가 붙어 있다. 이 헤더가 이 글의 핵심이다. **작성자와 타임스탬프가 파일 안에 박혀 있다.**

```bash
git format-patch HEAD~5..HEAD --stdout > work.patch
```

`--stdout` 없이 쓰면 커밋마다 `.patch` 파일을 하나씩 흩뿌린다. 다섯 개 커밋이면 다섯 개 파일. 옮길 때 하나만 빠뜨려도 순서가 어긋난다. 그래서 나는 늘 `--stdout` 으로 하나에 몰아 넣는다. USB에 던지든 첨부파일로 보내든 실수할 여지가 준다.

한 가지 착각했던 것: staged / unstaged 변경은 안 담긴다. `format-patch` 는 이름 그대로 **커밋된 것만** 패치로 만든다. 옮기기 전에 반드시 커밋을 마무리해야 한다. `git status` 가 깨끗해야 한다.

## 받는 쪽에서 복원한다 — am

받는 쪽에서는 `git am`(apply mailbox) 을 쓴다. `git apply` 랑 헷갈리기 쉬운데 둘은 다르다. `apply` 는 diff 만 파일에 얹는다. 커밋을 안 만든다. `am` 은 패치 헤더에 있던 작성자·시간·메시지까지 읽어서 **커밋 자체를 재현한다.**

```bash
git am work.patch
```

붙이고 나서 `git log` 를 보면, 원본 쪽에서 찍혔던 시각으로 커밋이 들어와 있다. SHA 는 새로 계산되니 값 자체는 바뀌지만, 그 외에는 원본이다. `git blame` 이 다시 살아난다.

충돌이 나면 이렇게 다룬다.

```bash
# 상황이 꼬였으면 되돌리고
git am --abort

# 손으로 고친 뒤에는
git add <resolved-files>
git am --continue
```

`--abort` 를 아는지 모르는지가 이 도구를 처음 쓰는 사람과 몇 번 써본 사람을 가른다. 중간에 멈춰도 저장소 상태가 애매하게 남지 않는다는 걸 알아야 마음 놓고 쓴다.

## cherry-pick 이 아니라 이걸 쓴 이유

같은 저장소 안에서 다른 브랜치의 커밋을 끌어오는 상황이었다면 `git cherry-pick`(체리픽) 으로 끝났다. 이번 상황은 그게 아니었다. 원격이 아예 닿지 않으니, **저장소를 물리적으로 건너뛰어야** 했다. 파일로 뽑아서 옮긴 다음 다시 넣는 방식. cherry-pick 은 네트워크가 살아 있어야 성립한다.

## 남은 것

패치 파일 자체는 텍스트라 diff 를 읽을 수 있다. 옮기기 전에 열어서 훑어보면 뭘 옮기는지 눈으로 확인이 된다. 이게 파일 복사와 결정적으로 다른 지점이다. 파일 복사는 결과물만 옮기고, 패치는 **변화의 이력** 을 옮긴다.

아직 안 해본 것 하나. 바이너리 파일이 섞인 커밋에서 이 흐름이 얼마나 매끄러운지는 재보지 않았다. 텍스트 diff 만 다뤄본 상황에서 판단을 확장하지 않으려고 여기서 멈춘다.
