## 모델이 아니었다

추천 결과가 한쪽으로 쏠렸다. 특정 콘텐츠 군만 계속 상위에 뜨고, 나머지는 4갈래(job·career·company·best) 어디에도 안 잡혔다. 반사적으로 스코어링을 열었다. 가중치를 만졌고, RRF 병합 로직을 다시 봤고, 임베딩을 재계산할까 고민했다.

두 시간 정도 그 쪽만 팠다. 그러다 문득 이상해서 반대로 물었다. **"애초에 이 콘텐츠가 후보 풀에 들어오긴 한 건가?"**

## 조인은 안 깨졌다. 근데 절반이 없다.

추천은 콘텐츠 본체가 아니라 메타 테이블을 본다. NCS 코드, strand, sub_category, duration bucket, keywords — 이런 라벨이 붙어있는 행만 축(axis)별 후보로 뽑힌다. 그래서 콘텐츠 테이블과 메타 테이블을 LEFT JOIN 해서 커버리지부터 뽑았다.

```sql
SELECT
  COUNT(c.id)                       AS total_content,
  COUNT(m.content_pk)               AS has_meta,
  ROUND(COUNT(m.content_pk) * 100.0
        / COUNT(c.id), 1)           AS coverage_pct
FROM content c
LEFT JOIN content_meta m
  ON c.id = m.content_pk;
```

매칭된 행의 키는 100% 정합이었다. 그러니까 조인 자체는 멀쩡했다. 문제는 커버리지가 40%대라는 것. 나머지 60%는 **메타 자체가 없어서** 후보로 뽑히는 순간부터 탈락하고 있었다. 모델은 잘못 판단한 적이 없었다. 애초에 판단할 대상이 안 들어온 거였다.

이걸 뒤늦게 깨달으면서, 추천 API의 404 문구가 다시 보였다.

```python
if not service.company_exists(req.tenant_id):
    raise HTTPException(
        status_code=404,
        detail=f"추천 가능한 콘텐츠가 없습니다(미등록 회사이거나 콘텐츠 0건): {req.tenant_id}",
    )
```

"콘텐츠 0건"이라는 표현이 애매하다. 정확히는 "메타가 붙은 콘텐츠 0건"이어야 한다. 회사 콘텐츠는 있는데 라벨링이 안 돼서 후보 풀에 못 들어가는 케이스는 이 404에 안 걸린다. 그냥 조용히 빈 axes를 반환한다. 이 부분은 아직 안 고쳤다.

## "없다"에는 두 종류가 있다

여기서 한 번 더 갈렸다. 메타가 없다고 다 같은 없음이 아니다.

- 라벨은 만들어져 있는데 `content_meta`에 적재가 안 된 것 — 파이프라인 버그
- 라벨 자체를 아직 안 만든 것 — 라벨링 팀 백로그

이 둘을 섞어서 "메타 커버리지 60%"라고만 리포트하면 아무도 안 움직인다. 백엔드는 "그건 라벨링 이슈"라고 하고, 라벨링 팀은 "적재됐는지는 백엔드가 봐야 한다"고 한다. 실제로 초반에 그렇게 흘러갔다.

기준을 하나 잡았다. 운영 라벨 v2 테이블. 여기에 있으면 "만들어진 것", 없으면 "아직 안 만든 것". 이 기준으로 두 목록을 분리해 각각 다른 채널로 보냈다.

- v2에 있는데 `content_meta`에 없는 `content_pk` → 적재 파이프라인 담당에게
- v2에도 없는 콘텐츠 → 라벨링 담당팀에게

목록을 나눠서 던지자 그 주에 바로 움직임이 생겼다. 그전까지는 같은 숫자를 계속 서로에게 떠넘기고 있었다.

## 스냅샷 JSON이 만든 유령

정리하는 과정에서 다른 게 하나 더 튀어나왔다. 몇 주 전에 뽑아둔 라벨 export JSON 파일이 여러 스크립트에 참조되고 있었다. 누군가는 그걸 기준으로 "이 콘텐츠는 라벨 있음"이라 판단하고 있었고, 누군가는 운영 테이블을 보고 있었다. 같은 콘텐츠에 대해 두 팀이 정반대 답을 하고 있었다.

이건 코드 문제도, 데이터 문제도 아니었다. **"어디를 기준으로 볼지"가 합의 안 된 문제**였다. 운영 기준은 `content_meta` 하나로 못박고, 나머지 JSON은 파일명에 스냅샷 날짜를 박아 참고용임을 명시하는 걸로 정리했다. 그 이후로 "어느 쪽 기준으로 커버리지 봐야 하냐"는 질문이 없어졌다.

## 아직 안 끝난 것

지금 시점에서 커버리지는 아직 100%가 아니다. 라벨링 백로그가 남아있고, 그건 시간이 해결한다. 대신 API 쪽에서 하나 남겨둔 게 있다. 회사 콘텐츠는 있는데 메타가 없는 경우를 지금은 빈 axes로 조용히 넘기는데, diagnostics에 `no_meta_coverage` 같은 경고를 넣을지 고민 중이다. 프론트가 그걸 보고 "라벨링 대기 중"이라는 상태를 사용자에게 노출할지, 그냥 다른 콘텐츠로 대체할지도 아직 안 정했다.

모델 파라미터를 만졌던 두 시간이 계속 마음에 걸린다. 다음에 추천 이상현상이 오면 커버리지부터 볼 거다. 그게 지금 유일하게 확실한 교훈이다.
