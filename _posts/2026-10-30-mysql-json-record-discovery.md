사용자 한 명의 활동 기록을 찾아 달라는 요청이었다. 어느 테이블에 들어 있는지는 아무도 정확히 몰랐다. 예전 문서에는 어떤 데이터베이스 이름이 적혀 있었다. 그 이름이 지금도 맞는지는 확인한 사람이 없었다.

## 문서를 믿지 않고 목록부터 봤다

문서에 적힌 DB로 바로 들어가지 않았다. 서버에 붙어서 목록부터 뽑았다.

```sql
SHOW DATABASES;
```

DB가 여러 개 나왔다. 이름만 보면 후보가 몇 개 있었다. 이름으로 고르면 틀릴 수 있어서 후보 DB마다 테이블 목록과 컬럼을 봤다. 그다음 최근 행이 실제로 들어오고 있는지 확인했다. 스키마가 그럴듯해도 몇 달째 쓰이지 않는 테이블이 있을 수 있기 때문이다.

이 단계는 지루한데, 건너뛰면 엉뚱한 테이블을 한참 파게 된다. 과거 문서가 알려 주는 건 어디서부터 보면 되는지까지다. 지금 어디에 있는지는 알려 주지 않는다.

## 검색 결과 0건

기록이 있을 만한 테이블을 찾았고, 사용자 ID로 검색했다. 결과는 0건이었다.

여기서 "이 사용자의 기록은 없다"고 결론 내릴 뻔했다. 그런데 내가 본 건 짧은 ID 컬럼들뿐이었다. 그 사용자의 식별자가 다른 곳에 들어 있다면 이 검색에는 걸리지 않는다. 예를 들어 JSON 본문 안의 필드나 URL 문자열 속에 있을 수 있다.

그래서 범위를 넓혔다. 컬럼 하나를 정확히 일치시키는 대신 JSON·텍스트 컬럼 전체를 대상으로 식별자가 포함된 행을 찾았다. 그러자 기록이 나왔다. 데이터는 처음부터 있었고, 내가 본 컬럼에 없었을 뿐이다.

검색 결과가 없다는 것과 데이터가 없다는 것은 다른 얘기다. 검색 결과가 없다는 건 내 검색 조건에 걸리는 게 없다는 뜻일 뿐이다.

## 원문을 찍지 않고 구조 보기

찾은 기록은 중첩된 JSON이었다. 통째로 출력하면 길고, 개인 활동 내용이 그대로 화면에 남는다. 그래서 값은 보지 않고 키 경로만 모았다. 어떤 경로가 몇 번 나오는지, 페이지 유형이 어떤 종류인지 센다. 이렇게 하면 본문을 읽지 않고도 구조가 보인다.

구조를 보면서 따로 점검할 것도 정했다.

- 누락된 기록이 있는지. 있어야 할 유형의 기록이 비어 있는 구간이 있는지 본다.
- 시험 데이터가 섞여 있는지. 실제 사용자 기록과 개발 중 만든 기록이 같은 테이블에 들어 있을 수 있다.

둘 다 분석 결과를 왜곡할 수 있다. 몇 건이 누락됐고 시험 데이터가 몇 건인지는 이 글에 적지 않는다. 비율을 확정할 만큼 재보지 않았다.

## 압축된 기록, 디코딩 실패

일부 기록은 압축된 문자열로 저장돼 있었다. 해제하려고 하면 디코딩이 계속 실패했다. 압축 방식을 의심했는데 원인은 다른 데 있었다. 문자열 앞에 접두어가 붙어 있었고, 이게 디코더 입력에 그대로 들어가고 있었다. 접두어를 떼고 나서 해제가 됐다.

압축 알고리즘이 틀렸다고 가정하면 엉뚱한 방향으로 간다. 에러가 나면 데이터 앞부분의 바이트부터 보는 편이 빨랐다.

해제한 결과가 기존 분석 입력과 구조적으로 호환되는지도 점검했다. 키 경로를 기준으로 맞춰 봤다. 값 단위의 일치까지 확인하지는 않았다.

## 이 데이터를 쓰려던 일

이 조사는 AI로 진단평가 문항을 만드는 작업의 일부였다. 생성에 필요한 메타데이터를 설계하다가 불일치 몇 개를 만났다. 생성 지침, JSON 스키마, 참고 문항이 서로 다른 걸 요구했다. 예시 문항을 생성 입력으로 줄지 평가 기준으로만 쓸지도 따져야 했다. 입력으로 주면 모델이 예시를 베낄 수 있고, 기준으로만 쓰면 비교는 깨끗하지만 모델에게 방향을 알려 주지 못한다.

실험 코드와 입력 조건은 준비해 뒀다. 그런데 API 크레딧이 부족해서 생성 실험이 실패했다. 이후 확인된 건 API가 정상 응답한다는 것뿐이다.

그러니 메타데이터를 바꾸면 문항이 좋아지는지는 아직 모른다. 설계는 했고 검증은 못 했다. 크레딧을 채운 뒤에 조건별로 돌려 볼 예정이다. 예시 문항을 입력으로 줬을 때와 평가 기준으로만 썼을 때 차이가 나는지가 가장 궁금하다. 나오는 결과가 어떨지 지금은 짐작이 안 된다.
