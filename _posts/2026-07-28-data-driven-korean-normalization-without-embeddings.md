"검색이 왜 못 찾지" 소리를 들으면, 손이 먼저 임베딩 모델 카탈로그로 간다. 나도 그랬다. 더 큰 모델, 더 좋은 리랭커, 아니면 프롬프트를 어디 손대야 하지. 그러다 개발 DB에 쌓인 질문 로그를 그냥 열어봤다. 그때 방향이 뒤집혔다.

## 로그를 열기 전에 가진 가설

내 가설은 "사용자가 같은 개념을 다른 단어로 표현한다" 였다. 동의어 문제, 의미 변형 문제. 그러면 처방은 임베딩이다.

로그는 2104건이었다. 일단 `strip()` 하고 연속 공백만 하나로 줄여서 중복 제거를 걸어봤다. 1849건이 남았다. **약 12%가 순수한 공백 차이였다**. 의미가 다른 게 아니라, 문자열이 다른 거였다.

거기서부터는 눈으로 훑는 시간이었다. 패턴이 몇 가지로 뭉쳤다.

- 띄어쓰기 유무: `분수의나눗셈` / `분수의 나눗셈`
- 어미·조사가 붙은 형태: `뺄셈해줘`, `곱셈알려줘`
- 반복 등장하는 오타: `뺄샘`, `곱셉`, `팬투미노`
- 의문형 후미: `~이 뭐야?`, `~은 어떻게 해?`

의미 변형은 있긴 있었는데, 표면 변형의 볼륨이 훨씬 컸다. 임베딩 모델을 바꾼다고 "분수의나눗셈"과 "분수의 나눗셈"이 안정적으로 같은 걸로 잡히리라는 보장이 없다. 반대로, 이 표면 노이즈는 `re.sub` 몇 줄로 제거 가능하다.

가설이 틀렸다. 그리고 로그를 열지 않았다면 계속 틀린 채로 GPU 비용을 늘리고 있었을 것이다.

## 어디에 정규화를 걸 것인가

정규화를 만들면서 제일 조심한 건 "어디까지 정규화하냐" 가 아니라 **"어느 지점에 정규화된 값을 쓰냐"** 였다. 이걸 헷갈리면 LLM에 넘어가는 원문까지 뭉개져서, 사용자가 "뺄샘" 이라고 물었는데 답변에서 "뺄셈" 이라고 되받아치는 어색한 상황이 나온다.

원칙은 이렇게 잡았다.

- **정규화된 문자열은 캐시 키·후보 검색·fallback 매칭에만 쓴다**
- **LLM 프롬프트에 들어가는 원문·화면에 표시되는 텍스트는 절대 손대지 않는다**

이렇게 나누고 나니까 함수가 하는 일이 명확해졌다. 정규화 함수는 "이 두 입력을 같은 것으로 볼 것인가" 만 판단한다. 표시 문제는 다른 계층이 책임진다.

```python
import unicodedata
import re

_TRAILING = re.compile(r"(해줘|알려줘|이 뭐야\??|은 어떻게( 해)?\??)$")

def normalize_text(s: str) -> str:
    s = unicodedata.normalize("NFC", s)
    s = s.strip()
    s = re.sub(r"\s+", " ", s)
    s = _TRAILING.sub("", s).strip()
    return s
```

`unicodedata.normalize("NFC", ...)` 는 한글 자모가 개별 코드포인트로 흩어진 걸 완성형 한 글자로 합친다(NFC — Normalization Form C, 유니코드 정규형). macOS에서 파일명을 붙여넣거나 특정 브라우저에서 IME 조합이 덜 끝난 채로 넘어오면 같은 "가" 처럼 보여도 코드포인트가 다르다. 이 케이스는 자주는 아니지만 확실히 존재했다.

의문형 후미 제거는 조금 논쟁적이었다. `이 뭐야?` 를 떼면 "미분이 뭐야?" 와 "미분" 이 같은 캐시 키가 된다. 답이 다르지 않냐고 물을 수 있는데, 우리 파이프라인에선 그 뒤에 답변 생성 프롬프트가 원문을 그대로 받는다. 캐시 키만 같아지는 거고, 답변 톤은 원문에 맞춰 나간다.

## Levenshtein을 안 쓴 이유

오타 보정으로 편집 거리(Levenshtein distance — 두 문자열을 같게 만드는 데 필요한 최소 편집 횟수)를 넣고 싶었다. `뺄샘` 과 `뺄셈` 은 거리 1이니 쉽게 이어진다. 자동화도 되고.

그런데 로그를 더 훑다가 마음이 식었다.

- `미분` ↔ `미션` : 편집 거리 1. **절대 이으면 안 된다**
- `확률` ↔ `확율` : 편집 거리 1. 이어야 한다

알고리즘 관점에선 두 쌍이 구분되지 않는다. 사전을 붙이면 되지 않냐 싶은데, 그 사전을 만드는 게 결국 사람이 로그를 보고 판단하는 일이다. 그러면 **자동 보정을 켜서 사후에 예외를 파는 것보다, 처음부터 화이트리스트로 가는 게 안전하다**.

false positive 하나가 검색 결과 전체의 신뢰를 무너뜨린다. "미분" 이라고 쳤는데 "미션 관련 콘텐츠" 가 상단에 오는 상황을 상상해보면 답은 나와 있었다.

```python
ALIAS_MAP: dict[str, str] = {
    "뺄샘": "뺄셈",
    "곱셉": "곱셈",
    "팬투미노": "펜토미노",
    # 로그에서 실제로 관측된 것만
}

def apply_alias(s: str) -> str:
    return ALIAS_MAP.get(s, s)
```

"있을 법한 오타" 는 절대 넣지 않았다. 근거는 딱 하나 — **이 로그에서 봤는가**. 이게 알리아스 맵의 유일한 입장 조건이다.

## 정규화가 룰이 아니라 계약이 되도록

룰이 쌓이면 서로를 부순다. 후미 제거를 추가하니 "은 어떻게 해요" 는 잘 떨어지는데 "은 어떻게 되나요" 가 남더라, 하는 식의 미묘한 회귀가 생긴다. 그래서 룰을 추가할 때마다 **먼저 실패하는 테스트를 쓰고**, 룰을 고쳐 통과시키는 순서를 지켰다.

```python
def test_trailing_request_stripped():
    assert normalize_text("분수의 나눗셈 알려줘") == "분수의 나눗셈"

def test_whitespace_collapse():
    assert normalize_text("분수의  나눗셈") == "분수의 나눗셈"

def test_nfc_composition():
    decomposed = "\u1100\u1161"  # ㄱ + ㅏ
    assert normalize_text(decomposed) == "가"

def test_alias_known_typo():
    assert apply_alias("뺄샘") == "뺄셈"

def test_alias_no_false_positive():
    assert apply_alias("미분") == "미분"
    assert apply_alias("미션") == "미션"
```

마지막 테스트가 이 시스템에서 제일 중요하다고 생각한다. 잘 되는 걸 증명하는 테스트보다, **잘못 되면 안 되는 걸 못 박아두는 테스트**. alias 맵을 늘릴 사람이 미래의 나 자신이든 다른 사람이든, 이 테스트를 지나야 한다.

## 아직 못 푼 것

지금 정규화 파이프라인은 캐시 히트율을 눈에 띄게 올렸다. 다만 두 가지가 남았다.

하나는 **후미 제거 정규식이 너무 문자열 매칭에 가깝다**는 것. `은 어떻게 되나요` 같은 변형이 들어오면 놓친다. 그렇다고 여기서 형태소 분석기를 붙이면 배포·의존성 부담이 커진다. 지금은 새 패턴이 로그에 반복 등장할 때마다 정규식을 늘리는 방식으로 버티고 있고, 이게 언제쯤 무너질지 감이 안 잡힌다.

다른 하나는 alias 맵 관리다. 지금은 새 오타를 발견하면 사람이 커밋한다. 로그 유입량이 늘면 이걸 사람이 감당할 수 있는 형태로 유지할 수 없을 것이다. "후보를 자동 추출하고 사람이 승인" 하는 반자동 파이프라인이 어딘가 필요할 텐데, 그때는 편집 거리 후보 생성을 다시 꺼내 쓰게 될 것 같다. 이번에 자동 적용을 거절한 이유가 그때는 다르게 재구성되는 셈이다.

임베딩 모델은 아직 안 바꿨다. 바꿀 필요를 못 느꼈다는 게 이번 작업에서 제일 예상 밖의 결론이다.
