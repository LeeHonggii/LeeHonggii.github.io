백엔드를 FastAPI로 옮기자는 이야기가 나왔다. 처음엔 "옮기는 김에" 하고 싶은 것이 줄줄이 따라왔다. 응답 구조도 정리하고, 중복된 로직도 합치고, 기능도 몇 개 붙이고.

그 목록을 일단 접었다. 이번 글은 무엇을 접었고, 접은 뒤에 무엇으로 "같다"를 증명할지 정리한 학습 노트다. **전환은 아직 끝나지 않았다.** 아래는 계획과 검토 단계의 기록이다.

## 범위를 먼저 자른다

선택한 범위는 이렇다. 프론트엔드는 그대로 두고, 백엔드만 FastAPI로 1:1 이식한다. 화면과 기능은 바뀌면 안 된다. 기능 확장은 이식이 끝난 뒤의 별도 작업으로 뺐다.

이유는 단순하다. 언어 전환과 기능 변경을 한 번에 하면 결과가 달라졌을 때 원인을 못 가른다. 프레임워크 차이 때문인지, 내가 로직을 바꿔서인지 알 수 없다. 이식 중에는 "달라진 것은 전부 버그"라는 규칙이 있어야 판단이 빨라진다.

## 기존 테스트를 못 쓴다

기존 백엔드에는 TypeScript 테스트가 있다. 서버를 Python으로 바꾸면 이 테스트를 그대로 돌릴 수 없다. 테스트를 Python으로 다시 쓰면 "기존 동작"이 아니라 "내가 이해한 기존 동작"을 검증하게 된다. 이해가 틀렸다면 테스트도 같이 틀린다.

그래서 **골든 마스터(golden master) 검증**을 제안했다. 기존 동작을 정답으로 박제해 두고 새 구현과 비교하는 방식이다. 순서는 이렇다.

1. 대표 입력을 모아서 기존 서버에 보낸다.
2. 응답을 파일로 저장한다. 이것이 정답이다.
3. 같은 입력을 FastAPI 서버에 보내 응답을 비교한다.

테스트 코드를 다시 쓰지 않아도 되고, 이식하는 사람의 해석이 끼어들지 않는다. 대신 정답의 품질은 입력의 폭에 달려 있다. 입력이 빈약하면 통과해도 아무것도 증명하지 못한다. 어떤 입력을 얼마나 모아야 충분한지는 아직 정하지 못했다. 타임스탬프나 생성 ID처럼 호출마다 달라지는 필드를 비교에서 어떻게 뺄지도 열려 있다.

## 목표 구조

새 서버의 뼈대는 이렇게 잡아 두었다. 진입점은 `create_app()`으로 앱을 조립하는 팩토리 함수로 하고, 요청·응답 모델은 Pydantic으로 선언해서 `Field(example, description)`에 예시와 설명을 같이 적는다. 문서가 코드에서 나오게 하려는 것이다.

```text
app.py
restful/router.py
restful/model/
storage/
tests/
```

모델에 예시와 설명을 적어 두면 자동 생성되는 API 문서가 곧 이식 명세 역할도 한다. 다만 이 구조는 목표일 뿐이다. 실제로 채워진 정도는 이 글에서 주장하지 않는다.

## 상속을 예상했는데 아니었다

기존 Python 코드를 재사용할 수 있는지 보려고 열어 봤다. 클래스 구성이 상속과 오버라이딩으로 짜여 있을 거라고 예상했다. 그렇다면 부모 클래스를 먼저 옮기고 자식을 얹는 식으로 FastAPI 쪽도 같은 틀을 쓸 수 있다.

실제로는 달랐다. 작업별로 클래스가 하나씩 있고, 각 클래스 안에서 단계별 메서드가 이어지는 구조였다. 클래스들은 서로 같은 형태를 병렬로 반복할 뿐 공통 부모를 두지 않았다.

그래서 "상속 구조를 가져온다"는 계획은 버렸다. 가져올 것은 상속 계층이 아니라 **작업별 클래스 + 단계별 메서드라는 일정한 모양**이다. 이식할 때도 그 모양을 그대로 따르면 클래스 하나를 옮기는 비용이 일정하다. 설계 패턴의 이름으로 코드를 상상하면 틀린다. 열어 보기 전에는 모른다.

## 아직 못 정한 것

- 골든 마스터 입력 세트를 어떻게 모을지. 운영 데이터에서 뽑을지, 직접 만들지.
- 비교에서 제외할 가변 필드의 기준.
- 병렬 클래스가 정말 같은 모양인지, 겉보기만 같은지. 전수로 확인하지 않았다.

이식 첫 단위로 어느 클래스를 고를지도 아직 고르지 못했다.
